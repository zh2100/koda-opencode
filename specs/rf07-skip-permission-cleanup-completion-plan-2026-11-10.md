## 4. RF-07A：修正跳过与通过的统计

### 4.1 注册时决定已知条件

1. 将 Windows 与 POSIX 平台选择保留在注册阶段，Windows 执行 ACL 用例，Linux/macOS 执行 mode 用例。
2. 将 root 检测从 Effect 测试体移到注册阶段：非 Windows 且 `process.getuid()` 明确不为 0 才注册正常 mode 用例；root 使用现有 `it.live.skip`。
3. 非 Windows 无法确认执行身份时，不默认具备能力。注册为 skip 并写明原因，或使专门要求此能力的 CI job 失败；不得默认为 pass。
4. skipped 用例标题或记录写清理由，例如 root / platform mismatch。不要通过执行一个没有权限断言的正常测试来承载这条记录。
5. 保留全平台通用来源契约测试，不随权限用例一起跳过。环境 raw 引用、PATCH 403、无效文档 400、缺失 GET 200 null 仍必须执行。

### 4.2 运行中探测失败必须明确失败

当前测试包装器没有运行中跳过接口。本轮采用以下确定策略，避免为了一个测试扩展框架：

1. 注册为正常执行的 POSIX 用例，在 chmod 后使用真实 readFile 检查是否出现 EACCES 或 EPERM。
2. 若 readFile 成功，则抛出“无法建立读取拒绝夹具”的测试准备错误，进入权限恢复清理。该用例为 fail，不能打印 skip 后成功返回。
3. 若 readFile 抛出 ENOENT、EIO 或其他异常，保留为准备失败，不把所有错误都视为读取权限拒绝。
4. Windows 同样先验证测试文件确实不可读；icacls 返回 0 本身不能证明实际拒绝读取。实际错误必须是已识别的 EACCES/EPERM。
5. 运行时能力不足若发生在非必需平台环境，可由执行者更换合适环境重跑，并在结果中记录失败及原因；不能删除该次失败记录或自动转成通过。

### 4.3 必须验证报告统计

- Windows：Windows ACL 用例正常执行，POSIX 用例真实 skip。
- 非特权 Linux/macOS：POSIX mode 用例正常执行，Windows ACL 用例真实 skip。
- root：POSIX mode 用例真实 skip；不能出现“打印 root skip，但该用例 pass”。
- 运行中无法拒绝读取：用例 fail，且执行恢复。

验收应检查 Bun 最终 pass/fail/skip 统计和目标用例标题，而不只查看日志中的 skip 文本。root 验证不要求在本机提升权限；使用现有受控容器/CI，缺环境则记待验证。

## 5. RF-07B：建立可靠的权限恢复状态

### 5.1 状态含义

使用少量明确的状态，不创建通用资源管理框架：

| 状态 | 含义 | 恢复行为 |
| --- | --- | --- |
| 未修改 | 尚未执行任何可能改变权限的操作 | 无需恢复 |
| 待恢复 | 修改已开始，可能已部分生效；或上次恢复失败 | 必须尝试恢复 |
| 已恢复 | 恢复调用成功且必要的可读性检查通过 | 后续恢复调用幂等返回 |

POSIX 保存原始 permission bits（例如 stat.mode & 0o7777）与“待恢复”状态；不能用清空原 mode 的方式提前表示成功。

### 5.2 修改前登记恢复责任

1. 创建并写入临时文件，记录恢复所需信息。
2. 在任何 chmod/icacls 修改之前注册 finalizer。临时目录由 fixture 先注册，权限 finalizer 后注册，利用作用域清理顺序确保先恢复权限再删除文件。
3. 紧接着在修改操作之前进入“待恢复”。因此，即使操作返回非零或抛错，也按“可能部分修改”执行清理。
4. 不在检查 deniedAcl 成功后才设置 acl=true。工具存在但准备部分失败同样需要恢复。
5. 对“状态置为待恢复 + 启动权限修改”使用窄小、不可中断的边界。POSIX 异步权限操作必须等其实际完成再开始收尾，防止取消后晚到 chmod 再次改变已经恢复的文件。
6. 不把整个 HTTP 请求设为不可中断。保护范围只包括短小的权限修改、恢复及其状态提交。

### 5.3 恢复成功后清除状态

Windows：

1. 仅对隔离文件调用现有恢复方式（例如 icacls /reset；该文件必须是新建且使用可恢复的继承 ACL）。参数使用数组，不拼接命令字符串。
2. 检查启动 error 和退出码；非零、超时或启动失败都保持“待恢复”。
3. 验证文件已经可读，内容未被修改；验证成功后才变成“已恢复”。
4. 若需要保留并恢复原始自定义 DACL，使用对应保存/恢复方式；不要把 /reset 宣称为任意 ACL 的精确还原。本方案不修改已有自定义 ACL 文件。

POSIX：

1. await chmod(原 permission bits)。
2. 验证 permission bits 恢复，且文件可读、内容未变。
3. 上述步骤全部成功后才清除待恢复状态。chmod 或检查失败均保留原 mode 和恢复责任。

### 5.4 有界重试与错误保留

1. HTTP 请求结束后的立即恢复和作用域 finalizer 使用同一份恢复状态，不各维护一套布尔标记。
2. 立即恢复失败时保留待恢复，让 finalizer 再尝试；恢复成功后的 finalizer 为幂等空操作。
3. 设置固定的小次数上限，例如总计两次：请求收尾一次、finalizer 再一次。准备阶段失败、尚未进入请求收尾时，由 finalizer 使用同一总预算。不无限循环、不递归重试、不通过长 sleep 处理。
4. 最终仍无法恢复必须使测试失败，记录隔离目标和恢复错误，不声称临时资源已清理。禁止扩大 ACL 修改到父目录来补救。
5. 若正文请求失败且恢复也失败，报告必须保留两者；使用 Effect Cause 组合或等效聚合方式，避免 finally 抛错把原失败完全遮住。
6. 如果立即恢复失败、finalizer 后来恢复成功，资源状态可记清理成功，但这次异常仍保留在验证记录中；受控注入测试应断言预期错误与最终资源状态。
7. 环境恢复使用独立 finalizer 或其他保证必达的方式，不能因权限恢复抛错而跳过环境恢复。实例释放、数据库重置同理。

## 6. 失败路径验证设计

### 6.1 使用同一真实夹具

如为失败注入抽取权限夹具，则真实 HTTP 测试也必须调用该夹具。新增测试调用同一实现，不能复制一份“正确的状态机”只用于断言。

允许在测试夹具边界传入最小权限操作函数，例如 apply/restore/read，用于指定某一次调用失败；不替换全局 fs、spawnSync 或 globalThis。默认操作使用真实 OS 实现。

受控替身测试验证清理控制逻辑；各平台真实 HTTP 测试继续证明系统拒绝和 503 契约。两类证据分开记录。

### 6.2 最小回归矩阵

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| P01 | root 注册 POSIX 用例 | 框架真实 skip，正文未执行，不计 pass |
| P02 | Windows / 非 Windows 平台不匹配 | 不适用用例真实 skip，共用契约继续执行 |
| P03 | 修改后 readFile 仍成功 | 准备失败，不误报 pass；权限恢复、环境恢复 |
| P04 | 探测读取抛 ENOENT 等非权限错误 | 失败原因保留，不当成有效拒绝 |
| C01 | 权限修改完全成功、HTTP 正常响应 | 返回 503/code/ref，立即恢复成功；finalizer 不重复修改 |
| C02 | 实际完成部分修改后，apply 返回失败 | 即使尚未创建 HTTP 请求，finalizer 也执行恢复 |
| C03 | 第一次恢复失败，第二次成功 | 第二次确实调用；最终可读、原 mode/继承 ACL 状态恢复；错误不被静默吞掉 |
| C04 | 所有允许的恢复尝试都失败 | 达到上限后结束并失败，不清除待恢复状态，不宣称已清理 |
| C05 | HTTP 抛错或断言失败 | 保留原失败，权限、环境与实例均完成清理 |
| C06 | HTTP 失败且恢复失败 | 报告同时保留两个错误，不互相覆盖 |
| C07 | 权限修改期间取消 | 等修改真正完成后恢复，没有晚到修改破坏恢复 |
| C08 | HTTP 等待期间取消 | finalizer 运行，恢复可读性，后续夹具不受污染 |
| C09 | 成功恢复后再次恢复 | 幂等，无额外 OS 权限操作 |

C02 可以通过真实 apply 后返回受控失败验证“已修改但报告失败”；C03/C04 在恢复调用边界注入一次或持续失败，不修改生产系统权限。无对应 OS 的平台可验证共享控制逻辑，但不能宣称 OS 行为已实测。

用同步信号控制取消发生的时点，不使用固定延时猜测操作已经开始。权限真实变化只发生于临时文件。
