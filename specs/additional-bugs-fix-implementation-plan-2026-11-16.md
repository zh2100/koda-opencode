## 2. 先确定统一行为规则

| 维度 | 所有修复单元必须遵守的规则 |
| --- | --- |
| 身份 | 文件使用当前锁协议的规范身份和来源版本；前端使用 server scope、生命周期 generation、实体身份、操作序号；任务创建使用稳定命令身份 |
| 发现 | 普通读取、编辑来源、迁移、保存共享来源资格和优先级。环境/托管/远程原文不能被凭据展开结果替代 |
| 提交 | 文件以确认的原子发布、数据库以事务提交为准。通知、刷新、清理不能把已提交伪装成未提交 |
| 结果 | 区分确定未提交、已提交但后续未完成、结果未知。未知结果先核对原操作，不能换编号再次写入 |
| 取消 | 投递前可以放弃；不可取消 IO 投递后等实际结束，保留租约及清理责任。中断和清理错误不能被吞掉 |
| 接纳 | 旧响应不能写当前页面，但已提交操作仍需刷新其原服务器。丢弃显示结果不等于免除同步责任 |
| 清理 | 仅清理有本操作身份/版本证据的资源。清理失败留下安全恢复信息；记录不含密钥、展开配置或完整 Prompt |
| 迁移 | 用持久进度表达迁移状态，不以目标存在或业务表非空代替完成。失败重试不能覆盖用户新数据或恢复用户已删除数据 |
| 解析 | 原始 bytes、语法 token、Unicode 文本、最终输出预算分层处理，不因输入的等价写法改变正文 |
| 验收 | 对适用场景同时核对响应、持久状态、有效内存状态和实际页面；无页面入口的单元明确记 N/A 及理由 |

每个写操作实现前填写一张阶段表：`发现 → 获取租约 → 重读 → 构建补丁 → 预检/预留后续责任 → 投递 → 确认提交 → 刷新/通知 → 清理 → 释放`。逐格写清异常、取消、责任人和可重试条件。不能用“已调用 AtomicDocument/共享锁”代替这张表。

### P1-A.2：创建时访问隔离与持有句柄回归

1. 临时文件从诞生到发布都不能让最终策略未授权的主体取得读取或写入句柄，包括尚为空文件时。不能先以宽权限创建、再依赖 chmod/setfacl 撤销访问；POSIX 已成功打开的句柄通常不会因随后收紧权限而失效，写句柄也可能破坏待发布内容。随机文件名、wx/O_EXCL、快速收紧权限以及“正文尚未写入”均不构成该保证。
2. 本方案采用同文件系统受保护暂存区：优先在目标父目录内创建本操作专属的受保护子目录，其访问边界必须在创建调用时成立，而不是 mkdir 后再补。Linux 在已验证的 POSIX ACL 权限模型上使用创建时 0700 限制目录遍历并复读实际 ACL，内部临时文件以 0600 独占创建；父目录 default ACL 中的 named 主体不能借此获得有效访问。Windows 通过创建接口提供受保护、限制主体的安全描述符，不能用 Node 的 mode 参数替代。macOS 单独验证创建时限制与继承 ACE；mode 无法覆盖的继承允许项不能当作已隔离。平台适配器无法提供这种创建语义时，只能使用已建立且经核验的私有父目录中、与目标同文件系统的暂存区；没有可证明安全的位置则在创建临时对象前失败，不退回先创建后收紧。
3. 拒绝接管未知现有暂存路径；记录新目录与文件的身份和本操作归属。暂存区只供当前写入身份使用，所有权及访问边界在整个操作期间不放宽。最终文件的 owner/group/ACL 可在区内设置为源的合法共享策略，目录隔离仍保护各中间步骤；不得为了校验或发布先把暂存目录开放给其他主体。若更改文件所有者后当前身份无法完成后续准备，提前失败，不通过修改源或父目录权限绕过。
4. 在区内完成正文写入、flush、内容/安全描述符校验后，使用既有原子替换或 no-replace 将文件发布到目标位置。必须确认同文件系统及平台原子发布能力；跨设备 EXDEV 不得回退 copy+unlink。发布不能引入额外继承权限；最终合法共享访问在发布后仍应保持。若 no-replace 使用 hard link，暂存目录仍保持私有，之后只清理本操作链接，不影响最终目标。沿用 P1-A.1 的发布前复检和已提交/unknown 分类，不在确认失败时盲目重写。
5. 若检测到创建保护未成立、暂存区边界失效或测试中未授权主体已取得句柄，本次对象不再用于保存；保持未提交、停止正文写入，按身份清理并报告失败。不能通过稍后收紧权限后继续写入同一个 inode 来“修复”。重试需要新的安全对象和重新核验；不能假定删除路径就撤销了已打开句柄。
6. 安全暂存创建能力同步覆盖配置文件、TUI 备份、TOML 新文件及恢复记录。目录/文件创建、ACL 应用、正文写入、发布、清理全部纳入已投递 IO 的排空责任。清理仅删除本操作拥有的文件，随后对核验归属的空目录做非递归移除；目录含未知内容或身份变化时保留并报 cleanupPending，不递归删除。退出遗留目录依据可信日志/身份核对，不能按名称或年龄扫描即删。
7. 新增受控时间窗：实际创建临时文件返回后、第一次权限调整前暂停；主体 B 已有目标父目录遍历权限且不被源授权，使用确切路径分别尝试打开读/写句柄。补每次 chown/chmod/ACL 调整后的闸门、正文写入后以及发布后检查。修复路径要求 B 从第一窗口起即不能打开；另设源合法授权 B 的对照，最终发布后 B 可按原规则访问，不能用最终 0600 导致共享回归。
8. 在完全隔离的对照夹具中明确演示“宽权限空文件→B 打开并保留句柄→收紧 ACL→写入假标记”的错误顺序，核对持有句柄能否读取后续内容；只使用无敏感信息的标记，记录断言而非正文。该对照证明测试确实覆盖先取得句柄的路径。修复路径如果 B 意外打开成功即判失败，不以收紧后新打开被拒绝替代。测试 finally 关闭双方句柄并恢复夹具，缺真实第二主体/平台能力时按框架 skip、保持待验。

退出：创建保护、权限转换各阶段、原子发布及归属清理均有实际入口证据；P1-A.1 的最终 ACL 校验与本节创建时隔离必须同时满足。

## 7. P2：迁移作为可恢复的多文件操作

主要文件：`packages/opencode/src/config/{tui,tui-migrate,paths,config}.ts`、必要共享发布能力；测试放 `test/config/tui.test.ts`、`atomic-entry.test.ts` 和独立迁移回归。

### P2-A：ADD-07/11，先确定输入集合

1. 让迁移消费与加载一致的发现结果，给每个来源标明普通项目、显式文件、自定义目录、home/global。禁用项目配置时剔除普通项目及其祖先/.opencode 来源，保留实际规则允许的显式和全局来源。
2. 先读取同一目标的全部合格源，按加载顺序合并将迁出的字段，再生成目标。禁止边遍历边创建目标，使先处理的低优先级文件排除后续来源。
3. 用 JSON 低优先级主题+scroll_speed、JSONC 高优先级主题+diff_style 的样本验证覆盖和互补字段同时保留。
4. 现有独立 TUI 目标优先规则保持不变；目标已存在时必须区分用户文件与本迁移已提交成果，不凭文件名猜测。

### P2-B：ADD-06，备份也属于敏感发布

1. 对每份待剥离源捕获身份、原字节摘要和安全描述符。源、目标、备份、恢复记录需要统一排序的锁集合和操作 ID。显式保存允许有界、可取消的等待；启动加载器的可选迁移必须 try-all 非阻塞获取：按同一规范身份排序逐把尝试，任一不可得立即释放已获租约，不持部分锁等待，不修改业务文件或恢复记录。
2. 备份从创建时起遵守 P1-A.2 的安全暂存隔离，写入第一字节前按 P1-A.1 应用并复读源安全元数据，包括 Linux/macOS ACL；源无扩展条目时也不能让备份继承更宽条目。发布采用 no-replace。已有备份需核对源版本/归属及权限，冲突时保留并退出，不能覆盖。
3. 多来源合成目标不得使任何敏感来源的访问范围变宽；优先采用可证明不放宽的权限策略。无法表示/应用时失败并保留全部原源，不用宽默认权限继续。
4. 恢复记录只存身份、摘要和阶段，不存原配置或密钥；记录本身从创建时起按 P1-A.1/A.2 限制权限。含配置的业务备份仍需保护，不能因叫 .bak 就放宽。
5. 全部租约取得后重新发现并读取来源/目标布局；有变化则释放并跳过本次可选迁移，不在加载路径无限重选。已投递的 IO 在取消/异常时先等待实际结束并完成归属清理，再释放租约。跳过新迁移不得丢弃已有日志代表的恢复责任。
6. 锁占用或无法安全写入时，按 P2-E 状态表决定是否提供旧 TUI 的虚拟投影，不无条件合并旧字段与已有目标。已确认的中间态按 P2-C/P2-E 解释，不能把跳过迁移缓存成空配置。接线包括 TuiConfig.loadState：当前“先 migrate 再只读 tui 文件”不足以保证回退，需增加共享发现/合并的纯读取路径。来源损坏/拒读沿用错误契约，不伪装成正常空值。
7. 回归第 1/中间/最后一把锁失败、持锁者未释放而加载已返回、部分租约全部释放、锁内重读源变化、禁用项目配置及同目录 JSON/JSONC 合并；同时断言无业务写入且旧设置仍可见。

### P2-C：ADD-08/12，多阶段发布与恢复

1. 全局状态 prepared → backups-ready → target-committed → sources-retired → complete 仅作汇总；源、备份、目标各有独立的 prepare/publish/confirm/cleanup 进度。每次修改前先安全持久化 write-ahead intent，记录操作 ID、规范路径/租约身份、before/after 摘要（含“原本不存在”）、安全元数据引用及预期发布产物身份，修改确认后才推进该文件状态。日志不存配置或密钥正文。日志持久化失败时不投递对应业务修改。
2. 先验证全部输入和目标投影，再安全生成备份；准备完整目标临时文件、写完校验后原子 no-replace 发布。部分写失败只留下可识别的本操作临时文件，不发布损坏目标。
3. 若竞争者先创建目标，保留其字节、保留全部源，不执行剥离；不得覆盖后再“恢复”。对不支持可靠 no-replace 的环境明确失败。
4. 只有目标已确认包含全部应迁字段、备份确认后，才逐源核对并剥离。每份源分别经历 intent 持久化、剥离发布、结果确认；恢复不一律要求全部源仍等于初始摘要。已剥离但未记账的源按该源 after 与发布证据补记，尚未剥离的源按 before 继续。非迁移字段保持；任一源被用户更新时停在可恢复状态，不按旧快照继续改它。
5. 目标已提交但剥离/清理失败时，重试只继续该操作未完成步骤。须确认目标仍是本操作成果；若用户已修改目标，保留用户数据，进入人工可诊断的冲突状态。
6. 若迁移中部分源已剥离，读取按 P2-E 使用已确认目标，不再次合并该批已覆盖的旧源；其他目录仍按正式层次加载。归属或完整性无法证明时停止写入并报告迁移未完成，不用猜测合并返回伪成功。
7. 旧版本曾留下的损坏 tui.json 无身份凭据时，不能当本操作垃圾自动删除；提供诊断/离线恢复预览，不自动修生产文件。
8. 原子替换会改变文件身份，不能要求新 inode 等于旧 inode，也不能只凭字节等于 after 就认领他人文件。准备阶段需记录本操作暂存产物可验证的身份，发布后核对最终产物及安全元数据；无法建立归属时保留文件并报告冲突。当前 AtomicDocument 的 before/text/onCommitted 与 committed/cleanupPending 不提供完整的可持久发布证明，须先增加并测试准备/确认能力：暂存产物准备好后、实际发布前可持久化其身份及 intent，明确平台支持边界和崩溃后证据。不能仅在返回值新增字段，遗漏“发布成功但调用尚未返回”的窗口。
9. 恢复重取同一排序租约集合并逐项核对：身份、版本和安全元数据仍符合 before 时可继续；符合 after 且发布归属证据成立时只补记确认；第三种状态或无法确认时保留全部文件并报冲突。缺失文件只有符合已记录删除步骤才算完成。未持有完整租约集合时不推进恢复。
10. 对目标发布成功但日志确认未写、源 1 已剥离未记账而源 2 尚未处理、日志更新失败、备份/临时文件清理失败分别设置受控进程退出点；用新进程恢复，核对全部文件字节、身份、权限、有效投影和逐文件进度。追加用户修改目标/源、同字节不同身份、日志损坏及恢复中再次退出对照；不能只测试函数抛错后原进程继续。

### P2-D：ADD-13/14，旧 TOML 读取与发布解耦

1. 先读取、解析并纳入合法旧配置，再独立尝试可选迁移。锁不可用只表示暂时不迁移，不表示旧来源不存在。
2. 新 JSON 按 P1-A.1 使用源安全元数据发布，权限（包括扩展 ACL）无法读取、维持或验证则不迁移；旧文件仍可参与读取。新目标已出现时重新按正式优先级加载，禁止旧快照覆盖它。
3. 可选迁移沿用 P2-B 非阻塞 try-all，不等待业务写者；锁集合不完整时不修改业务文件或恢复记录。迁移结果、缓存失效和读取结果分开：不得缓存因跳过可选写入而遗漏字段的“成功空配置”。源损坏与拒读按既有错误契约处理，不默认为空。
4. 回归持锁/释放/显式失效、目标缺失/已有、只读加载模式、JSON 发布失败、目标竞争、权限保留；同时检查返回的 username/model 和所有文件字节。

### P2-E：TUI 迁移状态与纯读取决策

1. 先按 P2-F 判定目标是否有正式加载位置。可迁移来源按实际目标 tui.json 分组，不将 global、项目、.opencode 和显式文件的来源扁平化成一个目标。加载链之外的显式来源只进入 P2-F 的纯读取兼容位置，不进入写入批次。组内候选按正式发现顺序合并，JSON 后 JSONC 覆盖同名字段，未覆盖字段保留。虚拟投影只包含本组可迁移 TUI 字段，在原本 tui.json 的加载位置参与；不同目录以及 OPENCODE_TUI_CONFIG 的先后顺序继续由现有 TuiConfig.loadState 决定，同目录 tui.jsonc 仍在 tui.json 后覆盖。文件身份用于锁去重，来源的实际合并位置不能因去重而改变。
2. 用户已有目标指实际迁移目标 tui.json 已存在且没有本操作可信归属。该文件保持原有优先规则：不把该组残留旧字段补入其缺失项，不覆盖、不剥离源。仅有 tui.jsonc 不等于 tui.json 已存在；目标尚未发布时，合法旧源可形成虚拟 tui.json，再由实际 tui.jsonc 覆盖。来源资格、项目禁用规则与 P2-A 共用实现。

| 读取时状态 | 本组贡献及处理 |
| --- | --- |
| 无目标且源完整，未开始迁移或因取锁失败/只读跳过 | 使用合法旧源合成的虚拟 tui.json；业务文件和日志不变 |
| backups-ready，目标尚未发布且全部源符合 before | 仍使用同一虚拟投影；备份不直接进入加载链 |
| 目标已发布但确认日志未推进 | 只读核对 intent、最终身份/摘要和权限；证明完整发布后采用目标，不为读取而补写日志；证明不足则报告未完成，禁止混合猜测 |
| target-committed，部分/全部源尚未剥离 | 使用目标作为该批的完整投影，忽略该批未变的残留旧字段；各源剥离进度不改变读取值 |
| complete | 走正常独立 TUI 加载；残留旧字段不重新参与，不重新触发同批迁移 |
| 用户原有 tui.json，或可信迁移目标后来被用户编辑 | 使用当前独立目标，缺失字段不从旧源补回；后者停止恢复写入并报告冲突，保留用户字节 |
| 目标缺失但部分源已剥离、日志损坏且无法确认归属 | 不自动从备份回填、不剥离更多源；明确记录不可确认/恢复待处理，不能报告完整设置已成功加载 |

3. 对已提交但未完成批次，若残留源变为第三种版本，停止恢复并报告冲突；目标仍作为独立配置读取，不自动把该源新字段覆盖到目标。若目标自身不可读/无效，沿用 TUI 现有日志和跳过该目标的错误策略，不反向启用旧源来掩盖错误；诊断必须区分“本次配置未加载”与合法空配置。日志状态和文件版本纳入缓存失效依据，不能把暂时跳过迁移固化为遗漏旧值的成功缓存。
4. 无写锁的读取不能推进迁移：读取前后核对本组来源/目标/日志版本；变化时最多重读两次，仍变化则报告来源变化，不返回混合世代成功值。协作迁移先发布完整目标再剥离源，使读者可以选择旧完整投影或新完整目标。不能把这一检查宣称为对任意外部写者的完整文件系统事务。
5. 固定样本：旧 JSON 为 theme=low、scroll_speed=3；旧 JSONC 为 theme=high、diff_style=stacked。无目标且锁忙时应读到 high/3/stacked，且所有文件不变；目标完整提交及任一源剥离后仍为 high/3/stacked。另一个干净夹具中用户先有 tui.json={theme:user}，旧源不得补回 scroll_speed/diff_style（最终默认值另按 TuiConfig.resolve 断言）；只有 tui.jsonc={theme:overlay} 时应得到 overlay/3/stacked。迁移后用户移除目标中的 scroll_speed，旧源不能让 3 复活。
6. 对照 global/project/.opencode/显式 TUI 文件、项目禁用、目标确认前后进程退出、只读/锁忙、用户改目标/源以及读取期间源变化；共享发现投影函数同时服务迁移和 fallback，但期望值由固定样本独立给出，不能把同一 helper 的输出当测试 oracle。核对字段贡献、最终默认值、字节/权限及诊断状态。

### P2-F：加载链之外的显式旧配置

1. 在发现阶段生成有序 TUI 加载计划，供实际读取、虚拟投影、迁移资格及提交前校验共用。计划须包含合法搜索目录中尚不存在的 tui.json 候选位置，不能只枚举已经存在的目标，否则首次迁移和锁忙时的虚拟投影都会被遗漏。候选资格由目录、来源类型和禁用规则决定，存在性只决定读文件还是使用虚拟投影。对于 OPENCODE_CONFIG 指向的文件，按当前锁协议可支持的路径身份计算其旁置 tui.json；只有该目标在当前 TUI 正常加载链中有确定位置，才允许按 P2-A～E 参与自动迁移。不能以“能创建文件”或“主配置加载过源”推导 TUI 一定读取目标。别名不能安全写时仍可纯读，不绕过已有写入门禁。
2. 本方案对旁置目标不在正常加载链的显式旧文件选择纯读取兼容：只提取该显式文件本身的合法 TUI 字段，提供一份虚拟投影；不枚举其目录中的其他 opencode.json/jsonc 或 tui.json/jsonc，不创建目标、备份或迁移日志，不剥离源。即使相邻目录可写、存在看似迁移产物，也不能自动扩大读取范围。主配置中的非 TUI 字段保持原读取规则。
3. 新增兼容位置固定在全局 TUI 层之后、OPENCODE_TUI_CONFIG 之前；后续项目 root-first 和 .opencode/OPENCODE_CONFIG_DIR 的相对顺序不变。禁用项目配置时仍保留这份显式虚拟投影和正式规则允许的全局/自定义来源。若候选目标已在正常加载链，则不新增兼容位置，使用原位置与 P2-E 状态表，避免重复贡献。路径身份去重不能改变其他既有来源的先后关系。
4. 每次加载根据当前 OPENCODE_CONFIG、来源资格和加载计划重新判断，虚拟值不依赖当前进程内的迁移对象。读取明确的源缺失/损坏/拒读时按既有 TUI 诊断与跳过规则处理，不猜测加载旁置文件，也不缓存成该来源成功。历史旧版本若已经剥离外部源并遗留旁置 tui.json，本轮不自动认领或恢复；提供安全诊断，用户可另行明确指定 OPENCODE_TUI_CONFIG。报告中单列这类历史数据缺口。
5. 对允许写入的组，完整租约内重建有序加载计划，并确认拟发布目标仍有可读取位置、版本/来源资格未变。无法证明时不发布或剥离，退出本次可选迁移并按读取规则处理。已经发布后若外部布局变化导致计划失效，保留源和恢复记录，报告冲突；不能为追求迁移完成继续剥离。不声称能锁住任意外部环境修改。
6. 固定隔离样本：项目 P 外的 E/custom.json 含 theme=external 和 scroll_speed=4，E 不属于任何常规 TUI 搜索目录。只设 OPENCODE_CONFIG 时读到 external/4，且 E 下无新增文件、源字节不变；结束本轮实例后新进程读取仍相同。设置显式 TUI 文件 theme=override 后读到 override/4；再加高优先级项目 theme=project 时读到 project/4；禁用项目配置后恢复 override/4。相邻无关 tui.json 不参与，不能借其字段让测试通过。
7. 补目录外源只读/锁忙、显式文件落在已有加载目录、重复别名、目标可见性在获取租约前改变、显式源修改/删除、完整迁移后新进程以及历史已剥离外部源。分别核对真实 TuiConfig.get、贡献顺序、源/目标/备份/日志和诊断。预期值不由被测发现函数生成。

退出：每个发布/剥离/恢复边界都有受控失败及取消；Windows 实际 DACL 通过，Linux/macOS 对应权限场景各自登记。未测平台不得关闭。

## 8. P3：配置来源与实际生效值统一

### P3-A：ADD-03 来源依赖快照

文件：`packages/opencode/src/config/config.ts` 的 mcpSource/sourceDependencies、主加载器来源链及失效入口。

1. 当前有效来源链先重算，再决定需要读取哪些原文。缓存以实例/来源 generation 归属，不能在当前链重算前强制读取上一代全部文件。
2. 保留实际参与主加载器合并的顺序及同文件重复出现的位置，不用路径 Set 随意消掉重复优先级。
3. 当前获胜条目自包含时，旧基础文件退出不阻断；仍需基础 type/url/command 等字段时，必要来源消失安全失败。区别磁盘删除、拒读和语法损坏。
4. 远程 well-known、组织、环境内容、托管偏好、显式文件和 .opencode 均保持未展开原文，返回或落盘不得含展开秘密。
5. 失效、删除重建、同获胜路径跨代、保存前 source/version 检查都绑定当前链；实例销毁后旧读取不得写新快照。

### P3-B：ADD-09 MCP 部分补丁

1. 默认采用较小改动：保留当前逐文件 schema，补丁缺少 discriminator 时根据已核验的有效条目补入必要 type；不把所有继承字段复制到项目文件。
2. 用主加载器相同解析/规范化规则计算发布后的有效投影，确认 URL/command/header 等补丁确实生效。不能只按原文深度合并后的 mcpSource 判断成功。
3. 类型切换清除本文件不兼容字段，并验证低层继承不会重新引入错误语义。若最小方案无法覆盖支持的片段，先补正式 overlay schema 设计与全部读写路径测试，不偷偷放宽一个接口。

## 9. P4：ADD-10 刷新覆盖责任

## 10. P5：定时任务创建和迁移

3. 仅在已确认事务提交后的通知调用边界分类处理 Cause：typed failure 和监听器 Effect.die 均记内部诊断/通知责任，返回已确认任务，不能把 ADD-26 原始 die 复现再次变成普通 HTTP 500。不得全局吞掉 defect，也不能把事务缺陷伪装成成功。真正的请求/服务中断保持中断；复合 Cause 同时保留中断和故障诊断，已提交回执不回滚，新客户端用原编号核对。通知责任不可重放部分投递的监听器副作用，只能按明确安全步骤重建最新投影。

8. 弹窗区分未提交可重试、已提交仅刷新、未知先核对。刷新失败不自动再次创建，不关闭其他弹窗/服务器状态。

### P5-A.1：按操作编号核对与终止未知意图

1. 新增 GET /api/scheduled-task/operation/:operationId，只读查询该调用者/服务资源域的回执；不得扫描任务名或完整 Prompt 猜测归属。成功返回带 discriminator 的 committed、deleted、expired、abandoned、not_observed。committed 返回 taskID 和当前授权范围内的任务；其余状态不返回秘密正文。读取失败为脱敏 typed 错误，不能包装为 not_observed。更新 Protocol、Server、Core、生成 Client 及弹窗恢复流程；与已有 :taskID 路由做匹配测试。
2. not_observed 仅表示该次一致性读取尚未看见持久回执，不表示原请求已结束或确定未提交。客户端继续保留原编号；可轮询，或在仍持有完全相同 DTO 时以原编号重试创建。缺失原 DTO 时只查询/放弃，不重构近似 payload。提交事务与唯一约束保证并发的原请求/重试只创建一次；“查询为空→生成新编号再创建”禁止。
3. 为用户退出未知意图提供 POST /api/scheduled-task/operation/:operationId/abandon。在与创建相同的 SQLite 写事务/唯一键下竞争：无回执则插入 abandoned 最小记录；已有 committed/deleted/expired 则返回现状态，不能覆盖或删除任务；已有 abandoned 幂等返回。创建必须在同一事务内检查记录并拒绝 abandoned，不能先检查再另开事务插入。该操作阻止迟到创建，不调用任务执行器，也不等同于删除已创建任务。
4. 客户端只有确认原意图 committed/deleted/expired/abandoned，才能结束未知流程。单个请求确定未提交也不证明同编号的其他在途重试已终止；若要放弃该编号，先完成 abandon 事务。用户再明确创建时生成新编号；abandon 返回 committed 时展示已有任务，不能把它当取消成功。网络超时/查询失败仍保持未知，刷新列表不替代回执核对。
5. 创建路由新增 typed 状态：同编号不同摘要 409、已删除/已过期/已放弃 410（用不同 code），不可用 503；查询/放弃用上述状态体表达已知结果。无权限或跨资源域查询不能暴露他人状态；错误 code/ref 脱敏。明确 operationId 的长度/格式校验与 DTO 摘要规范化版本，摘要包含 name、enabled 及所有业务字段，不仅是 Prompt。未知摘要版本拒绝猜测兼容。
6. 必测：原 POST 挂起→GET not_observed→原 POST 提交；GET not_observed→abandon 先提交→迟到 POST 被拒；POST 先提交→abandon 返回 committed；查询与删除竞争；只保留编号后重建客户端；跨 scope 同编号；查询异常；真实 HTTP/SQLite 与生成客户端往返。每条同时核对任务行、回执和模型调用数。

### P5-A.2：回执过期、任务删除与防重放

1. 默认重试窗口固定为首次提交后 30 天，expiresAt 由服务端写入且重试不延长。窗口内持久记录至少含资源域、operationId、摘要及算法版本、taskID、提交时间、expiresAt 和状态；不保存第二份完整 Prompt。创建成功响应仍兼容原 ScheduledTask.Info，重试窗口/状态通过查询接口和 API 文档公开。
2. 任务删除与将相关回执标为 deleted 放在同一事务；回执不可使用 onDelete:cascade 随任务一起清除。任务已不存在但回执仍可验证时亦返回 deleted，绝不重新生成任务。是否有运行记录不改变此规则。
3. 窗口到期后将记录压缩为 expired tombstone，保留资源域、operationId、失效状态/时间和协议版本；不必保留任务正文或摘要。abandoned 也保留最小记录。最小防重放记录在该数据库资源域生命周期内不按年龄删除；本轮不增加自动清除 tombstone 的逻辑。容量不足时新建在提交前明确失败，不驱逐旧编号来腾空间。
4. 每次创建/查询都检查 expiresAt，不能依赖清理任务及时运行。过期状态优先返回 410/expired，不再比较已裁剪的 payload 摘要，更不能作为新编号受理；未过期的 deleted 返回 deleted。清理与重试/删除在事务中协调，失败不丢唯一键。尚未被服务接纳过的编号没有服务端过期回执；用户需要阻止迟到请求时使用 abandon，不靠本地时钟宣告它失效。
5. 只恢复同一数据库时须同时恢复回执和 tombstone；不得只迁移任务表后仍宣称跨恢复幂等。人工删除数据库/回滚备份超出本方案防重放保证，结果报告明示边界，禁止自动替用户执行。schema 升级测试要核对无级联删除及唯一索引仍存在。
6. 使用可控服务端时间验证 30 天边界前后、清理未运行、压缩后重启、任务删除后重试、同编号异 payload、abandon 后延迟到达、压缩与重试并发、容量拒绝。过期/删除/放弃重试都不增加任务，不重新发送通知或触发执行。

6. 地址编辑开始时捕获默认快照，仅当 expectedKey 为原地址时申请迁移；冲突后保留最新默认值，不能重新读新 revision 再强行执行旧迁移。若最新值仍指向已失效旧地址，保留可恢复冲突并要求用户重新选择，不自动关闭。请求已提交但回包丢失时，以原 expectedRevision 重试不会再次生效；再读当前快照核对，不能以新版本重放。跨存储步骤继续沿用 P6-B 的编辑命令记录，不回滚用户后续选择。
7. 用受控闸门测：地址迁移 A→B 排队时另一窗口/标签页先设 C、C→A 的 ABA、原迁移已提交后用户设 C 再丢失响应重试、清空默认、删除与迁移竞争、初始化并发、事务失败/退出恢复。最终权威存储、所有页面缓存与新隔离实例启动选择一致；冲突写不增 revision、不改变 key。

### P6-B.2：Web 启动与权威默认值初始化

1. 将 packages/app/src/entry.tsx 的同步 readDefaultServerUrl/getDefaultUrl 启动分支纳入修改。locale 与默认值初始化可以并行，但必须等权威快照明确成功后才创建 AppInterface/服务器 SDK 上下文；不能先用旧 localStorage 或当前 origin 连接，再由晚到 IndexedDB 结果切换。启动只读取默认值，不因读取而再次执行 setActive 或默认值写命令。
2. 初始化结果分为 ready({ key, revision })、loading、failed。权威记录不存在时，按 P6-B.1 在事务内完成一次旧值导入；旧值确实不存在则持久化 { key:null, revision:0 }，以后即使旧 localStorage 留有值也不能复活。ready 且 key=null 才按现有 getCurrentUrl 规则选启动地址，不把该回退地址写成持久默认值。坏记录、localStorage 迁入读取抛错、IndexedDB 拒绝/事务失败不能转成 null。
3. loading 显示独立启动状态；failed/数据库升级 blocked 显示明确原因和重试入口，不启动任何服务器请求，不自动清空数据库或回退旧存储。onversionchange 关闭本标签页旧连接以允许升级；blocked 提示关闭阻塞的旧标签页，不能无限展示无说明的加载。重试使用同一个初始化协调入口，防止重叠导入。
4. 初始化事务确认 complete 后才接受 ready；单条 put 的 success 不代表事务已提交。为启动尝试维护生命周期代次，重试/卸载后旧结果不能启动应用；late Promise/IDB 回调要结束自身责任。故障恢复过程中不重复 render、不重复建立 SDK 或重复订阅通知。平台 getDefaultServer、设置页及启动入口消费同一权威访问层。
5. 将启动时取得的 revision 交给默认值缓存。后续通知/重读可以更新默认标记，但不自动抢占用户已经主动选择的活动服务器；默认服务器与当前服务器仍是两个状态。读取期间其他窗口已提交新版本时，按版本拒绝晚到旧快照，并测试初始化和通知交接不会丢掉已接收的新版本。启动使用经一致性读取确认的快照，不承诺永远追随之后的默认值修改。
6. URL 中的 auth_token 在等待存储前捕获并及时从地址栏移除，仍只绑定当前 URL 对应的原始服务器对象，不能因持久默认值指向其他主机而把该凭据复制过去。失败重试不重复从已清除的 URL 获取 token，不记录凭据；保留现有默认服务器、当前 URL 及显式连接的身份关系。
7. 真实 Web 启动验收：首次旧值导入；旧值 A、权威值 B 时只连接 B；权威 key=null、旧值 A 时使用当前 URL 且不恢复 A；清空默认后刷新；IndexedDB 慢读取期间零服务器请求；坏记录/拒绝/blocked；事务 put 成功但最终 abort；失败后重试与旧回包晚到；读取期间另一标签页改默认；新页面重开。通过浏览器网络记录确认第一笔请求的主机及次数，补 auth_token 只发往其原主机的断言，不能只检查最终页面选中项。

退出：列表、active/current、默认持久键、SDK 归属及页面标记一致；历史 OA-06/UI01～UI08 只有对应原场景重验后才能更新状态。

## 12. P7：文档解析按层收口

修改两套 `packages/{core,opencode}/src/util/office-text.ts`，data URL helper，Core `session/runner/to-llm-message.ts` 与旧 `session/prompt.ts` 的实际接线。优先共享契约样本；如抽公共代码，遵守 Schema/Core/Protocol/Server 依赖方向，不让旧运行时与 Core 形成循环，也不为消除复制而全面搬模块。

### P7-A：ADD-25/27，基础解码

1. 百分号编码直接还原 bytes；不使用 decodeURIComponent 强制 UTF-8，不把 + 当空格。定义无效 %、大小写 hex、逗号、零字节、裸 Unicode 和 Base64 的兼容行为及输入限额。
2. 文本消费层再按严格 UTF-8/声明规则解码，二进制文档直接送解析器。同 DOCX 的 Base64/percent 必须得到逐字节相同输入和相同最终正文。
3. XML 实体使用单次 token 扫描，只解码原输入中的五个命名实体及数字引用，不再扫描替换结果。非法码点、未闭合/未知引用明确处理，禁止抛出未映射异常。
4. 使用独立 XML 解码参考固定 `&#38;lt;`、`&#x26;#65;` 的字面结果，补 Unicode/相邻实体。若引入 XML parser，禁用 DTD/外部实体/网络加载，设置大小与深度限制。

### P7-B：ADD-18/19，逻辑成员与预算

1. XLSX 从 workbook 的 sheet 顺序和 relationships 解析目标；PPTX 从 presentation 的 slide ID 顺序及关系解析；EPUB 从 container→OPF manifest→spine 读取阅读顺序。不得用文件名排序替代文档逻辑。
2. 路径相对关系所属 part 解析，规范化点段，限制在 archive 内，拒绝外部关系及越界；处理属性顺序、命名空间、合法自定义 part 名、缺失关系、重复 ID 和缺失成员，不静默漏正文。
3. 导航/元数据/未引用 HTML 不自动成为正文；EPUB 非线性资源的纳入策略明确并测试。顺序与正文标题不要再依赖物理 slide 编号。
4. 共享累积输出账本，在数组/重复串构造前预留 UTF-8 字节、列分隔符、换行、标题和跨表分隔符；XLSX 不得让每行重复借用同一个 remaining。
5. 中间展开额度和最终输出额度分开，但都必须有界。成功只计费一次；失败不能继续构造下一批大数组。保留 ZIP 项数/单项/总解压预算及已有 ODS/text:s 防放大规则。
6. 测正常和逆序清单、自定义 part、缺失/外部关系、稀疏 AA/XFD、多行累计、中文/emoji、空表和多表边界；每个预算样本固定 N 成功且字节恰为 N、N-1 失败。不能只做“超大样本最终失败”。

### P7-C：ADD-21/22/29，RTF token 与代码页

1. 统一 tokenizer 识别组、控制词、控制符、hex byte、普通原始 byte、Unicode 指令和 binary 段。组栈保存忽略状态、代码页、uc fallback；只改三处正则不作为设计。
2. 原始/hex 文本字节进入同一代码页 decoder，按编码边界 flush；CP936 等多字节字符不能被每个普通字符的 flush 拆坏。
3. Unicode fallback 按语义字符/token 消耗，不把 hex 语法四字符当四个正文字符；处理转义括号/反斜杠、控制符、组边界及 Unicode surrogate，避免吞随后正文。
4. 未知 starred destination 忽略整组及嵌套内容，已知正文相关目标按规格处理；忽略状态退出组后恢复。binary 长度内容不得按花括号误解析。
5. 代码页映射列出支持集合，不支持或损坏输入给明确不可读结果，不能默默按 CP1252 解所有代码页。保留既有 936/65001 行为并测试。
6. 预算在解码输出过程中累计 UTF-8 及中间缓冲，避免先展开全部 RTF 再做 boundedText。
7. 使用 Windows 独立 RTF 参考样本及固定预期；两套提取器和 Core 消息入口必须一致。旧运行时实际附件调用路径单独补测，不能只用 helper 通过代表已完成。

退出：同一共享样本跑两实现、实际附件入口以及文本/文件移除语义；不得通过关闭附件功能、删除失败样本或截断正文绕过。

### 17.2 先固定必须成立的行为

1. `AtomicDocument.publish()` 的返回值与拒绝分开处理。正常返回遵守 `Result` 契约；拒绝才按 `CommitError.stage` 分类。
2. 仅明确 `prepare` 的失败可以表述“本次未替换”。`unknown` 必须表述“提交状态待核对”，不得自动重试发布。普通未知异常使用不承诺提交结果的脱敏错误，不武断归入未提交。
3. `committed: true` 即已提交。`cleanupPending: true` 不转换成保存失败、不再次发布；继续保留 AtomicDocument 既有清理责任与隔离记录。完整持久恢复仍按原计划执行，不在本节冒充已解决。
4. 等锁和投递前可以取消；发布投递后，必须等该次 Promise 及它负责的收尾结束才能释放租约。取消不能触发第二次发布、回滚或提前按路径删临时对象。
5. 有待处理取消时，收尾完成后保持中断，不伪造保存成功。取消期间可能已经提交，取消本身不能证明磁盘未变。测试必须分别检查终态和磁盘。
6. 保留当前工作区的 `ImageGenerationSettings.Error { code, message }`，以及 handler 到 `InvalidRequestError { kind, message }` 的映射；成功响应仍为现有配置。`code` 限于现有 alias/conflict/invalid/unavailable/unknown，本轮不扩展公开协议。内部错误在入口映射为固定、安全的信息；不得把 `cause`、配置正文、凭据或任意系统错误消息直接拼入响应。
