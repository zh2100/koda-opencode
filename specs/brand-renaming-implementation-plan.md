# Koda 可重复换品牌：实施方案

状态：待评审。本文只规划，不实施改名或迁移。当前品牌是 Koda，未来品牌名未定。

## 1. 目标与原则

下一次换品牌应主要修改一份品牌定义、一组品牌资源和对应的发布文案，不应要求用户移动项目配置、重新登录、重建会话或修改脚本。

1. **对外展示随品牌改**：窗口标题、关于页、安装器显示名称、图标、帮助与发布材料使用同一品牌定义。
2. **已有身份不随品牌改**：应用 ID、更新通道、配置发现规则、会话与凭据位置、命令和协议标识都是兼容接口。内部包名和上游归属也不是品牌资源。
3. **真实路径不改写成假名**：项目仍使用 `.opencode/` 时，错误、状态页和设置可以说「项目配置」，但「打开配置文件」必须指向并显示实际路径。OpenCode 上游项目、第三方服务名和历史内容不做字符串替换。
4. **先改展示，再决定是否改新项目默认值**：不引入跟随短期品牌变化的 `.koda/` 或 `koda.json(c)`。若确认新项目不应再创建 `.opencode/`，只引入一次不随品牌变化的项目配置约定。

## 3. 分阶段实施

### 阶段一：建立基线，集中管理展示品牌

1. 记录当前版本的干净安装和覆盖升级行为：安装目录、卸载项、快捷方式、任务栏分组、默认数据目录、更新源、协议和 CLI 调用。在同一份隔离数据中保留升级前后的可比证据。
2. 建立一份无运行时依赖、桌面构建与前端都能消费的品牌定义。仅承载展示名称、渠道展示名、图标与品牌链接等展示属性；稳定兼容标识单独维护，不从名称推导。若现有资源机制可扩展，优先复用，不新增公共 API 或不必要的包。
3. 分别接入 Web、Electron 渲染及主进程、安装器可见资源、帮助与发布文档。品牌名使用 i18n 占位符，不能把整句翻译拼起来。路径、文件名和协议在 RTL 文案中保持可读；上游署名、许可证、第三方品牌、真实配置位置均列入保留清单。
4. 打包单独核验：不能假设 `productName` 只影响展示。若它会改变默认安装路径、EXE、快捷方式、卸载项或自动更新匹配，显式固定可固定的标识；无法安全分离的项暂缓改名，不接受同渠道被识别为两个应用。
5. 在隔离构建中用一个临时品牌名演练换名：只改品牌定义和资源，验证显示随之变化，而配置来源、更新身份和数据路径不变。阶段一可以独立发布，**不改变任何配置读写位置**。

**阶段一放行前须完成以下三项实测：**

- **可见品牌**：在生产 Web 构建与打包后的桌面端切换临时品牌，打开关于页、原生菜单、更新提示和 WSL 引导。检查 `Koda`、`OpenCode` 及大小写变体，而不只找更早的旧名。以 `desktop.about.title` 为例，原生菜单目前只传 `version`；改为品牌占位符时，要同时验证英文默认消息、各语言覆盖、调用方传参，不能留下旧品牌或未展开的占位符。可见的上游名称、兼容路径等逐项记录保留原因；内部翻译键不要求改名。
- **Web 设置连续性**：在旧版本的隔离浏览器配置中通过界面设置非默认语言和一项持久化偏好；保留同一浏览器配置和同一来源（协议、主机、端口），加载新品牌版本，确认两项设置仍生效，新修改也能在重载后保留。`packages/app/src/utils/persist.ts` 的 `opencode.global.dat` 与 `packages/app/src/context/language.tsx` 使用的 `opencode.global.dat:language` 是存储键，不是文案。更换域名属于跨来源迁移，单独评审，本方案不承诺设置自动随域名迁移。
- **实际发布资产**：展示名、发布资产文件名和更新源独立配置；本阶段只改展示名，后两者保持不变。核对 `packages/desktop/electron-builder.config.ts` 的产物命名与 `.github/workflows/koda-linux.yml`、`.github/workflows/koda-macos.yml` 的 `Koda-desktop-*` 收集规则。在隔离发布链中从产物收集走到下载：按平台、架构核对实际收集的文件非空，更新清单引用的文件能下载，大小和校验值匹配。仅本地成功生成 EXE 不算通过。

### 阶段二：可选，仅在批准后引入中立项目配置

候选约定为 `.agent-config/config.jsonc` 及同目录的扩展资源。名称只是评审用例，不是现有功能。定稿前需调查目录碰撞、跨平台大小写行为、与上游 OpenCode 共用工作区的需求，以及旧版本是否仍需访问这些项目。此阶段不迁移用户全局配置和数据根目录。

| 场景                                   | 建议规则                                                                                                                               |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 只有旧项目配置                         | 保持原读取和写回位置，不创建中立目录，不自动移动文件，也不弹强制迁移提示                                                               |
| 只有中立项目配置                       | 新版本使用它；新项目初始化只在启用新默认值后创建该目录，不附带旧文件或双写                                                             |
| 同一项目层级有旧目录和中立目录         | 目录存在不代表已选择新来源。按下文分别处理设置、扩展和权限；不能让中立目录整体替换旧目录。诊断须列出实际来源和未采用的同层来源         |
| 同层还存在根目录 `opencode.json(c)`    | 按实际加载器定义的来源层级处理，不把不同来源无条件视为同一文件；需要明确列出与中立目录的读写关系，避免旧策略或限制被无提示忽略         |
| 上下级目录、全局、显式覆盖和环境变量   | 基于现有语义编写并评审完整优先级表，分别记录配置值、规则和资源的顺序；不通过改名顺便重排既有来源。保持 worktree 边界与禁用项目配置开关 |
| 已选中立配置损坏，或写入目标被并发改动 | 按下文区分缺失、不可读和无效；写入前若来源、版本或内容已变化，拒绝本次保存并提示重新加载，不覆盖外部修改                               |

**共存规则须按内容分类，不能使用一个目录优先级解决所有问题：**

1. **普通设置**：同层有效中立配置优先是候选规则，不是既定行为。先列明根文件、旧目录文件和中立文件之间的覆盖单位、缺省值与写回目标；混合项目无法唯一确定来源时不自动写入。空中立目录本身不改变旧项目行为。
2. **可执行扩展**：为插件、命令和技能分别列出发现位置、标识和同名冲突处理方式。只从已选且受信任的来源加载；不能因目录并存而重复执行同一插件，或启用原来未启用的扩展。无法判定的冲突须在加载前报告，不能两个都执行后再提示。
3. **权限策略**：`packages/core/src/config.ts` 当前对策略按普通配置的相反来源顺序加载。不得把设置的覆盖规则套给权限，也不能为兼容而一律合并或丢弃旧策略。以实际权限判定为基线：添加空中立目录，或仅添加与权限无关的设置后，原来拒绝的操作仍须被拒绝。覆盖全局与项目规则冲突、同文件语句顺序；若改选来源会削弱既有限制，阻止自动切换，列明规则差异供人工处理。

**配置读取约定**：Core 当前 `loadFile` 对 JSONC 解析失败或 Schema 校验失败可直接返回，不能单靠“未得到配置文档”判断文件不存在。中立来源必须向选择、诊断与写入入口传递以下不同结果；这是新来源的要求，不借机更改仅有旧配置的项目：

| 读取结果       | 选择、诊断和写入行为                                                                   |
| -------------- | -------------------------------------------------------------------------------------- |
| 不存在         | 自动发现可继续检查原有来源；若用户显式指定的文件不存在，报告该路径，不擅自改写其他文件 |
| 存在但不可读   | 报告来源和读错误，不按缺失处理，不改读旧配置后保存                                     |
| 存在但内容无效 | 报告实际文件和解析或校验原因，不回退、不覆盖、不新建另一份；诊断不输出凭据或整份配置   |
| 有效           | 按分类规则参与选择；只写可写的真实来源，保存前复核来源和版本                           |

V1、Core、同步发现与设置写入使用同一组磁盘样例，至少覆盖缺失、拒绝读取、空文件、损坏 JSONC、Schema 不符、合法空对象和写入前被修改。断言实际生效来源、诊断和磁盘写入结果，而非仅比较界面提示；涉及策略解析失败时，不得在权限不明的情况下执行受保护操作。

实施顺序：先让 V1、Core、同步发现入口、诊断与设置写入能够识别中立来源，再验证初始化模板和插件/技能/命令/权限行为，最后才考虑把新项目的默认写入切过去。已存在且生效的文件继续按原路径写入；编辑时保留相对路径、JSONC 注释和未修改内容。混合项目先展示生效来源，不自动迁移；如未来提供迁移入口，应先预览文件、相对引用和规则变化，由用户确认后执行，不删除旧文件、不复制凭据、不通过符号链接或双写维持兼容。

**上市前门槛**：完成旧版、新版和上游兼容矩阵后再切默认值。旧版不会自动理解中立目录，新项目若仍须供旧客户端或上游直接读取，应继续沿用旧入口，不承诺无损降级。

### 阶段三：命令、链接及真实存储迁移另立项目

- 如确有新命令或链接需求，评估可选别名和冲突（PATH、WSL、现有 shell 脚本、其他应用的协议注册）；不得替换或抢占原入口。新的展示品牌不必新增环境变量或协议。
- 数据根目录、应用 ID、更新端点或安装身份若因法律或分发要求必须更换，单独设计一对一映射、版本门槛、维护窗口、备份和恢复。不能在两个 daemon 仍持有同一资源时迁移或用不同锁身份并发写入同一个数据库。

## 4. 验收与回滚

| 检查                   | 放行标准                                                                                                                                                                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 展示和可重复换名       | 完成阶段一临时品牌演练；英文、中文与一个 RTL 界面实测；可见的 `Koda` / `OpenCode` / `.opencode` 残留各有保留理由，稳定标识不变                                                                                 |
| 包和覆盖升级           | 构建实际安装包，在隔离 Windows VM 或测试账号做干净装、同渠道升级与卸载；同一个应用身份、没有重复卸载项、不丢快捷方式关联；更新元数据和包签名遵循发布策略。其他在发平台需独立验收，不能以 Windows 代替          |
| 会话、设置和集成连续性 | 用合成数据验证原会话、模型设置、权限、插件和登录状态引用不丢，CLI 及 `opencode://` 正常；数据目录和资源锁身份保持不变。不用生产凭据或真实付费模型                                                              |
| 中立配置（阶段二）     | V1/Core、桌面/CLI、同步/异步、独立项目/worktree/嵌套目录；旧专用、新专用、共存、损坏、显式覆盖、禁用项目配置、只读目录和相对引用；覆盖插槽冲突、策略顺序、无重复插件执行及写回归属                             |
| 回滚                   | 阶段一按下述递增版本演练回退。阶段二可关闭新项目默认创建中立目录，但对已有中立项目保留读取能力；若必须使用不识别中立约定的版本，使用经验证的显式兼容方案或在用户确认下恢复备份，不双写、删目录或覆盖用户新改动 |

**回退展示改动，不降低版本号。** `packages/desktop/src/main/updater.ts` 将 `allowDowngrade` 设为 `false`。阶段一放行前，用同一隔离更新源和三个严格递增的测试版本演练：A（旧展示）→ B（新展示）→ C（恢复旧展示，保留兼容改动）。两跳均由已安装客户端检查更新、下载、安装并重启；每跳核对实际版本、展示品牌、同一安装身份和原测试会话。不得通过手动覆盖安装、打开降级开关、复用版本号或覆盖旧发布资产来代替。保留各版清单、资产校验值及两跳日志，不发布到生产通道。

## 5. 待拍板事项

1. 首次实施是否只做展示品牌集中化和可见残留清理？**建议先批准盘点和展示原型；发布以阶段一实测和两跳更新演练通过为前提。**
2. 新项目是否必须不再生成 `.opencode/`？如果是，先确定中立命名和上游同工作区要求，并评审共存权限及读取失败规则；在规则和预期样例获批前，不启动阶段二。
3. 是否需要一起更换对外域名、安装包文件名或添加命令别名？这些和显示名独立决策；默认保持现状。
