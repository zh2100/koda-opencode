## 5. S1：双后端凭据清理（FOLLOW-001）

入口：[relay-secret-store.ts](D:/opencode/packages/core/src/relay-secret-store.ts)、[relay-auth.ts](D:/opencode/packages/core/src/relay-auth.ts)。

### 修改步骤

1. 梳理系统凭据后端与文件备用后端的读取、写入、删除关系，包括系统写入失败或校验失败后写入文件的路径。
2. 明确每个后端的删除结果：已删除、确认不存在、清理失败。仅前两种可视为该后端完成。
3. 修改 remove，使两个后端都被尝试清理；不能用“系统失败后才删除文件”的互斥流程，也不能因第一个失败跳过第二个。
4. 区分文件不存在与读取失败、格式损坏、权限错误。清理路径不能将所有读取异常转换为空对象，再据此宣称清理成功或覆盖原文件。
5. 系统后端依据实际 API 语义识别不存在；不能把服务不可用或拒绝访问当作不存在。运行时没有系统接口时，遵循该环境明确支持的后端范围，不对无法验证的历史系统副本作成功承诺。
6. 只有所有适用后端都完成清理，remove 才成功；部分失败返回可重试错误。已成功删除的后端不需要恢复，下一次删除必须幂等。
7. 修改 finishCleanup：保留“当前配置仍引用该 ref 则不删除”的保护；对退休引用直接调用可靠的幂等删除，避免由会吞掉读取异常的 get 判断不存在。
8. 未完成时保留 pendingCleanup；完成后再移除记录。若凭据已删除但记录持久化失败，下次重复删除应安全完成。
9. 待清理记录及日志只保存引用和必要错误分类，不包含密钥内容。

### 测试矩阵

| 场景 | 预期 |
| --- | --- |
| 仅系统后端存在 | 删除完成，后续无法读取 |
| 仅文件后端存在，系统删除返回不存在 | 文件副本也被删除 |
| 两个后端均存在 | 两处均删除 |
| 系统成功、文件失败 | 返回清理失败，待清理记录保留 |
| 系统失败、文件成功 | 返回清理失败，不能掩盖系统失败 |
| 两个后端均不存在 | 幂等成功 |
| 文件读取失败或内容损坏 | 不当作空文件，不清空无关凭据，不宣称完成 |
| 部分失败后恢复 | 同一记录重试完成，revision 不变 |
| 删除成功、清理记录写回失败 | 再次执行可完成，不要求凭据仍存在 |
| 引用被当前配置使用 | 不删除当前凭据 |

完成标准：remove 成功意味着所有适用后端已删除或确认不存在；认证层不会提前移除未完成的清理记录。

## 6. S2：统一已提交操作的重试语义（FOLLOW-002）

入口：[relay-auth.ts](D:/opencode/packages/core/src/relay-auth.ts)、[Server relay handler](D:/opencode/packages/server/src/handlers/relay.ts)。

### 修改步骤

1. 明确配置提交成功的边界。提交前失败与提交后的清理失败必须分别处理。
2. 让 commit 和 replay 共用“已提交操作尝试清理并返回状态”的处理入口，避免两份不同的异常语义。
3. replay 根据 operationId 找到持久化待清理记录后，只执行剩余清理，不再次执行供应商增删改或密钥轮换。
4. 清理失败但已提交配置可可靠读取时，返回当前已提交 AuthState，并设置内部 cleanupPending 为 true；保留待清理记录。
5. 清理完成后返回 cleanupPending 为 false。无论是否完成，都不增加配置 revision。
6. 不把配置提交失败、配置无法可靠读取或无法构造有效状态包装成成功；错误分类必须保留真实边界。
7. HTTP 层继续去掉内部 cleanupPending，返回现有 AuthState；不因单纯的后续清理失败返回服务不可用。
8. 保持新引用写入 → 配置提交 → 旧引用清理的顺序，并复查配置提交失败时旧地址和旧密钥仍可解析。

### 回归要求

1. 首次删除已提交但清理失败，随后使用相同 operationId 连续重试且清理仍失败：每次返回已提交状态，revision 不变。
2. 清理恢复后，同一 operationId 完成清理，记录被移除。
3. 重新初始化服务后仍有清理失败，再次重试保持相同语义。
4. 覆盖删除供应商、清除供应商密钥、轮换供应商密钥与统一密钥等实际复用路径。
5. HTTP 测试经实际 handler 验证响应状态与 AuthState 结构，不能只检查 Core 返回对象；单纯清理失败不能变成失败响应。
6. 配置提交失败仍返回错误，并保留旧配置与旧密钥。

完成标准：已提交操作不会因重复清理失败而从成功变成失败；重试不重复修改配置。

## 7. S3：绑定网络请求和版本基线（FOLLOW-003）

入口：[server-sync.tsx](D:/opencode/packages/app/src/context/server-sync.tsx)、[server-sync.test.ts](D:/opencode/packages/app/src/context/server-sync.test.ts)。

### 修改步骤

1. 梳理首次加载、server.connected、手动刷新和查询缓存的所有活跃会话读取入口，避免只修复其中一个。
2. 统一请求协调方式：在实际 queryFn 执行网络请求前采集会话事件版本及请求身份，随快照结果一起保留。
3. 合并时使用该快照所属请求的基线。QueryClient 复用旧 Promise 时，必须同时复用旧基线，不能在外层 begin 时给旧响应换上新基线。
4. 保持查询过程不直接写 session 状态；结果由统一合并入口应用。内部结果可携带必要元数据，公开接口保持不变。
5. 查询正在执行时收到重连刷新，记录一次补刷需求；当前查询结束后执行一次新的网络请求。连续触发可以合并，但补刷期间的新需求不能被误清除。
6. 单轮请求成功或失败后都释放协调状态；网络错误不能导致刷新永久卡住，也不能生成未处理的 Promise rejection。
7. 保留请求代次保护；旧请求结果不能覆盖较新请求结果。请求期间有实时状态事件的会话，以事件结果为准，包括快照中缺失的会话。
8. 首次加载和重连使用相同规则；查询缓存命中时也不得将旧快照按“刚发出的请求”处理。
9. 请求状态、快照元数据和补刷需求按服务器作用域隔离；上下文销毁后旧响应不能写入新上下文。

### 必须使用真实 QueryClient 的时序回归

1. 请求 A 开始 → 收到 idle → 重连请求 B 复用 A → A 返回 busy：不能覆盖 idle，且需要的新查询最终执行。
2. 首次加载未完成就发生重连：旧初始快照不会使用重连的新基线。
3. 快照没有某会话，但请求期间收到该会话 busy：不能删除该实时状态。
4. 连续多次重连：请求数量受控，最后一次刷新需求最终完成。
5. 正在补刷时又发生重连：仍能补齐下一轮需求，不丢失刷新。
6. 当前请求失败：补刷或后续重连仍可执行，无永久 pending 状态。
7. 较旧请求晚到、缓存命中以及服务器切换：旧数据不能越过版本或作用域保护。

完成标准：基线始终属于实际产生快照的请求；重连需要新快照时最终发出新查询；所有实时事件保护继续有效。

## 8. S4：补刷断线期间结束的会话（FOLLOW-004）

入口：[refreshActiveSessionData 与重连调用](D:/opencode/packages/app/src/context/server-sync.tsx)。

### 修改步骤

1. 重连刷新开始前复制当前会话状态，保留稳定的会话 ID 和状态值；不能仅持有会随合并变化的 store 引用。
2. 在合并新快照前保留此前非 idle 会话集合。与 S3 协调：被合并的刷新请求仍需累积待补刷会话，不能仅保存最后一轮集合。
3. 将保存的状态副本传给 refreshActiveSessionData 的 beforeRefresh 参数，或使用等价的显式目标集合；不要继续依赖空默认值。
4. 补刷目标取新快照活跃会话与刷新前非 idle 会话的并集，去重后分别强制刷新消息和待办。
5. 某个会话刷新失败不能阻止其他目标被尝试；失败目标应保留后续重试途径，不能无条件标成全部完成。
6. 仅在相应补刷已安排并按既定规则处理结果后清理协调记录；拒绝旧快照不能顺带丢失仍需补刷的会话。
7. 检查最终消息、待办和运行状态的更新链，避免只修复状态标记，内容仍停留在断线前。

### 回归要求

1. 断线前 busy，重连快照为空：必须分别调用一次强制消息刷新和待办刷新。
2. 断线前 idle，快照也不活跃：不因本规则额外刷新。
3. 会话同时属于刷新前活跃集合和新快照：同一轮不重复刷新。
4. 连续重连且请求合并：早先记录的已结束会话不会丢失。
5. 某个会话刷新失败：其他目标仍被刷新，后续重连仍可重试失败目标。
6. 至少一项通过实际重连入口验证参数传递和调用结果，不能只有手动传第三个参数的辅助函数测试。

完成标准：断线期间结束的会话能够获取最终消息和待办；合并请求、旧快照被拒绝或单个刷新失败都不会永久遗漏补刷。

| 场景 | 操作 | 通过标准 |
| --- | --- | --- |
| 供应商删除与密钥轮换 | 聊天保持打开，在设置保存、删除或轮换合成凭据 | 配置状态正确，供应商和模型列表同步 |
