# 会话任务状态修复方案

状态：待评审，未实施。范围：Web 和桌面端共用的 `MessageTimeline`，覆盖支持该契约的 V2 和 V1 会话；不改 TUI、分享页面、子代理调度、通用 `task` 工具、权限规则或计划任务。工作树里的多模型协作删除和其他未提交改动不回退、不混改。

## 1. 验收失败原因

- `packages/app/src/pages/session/timeline/rows.ts` 用 `finish === "stop"`、助手完成时间和工具展示部件猜测成功。`packages/core/src/session/runner/llm.ts` 在发布 `Step.Ended` 之后还要决定是否续跑，包括已经等待的 `steer`；因此 A 可以先被标为完成，随后同一轮又在 B 下被标一次。
- `packages/app/src/context/server-session.ts` 收到单个步骤结束就把会话状态置为 `idle`。用这个状态驱动绿色，工具和模型续跑之间会闪断；没有首个助手步骤时也无法表达已经开始的执行。
- V2 实时归约保留了工具部件，但 `normalizeContextMessages` 的历史转换目前只投影文本和推理。Chromium 已复现同一条含托管工具的回复实时不显示橙色、刷新后却显示。补齐工具展示不属于本方案：即使两条路径都保留工具，也不能据此判定整轮结果。
- 新旧布局共用时间线，但后端 V1、V2 是不同契约：V2 由 `SessionV2` 和串行 runner 执行，V1 路由使用 `SessionPrompt`。布局开关不能用来判断数据能力。现有前端对 `session.execution.*` 的归约只清理重试信息，不能提供轮次归属或历史结果。

## 2. 生命周期契约

新增独立于聊天内容的轮次状态。建议数据为 `sessionID`、`rootMessageID`（原始用户消息）、`attemptID`（一次被明确启动的尝试）、单调版本及状态 `running | succeeded | failed | interrupted`。关联到本轮的用户输入（包括 `steer`）和助手输出均使用明确的轮次归属；不靠列表最后一条、时间戳排序或当前选中的会话猜测归属。`attemptID` 不是 drain ID、集群租约或 EventV2 replay owner；同一次历史消息的显式重新执行可创建新尝试，界面仍只保留根消息的一行。重复提交、协同唤醒、自动重试不能凭空创建新尝试。

| 场景 | 约定 |
| --- | --- |
| 输入提交、持久接纳、排队、单纯历史读取 | 不显示本轮绿色。 |
| 串行执行端取得本轮输入，正式进入回复执行 | 在等待首个提供方事件之前写入 `running`；尚无输出时显示在根用户消息下。 |
| 工具执行、模型续跑、可恢复失败、自动重试 | 不结束尝试；保留同一行身份。授权、提问、重试和错误提示优先，等待期间可隐藏绿色，解除等待后恢复，不另建一行。 |
| A 执行时 B 以 `steer` 被当前轮接纳 | A 保持原归属，B 及后续助手输出关联到 A；B 不产生独立完成行。 |
| A 执行时 B 以 `queue` 等待 | B 不关联 A。A 先落定；B 实际启动时再获得新轮次。 |
| 执行端确认工作全部结束，而且没有当前轮须执行的续跑 | 持久化 `succeeded`，原行换橙色。正常步结束、工具完成、`busy → idle`、缺少终态、流意外结束都不是成功证据。 |
| 最终失败、取消或中断 | 不显示橙色，并清除绿色；中间已恢复的错误不阻止后续正常完成。 |
| 进程异常退出或断线 | 断线本身不等于失败，也不等于成功。重新连接后从服务端核实终态和本次尝试是否仍实际活跃；无活跃证据时不渲染历史残留的 `running`，不自动重试提供方。 |

同一尝试只允许一个终态；终态落盘为分界：取消若在成功提交前赢得竞争则不能写成功，成功已提交后的空闲中断不改历史。过期尝试、重复和迟到事件不能覆盖新版本。正常终态须由执行端显式返回：区分可继续、成功、不可恢复错误和中断，逐一界定空流、截断、内容过滤和步数耗尽等结束原因；没有明确成功的路径不标橙。

## 3. 最小数据变更与实现顺序

### 3.1 V2：执行端定界，复用现有持久化

1. 在 `packages/core/src/session/runner/llm.ts` 中区分外层 drain、业务回复轮次、内层模型步骤。首次启动取自本轮实际提升的输入；工具、压缩恢复和自动重试沿用同一归属。核对显式 `resume` 的输入解析：只有确实执行用户回复时才启动状态；不能把空唤醒、独立压缩或 Shell 记到上一条用户消息。空闲时一次提升多个 `steer` 的情况，固定以该批首个实际执行的用户输入为锚，其余关联同轮。
2. 在明确的执行边界提交终态：完成待执行的工具和恢复逻辑，做当前轮 `steer` 的最后一次判定，然后在提升下一条 `queue` 前结算。沿用 Session 串行执行，在最终检查与成功写入之间定义可验证的接纳截止点：以同一数据库事务串行化检查/结算，或以明确的提交水位划分边界。截止前尚可被本轮消费的 `steer` 不得漏掉；截止后的输入由后续唤醒接手，不回改 A。为此补并发边界测试，不能只依赖一次 `hasPending` 后再异步发布成功。
3. 在 `packages/schema/src/session-event.ts` 建议增加专用、持久的轮次生命周期事件；通过 `packages/core/src/session/projector.ts` 投影到现有 `session_message.data`：根用户消息带可选的 `turnStatus`，相关用户及助手带可选归属引用。优先用专用可选字段而非信任可由客户端提交的通用 `metadata`。状态事件不创建聊天消息，也不改变原消息的排序、分页或模型上下文。归属应随相关消息的首次写入投影；必须补写时也使用同一有序事件流和版本规则。成功广播须在持久事件及投影提交之后。该设计默认不新增表、列或迁移；用真实库验证事件重放、分页和现有消息读接口之后再定协议字段。若消息裁剪、回退或复制会丢失归属，先解决投影/读取约束，再单独评审其他存储改动。
4. 实时和历史统一使用持久的根状态及轮次归属。对刷新时的绿色，检查现有活跃接口能否提供精确的当前 `rootMessageID` / `attemptID`；只有会话级活跃标记时，扩展返回最小的可选匹配字段，并在执行收尾时清理本地活跃登记。持久事件用于还原结果，本地活跃记录只用于确认当前执行；不能把它作为历史成功来源，也不从历史残留恢复模型执行。中断在首个助手事件之前也必须能结算。

### 3.2 V1：独立接入，不挪用 V2 语义

1. 在 `packages/opencode/src/session/prompt.ts` 的 `SessionPrompt.runLoop` / `ensureRunning` 入口与终止分支核对真实用户归属、连续输入、终止和返回旧助手消息的分支。V1 不假设具备 V2 的 `steer` / `queue`；连续输入按 V1 实际执行边界归属。为两个协议复用显示契约，不桥接两个 runner。
2. V1 优先在现有 `message.data` 的用户记录上增加同义的可选字段，通过提交后消息更新事件和现有消息列表返回；检查 V1 `User` schema、读写路径、同步裁剪和 SDK。若现有 V1 循环未区分「这次正常结束」和「返回已有助手」，先补明确结果与归属，再启用状态。老服务器没有契约时不渲染任务状态，继续原有思考、权限和错误提示；不能以 `finish` 兜底。V2 先验证不等于 V1 已验收，若两条路径都在交付范围内，缺一不签收。

### 3.3 应用、兼容与工作树回归

- 在 `server-session.ts`、`server-session-v2-reducer.ts`、V1 消息同步与 `timeline/projection.ts` 中合并状态和归属。以服务端作用域、会话、根消息和尝试版本隔离数据。历史响应和实时事件竞争时按权威版本归并；缺少根消息或归属时按需补读，不把状态借给其他轮。翻页、回退隐藏的消息不产生孤立状态行。旧消息缺少字段则不标记。
- 移除 `rows.ts` 的 `finish` / 时间 / 工具和 session busy 状态推断，不连带改变其他现有 thinking/重试行、会话忙闲、停止按钮或面板的归属逻辑。沿用 `task-status:<rootMessageID>`，按明确归属把唯一状态行放在本轮最后可见内容后。绿色与橙色更新同一行，不用 `scrollToBottom`，用户离底时保留滚动锚点；浅色/深色验证实际背景下小字对比度，使用逻辑方向，简繁中文保持已定文案。若增加读屏即时通知，只公告当前会话的实时转换，历史加载、翻页和重连补帧不批量公告。
- 公共 Protocol/HttpApi 变更后，从 `packages/client` 运行 `bun run generate`；若触及旧 SDK 公开面，从 `packages/sdk/js` 运行 `bun script/build.ts`，不手改生成目录。先用旧数据、旧客户端和旧服务器验证可选字段、未知事件与回放兼容性；如不兼容，先修兼容或改为独立受版本保护的契约，再上线。降级可关闭新状态显示，不删消息、事件、历史表或既有设置。
- 工作树提交失败单独定位、单独修复或说明是否为基线失败。隔离检出基线 `ac5272bc2a`，以相同 Bun 和测试配置复测 `reads the latest worktree accessor value per submit`，再比较 `submit.ts` 的选定工作树、路由目标和会话恢复逻辑。当前证据仅为第二次 Shell 期望 `/repo/worktree-b`、实际 `/repo/main`。不靠改断言或跳过测试解决；具体修法以基线和实际路由语义为准。

## 4. 验收门槛

1. **核心生命周期**：真实 runner 与数据库回放覆盖普通问答、首个提供方事件阻塞、工具续跑、托管工具与正文同一步、重试后成功、最终失败、输出前停止、执行中停止、完成后停止；另测 A/B 排队、一个及多个 `steer`、成功提交边界并发入队、提交后广播失败和进程重启。断言每次尝试仅一次终态，且不引入额外 `llm.stream(request)` 或上下文消息。
2. **协议和投影**：验证各实际服务器路径中事件与历史返回一致；覆盖消息版本乱序、重复帧、并行载入、活动状态过期、翻页缺根、切会话、回退与旧历史。已完成的运行不因刷新重复终态，持久未完成不伪造成功。普通 Shell、分享、子代理、通用 `task`、权限和计划任务执行回归。
3. **浏览器及桌面验收**：Chromium 建立可控首响应、工具、暂停和中断场景，至少一条用真实本地服务器、受控提供方贯通提交、流事件、历史和刷新；V1/V2 与新旧布局用各自实际路由验证。检查同一行键、内容位置、翻页和会话切换时滚动、授权/问题/重试优先级，浅色/深色、简繁中文、英语强制 RTL 和真实 RTL 语言。补桌面端实机复测。模拟消息夹具不能代替本项。
4. **检查和交付**：在对应包目录运行 `bun typecheck`、相关核心/协议/应用测试与工作树提交回归，并运行 `git diff --check`。测试和兼容性过关后再移除旧猜测路径或随替换同一提交删除；任何不具备可靠契约的路径保持无状态显示，不以部分通过签收完整需求。
