# OA-06 与 OA-01 通知补修复核（2026-11-11）

结论：目前不能关闭 OA-06；OA-01 的通知生命周期和服务构建错误边界也仍未收口。本轮确认 6 处问题。既有 17 项状态测试与 App 类型检查确实通过，但测试覆盖方式遗漏了真实首次加载、正常刷新、后端幂等协议和通知取消/销毁。

本轮只做复核及隔离复现，没有修改业务源码、提交或重启应用。本文追加审查证据，不覆盖原实施结果。

## 1. R01 / P1：首次打开设置不再自动读取，切换服务器也不加载

位置：[use-relay-settings.ts:182](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:182)。

createResource 的 source 会观察 scope 并重置状态，但 fetcher 是 () => undefined，没有调用 load。useRelaySettings 仅返回工厂结果，旧、新设置页都只在出现错误时提供 reload 按钮，没有主动调用 load。

因此真实页面首次打开时 auth 始终为空，只显示默认供应商卡片；已有自定义供应商和保存状态不能读取。由于没有请求，也不会出现可点击重试的读取错误。

使用正式工厂、真实 Solid createRoot/createSignal，构造后等待一轮，再把 scope 从 A 改成 B：

~~~json
{"case":"automatic-load","afterOpen":[],"afterSwitch":[]}
~~~

修复要求：

1. 让 resource 的正式 fetcher 执行捕获上下文的加载。
2. 首次挂载自动读取一次；响应式 scope 变化自动读取目标服务器。
3. 同服务器手动 reload 使用同一路径，不能靠测试或组件额外调用 load 掩盖缺失行为。
4. 调整夹具的请求闸门以覆盖真实自动加载，不为方便测试删除生产行为。

必要补测：真实 createRoot 内构造状态，不显式调用 load；断言 A 的 get 自动发生。用 createSignal 切换 B，断言 B 自动读取，并确认第一轮 A 回包无效。现有 U03/U04 使用普通变量加显式 reload，不能证明自动响应式加载。

## 2. R02 / P1：不同写命令复用 operationId，认证模式切换被当作重试

位置：

- [use-relay-settings.ts:209](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:209)
- [use-relay-settings.ts:269](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:269)
- [relay-auth.ts:319](D:/opencode/packages/core/src/relay-auth.ts:319)

saveVendor 使用 context.operationId 提交 vendor；随后 setMode(false, context) 又使用相同编号提交 mode。真实 RelayAuth 的 replay 缓存按 operationId 跨方法查找，因此 mode 命令返回 vendor 命令的已有结果，不执行切换。

正式前端工厂的受控请求捕获：

~~~json
{"methods":["vendor","mode"],"sameOperationId":true,"unified":true}
~~~

真实 RelayAuth、隔离文件根、内存 SecretStore 的独立验证：

~~~json
{
  "vendorResult":{"revision":3,"unified":true},
  "sameIdResult":{"revision":3,"unified":true},
  "freshIdResult":{"revision":4,"unified":false}
}
~~~

这说明后端不是未收到请求，而是正确地按重复 operationId 重放了前一条命令。界面可能认为独立供应商密钥已经生效，实际仍处于统一模式。

修复要求：

- scope、generation 可以沿用父操作；不同后端写命令必须有不同的幂等编号。
- 同一条命令重试继续使用原编号，不要每次重试重新生成。
- 可分离 UI actionId 与 command operationId，或为每个子命令生成并保留独立 ID。
- 不通过删除后端幂等缓存解决。

必要补测：在统一模式下保存单供应商密钥，使用真实 RelayAuth 或忠实保留其幂等行为的接口；断言 vendor/mode ID 不同、统一模式最终关闭、相同 mode 重试不增加 revision。U06 的 mode stub 仅返回期望状态，未覆盖该协议。

## 3. R03 / P2：未编辑供应商直接刷新，正常结果被丢弃

位置：[use-relay-settings.ts:138](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:138)，以及第 148、154 行的比较。

请求开始时 vendorVersion 取 vendorCatalog.get(vendorId) ?? 0，但完成时直接用 vendorCatalog.get(vendorId) 比较。供应商尚未 invalidate 时 Map 没有条目，完成时 undefined !== 0，所有结果被当成过期。

正式工厂复现：先读取已有有效凭据，然后不修改草稿，调用 fetchModels。refresh 与 candidates 都成功，返回非空模型：

~~~json
{
  "case":"refresh-unchanged-vendor",
  "calls":["all-candidates","refresh","vendor-candidates"],
  "candidates":[],
  "status":"empty"
}
~~~

新增供应商的 addVendor 直接调用 loadCatalog(context, id)，也可能命中同一缺省代次问题。现有 U09 先修改 key，invalidate 提前创建了 Map 项，恰好避开缺陷。

修复要求：开始与完成统一使用同一规范化读取方式，例如缺省值均为 0；或始终初始化条目，再比较。不能通过强制用户改一次设置来初始化 Map。

必要补测：首次加载已有供应商、不改字段直接刷新；新增供应商后首次获取；相同供应商两次逆序刷新；同时保留不同供应商互不淘汰的用例。

## 4. R04 / P2：保存密钥后 managed 被清空，没有补读

位置：

- [use-relay-settings.ts:136](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:136)
- [use-relay-settings.ts:268](D:/opencode/packages/app/src/hooks/use-relay-settings.ts:268)

保存 key 或变更地址后 invalidate 会从 managed 中删除该供应商条目。后续 loadCatalog(context, vendorId) 在 vendor 分支却将 managed 固定设为 undefined，也不应用任何 managed 结果。因此候选列表恢复了，已有可见模型/勾选状态没有恢复。

正式工厂复现：

~~~json
{"case":"managed-after-key-save","before":1,"after":0,"candidates":1}
~~~

影响：本地供应商卡片的 visibleCount/isVisible 使用该 managed 列表，保存后显示数量和勾选状态错误。后端目录是否仍正确与这处本地展示错误是不同问题。

修复要求：

1. vendor 刷新后重读对应 managed 状态。
2. 使用该 vendor 的请求版本、失效版本及 visibility mutation 水位保护结果。
3. 合并该 vendor 的 managed，保留其他 vendor 的较新结果。
4. 不为补回列表而无保护地应用旧全量 managed 快照，否则重新引入 U08 乱序覆盖。

必要补测：已有 visible:true 模型，修改 key/URL 并保存后仍显示可见；刷新期间切换可见性，旧读取不能覆盖；两个 vendor 并行保存后双方 managed 都保留。

## 5. R05 / P1：CatalogError 是 OA-01 服务构建通道未收口

位置：

- [relay-catalog.ts:200](D:/opencode/packages/core/src/relay-catalog.ts:200)：严格 read。
- [relay-catalog.ts:287](D:/opencode/packages/core/src/relay-catalog.ts:287)：初始化 yield* read()。
- [relay-catalog.ts:588](D:/opencode/packages/core/src/relay-catalog.ts:588)：node 直接导出 layer。

复跑 Core bun typecheck，仍有四个 TS2322，位置是：

- session.ts:570、578
- session/execution/local.ts:19
- tester-session-bridge.ts:31

原因不是这些调用点没有更新文件，而是 OA-01 把初始化 read 改成 typed CatalogError 后，Layer 构建错误进入依赖该服务的位置服务图。HEAD 版本的初始 read 吞错为空，因此没有这个构建错误通道；审查修复前的八包类型检查也曾通过。

相对 OA-06，这确实是前置错误；相对 OA-01～OA-06 整批修复，它是未解决的回归，不能按“既有且无关”排除。

修复要求：

- 在 RelayCatalog 的服务初始化/Layer 构建边界处理读取失败，让损坏目录阻止该服务正确构建。
- 保持运行中 transact/read 返回的 CatalogError 为明确业务失败。
- 不能恢复“读错就当空文件”，也不能扩大 Session 公开错误类型掩盖依赖构建错误。
- 可按既有项目模式，把初始化 read 的失败转为构建 defect，或在适当的 node layer 构建边界使用 Layer.orDie。只处理构建期，不吞运行期失败。

必要补测：损坏目录构建失败且不覆盖文件；构建正常后模拟读取损坏，业务操作返回 CatalogError；Core、OpenCode、Server 类型检查全部通过。

本轮实际复跑 Core 命令的工具返回 exit_code 为 1，并输出上述 TS2322；未重新运行 OpenCode/Server 类型检查。不要把用户此前记录的 exit_code 2 当成本轮独立复跑结果。

## 6. R06 / P2：通知 catchCause 吞中断，重试脱离服务生命周期

位置：[relay-catalog.ts:252](D:/opencode/packages/core/src/relay-catalog.ts:252)。

两层 catchCause 都忽略了具体 Cause，重试使用 Effect.forkDetach：

1. 事件发布返回 Effect.interrupt 时，修改调用被恢复为成功。
2. 服务作用域已经结束后，通知重试仍继续调用已释放的发布器。

真实 RelayCatalog + 隔离数据根 + 中断型通知器：

~~~json
{"mutationExit":"Success","interrupted":false}
~~~

真实服务退出作用域后，等待 1,200ms：

~~~json
{"afterScope":1,"afterWait":3,"publishedAfterDisposal":true}
~~~

修复要求：

- 检查 Cause。对于取消/中断，保留中断语义，不把它当成普通通知失败。
- 普通通知失败/defect 可以按“目录已提交”策略记录并重试；不能回滚已经提交的配置。
- 重试由服务拥有的作用域管理，在服务退出时停止；不能把它 fork 到短期事务作用域中导致立即取消，也不能用 forkDetach 脱离所有者。
- 合并同一服务的待通知 revision，限制重试数量，避免每次失败产生独立重试循环。

C12 目前只有“内存条目存在”和“两次文件文本相同”两个断言，没有断言恢复后实际成功发布，也没有验证次数、取消或服务销毁。因此 C12 通过只能证明文件没有被重写，不能证明通知恢复完整正确。

必要补测：

- 发布 Effect.die 后恢复，确实出现成功通知，且文件未重复提交。
- 发布中断，调用保持中断。
- 服务销毁后等待超过重试间隔，发布次数不再增加。
- 连续多次失败只保留受服务管理的有界重试。
- 发送期间新增 revision，最终最新 revision 的变化能被观察。
