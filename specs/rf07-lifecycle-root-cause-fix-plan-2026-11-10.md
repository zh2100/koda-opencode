## 2. 根因与必须成立的不变量

根因是权限生命周期分散在调用者、夹具和 finalizer 之间；取消、错误和恢复状态的含义不一致；测试又未从外部证明最终事实。

| 编号 | 不变量 | 对应现有问题 |
| --- | --- | --- |
| L01 | 任何权限修改开始前，已保存原权限并建立释放责任 | 部分 apply 失败后的恢复责任 |
| L02 | 修改实际结束先于任何恢复；整体结束后无晚到权限写入 | 取消后 restore → apply |
| L03 | 正常、准备失败、请求失败、取消共用一个收尾入口 | 分支不同，实际恢复次数不同 |
| L04 | 收尾总计最多两次尝试，首次失败且预算剩余时继续 | finalizer 只恢复一次 |
| L05 | 最终资源状态和历史错误独立，恢复成功不删除失败证据 | 后续成功吞掉首次恢复错误 |
| L06 | 恢复使用捕获的原始权限，验证原权限、可读性与内容 | 固定 0666/0644 与 umask 冲突 |
| L07 | 未执行的 OS 验证只能是框架 skip 或明确失败 | Windows 直接返回计为 pass |
| L08 | 测试能否失败取决于外部结果，不能使用恒真断言 | 成功或失败都接受、只检查调用次数 |

实施完成必须逐条提供测试证据。只有总数通过而缺少任意一条证据，不关闭 RF-07。

## 5. 目标接口与职责

### 5.1 对外只保留一个执行入口

将当前对外返回 deny、restore 的接口迁移为测试专用的统一执行函数，建议名称 `withConfigReadDenied`。名称可以适应仓库风格，但职责不能分散。

输入仅包括临时文件、测试文档、平台适配器和请求回调。回调在权限拒绝探测成功后执行，可接收实际 EACCES/EPERM；不向回调开放任意设置状态、增加预算或释放权限的能力。

函数正常返回意味着：正文成功、权限恢复验证成功、未发生任何需要报告的清理错误。恢复过程中发生过错误，即使最终修复了资源，本测试仍报告失败并保留记录。

内部状态和调用轨迹可通过窄小的测试观察边界获取，不将可修改的生命周期句柄公开给 HTTP 测试。

### 5.2 使用现有 Effect 资源结构

当前依赖为 Effect 4 beta。其 acquireUseRelease 支持 use 与 release 的错误类型，适合作为此处统一执行入口。建议按以下职责组织：

1. acquire 只创建/确认临时文件、保存原权限、构造内部上下文；此时不修改权限。
2. use 内先登记 pending，再在窄小不可中断区域中执行并等待 apply 真正结束。
3. apply 成功后探测真实拒绝；只有 EACCES/EPERM 才进入请求回调。
4. 请求回调保持正常可中断，不把 HTTP 请求放进权限修改的不可中断区域。
5. release 统一执行 finish，处理全部剩余恢复尝试、验证和错误汇总。

重要边界：acquireUseRelease 的 acquire 若失败，不会进入 release。因此可逆的权限修改必须发生在 use 内，不能放进尚未完成的 acquire。临时文件删除仍由外层 fixture 负责。

不要在 apply 的 Promise 等待上再次使用 uninterruptibleMask 提供的 restore 来恢复可中断性。取消调用者等待不能取消实际 chmod/进程操作；必须等实际操作结束后再进入 release。

如果实现改用 scoped/finalizer，必须满足同一顺序和错误语义，并证明 acquire 部分失败也有清理责任。不要同时保留两套会独立恢复权限的入口。

### 5.3 内部状态分开保存

上下文至少区分以下事实，字段保持小型、私有：

- 原始权限快照：由夹具实际读取，不由调用者传固定值。
- 当前阶段：准备、修改中、已拒绝、恢复中、已恢复、未恢复。
- 实际恢复尝试次数：总计最多两次。
- 只追加的失败记录：阶段、尝试序号、原始原因；不得含测试文档或凭据正文。
- 已完成收尾的标记/结果：重复收尾不再执行 OS 修改，仍返回一致结论。

失败记录与最终资源状态独立。可以同时出现“最终已恢复”与“本轮因首次恢复失败而失败”。

不开放新的可配置任意重试次数接口。本夹具固定两次上限，避免不同调用者改变验收语义。

## 6. 原权限捕获与平台适配

### 6.1 POSIX

1. 文件创建并写入后，修改前读取 stat.mode & 0o7777。
2. 将该值作为平台适配器 restore 的实际输入，或由同一作用域闭包持有。删除 posixOps(0o666) 和测试里固定 chmod(0o644) 的恢复逻辑。
3. apply 设置测试拒绝权限；restore 使用捕获的原值。
4. 每次恢复成功后读取实际 mode，与原值精确比较，并验证文档可读且字节未变。
5. 文件原权限受 umask 影响，任何固定预期都必须由用例事先明确设置，而非猜测默认值。

### 6.2 Windows

1. 保留对新建临时文件的继承 ACL 恢复方式，但在修改前确认夹具的初始 ACL 条件满足该恢复约定。
2. 如使用 icacls /reset，只适用于本夹具新建且原本使用继承 ACL 的文件；不得声称它能精确恢复任意用户自定义 DACL。
3. 在内存保存需要验证的初始继承/保护状态；恢复后确认没有测试添加的拒绝 ACE，继承状态符合原条件，并验证可读性和内容不变。
4. 子进程使用参数数组，检查启动 error 和退出码。非零、无法执行、读取验证失败均进入恢复失败记录。
5. 工具或适配器必须等待实际进程结束。超时/取消不能仅放弃等待并允许进程随后继续修改权限；若使用异步子进程，必须定义并测试终止后等待 close 的行为。
6. 失败时只处理该临时文件，不通过修改父目录 ACL 或提升权限补救。

## 7. finish 的唯一收尾规则

1. 如果从未开始权限修改，直接完成，不执行恢复。
2. 修改已经开始时，确认没有在途 apply；随后进入恢复循环。
3. 每次尝试先计数，再执行真实 restore，再验证原权限、可读性及内容。执行或验证阶段抛错、返回失败、内容不符都记为一次失败尝试。
4. 第一次失败且预算剩余时，继续第二次；不依赖外层调用者或第二个 finalizer 再触发。
5. 任一次成功，最终资源状态记为已恢复；已有失败记录保留。
6. 第二次仍失败，最终状态记为未恢复，返回明确清理失败和隔离目标；不声称已清理。
7. release 只做一次整体 finish。内部可以测试幂等，但成功/失败后重复调用不能重新获得两次预算，也不能重复修改权限。
8. 不长时间 sleep、不无限重试。每次底层命令的存活结束必须确认，不能用预算上限掩盖仍运行的修改。

错误结果必须满足：

| 正文 | 收尾 | 整体结果 |
| --- | --- | --- |
| 成功 | 一次成功，无错误 | 成功 |
| 成功 | 首次失败、第二次成功 | 失败；记录资源已恢复及首次原因 |
| 成功 | 两次失败 | 失败；记录资源未恢复及两次原因 |
| 失败 | 恢复成功 | 保留正文失败 |
| 失败 | 收尾出现错误 | 同时保留正文和全部收尾错误 |
| 取消 | 恢复成功 | 保留中断，不伪装成成功或配置错误 |
| 取消 | 收尾出现错误 | 保留中断与清理错误，并注明最终资源状态 |

使用真实 Effect Cause/Exit 组合验证正文和 release 的错误，不以替换成一个通用 Error 的方式丢失来源。对可预期的恢复失败采用明确错误通道，不能仅赋值后 return。环境、实例与数据库的清理保持独立，不能被权限恢复错误阻止。

## 8. 重写回归，使错误实现必然失败

### 8.1 移除无效证明

1. 删除 `Exit.isSuccess(x) || Exit.isFailure(x)` 等恒真断言，改为唯一预期的 Exit 与具体原因。
2. 删除用例体内的 Windows 直接 return、root 打印 skip 后 return。所有 OS 用例在注册阶段使用框架 skip，并写明原因。
3. 请求用例通过统一入口执行；测试不再手动调用两次 restore 来代替验证自动收尾。
4. 替身记录真实观察到的操作事件、最终权限状态和请求是否执行。不能只检查夹具自报的 state 字符串或调用次数。
5. 失败注入测试与 HTTP 测试共用同一夹具。不得复制一个只用于测试的正确状态机。

### 8.2 取消测试的正确顺序

旧测试等待 Fiber.interrupt 完成之后才解除 apply 的挂起，正确实现下会相互等待；错误实现则过早取消并通过。必须替换该控制顺序。

新顺序：

1. fork 整个统一生命周期，等待 apply 明确发布 started 信号。
2. 请求中断但不在控制器此处等待整体结束。当前 Fiber 类型提供 interruptUnsafe() 这一低层同步请求入口；仅限该确定性测试使用，或采用能证明中断已经送达的等价公开 API。
3. 独立控制器放开 apply，使底层修改实际完成。
4. 等待目标 fiber 和其 release 完整结束，再检查事件和最终文件状态。
5. 断言 apply-finished 严格早于 restore-started、最终未拒绝读取、中断被保留。
6. 再触发并等待所有受控在途操作结束，确认完成后没有晚到修改。

使用同步信号和可控 Promise；超时只用于发现死锁。不得用 sleep 猜测请求或清理已经开始，也不得在恢复断言之前人为执行一次额外恢复。

### 8.3 必跑矩阵与不变量映射

| 用例 | 输入/边界 | 唯一预期 | 不变量 |
| --- | --- | --- | --- |
| T01 | 正常拒绝、请求成功、恢复成功 | 请求只执行一次；权限/内容恢复；整体成功 | L01、L03、L06 |
| T02 | apply 修改后报告失败 | 请求不执行；自动进入 finish | L01、L03 |
| T03 | T02 且首次恢复失败、第二次成功 | 两次恢复；资源已恢复；原 apply 和恢复错误都可见 | L03、L04、L05 |
| T04 | 请求成功，首次恢复失败、第二次成功 | 整体失败，首次错误未丢失 | L04、L05 |
| T05 | 两次恢复失败 | 恰好两次；明确未恢复；整体失败 | L04、L05 |
| T06 | 探测仍可读或为 ENOENT | 准备失败；请求不执行；自动恢复 | L01、L03 |
| T07 | apply 挂起期间中断 | apply 完成后恢复；无晚到写入；保留中断 | L02、L03 |
| T08 | 请求回调挂起期间中断 | 请求作用域释放；权限恢复；保留中断 | L02、L03 |
| T09 | 请求失败且恢复失败 | Cause 同时包含正文与收尾原因 | L05、L08 |
| T10 | 恢复命令成功，验证读取或 mode 检查失败 | 计入失败并使用剩余预算；不伪报已恢复 | L04、L06 |
| T11 | 原 mode 分别为 0600、0640、0644、0664 | 精确恢复各原值，不依赖默认 umask | L06 |
| T12 | 完成后再次收尾 | 无额外权限调用，结果一致 | L03、L04 |
| T13 | Windows、非特权 POSIX、root 平台注册 | 不适用用例真正 skip；共用契约仍执行 | L07 |
| T14 | 当前用户真实 EACCES/EPERM | HTTP 503/code/ref，不泄密，恢复后文件正确 | L06、L08 |

T03、T04、T07 是上轮失败复现的长期替代用例，修复前必须证明它们失败，修复后再证明通过。每个错误实现都必须被至少一条有效断言拦住。

T11 的真实 POSIX 验证在对应系统执行；Windows 上的受控适配器只能证明原快照被传入，不能证明 chmod 行为。T08 的受控回调用例不能写成真实 HTTP 取消已完成；若补完整路由取消，需独立记录传输与服务端执行是否都已结束。

## 9. 逐步执行与每步产物

1. 固化三个失败回归并修正用例统计，保存旧实现失败的名称、断言和退出码。取消测试不得对生产文件操作。
2. 定义统一入口、原权限快照和只追加错误记录，先在受控适配器测试上落实 L01–L06。
3. 实现唯一 finish，覆盖准备失败、恢复失败、取消和错误组合；不保留调用者手动凑次数的兼容路径。
4. 接入窄小不可中断 apply，证明 T07 真正保护操作顺序。
5. 修改平台适配器，让实际捕获值控制恢复；删除固定 mode，并验证 Windows 临时继承 ACL 约定。
6. 将 HTTP 套件迁移到统一入口。权限生命周期回调内取得 HTTP 结果，整体收尾完成后再做响应断言。
7. 统一平台注册，检查两个测试文件中所有提前 return。能力不足的已注册用例明确失败；已知平台不适用用框架 skip。
8. 删除旧 deny/restore 导出、旧布尔标记和重复收尾分支。先搜索全部调用者，确认无残留再删除，不清理无关历史代码。
9. 本机真实权限测试、联合回归和类型检查通过后，运行非特权 Linux/macOS 与 root job；缺机器的部分保持待验证。
10. 逐条填写下一节证据表，再决定 RF-07 状态。不能在步骤 9 缺平台时写跨平台全部通过。
