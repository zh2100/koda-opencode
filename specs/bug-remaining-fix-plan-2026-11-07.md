## 4. R1：SYNC-001 重叠快照保护

### 问题与根因

入口：[bootstrap.ts](D:/opencode/packages/app/src/context/global-sync/bootstrap.ts)、[server-session.ts](D:/opencode/packages/app/src/context/server-session.ts)。

请求 A 记录旧基线后收到新权限事件，请求 B 记录新基线并先完成。B 释放标记后，A 已无法判断该会话发生过新事件，旧空快照于是清空提示。问题列表使用同类逻辑，也必须覆盖。

### 解决方案

将事件版本与请求生命周期分开：请求完成不删除仍可能被其他请求依赖的版本。每份快照携带实际网络请求发出前的事件基线和请求代次，由统一入口判断是否可合并。状态跟踪应由对应服务器／会话上下文持有，避免全局 Map 按裸目录相互影响。

### 实施步骤

1. 列出 permission/question 的 asked、replied、rejected 等实际事件入口，确认 V1/V2 事件转换都会更新版本。
2. 在服务器上下文内记录每个会话、每类提示的单调事件版本。事件可能先于会话详情到达，不应因 directory 尚未知而只记到空字符串作用域、随后失去保护。
3. 请求发出前采集相关会话版本；对基线中没有但请求期间出现的会话，也能通过非零版本识别变化。
4. 按服务器、目录和提示类型分配请求代次。合并前同时检查上下文仍有效、请求未过期、该会话版本未变化。
5. 将“快照包含会话”和“快照不包含会话，因此准备清空”的分支接到同一保护规则。已回复提示不能被旧快照恢复，新提示不能被旧快照删除。
6. 移除当前请求完成时直接删除共享事件标记的行为。短期可随对应上下文生命周期保留；如需按会话回收，必须确认没有相关在途请求，并让旧请求永久失效，不能将版本归零后允许旧响应写回。
7. 目录卸载、服务器切换及上下文销毁时作废请求身份；旧 finally 不得清除新上下文的记录。
8. 新请求失败不能使旧快照重新获得覆盖资格；保留实时状态，按既有重试入口重新获取，不伪造成功快照。

### 必须通过的回归

| 场景 | 预期 |
| --- | --- |
| A 发出 → asked → B 返回新提示 → A 返回空 | 提示保留，数量为 1 |
| A 发出 → replied → B 返回空 → A 返回旧提示 | 已回复提示不复活 |
| question 的 asked/replied/rejected 对应时序 | 与权限一致 |
| 两个请求逆序返回，没有实时事件 | 旧结果不覆盖较新结果 |
| 事件早于会话详情到达 | 后续补齐目录后仍保留事件保护 |
| 两服务器使用相同目录与会话 ID | 互不影响 |
| 请求失败、上下文销毁后旧响应返回 | 不清空有效状态、不写入新上下文 |

完成标准：原 1 → 0 场景不再出现；权限和问题均经过同一保护原则，版本回收不会重新引入竞争。

## 5. R2：SYNC-007 保存结束恢复刷新队列

### 问题与根因

入口：[server-sync.tsx](D:/opencode/packages/app/src/context/server-sync.tsx)、[queue.ts](D:/opencode/packages/app/src/context/global-sync/queue.ts)。

onSettled 不等于 Mutation 已离开 pending。当前 resume 调用发生时 paused 仍为 true，因此提前返回；后续没有必然发生的恢复通知。

### 解决方案

恢复动作由真实暂停状态解除驱动。推荐在拥有 Mutation 和队列的上下文中建立响应式观察，实际观察 pending 状态；当暂停条件解除且有积压时调用 resume。保留 queue.resume 的幂等性，不用固定延时或轮询等待状态变化。

### 实施步骤

1. 核对 paused 的全部来源和保存调用方；确认当前只取最后一次 Mutation 状态是否足以代表全部保存操作。
2. 在 Mutation 创建后建立状态观察。不能通过现有含 untrack 的 paused getter 作为唯一响应式依赖，要直接订阅可靠的 pending 状态。
3. 若允许同一作用域并发保存，使用作用域内待完成写操作数量或可靠的 Mutation 聚合状态；必须等所有相关写操作结束，不能一笔结束就提前恢复。
4. 删除或调整 onSettled 中无效的早期恢复调用。保存成功后的其他查询失效逻辑保留，但不能依赖另一个偶然事件解锁积压。
5. 无论保存成功、服务端冲突、网络失败还是调用取消，只要实际暂停条件解除，都进入同一恢复路径。
6. 多次解除通知不应重复处理同一目录；恢复时已在 drain 的队列由原有调度协调，不新开竞争 drain。
7. 上下文销毁时清理观察者与定时器；不同服务器的 Mutation 和队列相互隔离。

### 回归步骤

1. 使用真实 MutationObserver 建立可控保存请求，pending 时分别入队目录刷新和全局刷新。
2. 让保存成功，期间不再发任何刷新事件；确认积压任务自动执行。
3. 让保存失败，重复验证；不能只覆盖 success。
4. 同时入队重复目录、多个目录，确认去重和最终处理顺序。
5. 若支持并发保存，先完成其中一笔，确认队列仍暂停；最后一笔完成后恢复。
6. 增加 Solid 上下文集成测试，验证实际响应式状态更新触发恢复；仅手动修改 paused=false 后调用 resume 的单元测试不够。

完成标准：没有额外事件的情况下，保存结束后积压目录和全局刷新均可完成。

## 6. R3：SYNC-005 统一文件树删除失效

### 问题与根因

入口：[tree-store.ts](D:/opencode/packages/app/src/context/file/tree-store.ts)、[watcher.ts](D:/opencode/packages/app/src/context/file/watcher.ts)。

显式 watcher 删除会调用 removeDir，但父目录快照发现子目录消失时只删 node，仍留下 dir.loaded、children 和旧请求身份。重建后展开因此不再读取。

### 解决方案

让所有“目录消失”入口共用一个完整的失效操作：删除节点与加载状态，清除待强刷标记，使目标目录及后代在途请求失效。父目录快照负责最终父子列表，不在同一 store produce 内嵌套调用其他 setStore。

### 实施步骤

1. 在应用父目录快照前，比较旧 children 与新 children，收集消失的目录；同时处理 directory 被 file 替换的情况。
2. 将完整失效边界复用于显式 removeDir 和父目录差异处理，避免两份清理逻辑继续分叉。
3. 对目录自身及所有后代清理 node、dir、loaded/loading/error/children、forceAgain 和 inflight 关联。
4. 对每个被移除目录提升请求代次或使用不会复用的请求身份。不能只删除 generation 并从旧数值重新开始，否则旧请求可能与新请求碰撞。
5. 在旧请求 then/catch/finally 中核对身份；旧响应不得重新创建节点，旧 finally 不得清掉新请求。
6. 在一致的 batch 或顺序明确的状态更新中应用失效和新的父目录列表，避免中间状态触发错误的展开请求。
7. 目录重建后不带旧 loaded 标记，首次展开必须读取新内容。
8. 核对路径边界：删除 dir 不影响 dir-other；统一 normalizeDir 的分隔符和根目录处理；scope reset 同样不能让旧请求写回。

### 回归步骤

1. 真实 createFileTreeStore：加载 dir/old.ts → 父目录返回空 → 父目录重新返回 dir → listDir(dir)。断言再次读取且包含 dir/new.ts。
2. 不调用 removeDir，确保测试命中原来的父目录差异入口。
3. 子目录旧请求在途时删除并重建，先返回新请求，再返回旧请求；新内容不能被覆盖。
4. 覆盖多层后代、相似前缀、连续删除、重复 watcher 通知、目录与文件互换。
5. 运行 watcher 原有回归，确保显式删除路径继续有效。

完成标准：任何删除发现路径都会完整失效；同名重建能读取新内容，旧在途响应不能复活旧目录。

## 7. R4：SET-005 MCP 表单加载与草稿

### 问题与根因

入口：[dialog-mcp-v2.tsx](D:/opencode/packages/app/src/components/settings-v2/dialog-mcp-v2.tsx)、[mcp.tsx](D:/opencode/packages/app/src/components/settings-v2/mcp.tsx)、[bootstrap.ts](D:/opencode/packages/app/src/context/global-sync/bootstrap.ts)。

当前 ready 既承担“配置已加载”，又承担“表单已初始化”。dirty 阻止回填的同时，也阻止 ready 变为 true。全局 bootstrap 完成不等于具体配置请求成功，不能用它掩盖配置错误。

### 解决方案

推荐把配置加载状态、已加载原始配置、用户草稿分别管理。配置成功后可以解除保存门槛；草稿是否覆盖只由字段是否编辑过决定，不由全局 dirty 阻止整个初始化。若选择初始加载前禁止编辑，必须明确加载和失败重试行为，不能继续呈现可编辑但永远无法保存的状态。

### 实施步骤

1. 先用实际组件补慢配置请求的失败回归：打开 edit、输入命令或切换类型、再返回配置，断言当前实现无法保存。
2. 从正确配置请求获取 pending/success/error 状态，必要时通过内部上下文暴露查询状态；不要仅使用 serverSync.data.ready。
3. 核对 MCP 的配置作用域：列表、编辑读取和保存必须针对同一服务器与目录。不要把本来来自项目配置的服务，当作全局配置中不存在的新服务。
4. 定义初始加载、加载失败、已加载三种状态；失败提供重试。成功但目标服务不存在应明确提示，不能无提示地按空 local 配置覆盖。
5. 记录各字段是否被用户修改。加载成功时只回填未修改字段；类型切换后的草稿仍应一致。配置加载完成的状态必须独立更新。
6. 保存条件由配置是否可靠加载、表单是否合法、是否正在提交共同决定。dirty 不应导致永久未就绪。
7. 保存时按既有配置合并受编辑字段，核对 headers、env 等未编辑字段是否保留，避免修复回显时引入配置丢失。
8. 每次打开窗口、切换目标服务或服务器时重置相应请求身份；旧请求不能覆盖新窗口草稿。
9. 新的加载、错误和重试文案使用 i18n；添加模式保持原有可用流程。

### 必须通过的组件／集成回归

- V1/V2、本地／远程 MCP 的正常回显。
- 慢加载期间先输入，返回配置后草稿保留且能够保存。
- 加载失败 → 重试成功，正确初始化并解除禁用。
- 目标服务已删除、目录配置与全局配置不同的情况。
- 加载后背景刷新不覆盖未保存草稿。
- 关闭重开或切换服务时，旧响应不污染新表单。
- 实际保存完成后通过 R2 路径恢复相关刷新。

完成标准：原错误路径可稳定复现并在修复后通过；配置错误可恢复，类型／命令／URL 回显正确且不会覆盖用户草稿。

## 8. R5：ATT-003 ODS 坐标和有界输出

### 问题与根因

入口：[Core office-text.ts](D:/opencode/packages/core/src/util/office-text.ts)、[旧运行时 office-text.ts](D:/opencode/packages/opencode/src/util/office-text.ts)。

300 个重复空列被截断为 256 后，后续值仍接在后面，产生合法格式但错误位置的文本。行重复也有同样的截断方式，必须核对。

### 解决方案

在有界输出预算内保留真实重复次数和列位置；超限明确失败，不能静默裁剪次数后继续输出错位数据。保留现有归档条目、单条目解压和总解压限制，另外控制解析后文本扩展的大小。

建议初始输出预算与现有 16MiB 总归档输出上限保持一致，作为待实施校验的内部常量。预算必须覆盖所有表、行、单元格、分隔符及重复展开，不能每个单元格分别获得一份完整额度；最终值及兼容性影响写入交付记录。

### 实施步骤

1. 在两份解析实现对应的测试中加入 314 字节、300 个重复空列的原样本，断言 Value 位于第 301 列。
2. 移除以 Math.min 截断语义次数的做法；验证重复数是合法、正的安全整数，拒绝非法值和无法安全计算的展开。
3. 空列按准确数量贡献制表符；覆盖单元格和重复有值单元格也保持正确顺序。仅在不会改变后续列位置时处理尾部空列。
4. 在分配数组、repeat 字符串或循环展开前检查剩余预算；使用不会整数溢出的加法和乘法判断，不能先展开再检查长度。
5. 对行重复执行相同原则：在预算内按明确文本语义保留，超限拒绝；不得静默截断后伪装为完整内容。
6. 检查解析后其他扩展点（如重复空格）的预算，避免归档本身很小但生成文本无上限。
7. 沿用并检查调用方的解析失败处理，让超限结果走明确失败／不可读取路径，不返回看似完整的半份表格。若需要新增用户提示，遵守对应 i18n 和错误契约。
8. 同步修改 Core 与旧运行时，分别调用实际导出函数验证；不只依赖两个文件内容相同。
