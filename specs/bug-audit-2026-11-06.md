## 模型与供应商设置

### SET-001：模型可见性设置不传播，且可能被旧状态覆盖

**影响**：设置里隐藏／显示模型后，聊天模型列表不变；之后在聊天中选择模型或改变变体，可能把刚保存的可见性设置覆盖掉。

**触发步骤**

1. 保持聊天页面已挂载，打开新版模型设置。
2. 在设置页隐藏一个模型。
3. 回到聊天模型列表检查可见性。
4. 在聊天中选择另一个模型，再检查保存的数据。

**原因**：设置的服务器作用域创建额外的 `ModelsProvider`，聊天页面有自己的实例。二者各自调用 `persisted` 读取相同的 `model` 存储键；`makePersisted` 没有配置实例间同步，任何一方保存时又写入完整状态。

**离线复现结果**

```text
设置隐藏后：settings.user = [hide]，chat.user = []，存储中 user = [hide]
聊天选择其他模型后：存储中 user = []，刚保存的 hide 丢失
```

复现使用真实 `persisted` 实现和隔离的内存存储，没有读写用户的实际模型偏好。

**修复与验收**：同一偏好作用域共享响应式状态，或提供明确的实例间同步和合并机制。设置隐藏后，已打开的聊天列表立即更新；随后选择其他模型、切换变体或重开设置，都不能恢复旧的可见性偏好。

**影响**：在 V2 服务器上编辑已有 MCP 服务时，服务类型、命令和地址无法正确回显；远程服务会被默认显示为本地服务，用户需要重新填写配置，并可能覆盖原类型。

### SET-006：并发保存供应商时，成功响应掩盖配置丢失

**影响**：两个窗口或客户端同时保存供应商，双方都收到成功，但其中一个供应商没有保留；现有 revision 检查没有阻止重叠请求相互覆盖。

**触发步骤**：两个请求都携带 revision=0，分别新增 audit-a、audit-b；在两个请求读完配置、进入凭据写入后，先让 A 完成，再让 B 完成。

**原因**：setVendor 读取配置并检查 revision 后，还有异步凭据写入，最后按之前读到的完整快照提交；读取、校验和写入之间没有共同的互斥或原子版本比较。

**离线复现结果**

```text
responseRevisions = [1, 1]
savedRevision = 1
customVendors = ["audit-b"]
```

复现执行真实 RelayAuth 服务，使用临时数据目录和内存凭据存储，通过凭据写入边界控制并发；未读写用户实际配置。现有测试只覆盖先后发生的旧 revision 请求，没有覆盖重叠保存。

**位置**：[版本检查](/D:/opencode/packages/core/src/relay-auth.ts:185)、[完整快照提交](/D:/opencode/packages/core/src/relay-auth.ts:215)、[供应商保存](/D:/opencode/packages/core/src/relay-auth.ts:323)

**修复与验收**：让配置读取、revision 校验和提交成为一致的并发控制边界，并检查其他配置写入口。两个使用相同初始 revision 的重叠写请求必须有一个得到冲突，不能都成功却丢数据；失败路径还应保持配置与凭据一致。

### SET-007：更换密钥后，旧响应覆盖新模型目录

**影响**：使用新密钥刷新后已经出现的新模型，会被旧密钥发起的慢请求覆盖，后端再次返回旧目录。此问题发生在后端目录状态，区别于 SET-003 的前端勾选状态回退，也区别于 SET-002 的变更未触发失效。

**触发步骤**：用旧密钥启动模型刷新并延迟响应；更换密钥后再次刷新，先返回 new-model；最后放行旧请求，返回 old-model。

**原因**：refresh 在请求开始时捕获凭据指纹和 requestVersion，网络请求完成后没有校验当前凭据或刷新代次就写回快照；重叠请求甚至可能获取相同的 requestVersion。

**离线复现结果**

```text
CATALOG_AFTER_NEW_KEY_REFRESH ["new-model"]
CATALOG_AFTER_OLD_RESPONSE ["old-model"]
```

复现执行真实 RelayAuth／RelayCatalog，使用隔离 HTTP 响应、内存凭据、临时数据目录和显式内存数据库；未访问外部模型服务。

**位置**：[请求开始时捕获版本](/D:/opencode/packages/core/src/relay-catalog.ts:248)、[响应直接写回目录](/D:/opencode/packages/core/src/relay-catalog.ts:284)

**修复与验收**：为刷新分配独立代次，提交时核对代次与当前凭据／配置身份。新密钥刷新完成后，旧请求无论何时返回都不得改变目录；同一凭据下的乱序刷新也应验证。

## 刷新与状态同步

### SYNC-001：旧刷新快照清空新权限提示

**影响**：任务仍等待授权，界面却没有待审批提示，用户无法继续任务。

**触发**：权限列表刷新请求在途时，收到新的 `permission.asked` 事件；随后旧请求返回空列表。

**原因**：刷新直接按快照清理当前权限，没有保护请求发出后新增的事件状态。问题请求列表也存在相同结构，需一并检查。

**复现结果**：真实会话事件处理后待审批数为 `1`，旧空快照返回后变为 `0`。

**位置**：[权限快照覆盖](/D:/opencode/packages/app/src/context/global-sync/bootstrap.ts:450)、[问题快照的同类路径](/D:/opencode/packages/app/src/context/global-sync/bootstrap.ts:485)

**修复与验收**：为快照合并增加事件版本／基线保护。刷新期间新申请不得消失，已回复的申请也不得被旧快照恢复；问题提示需要相同验证。

### SYNC-002：V2 重连后仍显示旧 idle 状态

**影响**：运行状态及发送／停止相关界面可能错误。

**触发**：断线前缓存为 idle，断线期间会话开始运行；重连的 active 快照返回 running。

**原因**：`seedActiveSessionStatuses` 跳过任何已有状态，包含没有更新过的旧 idle；重连合并也复用了该函数。

**复现结果**：输入快照为 `running`，合并后的状态仍为 `idle`。

**位置**：[已有状态直接跳过](/D:/opencode/packages/app/src/context/server-sync.tsx:188)

**修复与验收**：用快照纠正未发生后续事件的旧状态，同时保留请求期间的新事件。覆盖 idle→running、busy→idle、重连期间收到新状态三种情况。

### SYNC-003：Agent 更新后的刷新继续使用旧缓存

**影响**：新增、修改或删除 Agent 后，界面选择列表仍旧。

**原因**：目录 bootstrap 使用 `ensureQueryData(loadAgentsQuery(...))`；该调用默认返回已有缓存，不因数据失效而主动重新获取，事件链也没有对应的 Agent 查询刷新。

**复现结果**：模拟远端 Agent 从 old 改为 new；即使先将查询标记失效，再调用同一刷新方法，也仍只请求一次，返回 old。

**位置**：[Agent 刷新调用](/D:/opencode/packages/app/src/context/global-sync/bootstrap.ts:367)

**修复与验收**：设置变更事件显式使 Agent 查询重新获取，并更新目录 store。更新事件后已打开的选择列表应立即反映新增、改名和删除。

### SYNC-004：请求在途时，后续强制刷新被吞掉

**影响**：目录中的新增／删除文件未显示；文件内容加载也有相同的请求合并逻辑，可能显示旧内容。

**触发**：已加载目录正在刷新，此时新增文件并触发 watcher；第二次刷新带 force=true。

**原因**：force 只绕过 loaded 检查，遇到 inflight 请求仍直接复用；没有安排完成后的补刷。

**复现结果**：首次加载后进行一次刷新，期间 watcher 报告 new.ts；最终共读取两次，仍只有 old.ts，没有第三次获取新快照。

**位置**：[目录请求合并](/D:/opencode/packages/app/src/context/file/tree-store.ts:49)、[文件内容的同类逻辑](/D:/opencode/packages/app/src/context/file.tsx:178)

**修复与验收**：在途时记录待刷新状态，结束后补取，或采用可取消／可替换的请求机制。刷新期间发生变化，最终列表和打开的文件内容必须达到最新状态。

### SYNC-005：同名目录重建后复用旧 loaded 标记

**影响**：删除后重建的同名目录实际有文件，但界面展开后为空。

**触发**：加载 dir/old.ts，删除 dir，刷新父目录，再创建含 dir/new.ts 的同名目录并展开。

**原因**：移除目录时只删除 node 及后代节点，没有删除 tree.dir 中的加载状态。展开时看到 loaded=true，因此跳过获取。

**复现结果**：重建后 dirReads=1、loaded=true、children=[]。

**位置**：[删除节点而保留目录状态](/D:/opencode/packages/app/src/context/file/tree-store.ts:76)、[loaded 检查](/D:/opencode/packages/app/src/context/file/tree-store.ts:47)

**修复与验收**：删除目录时清理对应目录和后代加载状态，并处理旧的在途请求。重建同名目录后应重新请求并显示 new.ts。

### SYNC-006：重连时侧栏会话列表复用旧缓存

**影响**：断线期间其他客户端新建、删除或归档会话，重连后侧栏仍可能显示旧列表。

**确认的调用链**：重连将活动目录加入刷新队列，bootstrap 再调用 loadSessions；只要 sessionMeta 已有相同或更大的 limit，就直接返回旧列表。sessionMeta 的删除仅发生在目录 store 销毁时。

**位置**：[缓存提前返回](/D:/opencode/packages/app/src/context/server-sync.tsx:497)、[重连调度](/D:/opencode/packages/app/src/context/server-sync.tsx:673)

**修复与验收**：区分“确保已加载”和“强制刷新列表”，重连需失效相应 metadata。补充双客户端断线期间会话增删／归档的界面验证。

### SYNC-007：保存设置后，暂停的刷新队列没有恢复

**影响**：保存配置期间收到的目录刷新事件被留在队列里；保存成功后，对应命令、配置或其他目录信息仍不刷新，直到另一个事件再次推动队列。

**触发步骤**

1. 配置保存 mutation 处于 pending，队列的 paused 为 true。
2. 收到需要刷新目录的事件，调用 queue.push。
3. 保存结束，paused 变为 false，但没有其他刷新事件。

**原因**：queue.push 在暂停时只入队而不调度；队列不监听暂停状态变化，也没有独立恢复入口。调用方在保存成功后只刷新全局 bootstrap 和 provider 查询，没有恢复目录队列。

**离线复现结果**：暂停时加入 `/audit`，解除暂停后等待，调用列表仍为 `[]`；再加入一个无关事件后，调用列表才变为 `["/audit", "/another-event"]`。复现使用真实 createRefreshQueue；保存生命周期与队列的连接通过调用链核对。

**位置**：[暂停时只入队](/D:/opencode/packages/app/src/context/global-sync/queue.ts:37)、[保存时控制暂停](/D:/opencode/packages/app/src/context/server-sync.tsx:448)、[保存成功后的处理](/D:/opencode/packages/app/src/context/server-sync.tsx:770)

**修复与验收**：在 mutation 结束、暂停解除时明确恢复队列，成功和失败都需处理。不再产生额外事件的情况下，保存期间积累的目录刷新也必须执行。

### SYNC-008：目录刷新提前返回，旧请求覆盖较新的结果

**影响**：较新刷新已经显示新的命令列表，较早的慢请求随后返回，却把界面改回旧列表。其他没有版本保护的目录状态也需要一起检查。

**触发步骤**：开始一次目录刷新并延迟旧命令列表响应；在其未完成时再刷新同一目录，先返回新命令列表，再返回旧列表。

**原因**：bootstrapDirectory 启动异步 IIFE 后没有 return／await 它，调用方会提前清除 booting 标记和解锁刷新队列；虽然维护了 providerRev，写入结果时没有校验该版本。两次后台刷新因而可并发写入同一 store。

**离线复现结果**

```text
await bootstrapDirectory 返回时：commandRequestsStarted=0
新刷新先完成：列表为 new-command
旧刷新随后完成：列表回退为 old-command
```

复现调用真实 bootstrapDirectory，在 API 边界控制请求先后顺序；未重启或操作实际服务。

**位置**：[后台刷新启动及版本记录](/D:/opencode/packages/app/src/context/global-sync/bootstrap.ts:360)、[未等待的 IIFE 结束](/D:/opencode/packages/app/src/context/global-sync/bootstrap.ts:544)、[调用方提前释放 booting](/D:/opencode/packages/app/src/context/server-sync.tsx:602)

**修复与验收**：明确 bootstrap 的完成语义，防止同目录后台刷新相互覆盖；必要时使用版本保护。故意让旧请求最后返回，最终命令列表仍必须是新结果。此问题与 SYNC-001 的“快照覆盖实时事件”有关，但本条复现的是两轮刷新之间的竞态。

### SYNC-009：在途消息请求吞掉重连后的强制刷新

**影响**：重连刷新虽然请求了 force，聊天记录仍可能缺少断线期间新增的消息，直到后续再次刷新。

**触发**：初次同步或预取消息尚未完成时，服务器已有更新；重连路径调用同一会话的 sync(sessionID, { force: true })。

**原因**：sync 在检查 force 前先进入 runInflight；只要已有请求，就直接返回旧 Promise，没有记录完成后需要再刷一次。force 因此不会产生新的消息请求。

**离线复现结果**：旧请求捕获 `[msg_old]` 后延迟；服务器列表更新为 `[msg_old, msg_new]`，再调用 force 同步；最终 `reads=1`，本地仍只有 `[msg_old]`。复现运行真实 createServerSession，同步与强制同步均等待完成后检查结果。

**位置**：[在途请求直接复用](/D:/opencode/packages/app/src/context/server-session.ts:186)、[sync 的外层请求合并](/D:/opencode/packages/app/src/context/server-session.ts:907)、[重连使用 force 同步](/D:/opencode/packages/app/src/context/server-sync.tsx:226)

**修复与验收**：对在途期间收到的强制刷新安排补刷，或取消并替换旧请求。断线期间新增消息后，在途旧请求与重连请求如何交错，最终都不能遗漏新增消息。本条涉及聊天消息，区别于 SYNC-004 的文件加载。

### SYNC-010：重连时只刷新消息，未刷新待办列表

**影响**：断线期间待办已完成，重连后当前会话仍显示 pending；在不切换会话、且没有新的完成事件时会一直过期。

**触发步骤**

1. 当前会话缓存一个 pending 待办，断线前会话为 busy。
2. 断线期间任务完成，服务器待办变为 completed，完成事件被错过。
3. 重连时刷新此前活跃的会话，保持当前会话页面不变。

**原因**：refreshActiveSessionData 只调用 session.sync，而该方法只刷新会话信息和消息；todo 使用独立缓存。页面的待办请求依赖会话／目录切换，重连不触发该 effect，也不能依赖已经错过的 step-ended 或 idle 事件。

**离线复现结果**：先通过真实 session.todo 缓存 pending，再将服务端待办改为 completed，执行真实重连刷新函数；结果 `todoReads=1`，缓存仍为 pending，没有补发待办请求。

**位置**：[重连刷新范围](/D:/opencode/packages/app/src/context/server-sync.tsx:215)、[独立的 todo 缓存](/D:/opencode/packages/app/src/context/server-session.ts:1460)、[页面待办请求仅随路由变化](/D:/opencode/packages/app/src/pages/session.tsx:939)

**修复与验收**：重连恢复时同步失效并强制刷新相关会话的待办缓存。任务在断线期间完成后，无需切换页面，待办也应更新为 completed。

## 定时任务

### TASK-001：同一项目的自动定时任务未串行执行

**影响**：同一项目两个到期自动任务会同时执行，可能同时操作项目文件。产品要求自动任务按项目串行；普通用户会话不在这一串行要求内。

**原因**：执行锁使用 task.id 与 projectID 的组合，不同任务不共享项目锁；而且会话 resume 通过 forkDetach 启动，perform 返回时会话尚未结束，锁无法覆盖完整执行周期。

**离线复现结果**：同一项目有两个到期的一次性任务，保持第一个会话未完成，真实调度器仍启动第二个会话；`startedSessions=["ses_audit_1","ses_audit_2"]`，实际运行记录中 `running=2`。

复现使用真实调度器、显式内存数据库和隔离迁移数据，开启 scheduledTasks gate；仅在项目解析和 SessionV2 执行边界替换服务，控制 resume 完成时机，没有运行真实模型或修改项目文件。

**位置**：[会话执行脱离当前 Effect](/D:/opencode/packages/core/src/scheduled-task.ts:303)、[锁按任务与项目组合](/D:/opencode/packages/core/src/scheduled-task.ts:306)、[自动任务按项目串行的要求](/D:/opencode/specs/single-relay-provider.md:1056)

**修复与验收**：按项目协调自动任务，并把协调范围延伸到实际会话执行结束。同项目第二个自动任务必须等待第一个结束；不同项目可并行；失败、取消后能释放执行位置，普通用户会话不受该限制。

### TASK-003：每日任务经过夏令时跳时后持续偏离原定时间

**影响**：设置为每天 02:30 的任务，在存在夏令时跳时的时区会从转换日起长期变成 03:30，后续正常日期不恢复原定时间。

**修复与验收**：使用保存的时区和原始每日时分生成下一执行日期，并明确转换日不存在／重复时间的策略。验证跳时日之后恢复原定时分，并覆盖回拨、无夏令时时区及跨日追赶。
