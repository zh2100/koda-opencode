## 1. 为什么调整

首次三个缺陷与再次审查的三项具体遗漏说明，原方法主要验证了具体复现路径，没有把规则落实到相邻动作和整个生命周期：

| 缺陷 | 已有保护 | 遗漏及责任 |
| --- | --- | --- |
| RV-01 | refresh 完成时核验身份；probe 发送前核验 | probe 完成时仍接纳失效成功，属于相邻入口覆盖不完整 |
| RV-02 | 失败/取消后条件清理 token | 正常提交已删除 token 后仍多取一次锁，属于上轮清理改动引入的回归 |
| RV-03 | saveVendor 区分命令 ACK 与快照接纳 | clearVendorKey 仍把两者绑定，属于相同状态规则未覆盖全部相关动作 |
| RV-04 | 认证层可返回已提交状态；旧方案提醒后续同步也可能失败 | Handler 仍返回一般 503，缺少可给客户端使用的阶段状态和仅同步重试出口 |
| RV-05 | 旧调用无身份字段时可重试删除 | 新版受保护请求先核验已删除实体，进入不了幂等确认；旧回归没有覆盖真实请求形状 |
| RV-06 | 发布端通知可有限重试 | 实际消费者一次失败就退出订阅；发布成功不能证明消费成功 |

旧通过结果保留为它实际覆盖范围的证据。新缺陷不能抹掉旧结果，也不能被旧通过数量掩盖。后续不再以“复现点不报错”和“通过用例很多”作为关闭依据。

## 3. 先写规则，再改实现

每条规则必须能说明保护对象、判断依据、允许改变的状态、失败行为以及原子边界。不要以增加 requestId、计数器或布尔值本身代替规则。

| 编号 | 必须保持的规则 | 检查重点 |
| --- | --- | --- |
| I1 归属 | 回包和收尾只影响同一服务器 scope、生命周期 generation 和持久化 entityId 所属的动作 | 切服务器、销毁、同 ID 重建均不得承接旧动作；本地请求序号不替代持久化身份 |
| I2 凭据与完成 | 一次网络动作使用一次捕获的不可变凭据；发送前与成功完成时分别核验其有效性 | 核对 entityId、供应商 revision、baseURL、hasKey；无关供应商修改不使本商失效；不重新 resolve 新 key；网络不在锁内 |
| I3 ACK 与快照 | 命令成功确认、精确重试与整份状态能否接纳分开处理 | 旧快照不能回退权威状态；有效同实体 ACK 仍可收尾其未再编辑的提交草稿；不据旧 ACK 覆盖新错误或新目录 |
| I4 编辑所有权 | 草稿收尾同时检查提交值和编辑代次 | 请求期间编辑后又改回相同文本，也应保留用户编辑；服务器或实体变化时拒绝旧收尾 |
| I5 提交事实 | 返回语义区分未提交、已提交、目录接纳、事件发布与实际消费 | rename 成功不伪装为未提交；明确目录待刷新，发布成功不等于消费成功；恢复不重放认证/HTTP 副作用 |
| I6 清理责任 | 清理依据“自身 token 是否仍有未完成责任”，而非“曾预留”或“结果为 Success” | 原子提交删除自身 token 时结束责任；成功但拒绝旧结果且自身 token 尚在时仍须清理；只能条件删除自身 token |
| I7 取消与错误 | 取消不能造成晚到租约、token 或通知责任泄漏；真实收尾保留主因与清理错误 | 正常取消与进程强杀分别定义；保留真正清理的 2 秒预算及原子提交短交接，不把整段等待屏蔽取消 |
| I8 一致性 | 返回值、磁盘、服务内存、客户端状态和真实页面在各自边界上符合相同事实 | 空结果、删除水位、其他供应商分片及目录版本不回退；日志不含 key、keyRef、凭据快照或上游原文 |

成功核验只保证该核验边界上的身份有效，不能保证此后永不变化。核验释放锁后发生的变化可与已开始网络重叠；不得为了消除该窗口而持锁联网。probe 不持有刷新 token；I6 对它不适用。

| refresh | I1、I2、I5～I8；预留、发送、提交、通知、终止 | 本批 RV-02 加既有 R101～R109 生命周期回归 |

| sync/reload | I1、I3、I8；只读快照、版本、缺席及错误票据 | 既有全量/分片/空快照回归 |

| 作用域退出/通知 | I1、I5～I7；提交后取消、服务退出不再发布、责任结束 | 既有生命周期/通知用例，加 RV-02 竞争对照 |

阶段划分：捕获前后 → 预留前后（仅 refresh）→ 最后发送核验 → HTTP 挂起 → 完成/提交核验 → 原子写入与内存安装 → 通知 → 响应送达 → 终止清理/销毁。

每条变更至少挑选其前后两个相邻阶段，并加入一个应当成功的对照。只在该动作确实有行为的阶段插入竞争。通过 Deferred、测试上游屏障或现有文件系统注入控制边界；跨进程事实使用真实子进程。不要用固定 sleep 猜测“已经发送/已经提交”，也不增加只复述实现的测试。

## 5. 本批具体实施顺序

### S1. 迁入失败样本，固定正确断言

将隔离副本中的 relay-followup-review-20261113.test.ts 样本按职责迁入正式目录事务、设置状态和 Handler 套件，保留 RV 编号和正常对照。迁入后不再让包内临时样本与正式用例重复执行。本次新增诊断位于 C:/relay-reaudit-20261113-01 的证据环境，对应 Core/Server 的 relay-reaudit-review-20261113.test.ts 及 Core 的 relay-plugin-reaudit-20261113.test.ts；一并迁入正式认证、Handler 和插件套件。先验证六项已确认失败及正常对照；若源码已变，先核对摘要与复现条件，不能仅因一次未复现便关闭。

### S2. 修 RV-01：probe 成功出口的权威复核

1. 复用现有捕获和只读事务比较，不另造凭据版本。HTTP 使用原快照，成功后按现有锁顺序重读并核验当前身份，再允许返回 count。
2. 清 key、轮换 key、换地址、删除/同 ID 重建均拒绝旧成功；沿用 REQUEST_CONFLICT 映射，不返回旧 count，不向新地址补发请求。
3. 无变化及无关供应商变化正常成功；核验不写目录、不增目录版本、不发无意义通知。上游本身失败仍沿既有失败语义，不把所有错误改成冲突。
4. 核对 refresh 的完成保护与 probe 一致；只提取真正共享的身份比较，不为形式统一合并两种不同的生命周期。

### S3. 修 RV-02：在真实完成边界结束清理责任

1. 标明“尚未预留、拥有未完成责任、责任已结束”的语义；可用最小状态表达，不强制引入新公共状态机或持久化格式。
2. 责任开始与预留实际提交对齐；成功提交删除自身 token 时，在现有不可中断提交/内存安装边界内结束责任，不能在可中断的通知返回后才修改标记。
3. 责任已结束不再进入额外清理事务。不能简单按 Exit.Success 跳过清理：被拒绝的旧结果也可能返回成功但仍持自身 token；该分支继续条件清理。
4. 后继 token 不得删除；失败/取消仍用既有 2 秒总预算，保留主因和清理 Cause。模型已提交后收到取消不撤销数据，按既有中断与通知契约收尾。
5. 在模型提交和通知之间安排真实 auth 锁竞争，证明请求不会因无须执行的清理而等待到报错；同时保留真正需要清理却超时的失败对照。

**此步骤修订总方案 C1.7b：正常提交已经证明自身 token 被删除时，不再为了确认缺失而重新取锁。** 不把这项修订扩大为吞掉真实失败，或把任意投递失败改成成功。

### S4. 修 RV-03：clear-key 的 ACK 独立收尾

1. 读取响应后分别判断“命令 ACK 是否属于本动作”和“Auth 快照是否可接纳”，不再以 applyAuth 返回 false 一并跳过草稿确认。
2. 生命周期、scope、实体、提交字段值和编辑代次均匹配时，成功 ACK 可清除自己提交的原草稿，即使整份响应旧于当前 Auth。
3. 用户继续编辑、编辑后改回、切服务器、销毁或同 ID 重建时拒绝旧收尾；旧 ACK 不清新错误、不回退较新 auth、不无条件失效新目录分片。
4. 与 saveVendor 的已有做法对照；仅在两者规则确实相同时复用局部逻辑，不新增第二套竞争水位。核对 delete/visibility 的不同收尾责任，不机械复制清草稿动作。

### S5. 修 RV-05：精确确认已提交删除，再判断是否执行新删除

1. 本项最低保证为同一服务存活期间，对相同受保护 DELETE 的原样重试成功确认；保留现有 pendingCleanup 启动恢复。不把它扩为所有旧命令的跨进程、跨重启永久幂等；旧操作字段不足时保守拒绝，不猜测身份。
2. 在执行首次删除前捕获内部命令归属：kind=vendor-delete、vendorId、原 entityId、原请求 revision、operationId。只有认证文件确实提交后，才在同一个提交交接边界建立对应内存确认记录；不能在后续目录同步或清理成功后才建立，取消也不能造成“已删但没有确认责任”的窗口。
3. 新请求先查精确删除确认记录。全字段一致时只返回当前权威 Auth 状态，并补本命令仍有的条件清理；不再执行删除、不推进 revision。原实体已消失或被后继替换不影响这次旧命令确认，但不得删除/修改后继或其凭据。
4. operationId 相同但类型、目标、身份或原请求 revision 不同，返回 REQUEST_CONFLICT。没有匹配的已提交记录时，仍按现有 requireEntity → requireRevision 执行新删除。不能把通用 replay 无条件前移，也不能把缺少身份当作匹配任意实体。
5. 若确认路径借用现有 cached/pendingCleanup，必须核对其元数据足以证明上述归属。现有 pendingCleanup 只有 operationId/refs/revision，不能单凭它放开身份校验；最小实现可使用本服务的绑定记录，重启后的旧记录仍由既有初始化恢复清理。若另行要求持久确认，需单独补存储版本、容量、旧记录迁移与真实进程证据后再扩大承诺。
6. 不无限保存含凭据的请求：删除确认只存非秘密身份和 revision，不记录 key 或配置原文。若设置缓存容量，必须明确保留期/满额行为及其保证范围；不得无声淘汰后将同号旧命令作为新删除执行。
7. 正式 Core/HTTP 回归必须按客户端真实 payload 携带 expectedEntityId，不能只沿用不带身份的旧调用。覆盖成功重试、丢响应、待清理、提交前失败、伪造记录/改 payload、同 ID 重建、清理失败和取消；另保留旧调用对照。

### S6. 修 RV-04：返回认证提交事实，单独表达目录待同步

1. 三个 Handler 保留认证事务作为提交边界。认证没有成功提交时沿既有错误映射；认证成功后进入目录同步阶段，后者的失败不能抹掉已提交确认。不能回滚凭据，也不能无条件吞错返回“全部完成”。
2. 在公开 AuthState 增加可选 catalogSync 字段，例如 `{ status: "synced" | "pending", retryable: boolean }`；写入口实际返回该字段。synced 仅说明本次服务目录快照接纳完成，不证明所有异步插件/页面已经消费。pending 表示认证已提交但目录接纳未完成；不携带原始错误、keyRef 或损坏文件内容，不复用私有 cleanupPending。
3. 新服务在 capabilities 声明 auth-commit-outcome-v1。三个认证写入口只捕获提交后可恢复的目录错误，记录脱敏关联诊断并返回认证提交结果与 pending；中断继续保持中断，未知缺陷保留诊断，不能 catchCause 后把一切失败都改为成功。网络丢响应的确认继续按各命令实际幂等范围处理。
4. 两套页面共用 hook 先按 I1～I4 接纳有效命令 ACK，清原草稿/删除旧实体状态，再显示本地化的“已保存、列表待刷新”。pending 时不显示普通保存失败，不再重发 vendor/key/delete。用户的 Retry refresh 仅调用现有 models.sync；成功后按目录版本/分片规则接纳，失败保持待刷新和原提交事实。切服务器、旧 ACK 与新编辑仍不能串状态。
5. 对旧服务缺少能力/字段保留原兼容路径，不能伪造已提交；也不恢复已移除的统一密钥功能。新服务器可选字段保持读取兼容，新增客户端与旧客户端分别验证。
6. 服务快照未接纳时，不能因此把旧投影当作新凭据/新实体使用；复验首次消费者、旧 URL/旧 entityId 和真实模型执行边界已有保护，发现旁路另列证据。不得绕过损坏目录保护写空文件来“修好同步”。
7. 修改公开 Schema 后从 packages/client 执行 bun run generate；按仓库规则更新受影响旧 JS SDK，运行编码解码与 App/Core/Server/OpenCode/Client 类型检查。仅生成真实受影响产物，不手改生成代码。
8. 真实 HTTP 断言三笔认证均只提交一次且返回 pending；真正认证冲突仍不提交。恢复夹具后仅 POST models.sync 成功，认证 revision、凭据及删除次数不再变化。两套真实页面确认保存状态、草稿与列表恢复，不能只测字段是否存在。

### S7. 修 RV-06：消费者的失败与恢复不终止订阅

1. 把预期的目录 sync/reload 失败限制在单次事件处理内；保留订阅继续接收。中断必须继续传播，不能 Effect.ignore 或对整个 Stream 无限重启来掩盖问题。
2. 同一事件内最多三次尝试，使用有界退避；只执行同步与目录投影，不重做认证、凭据或上游模型请求。记录本订阅最新待处理代次，旧尝试成功只能确认其捕获代次，新事件的恢复责任不丢。
3. 三次耗尽后保留脱敏诊断和未处理代次，继续接收下个事件；下一事件重新处理最新快照。scope 退出取消等待和重试，不创建脱离作用域的恢复线程，不重复注册活订阅。
4. 补齐无新数据的显式恢复：用户 models.sync(retryNotice=true) 在发布端已 idle 时，也允许开启一轮显式失效通知，唤醒此前失败但仍存活的消费者；已有 pending/exhausted 沿原责任处理，同一进行中的显式恢复合并。成功仅说明发布完成，不能改称所有消费者已确认。
5. 这是对旧 C2.5 的有意扩展：普通 GET、自动 sync、插件自身 syncVendors 仍不为无变化发事件；显式 idle 恢复可以发一次，不写配置、不增加目录版本，不制造自循环。新一轮明确点击可重新恢复，不永久高速重试。
6. 真实插件测试用一次可恢复文件错误和正常对照，证明后续事件还能更新模型；另让错误耗尽后恢复文件但不新增配置，经过真实 HTTP 显式 Retry 完成投影恢复。覆盖 reload 本身失败、失败期间又有新变化、并发恢复、通知发布失败、服务取消和退出后不再发布。
7. 若实际实现需要新增内部恢复入口，先写清它归属哪个服务 scope；不能把多个插件实例的失败用一个全局布尔值互相清掉。不要借此重写 EventV2 的通用投递协议或扩展历史锁迁移范围。
