## 3. 批次 B0/B1：持久化身份与新增供应商约束

### B0.1 持久化实体身份

当前本地 vendorEntities 只能识别页面实际观察到的删除或身份变化。其他客户端在两次读取间完成删除重建时，ID、地址、名称甚至供应商 revision 都可能再次相同，不能据此证明还是原实体。

1. 在 StoredVendor 增加持久化随机 `entityId`。新建自定义项生成新 UUID；同 ID 重建必须重新生成，不能由 ID、地址、时间戳或 revision 推算。
2. 修改名称、地址、密钥与清密钥保留 entityId；删除使其失效。所有保留的自定义供应商具有稳定持久化 entityId；不再创建内置供应商。
3. 在认证服务初始化阶段、对外提供服务前，持有现有 auth 写锁，重读并一次性补齐缺失 entityId。多个进程同时初始化必须读到并复用第一次成功写入的值。
4. 补齐仅在确有缺失时原子写入，并一次推进 auth 全局 revision；不改密钥引用，不重置已有供应商 revision。第二次启动不能再次改变身份或推进 revision。
5. 不在 auth.get、stateOf 或 catalog 已持 auth 锁的路径临时补写，避免嵌套获取同一把锁。初始化失败须在服务构建边界报错，不能临时生成内存身份继续服务。
6. 损坏或重复 entityId 明确失败，不能静默替换成新 UUID。备份/受控恢复遵循新运行代次，不保证旧运行中的请求可继续；锁迁移仍按 R3-03B 管理。

### B0.2 公开契约和服务端核验

1. Relay.Vendor 增加 entityId：为兼容旧响应，可在 wire Schema 中暂作可选，但新服务返回的每个实体必须有值。新客户端读不到身份时，相关身份保护动作标为不支持，不能以 vendorId 或本地代次补造身份后继续。
2. 新客户端的保存、清密钥、删除、probe、refresh、visibility 请求携带 `expectedEntityId`；probe/refresh 同时携带准备结果中的 `expectedVendorRevision`。Protocol 为旧客户端保留可选字段，新客户端必须实际发送。
3. 服务端在同一次持锁读取中验证 expectedEntityId。实体不存在或不符返回既有 REQUEST_CONFLICT；即使全局 revision 恰好正确，也不得创建/更新后继实体。
4. 对未提供期望身份的旧调用保留历史语义，但不能将其计入新身份保护保证。新客户端必须有服务能力/契约确认；不能假定旧服务会执行它不认识的可选字段。
5. auth 状态合并发现同 ID 的 entityId 改变时，推进本地实体代次，清理旧草稿/忙碌/错误归属；即使没有观察到中间空快照也必须执行。
6. 目录 vendorIdentity、刷新指纹、请求预留和投影接纳也包含 entityId，避免同 ID、同地址、相同 revision 的重建被视为旧实体。

能力协商采用明确的 AuthState 扩展：增加可选 `capabilities: string[]`，新服务返回 independent-vendors-v1、vendor-entity-v1、vendor-create-receipt-v1、catalog-sync-v1、notice-retry-v1 中实际已实现的能力。independent-vendors-v1 是移除共享认证后的写入语义门禁，缺少时只读，不恢复共享密钥或旧写协议。未知能力由客户端忽略，缺少所需能力不能假定已支持。

每个 scope/generation 的首次加载先调用现有 auth.get 协商，再调用已支持的同步入口；重连或服务身份变化后重新协商。旧服务缺少能力时，可继续只读显示旧查询结果，但禁用依赖这些保护的写入/测试动作，提供本地化说明。不将旧服务的 404/未知字段忽略当作成功，也不回退到未保护写入。兼容保证不覆盖连接存活期间未经重新协商的任意服务降级。

| B001 | 旧文件无 entityId，两个兼容进程并发启动 | 只补齐一次，两进程身份一致，后续启动稳定 |
| B002 | 修改名称、地址、key，再清 key | 身份不变，正常字段修订继续增长 |
| B003 | 删除重建同 ID、同地址、相同供应商 revision | entityId 不同，旧期望身份请求 409，无写入/上游请求 |
| B004 | 客户端未观察到删除，仅收到新实体快照 | 旧草稿和动作失效，新实体正常工作 |
| B005 | 补齐写失败、身份损坏、旧服务不支持保护契约 | 不生成不稳定替代身份，不误报已受保护 |

新字段属于本轮 schema/protocol 变更，生成客户端与 Schema 类型检查为必做项。保证范围是实现此契约的兼容进程；任意旧版本混写同根仍归 R3-03B，不能借身份补齐将其关闭。

### B1.1 固定接口契约

采用兼容扩展：在现有 vendor 写入 payload 增加可选 `createOnly?: boolean`。

| 请求 | 服务端处理 |
| --- | --- |
| createOnly=true，ID 不存在，revision 正确 | 创建自定义供应商 |
| createOnly=true，ID 已存在 | 返回现有 REQUEST_CONFLICT → HTTP 409；不写任何配置或密钥 |
| revision 已过时 | 返回 REVISION_CONFLICT → HTTP 409；不写入 |
| 未提供 createOnly | 保留现有更新/创建语义，兼容已有调用 |
| 已成功 createOnly 请求的原样 operationId 重试 | 按 B1.6 持久化记录确认已提交，兼容实例间不重复创建；未完成清理独立补做 |

不新增错误种类来代替已有冲突。createOnly 已在当前契约实现，按现存行为回归。任意已有自定义供应商都受 create-only 已存在检查保护；chatgpt 等旧名称不再天然代表内置项，空根可创建同名独立供应商。新客户端 createOnly 命令必须提供 operationId；缺失时在产生任何副作用前拒绝。旧的非 createOnly 命令继续保留原契约，不在本轮凭空承诺其跨实例重放能力。

### B1.2 先实现服务端原子防线

1. 在 RelayAuth.setVendor 的接口类型增加 createOnly。
2. 保持原有 mutate 锁。createOnly 先核验 B1.6 持久化操作记录，再走创建；不能只查实例内 cached Map。其他旧命令沿用原有重放/清理路径。
3. 在锁内重读存储并校验 revision 后，读取 existing。
4. 若 createOnly 且 existing 存在，立即返回 REQUEST_CONFLICT。
5. 此检查必须早于 replaceSecret、配置修改、revision 增长和旧密钥清理；不能在凭据已写后才发现撞 ID。
6. 不给创建失败生成清理旧密钥的任务；已有供应商仍可解析原地址和原密钥。
7. Protocol 增加可选字段，Handler 显式透传。保留 AuthState 的原有字段，并按 B1.6 增加可选 operationReceipt 确认元数据；不公开 keyRef、请求指纹或密钥。
8. HTTP 回归必须调用真实 Handler/Core，证明 409 后磁盘、内存、revision 和密钥均不变。

### B1.3 修正前端新增决策时机

1. 先固定用户本次提交的 name/baseURL/key 原始快照并校验格式，建立当前 scope/generation/action。
2. 如 auth 尚未就绪，读取当前服务器配置。读取失败时保留新增表单并展示归属正确的错误，不发送 vendor 请求。
3. 接纳有效读取后再依据当前完整供应商列表计算唯一 ID；不能复用读取前算出的 ID。
4. ID、供应商列表和提交 revision 必须来自同一份已接纳状态。计算后至发送之间不要插入额外异步工作。
5. 发送 createOnly=true。新增命令使用独立的 command 标识，避免与其他保存/模式命令复用。
6. 内部增加新增进行中保护，按 scope 和 action 归属收尾。两套按钮反映进行中状态，但安全性不能只依赖按钮禁用。
7. 保存期间继续输入的新表单内容仍按现有比较逻辑保留；旧成功不能清除新输入。
8. 发生 409 时保留表单，引导重载/重试；不要自动拿新 revision 重发旧 ID，更不能取消 createOnly 来“修复”冲突。
9. 网络结果不明时保留同一请求的 ID、payload、operationId 用于原样重试，通过 B1.6 记录确认提交状态。在确认原命令结果之前，不自动改 ID/revision 重试，也不将原草稿当作“全新新增”发送。用户明确创建另一项时才建立新命令；当前未确认结果须单独显示。
10. 依据 operationReceipt 确认原命令，而不是仅看到相同 vendorId 就认定创建成功。只有当前实体的 entityId 仍等于 receipt 中的创建目标，才继续为本次新增刷新其目录；原目标已删除/被替代时不重新创建、不刷新后继实体，提示原命令已完成但目标已变化。

### B1.4 补齐冲突显示和生成链

当前 relayErrorKey 未识别 REQUEST_CONFLICT，会退成 common.requestFailed。为新增碰撞提供可识别的冲突反馈：可映射到已有合适的冲突提示，或新增完整 i18n key。不要向用户直接显示裸错误码或密钥。

从独立副本的 packages/client 执行 `bun run generate`。检查 Promise/Effect 两套生成客户端与类型均包含 createOnly；不得手工修改生成文件。旧 JS SDK 仅在其契约确实包含受影响路由时重建，不能通过改无关生成物制造通过证据。

### B1.6 新创建协议的持久化幂等记录

当前 cached Map 随实例结束丢失，pendingCleanup 也会在清理成功后删除，因此不能直接承担新的跨实例成功确认。实施时采用以下契约，不能仅补前端重试按钮：

1. 在同一 auth 存储事务中增加新协议创建操作记录。记录至少含操作种类、operationId、目标 vendorId/entityId、请求指纹、committedRevision；成功标记必须与供应商配置同一次原子提交，不能另写无事务保证的 receipt 文件。
2. 新协议的原样重试先在 auth 锁内读记录。指纹相同则确认“该命令已提交”；先前 revision 已过时或目标后来被删，不得因此再执行创建。返回当前权威 AuthState，并附可选 operationReceipt={operationId, kind: vendor-create, vendorId, entityId, committedRevision}；首次成功也附同样元数据。Receipt 不含 key、keyRef、HMAC 或原请求体，不用历史快照复活旧供应商。
3. 相同 operationId、不同操作种类/目标/请求内容一律 REQUEST_CONFLICT。指纹覆盖规范化且无歧义编码的完整命令，包括原 revision、createOnly、name/baseURL 以及 key 内容；字段缺失与空字符串需要有明确编码区别。
4. key 仅在内存中参与指纹计算。使用数据根私有随机键计算 HMAC；持久化记录和日志不得保存 API key 明文、完整请求体或可直接用于离线猜测的裸摘要。
5. 私有 HMAC 键由兼容进程在 auth 锁内一次创建，使用原子落盘和受限权限，路径明确纳入资源根清单。存在操作记录但私有键丢失/损坏时，拒绝确认和新协议写入，不能重新生成键并清空旧记录。
6. 该记录的保留与 pendingCleanup 独立。清理成功、服务退出或切换兼容实例不得删掉成功记录；只重试未完成清理，不重复删除已完成引用。
7. 本轮不做自动淘汰。实施前固定可配置容量上限；达到上限时在写密钥/配置前拒绝新的 createOnly 命令并提供可诊断错误。后续若要 GC，须另定义到期 operationId 的拒绝/确认语义，不能简单删除后重新执行。
8. 新协议每次重试都重读共享存储，Map 最多作为已验证缓存，不能绕过磁盘更新。事务失败则不留下“已成功”记录；损坏的记录在服务构建/写边界明确失败，不静默当成从未执行。
9. 跨实例测试使用真实共享 data 根和可共用的隔离凭据后端；单个进程内存密钥存储不能证明另一个进程能解析凭据。原始响应丢失、请求落到另一实例、兼容服务重建三种路径均要执行。
10. 旧命令保持原有重放行为，不能为统一新规则而修改原测试“相同 operationId 旧调用保留首个结果”的历史断言。若未来扩展到所有认证命令，应另立兼容方案。

该保证适用于记录仍被合法保留、同一数据根与兼容写入者；旧版本覆盖文件、手动删除记录、生产迁移中断等不在本轮关闭范围。不能把新创建命令的持久化能力宣传成所有旧认证接口已支持跨进程幂等。

### B1.7 现存认证入口及退休迁移的元数据保留

认证 rollback、setMode、setUnifiedKey、clearUnifiedKey 已删除。后续不恢复这些接口，不要求它们满足运行时契约；保留历史日志，但将其原用例映射为现存入口和退休迁移回归。

| 入口/阶段 | 必须保留或处理的内容 | 禁止行为 |
| --- | --- | --- |
| Stored 解码、read/copy/encode 与原子写入 | receipt、entityId、revision/迁移信息、pendingCleanup，按 Schema 校验复制 | 遗漏元数据或损坏记录被当空值 |
| empty 与初始化 | 新根 vendors 为空；旧数据一次补齐缺失身份，保留已有元数据 | 恢复内置供应商、按每次读取生成身份 |
| migrationVersion 2 退休迁移 | 保留独立地址/keyRef/身份、receipt 和 HMAC 元数据；提交后才清理退休引用 | 由 empty 或旧备份覆盖配置；删除仍被使用的引用 |
| setVendor、clearVendorKey、deleteVendor | 保留其他实体及所有成功 receipt；同 ID 重建使用新身份 | 删除目标时顺便删 receipt，或复用旧身份 |
| settleCleanup、启动续清理 | 只处理未完成且未被当前配置引用的凭据 | 重做已完成清理，或清理成功后删 receipt |
| toState、HTTP、客户端解码 | 当前身份、实际 capabilities、对应命令的 operationReceipt | 公开 retired 字段、keyRef、HMAC、请求指纹或密钥 |

实施与回归步骤：

1. 盘点当前 relay-auth.ts 全部 Draft 构造和 read→write 路径，不按旧函数清单新建已删除接口。
2. 保留私有 Stored 中可选 unified/unifiedKeyRef，仅用于读取旧存储和退休引用；公开 AuthState 与 resolve 不再使用它们。不能为了清理弃用代码先删解码字段，造成待退休引用丢失。
3. 退休条件为 builtin 或没有独立 baseURL 的旧供应商。保留存活独立实体及其 keyRef/entityId，不从原始 auth.json 自动导入，不改写原文件。
4. 退休迁移在认证写锁内重读并原子提交。提交失败保留旧配置与凭据；提交成功后的清理失败留 pendingCleanup，重建后继续。重复启动与纯续清理不得重复推进业务 revision。
5. 创建确认先核验持久化 receipt 和私有 HMAC 键，再返回当前权威状态；目标已被删除/退休时不复活、不刷新后继实体。键丢失/损坏按现存错误边界失败，不以迁移为名丢证据。
6. B115 逐入口检查落盘状态；B116～B118 串联“旧格式已有 receipt→退休迁移→清理失败→服务重建→原样确认”，并保留真实兼容进程竞争、提交失败和取消屏障。
7. HTTP 继续断言 PUT auth/mode、PUT auth/unified、DELETE auth/unified、POST auth/rollback 返回 404；生成客户端不再暴露这些操作。移除不影响 R3-03B 资源迁移自己的 apply/resume/rollback 设计。

**B1.7 交付物：**现存入口保留矩阵、退休迁移前后元数据断言、跨实例确认和退休路由证据。旧功能测试不再计入当前必须通过的套件，但历史结果不覆盖或改写。

## 4. 批次 B2：BF-02 区分已提交规范化值和保存中新输入

### B2.1 明确三个值

对 name/baseURL 每个字段分别保存：

- submittedRaw：点击保存时的原始输入。
- submittedPatch：实际发给服务端的规范化补丁。
- currentDraft：ACK 到达时当前输入。

baseline 表示已确认的服务端比较基线。submittedRaw、submittedPatch 和 baseline 需要复制成稳定快照，不能持有会随 store 更新变化的引用。提交上下文另记录 scope/generation、entityId、操作编号及各字段编辑代次，供 B2.4 判断确认归属；这些数据只留在当前动作内存，不保存 API key 到持久化草稿或日志。

### B2.2 修改 ACK 合并

1. saveVendor 捕获原始字段，计算 patch，记录真正提交过的字段集合。
2. applyAuth 的 submitted 信息同时携带原始字段和实际补丁，不再只靠“补丁等于 incoming”判断 ACK。
3. 先验证 scope、实体代次和提交归属，再分别判断“完整快照能否接纳”及“本次命令是否成功确认”。不能先因全局 auth.revision 较旧 return，导致有效提交确认也被跳过；按 B2.4 分支逐字段处理。
4. 对已被 ACK 确认的提交字段：确认没有提交后编辑且 currentDraft 仍等于 submittedRaw 时，按 B2.4 取当前最新权威值规范化草稿与 baseline，仅清除可证明由本次未确认提交产生的伪冲突。ACK 快照较旧时不能直接使用其中 incoming。
5. 对同一提交字段：存在后续输入时保留输入；没有更新权威状态时 baseline 可推进到已确认 incoming，已有更新权威状态时禁止退回旧 ACK。按 B2.4 基于已提交值、本地新输入和最新权威值判断真实冲突。
6. 未提交字段继续使用现有三方合并：未编辑则接纳远端；本地与远端同时修改才保留冲突。
7. 不能因本次 ACK 清掉其他字段尚未解决的冲突，也不能让较旧 ACK 推进较新状态的 baseline。拒绝旧快照和确认原命令是两个判断，不能混成同一 return。
8. key 继续只在实体相同且当前值仍等于本次提交值时清空；新输入的 key 保留。
9. 不把所有相同 trim 结果的输入一概当成未编辑。保存期间用户主动输入的空格也要按当前输入保留。

### B2.3 必测用例

| 用例 | 场景 | 必须断言 |
| --- | --- | --- |
| B201 | 名称两侧空格、地址末尾斜杠后保存 | ACK 后字段规范化，字段与 baseline 相等 |
| B202 | B201 后远端修改并 reload | 自动接纳 Remote，无伪冲突 |
| B203 | 保存中继续改名称/地址，期间无更新权威快照 | 新输入保留，baseline 为 ACK，后续再保存提交新值；存在更新快照另按 B209～B212 验证 |
| B204 | 仅保存密钥，地址未编辑但有斜杠 | 不额外发送地址修改，不误判 dirty |
| B205 | 原本就有真实双方冲突，反复 reload | 冲突保留，不能以规范化清除 |
| B206 | 保存失败/无有效提交归属的旧 ACK/删除重建后 ACK | 不确认失败或错误归属，不把旧实体状态当作成功基线；有效但快照较旧的成功 ACK 另按 B209～B212 验证 |
| B207 | 保存中输入新 key | 新 key 不被旧 ACK 清空 |
| B208 | 只提交一个字段，其他字段远端更新 | 分字段接纳，未提交字段不被本次 ACK 当作自己提交 |
| B209 | A 规范化保存 rev2 的 ACK 延迟；B 更新产生 rev3，reload 先接纳 rev3，再到 ACK2 | 不回退全量状态；A 的已提交原始字符串变为当前权威值，无伪 dirty/伪冲突，B 的新值保留 |
| B210 | B209 中较新 rev3 又修改了 A 同一字段，本地无提交后编辑 | 仍确认 rev2 已提交，接纳 rev3 的当前值作为无新编辑基线，不安装 ACK2 旧值；其他未解决冲突不被顺带清除 |
| B211 | B210 同时存在 A 的提交后新输入，或编辑后又改回相同字符串 | 新编辑按字段代次保留；本地与最新权威值存在真实分歧时仍保留冲突，旧 ACK 不清新 key/错误 |
| B212 | ACK2 等待期间同 ID 重建/切服务器/销毁，或同字段较新提交已接管 | 旧确认不作用于新归属，不退回 baseline、不清新动作状态、不发后续 mode/probe/refresh |

**B2 关闭条件：** 既无伪冲突，也不丢保存中新输入；B209～B212 证明有效旧 ACK 的提交确认与快照接纳分离，原 RA-05 真实冲突与重复重载测试继续通过。仅证明旧回包被丢弃，不算完成。

### B2.4 迟到成功 ACK：独立确认命令，不回退权威快照

必须覆盖的时序：A 原始名称为 `" Saved "`，提交规范化值 `"Saved"` 得到 rev2；ACK2 延迟，其他操作形成 rev3，reload3 先到。此时整体拒绝 ACK2 虽能保护 rev3，却可能让 A 的原始字符串永远保持 dirty/伪冲突。

1. 发出保存前复制提交字段集合、submittedRaw、submittedPatch、scope/generation、entityId、操作编号与字段编辑代次。不能在 ACK 到达时从已变化 store 重建提交上下文，也不能仅比较字符串判断期间有没有编辑。
2. 成功回包先核对命令与实体归属。只有本次调用成功且仍属于同一有效实体/字段动作，才记录“该提交已确认”。这里的旧命令按原接口语义确认，不借 B1 的创建 receipt 扩展为所有更新都有跨实例幂等；网络失败或结果不明不能当作成功。
3. 完整 AuthState 继续走 revision 和生命周期保护。ACK.revision 低于当前已接纳 revision 时，不替换全量状态；但步骤 2 的有效确认仍交给字段合并。不能为了接纳确认而取消全量 revision 检查。
4. 对已提交字段，将 ACK 证明的已提交值 S、当前较新权威值 R、本地当前输入 L 分开。若无更新权威快照，使用 ACK 的值作为 R；若已有更新快照，只读取其中同 entityId 的 R，不能用旧 ACK 回写它。R 不存在或实体已变化时转为 superseded。
5. 本地没有提交后编辑，且 L 仍为 submittedRaw：将该字段视为本次已提交编辑已完成，草稿/baseline 整理为 R。R=S 时清除本次未确认规范化导致的伪冲突；R≠S 表示提交之后远端又变更，使用较新 R，不能把 S 写回。只处理本次提交所拥有字段，不清其他真实冲突。
6. 本地存在提交后编辑：保留 L，以 S 作为后续编辑的比较起点、R 作为最新远端值做三方判断。R=S 时仅为新的未保存编辑；L=R 时已一致；L 与 R 均偏离 S 且不同则保留真实冲突。权威快照与其已确认的新基线不回退到 ACK2；必要的提交比较起点作为动作元数据独立保留，不混入全局权威状态。
7. 若同字段较新的保存已接管确认归属，旧确认只结束自己的记录，不能改变新字段状态。同一字符串改出又改回也按编辑代次识别；保留原有“不丢保存中新输入”的行为。
8. key 清空、错误票据、pending 计数及后续 mode/probe/refresh 继续独立检查原有归属；提交确认不等于允许旧动作继续全部副作用。计数只释放本次持有份额，B3 的准备结果必须反映当前有效实体和最新字段状态。
9. 使用可控响应屏障执行 B209～B212：分别覆盖只变其他供应商、远端又变本字段、保存中继续输入、实体重建四组。断言字段值、baseline、dirty、冲突、key、其他供应商值和后续请求次数，不能仅断言返回 Promise 成功。

## 5. 批次 B3：BF-03 将归属校验前移到每个副作用之前

### B3.1 建立明确的准备结果

persistDraft 不再以 undefined 同时表示“完成”“实体消失”“旧回包已丢弃”。

建议内部采用可区分结果：

| 结果 | 含义 | 调用者 |
| --- | --- | --- |
| ready，携带有效实体/动作绑定 | 保存完成或已证明当前字段满足本次准备结果 | 可以进入下一步检查 |
| superseded | scope、实体、操作或目标身份已变化 | 静默结束旧动作，不发请求 |
| 异常 | 当前有效动作确实失败 | 沿现有错误票据路径展示 |

准备结果本身是内部契约；覆盖跨客户端未观察到的删除重建，还必须实现 B0 的 entityId 和公开请求期望身份。saveVendor 的外部按钮调用与内部准备调用都要核对，不能改返回类型后只修 probe 一处。

### B3.2 按步骤封闭窗口

1. probe/fetchModels 开始时捕获 scope、生命周期、本地实体代次、持久化 entityId 与 actionId，并取得忙碌/状态归属。缺少持久化身份时不降级成仅比较 ID。
2. 保存前后都检查实体仍属于本次动作；删除重建同 ID 不能通过检查。
3. saveVendor 只有在保存结果对当前实体仍有效时，才返回 ready；旧结果、未执行保存或目标消失返回 superseded。
4. 自己保存的地址/密钥会合理改变目录代次。**不能直接比较保存前后的全部 vendorIdentity 来禁止自己的合法修改。**
5. ready 中绑定保存后的有效目标：本地代次、持久化 entityId、本动作及已确认的供应商 revision/地址。前后 entityId 必须一致，自己的合法修改可推进 revision；不能从当前快照重新选择另一个实体作为准备结果。
6. 如果只是其他供应商推进了全局 revision，不应自动误判本供应商失效；以本供应商实际版本/身份判断。无法证明有效时结束旧动作，不重新绑定当前新实体。
7. 在真正调用 api.probe 或 loadCatalog 前，再检查 active、entityCurrent、statusOwner、entityId 和准备结果。请求携带 expectedEntityId/expectedVendorRevision；检查与调用之间不插入 await。
8. 结果回来仍保留原来的所有权检查；请求前防止错发，请求后防止错写，两个都需要。
9. finally 只清本 action 持有的忙碌状态，不能清后继动作的 testing/fetching 或错误。
10. 检查同文件内其他“await 保存/读取，然后发下一请求”的路径，复用明确结果，不扩散一套新版本计数器来替代已有归属。

服务端收到 probe/refresh 后，需在同一次持锁读取中校验期望身份与供应商 revision，并解析出固定的 URL/key，随后释放 auth 锁再进行上游 HTTP。不得先核验旧实体、后调用按 vendorId 重新解析的 fetchUpstream 而转到后继实体。refresh 提交时再次校验身份、指纹和预留 token；整个上游请求不占用 auth/catalog 锁。

该修复阻止尚未发出的旧请求以及服务端受理时身份已不符的请求；本地未观察到中间删除也由持久化身份识别。请求受理、解析完毕后发生的修改不会撤回已捕获的上游请求，但不能使它改用新实体的地址/key；旧结果不能再写入新实体。不要宣称完成任意远端并发下的整段网络原子操作。

### B3.3 必测用例

| 用例 | 场景 | 必须断言 |
| --- | --- | --- |
| B301 | 旧保存已提交 rev2、回包挂起；reload rev2；删除 rev3；重建 rev4 | 放行旧 rev2 后 probe 次数为 0 |
| B302 | 权威快照中目标消失 | 后续 probe/refresh 均不发送 |

| B304 | 正常保存自己的新地址/key 后测试 | 向已保存目标发一次，不能因自己 invalidate 被误取消 |
| B305 | 同一供应商的新测试替代旧测试 | 旧准备不继续，新操作状态不被旧 finally 清掉 |

## 6. 批次 C1：BF-04 将磁盘写入与内存接纳分离

### C1.1 固定事务不变量

锁顺序保持 commitPermit → auth 锁 → catalog 锁。HTTP 拉取仍在提交许可之外；不能把上游请求放进跨进程锁临界区。

每次事务区分以下事实：

| 名称 | 比较对象 | 用途 |
| --- | --- | --- |
| diskChanged | 锁内最新磁盘与本次修改结果，比较时排除自动增长的 revision | 是否真的需要提交文件 |
| snapshotChanged | 本进程快照与最终有效结果，包括版本和内部请求状态 | 是否需要更新内存 |
| identityChanged | 当前认证供应商身份与本进程已安装身份 | 是否需要更新 vendors/身份失效 |
| externalProjectionChanged | 本进程原快照与锁内最新磁盘的候选/managed 等消费者内容 | 外部变化是否需要本进程通知消费者 |

这些是语义要求，不要求为了变量名抽出大量只用一次的工具函数。

### C1.2 修改事务步骤

1. 取得锁后读取 latest 与当前 auth，不用旧 snapshot 构造写入草稿。
2. 在 latest 的副本上执行 change，算出最终 next。
3. diskChanged 为真时才增长 catalogRevision 并提交；否则保留磁盘已有 revision。
4. 成功事务中，即使 diskChanged=false，只要 snapshotChanged 或 identityChanged，也安装 next、vendors 和 vendorStamp。
5. 安装数据须为副本，避免 change/result 与本地可变对象交叉污染。
6. 文件提交失败时不安装本次修改、不推进身份基线、不发布成功通知，保留 C06 的既有保证。
7. 保持“文件已成功 rename → 安装内存 → 登记通知责任”的短收尾边界完整，取消不能留在“磁盘已提交但状态/通知责任没登记”的窗口。
8. 等锁和读写准备不要一概改成不可取消；只保护已经需要完成交接的提交/接纳收尾。
9. 同一运行代次不能因晚到请求接纳更低已知版本。无 catalogRevision 的历史文件按现有兼容规则解码并比较内容，不能为了兼容而虚构新版本。
10. 不通过多写一次目录来刷新缓存；只读同步应保持文件内容、revision 和写入次数不变。
11. candidates、managed、hasManaged、visible、apply 对同一已安装状态读出一致结果；首次公开之前先满足 C1.8。服务已可用后的任意外部写入仍通过显式同步观察，C1.5 的真实页面 reload 入口保持接通，不能依赖测试端预同步。

### C1.3 真实双进程测试

1. 父进程创建长期存活的真实 catalog 服务，读出初始目录。
2. 子进程使用相同 data 根，通过真实 API/Service 提交模型可见性或候选变化。
3. 使用 ready/go/done 屏障明确顺序，不以任意 sleep 猜测提交完成。
4. 等子进程完成并 await exited，再由父执行 syncVendors。
5. 对比磁盘、managed、candidates 和 apply 投影。不能重建父服务后再读，那只能证明启动加载。
6. 再反向修改/取消勾选，验证删除和空快照也被接纳，不只支持追加。
7. 所有父子异常路径都关闭 stdin/句柄、终止自己创建且未退出的 fixture，并 await exited。

| C113 | 新版空快照/删除先接纳，旧的非空结果晚到；同 ID 重建且目录版本相等 | 删除水位不丢失，不复活旧条目；旧 entityId/供应商版本不能写回后继分片 |
| C114 | 历史文件无版本，随后出现真实目录版本；追加服务器切换/重连与同根兼容进程响应 | null 不伪装为 0；历史同步受串行保护，已有版本不被 null 降级；不同 scope 水位不串，同根不按实例重新编号 |

**C1 关闭条件：** 实际子进程、真实同步 HTTP、C111～C115 的版本/分片乱序对照、C1.7～C1.9 剩余缺陷/独立凭据回归及两套页面 reload 场景通过。不能仅用同一进程两个 Layer 或测试内直接 catalog.syncVendors() 代替完整证据。

### C1.5 固定真实页面可调用的同步入口

当前共用 hook 已调用 relay.models.sync({ retryNotice })，同步 Endpoint、组合返回 Schema、Handler 与生成客户端均已存在。后续核验这条真实链路，不重复新建接口；auth.get → candidates → managed 仅为实施前历史路径，不再描述为当前现状。

| 契约 | 当前实现的回归约束 |
| --- | --- |
| Endpoint / operation | POST /api/relay/models/sync；relay.models.sync，生成客户端使用相应 sync 方法 |
| Query | 沿用 LocationQuery 和服务器作用域 |
| Payload | retryNotice?: boolean，默认 false；显式用户重新加载/Retry refresh 传 true，自动事件/后台调用传 false |
| Success | auth、candidates、managed、catalogRevision: 非负整数或 null，以及 notice.status（idle / pending / exhausted）；null 仅表示历史文件未携带可比较版本 |
| Error | 沿用 Relay 现有错误映射；同步失败不能返回旧缓存作为成功结果 |

1. 复核现有 Core synchronize(options) 同步读取方法。它复用 C1 事务，在同一 auth/catalog 临界区安装快照，并捕获该版本的 auth、candidates、managed、catalogRevision 返回副本；目录分片绑定于本次 auth.vendors 的 entityId 和供应商 revision。不能在释放锁后独立读取拼成声称一致的快照。
2. notice.status 是调用返回时本实例投递状态的观察值，与目录数据分开，不作为跨进程版本。实际事件投递放在锁外；通知仍 pending/exhausted 不得将已完成同步或认证提交伪装成未提交。
3. 现有 syncVendors 作为内部兼容入口复用同一事务，默认 retryNotice=false，避免消费者处理事件时重置重试预算。普通 candidates/managed 保留缓存查询语义，本轮不把每次 GET 都改成潜在写事务。
4. 复核已有 relay-sync.ts 组合返回 Schema、Protocol/Handler 与真实同步方法。若补修实际改变公开契约，再运行 Promise/Effect 客户端生成和请求编码测试；内部租约修复不强制制造公开协议变更。
5. 两套页面共用 hook 首次加载先按 B0.2 用 auth.get 协商，随后调用同步入口；已协商的 reload 直接调用同步入口。通过现有 applyAuth、候选/managed 分片合并入口接纳数据。首次自动加载用 false；用户主动重新加载和仅重试刷新用 true。
6. 请求前记录 scope、generation、错误票据和各供应商分片水位。响应接纳按 C1.6 同时核对服务端 catalogRevision、实体/供应商版本和本地编辑代次；客户端 requestSeq 不能替代数据版本。同步响应不得无条件 reconcile 整个 store，也不能覆盖请求期间的编辑、勾选或另一服务器状态。
7. auth 响应未被接纳时，继续按已存在的 revision/实体/分片规则判断目录是否可接纳；不能因请求成功就放开保护，也不能只因无关供应商推进全局 revision 就丢掉所有未变化分片。保留 F/G/H、RA 系列对照。
8. 同步失败保留现有界面和当前错误归属。查询库若携带旧缓存，不能拿它清冲突或显示“刷新成功”。notice.status=exhausted 则显示可本地化的 Retry refresh 状态，不重复提交 key/供应商配置。
9. 用真实 HTTP 证明子进程提交后，该 POST 自身完成磁盘接纳；页面用例只能点击实际 reload 触发该接口，不能额外从测试端直接调用 Service 来准备“最新”内存。
10. 不把该接口当成跨进程事件广播。进程 B 的页面要通过 B 的同步/重连获取外部变化；接口保证调用它的进程得到最新一致目录。

身份保护、createOnly、同步接口和通知重试均已在当前契约实现。按 B0.2 核验现有 capabilities 协商并保留旧服务对照；旧服务不支持时显示明确的不可用/升级状态，不静默回退为无保护写入，不能仅凭前端类型检查认定服务器已支持。

### C1.6 服务端目录版本与客户端分片接纳规则

客户端请求序号表示发送先后，不代表服务端读到的数据先后。尤其 auth.revision 不变时，仅比较 requestSeq 仍可能把较旧目录接纳为新结果。按以下步骤补齐公开契约和全部回写路径：

1. 组合响应增加必传的 catalogRevision，类型为非负整数或 null；值在 C1.5 的同一临界区随目录副本捕获。0 是合法的已知版本，不能作为“没有版本”哨兵；历史磁盘无该字段时返回 null，不能用请求号、时间戳、内存计数或 auth.revision 伪造版本。
2. 显式保留读取来源是否带版本的信息，不能先在 read() 中用 `?? 0` 丢掉存在性，再声称可以区分历史无版本和真实 0。真实目录写事务仍沿既有规则产生新版本；只读同步不为补版本额外写文件。新 Schema、Protocol、Handler、Promise/Effect 客户端编码解码都必须保留 null 与 0 的区别。
3. 版本比较限定于已绑定的服务器/资源根 scope 与客户端生命周期 generation。同根兼容进程共享持久化目录版本，不能按服务实例另起计数。切服务器、确认的资源根变化或受控恢复按明确生命周期重建绑定并拒绝旧回包；普通一次响应不能自行重置水位。生产回滚/迁移不由该规则隐式完成。
4. 为 candidates/managed 的每个供应商分片记录已接纳目录版本及 entityId/供应商 revision 绑定，沿用本地编辑/请求水位。数值版本低于该分片已接纳版本时拒绝；数值版本更新且身份/本地保护允许时，不得仅因 requestSeq 更小而拒绝。版本相等时核对身份和认证变更，并结合本地水位/请求序号避免重复或旧投影覆盖，不能假定相同目录版本就代表认证身份没变化。
5. 全量响应中的缺席同样是分片结果。对当前缓存、已知实体、请求基线和既有删除水位的并集判断是否移除；成功接纳空结果也保留本 generation 内的版本/身份水位。不能因删除数组项就丢掉防止旧非空响应复活的记录。
6. 全局“已见最大目录版本”可用于诊断，不直接替代分片判定。某次响应只接纳 A、B 因本地操作被保护时，后续响应仍逐一判断；不因无关 A 的较高版本或全局 auth.revision 变化丢弃所有 B。当前认证已证明实体删除/重建/供应商版本变化时，旧绑定分片仍须拒绝；不能用“分片合并”绕开身份保护。
7. 对 null 历史响应不提供不存在的数值顺序保证：同一 scope 的无版本同步串行/coalesce，避免并行响应按发送序号猜新旧；首次协商尚未知目录格式时也采用该保护。仍检查本地动作水位和实体身份。已有数值版本的分片不得被 null 响应降级；出现这种不一致保留当前状态并明确要求重新同步/诊断，不静默清空。旧写入者覆盖版本等不受支持的混写仍归 R3-03B。
8. 勾选、目录刷新、事件重连等凡能直接写入 candidates/managed 的响应，统一进入上述接纳入口。实现时列出这些响应是否携带同临界区版本/实体绑定；暂不携带版本的旧端点只触发分片失效及新 sync，不直接用无版本结果覆盖已知版本状态。不能仅修 reload，保留另一条无保护回写路径。
9. 保留请求归属和错误票据规则：接纳数据的新旧不能让旧错误覆盖新错误，也不能用目录较新放开草稿/密钥保护。notice.status 不参与目录版本比较；仅重试通知没有数据变化时不提高 catalogRevision。
10. C111 在真实 Handler 边界控制读取与响应屏障：B 捕获 rev1 后暂停返回，子进程提交 rev2，再放行 A 捕获并返回 rev2，最后放行 B；客户端断言两次响应的实际分片判定：rev2 可接纳，随后 rev1 不能回退已更新分片。另做“较早发送却读到更新版本”的对照，防止继续用 requestSeq 提前 return。保留 C112/C113 的正常分片与空快照对照。

**C1.6 交付物：**组合响应版本契约、全部目录回写入口清单、分片/删除水位规则和 C111～C115 的真实时序证据。只增加返回字段但客户端仍按请求序号接纳，或只在测试对象上附版本，不算完成。

### C1.7 RF-BF-01：共享刷新令牌失效依据与所有权

历史根因：synchronize 用本实例旧 vendors/vendorStamp 与当前认证的差异，删除锁内最新目录里的 refreshRequests。这个差异只说明本实例需更新缓存，不能证明另一实例刚取得的刷新令牌无效。相关主体补修已有结果；以下步骤保留为回归约束，新增 RV-01/02 按新方法补足完成与收尾阶段。

实施步骤：

1. 将隔离失败样本迁入正式目录事务测试，保留无同步插入的正常对照。另扩展真实子进程夹具：B 轮换独立 key、完成同步并发出模型请求，上游用就绪/放行屏障挂起；A 此时才同步。
2. 删除依据本实例 invalidated 集合批量过滤共享 refreshRequests 的决策。vendorStamp 只用于内存接纳/通知判断，不具有撤销共享租约的权限。继续保留事务已有的供应商不存在、持久化 entityId 不匹配等权威失效保护。
3. 明确令牌生命周期：准备阶段在锁内核验实体/供应商 revision 后预留；同供应商新刷新覆盖旧 token；提交仅接纳 token、实体和凭据版本仍匹配的响应。清理旧 token 时必须比较它仍属于本次请求，不能按 vendorId 删除后继 token。
4. 本轮固定保留 refreshRequests 的 vendorId→UUID 字符串结构，不为主动失效新增共享租约格式。同步只按供应商不存在或已证明的持久化实体失配清理；同实体的 key/地址变更由准备/提交时的实体与供应商 revision 检查拒绝旧响应。普通 sync 不根据本实例版本、时间或推测的进程状态删除 token。若实现中发现此规则无法满足 R103/R104，先给出失败证据并另审持久化租约协议，不能实施中静默切换。
5. 按 C1.7a 固定“认证捕获→目录预留→发送前核验→快照 HTTP→提交核验”步骤；HTTP 只能使用本请求不可变的凭据快照，不能调用 fetchUpstream 再次解析。网络在锁外，持有 auth 锁的目录事务不重入 resolve。
6. 验证 A 同步只接纳状态，不改 B 的有效 token，不因本地缓存落后制造目录写入和 revision 增长。确有共享数据失效时仍允许必要的修复事务，不能只为“零写”保留非法记录。
7. 按 C1.7b 固定失败/取消/进程退出的令牌处理，再复跑同商新请求胜出、不同商逆序、删除/重建、写失败和取消，记录 token 与版本。不得只证明锁已释放而不检查 refreshRequests。

| 用例 | 场景 | 必须断言 |
| --- | --- | --- |
| R101 | 实际子进程持有当前刷新 token，旧父进程同步 | token 保留，父同步不额外写盘/增版本，放行后子进程正常接纳模型 |
| R102 | 与 R101 相同但无父同步 | 正常刷新成功，排除上游/凭据后端异常 |
| R103 | 请求挂起后换独立 key、清 key、换地址，分别有/无显式同步 | 旧结果不覆盖当前状态，正常新请求仍可完成 |
| R104 | 同 ID 删除重建后旧请求返回 | 不给后继实体写模型，也不删除其新 token |
| R105 | 同商新请求先完成、不同商逆序、取消/失败后重试 | 旧请求不清后继租约；不同商互不影响；检查自身 token 的收尾结果与所有锁/作用域释放 |
| R106 | 凭据捕获后预留前、预留后发送前、发送后完成前分别换 key/地址/实体 | 前两阶段被核验发现时零 HTTP；已发请求始终使用原快照，不改用后继凭据，完成时拒绝旧结果 |
| R107 | 超时、401/403、无效 JSON/格式、普通传输失败 | 保留原错误；仅删除自身 token，无模型写入或后继 token 误删 |
| R108 | 取消分别与预留、后继请求、提交竞争 | 有界收尾，取消原因保留；已提交不回退；后继 token 不动 |
| R109 | 收尾取锁超时/写失败；持请求进程被强制终止 | 原错误与收尾失败均可诊断；遗留 token 不阻塞新刷新，重建/同步不按年龄误删，新请求覆盖并正常完成 |

**关闭条件：** R101～R109、既有 C03～C05 和相关目录事务回归通过；至少包含真实同根父子进程和可共用的隔离凭据后端。只去掉过滤后让顺序样本通过不足以关闭。

#### C1.7a 不可变凭据快照与线性化边界

1. 在认证层提供内部捕获方法（可扩展现有内部 resolve 返回值），一次持有既有 auth 写锁，重读并校验调用方 expectedEntityId/expectedVendorRevision，读取该独立供应商 keyRef 的值，返回只读的 vendorId、entityId、vendorRevision、baseURL、key。读取凭据沿现有 auth→secrets 锁顺序，不持有 catalog 锁。该快照仅在本次调用内存中保存，不进入磁盘、事件、错误、HTTP 响应或日志。
2. 认证捕获返回后释放 auth 锁。目录 transact 按现有 auth→catalog 顺序重读状态，对比捕获的 entityId、vendorRevision、baseURL 和 hasKey；匹配才预留 token。无关供应商的全局 revision 变化不取消本商请求。捕获后已经变化则返回现有 REQUEST_CONFLICT，零上游请求，不能临时重新解析后继续。
3. 发送前执行一次短的只读目录事务，复核 token 仍属本次请求且当前实体/供应商版本仍匹配；不增版本、不发布无变化事件。失败走 C1.7b 收尾，HTTP 次数为零。
4. 将真正 HTTP 与“按 vendorId 查凭据”拆开。refresh 调用只接收上述不可变快照的 HTTP 函数；probe 如复用该函数，也须先捕获一次。HTTP 函数不接收认证服务、不重新解析 baseURL/key，不允许旧动作向后继地址发送新密钥。
5. 最后一次发送前核验是“是否允许开始请求”的线性化点；释放锁后不再插入应用级异步准备，直接用原快照调用 HTTP。核验后发生的认证变更可能与已开始的网络请求重叠，不承诺追溯到零 HTTP；但请求仍只用原端点/原 key，提交核验必须拒绝其旧结果。禁止为了追求网络零窗口把整个 HTTP 包在跨进程锁里。
6. 完成阶段只比较本次 token、entityId、vendorRevision、baseURL/hasKey 与锁内当前状态；不得用“旧 key 加当前 revision”重新拼成似乎有效的身份，也不在 catalog 已持 auth 锁时调用捕获/resolve。由正常认证 API 更新 key 必须推进供应商 revision；绕过事务直接改凭据文件不在支持范围内。
7. 用精确屏障分别覆盖认证捕获前后、预留前后、发送前核验前后和完成前。R106 必须区分“变更在核验前已可见所以不发送”与“核验后已发出但结果被拒绝”，不使用固定 sleep 或不可能的绝对零请求断言。

#### C1.7b 终止路径、条件清理与错误保留

本轮 token 是刷新完成资格，不是持有中的互斥锁，也不代表持久化待执行任务；不引入心跳、年龄清理、退出后自动重放或 token 恢复执行。

| 终止路径 | 固定处理 |
| --- | --- |
| 捕获失败/预留前冲突 | 尚无本次 token，不执行清理，不修改其他请求 |
| 正常提交成功 | 同一事务仅在 token 匹配时安装模型并删除本次 token；在原子提交/安装边界结束清理责任，不再为确认缺失额外取锁 |
| 已被后继 token 替代 | 拒绝旧模型；收尾检查 token 不符即无操作，不能删除后继 |
| 超时、401/403、网络失败、JSON/Schema 无效、提交前冲突 | 保留原业务错误；在锁内 compare-and-delete 自身 token，不写模型 |
| 正常取消/服务作用域退出 | 等本次底层 HTTP 的取消/完成边界进入收尾；不接纳迟到响应；条件清理自身 token，保留中断原因 |
| 模型事务提交后才收到取消 | 不撤销已提交模型或还原旧状态；已完成清理幂等，通知责任按现有提交收尾规则保留 |
| 进程强制终止 | 不承诺 finalizer 执行；可能遗留 UUID。该 UUID 不阻塞后续预留，不被当作 pending 作业，不在启动时重放 HTTP |

仅在自身 token 尚有未完成责任时执行一次条件清理尝试，默认总预算 2 秒；不能根据曾预留或 Exit.Success 单独判断是否清理。正常提交已删除 token 时不再启动清理事务，旧结果被拒绝但自身 token 仍在时仍需条件清理。责任在原子提交/安装边界更新，不能拖到可中断通知之后。此处按 RV-02 修订，以新方法 S3 及 RV02-A～C 为验收依据。等许可、等文件锁、读写准备保持可中断且受预算约束；只有已经开始的原子提交/租约释放短交接沿现有规则完成，不能把整段五分钟锁等待放进不可中断 finalizer。条件清理的真实变更才推进目录版本；token 变化不触发模型内容未变的无意义通知。

清理失败不得吞掉原 HTTP 错误或中断：内部 Cause 保留二者；公开层沿既有错误/中断映射，另以请求关联号记录脱敏收尾失败，不携带 key、keyRef、快照或响应原文。只有收尾失败而无原错误时按现有 CatalogError 边界返回。预算外不启动脱离服务作用域的清理线程，不为 token 清理新增凭据/任务 journal。

遗留 token 可由同供应商下一次合法预留直接替换；普通 sync 保留仍有合法实体绑定的 token，删除/实体失配按权威规则处理。R109 要先检查遗留值，再发新刷新，证明它能替换并完成；不能靠测试手动删文件通过。

### C1.8 RF-BF-02：首次公开服务前完成实体一致性装载

根因：构建阶段直接安装 read() 的 snapshot，随后读取 auth，但未执行事务中的持久化实体过滤。认证删除/同 ID 重建成功、目录同步前退出后，重启服务会把旧实体的 managed 投影到新地址。

实施步骤：

1. 先保留“同实体重启模型仍保留”和“同 ID 新实体重启模型必须消失”两侧用例；初次消费者直接调用 managed/hasManaged/visible/apply，不提前调用 sync，也不打开设置页代为清理。
2. 在 Service.of 对外发布之前，复用现存一致性事务入口，按 commitPermit→auth→catalog 顺序在锁内重读认证和目录，复用持久化 vendorEntities 过滤规则。原始磁盘内容仅作为内部候选，不能在校验前被公开查询或插件使用。
3. 一次性移除退休实体的 candidates、managed、refreshRequests 和不再有效的绑定，安装一致的 snapshot/vendors/authStamp。不能仅在 apply 过滤而让 managed 或 visible 仍暴露旧模型；也不能将旧行的 entityId 改绑为当前实体来“修复”。
4. 无变化的有效目录不重写、不增版本。确有退休数据需要修复时，在同一目录事务中原子落盘并一次推进版本；写入/解码/身份校验失败在服务构建边界失败，不公开半就绪服务或假装空目录成功。
5. 历史无绑定行按 C1.8a 的同文件隔离策略处理，不再留到实施时任选。缺失绑定不能由本实例 vendors 补造；部分缺绑定、只有旧绑定元数据和重复启动均纳入同一规则。
6. 初始化必须在 C1.7 修复后验证，避免启动同步再次取消另一进程有效刷新。用 A 构建与 B 刷新交错的屏障覆盖“目录初始化完成前后”的窗口。
7. 初始化修复产生的通知沿用独立序号与作用域重试。检查服务尚未提供时 publish 是否会重入自身或等待插件服务；必要时先登记责任、服务可用后派送，不在锁内发布、不制造构建死锁。通知失败不伪装成磁盘未提交，不重复执行认证动作。
8. 接入真实 provider 插件/聊天模型消费者的初次装载，验证未打开设置页也不会看到退休模型；保留有效独立供应商的地址、模型 ID、勾选及 receipt。

#### C1.8a 无实体绑定数据的隔离与显式恢复

**固定选择：在 relay-catalog.json 同一次原子提交内隔离，不建立第二个需要跨文件事务的归档文件。** 不依据当前供应商 ID/地址或本地 vendors 推断历史实体，不为安全归属不明的行自动恢复可见性。

1. Stored/Draft 增加可选的内部 quarantine，形状为 `{ version: 1, entries: [...] }`；历史文件缺该字段表示尚无隔离记录。每条记录限定为可选 vendorId/sourceVendorId、上游 modelId、reason=missing-entity-binding、kinds（candidate/managed 的去重集合）、可选旧 visible/displayName/ownedBy，以及已知合法实体绑定 knownEntities。没有可证明来源的字段保持缺省，不写入猜测值；未知字段不透传。只复制明确白名单字段，禁止 key、keyRef、凭据指纹、请求 token 或任意原文。隔离项不是公开 Candidate/Managed，也不参加 hasManaged/visible/apply。
2. 只有 Schema 可解码且缺实体绑定的行进入隔离。已知绑定与当前实体不符的行属于已证实退休实体，按 C1.8 清退，不伪装为可自动继承的建议。格式错误、非法 UUID、未知 quarantine.version 或损坏隔离项在构建/读边界失败且保持文件不变，不能用默认空数组吞掉。
3. 一行关联多个供应商（vendorId/sourceVendorId）时逐个校验：任一已知绑定失配则退休；任一必要来源缺绑定则隔离；全部已知且匹配才保留活动状态。无来源且不能证明归属的历史候选同样隔离。部分合法、部分不明的数据不能按整个供应商或整个文件一刀切。
4. 隔离去重使用 vendorId/sourceVendorId（缺省按 null 编码）、modelId、reason 的无歧义稳定组合，不把行类别或时间戳当作不同条目。候选与 managed 的归属可唯一关联时合并 kinds 并保留显式 visible；不能唯一关联时分别保留来源不同的记录，不猜测合并。不自动淘汰隔离记录或将旧 visible 改为 false 后丢掉原值。read/copy/same/encode、所有目录事务都显式校验并保留 quarantine，不靠未知字段透传。
5. 将移除活动行、写入隔离项、清理失效绑定与安装有效快照放在同一目录事务。先完成包括 vendorEntities/quarantine 的最终归一化，再算 contentChanged；仅剩废弃绑定的情况也要识别为变化，不能在比较后才改元数据。真实变化只推进一次目录版本；再次启动及改其他商不重复隔离、不损失记录。活动投影变化登记通知，只有内部元数据变化不制造无内容刷新循环。
6. 重新获取模型仅生成当前实体的 candidates，不依据隔离项自动勾选或自动创建 managed。恢复沿用当前页面现有的用户显式模型勾选与 setVisibility(expectedEntityId)；无需新增共享密钥入口。已通过真实刷新获得的当前候选且显式勾选提交成功后，才删除与用户本次目标唯一匹配的隔离建议，且删除与可见性在同一事务完成；其他同名但来源不同的建议保留。没有当前候选、实体变更或请求冲突时保留隔离记录，不借隔离建议凭空创建当前模型。
7. 刷新后尚不存在的模型保持隔离，不静默删除建议。页面继续使用正常模型列表供用户重新选择；不将旧 visible 自动写到新实体，不声称所有旧勾选能无感恢复。结果文档须说明此兼容性变化、隔离所在路径及其仅含模型元数据的范围；后续专门的隔离管理 UI 另立范围，本轮不扩展公开接口。
8. 新内部字段要求所有支持本次共享数据根的目录写入者采用保留 quarantine 的实现；验证两个本轮兼容进程互写。旧写入者可能忽略该字段的混写不被宣传为安全，本轮不通过能力标记虚构对旧进程的约束，生产旧版本隔离仍归 R3-03B。需要生产滚动混写支持时，另立协议迁移后再放行该部署方式。
9. 新字段是目录内部 Schema，正常不触发公开 SDK 生成；它必须纳入资源根清单、存储验证和原子写入测试。遵守用户“不备份”的要求：不创建源码或配置备份，隔离记录是新版目录状态的一部分，不复制凭据或整个原文件。

### C1.9 RF-BF-03 的退出及独立凭据回归边界

1. 不再修复“只有统一 key 时内置商 KEY_MISSING”，也不恢复相关路由、默认地址或内置供应商。将原 RF-BF-03 明确登记为随功能移除不再适用，保留原根因记录作为历史证据。
2. 私有旧字段仅服务 B1.7 退休迁移。旧服务缺少 independent-vendors-v1 时新前端只读；能力协商不允许静默降级到共享认证。
3. 当前独立供应商 hasKey 仅对应自身凭据，不能机械删除其检查来套用旧修复建议。准备/实际 HTTP/提交中的凭据状态一致性由 R103 及正常请求对照验证。
4. 地址、key、entityId/供应商 revision 已改变时，旧请求不得更新当前目录；验证不经过 sync 也能在提交边界拒绝，防止把正确性完全寄托于 Handler 后续同步。发现独立路径新失败时记录具体根因再改实现，不直接沿用共享 key 的诊断结论。
5. 无 URL 或显式空白 key 在请求发出前失败；chatgpt 等旧名字作为新独立项时只用自己的 URL/key，custom 模型 ID 不复用旧智联裸 ID。

## 7. 批次 C2：BF-05 通知使用独立失效序号

### C2.1 为什么不能只删一个布尔条件

当前 pendingNotice 使用 catalogRevision，0 表示空闲。若只删掉 `&& contentChanged`：

- 空目录版本可能仍为 0，身份通知会被当成空闲。
- 同一目录版本内发生多个身份变化，可能被比较条件合并掉。
- 事务在许可内完成、通知在许可外登记，可能乱序或遗漏。
- 事件消费者自身调用 syncVendors，处理不当会形成持续自触发。

因此同时修改通知责任的识别和交接，保留已有重试与中断语义。

### C2.2 通知设计

保持公开 CatalogUpdated 的现有空 payload；不为该事件去重增加 payload 字段，也不引入持久化通知 outbox。同步接口单独返回 notice.status；B1 的持久化创建记录属于另一项契约，不受此限制。

在服务作用域内部使用单调的通知序号，独立于 catalogRevision：

1. 每次需要通知的成功状态转变分配新序号。
2. 记录已投递序号、待投递最高序号、当前尝试对应序号及重试次数。
3. 同一状态已安装、无变化再次 sync 时不分配新序号。
4. 普通目录提交遵循既有 notify 意图；供应商身份失效独立具备通知资格。
5. 外部候选/managed 的变化被本进程首次接纳后，也应通知本进程消费者；否则 BF-04 仅修内存，页面/插件仍可能旧。
6. requestVersion/refreshRequests 等纯协调元数据变化，不应仅因快照字节不同就发布用户目录事件。区分可见投影变化。
7. 在 commitPermit 内、成功安装状态时登记通知责任；实际 publish 放在 auth/catalog 锁和 commitPermit 之外。
8. publish 成功只确认本次捕获的序号；等待发布期间又登记的新序号必须继续保留。
9. publish 失败重试同一责任，不重写目录、不重复认证副作用。新责任到来时不能被旧 publish 的成功或失败清除。
10. 中断用 Cause 保留，不转成成功；通知任务属于服务作用域，退出后不继续投递。
11. 保持有限重试预算；耗尽后保留未确认序号并进入 exhausted，按 C2.5 的显式恢复规则处理。不能清零 pending 或记录成已成功投递。此设计不宣称提供进程崩溃后的持久化 outbox 保证。

允许合并尚未投递的多个失效事件，因为消费者会读取最新状态；不允许旧事件完成后抹去后来的失效责任。

### C2.3 消费者及循环检查

1. 真实事件到达 Relay 插件后，执行 syncVendors → catalog.reload。RV-06 已证明当前一次失败会终止订阅；按新方法 S7 在单事件内处理非中断失败、有限重试和待处理代次，保留后续事件接收。
2. 由于身份基线已在事件登记前安装，消费者的无变化 sync 不应再发一个同类事件。
3. 前端收到事件后刷新其实际模型/目录查询；断言数据变化，而不只统计订阅回调。
4. 双进程共享文件并不自动共享 EventV2 总线。分别验证“调用同步的本进程消费者”与“另一个进程主动同步/重连”的行为，不把本地事件说成跨进程广播。
5. 如发现某条真实认证入口未触发同步，再补该入口；不要仅为测试通过直接发布假事件。
6. 区分发布成功与消费成功。按 RV-06 让实际文件读取或 reload 一次失败后恢复，实际提交下一次变化并验证插件模型更新；耗尽后无新数据也须通过显式 Retry 恢复，不能靠服务重建。

### C2.4 必测用例

| 用例 | 场景 | 必须断言 |
| --- | --- | --- |
| C201 | 有模型时 clearVendorKey，目录行未变 | 安装身份并产生新的通知，插件 reload |
| C202 | catalogRevision=0 且目录为空，身份变化 | 仍通知，不把 0 当空闲 |
| C203 | 同一目录版本连续换 key/清 key | 两次分别完成的变化均可投递；pending 合并后读取最新状态 |
| C204 | 改地址、删除且没有可删行 | 失效通知有效，候选/投影不陈旧 |
| C205 | 通知失败/Effect.die 后后台重试 | 不重写文件，不重复凭据操作，最终可恢复 |
| C206 | 通知 A 挂起，变化 B 已登记，A 完成 | B 不被清掉；新状态最终被观察 |
| C207 | 通知被中断、服务作用域结束 | 保留中断，退出后不重试 |
| C208 | 插件处理事件时调用 sync | 不循环发事件，不无限 reload |
| C209 | 外部进程写入后本进程 sync | 内存接纳并驱动本进程消费者更新 |
| C210 | 仅预留刷新请求、无可见变化 | 不制造通知风暴 |
| C211 | 提交失败 | 不发布“本次提交成功”事件，保留旧内存与重试责任 |
| C212 | 同一通知连续失败至预算耗尽 | 保留未确认序号、exhausted 和诊断，不自动清空或持续高频重试 |
| C213 | 耗尽后发布恢复，无任何配置/目录新变化，点击 Retry refresh | 真实 sync(retryNotice=true) 补发原责任，插件/页面更新；不写配置或增加目录 revision |
| C214 | 自动 sync/普通 GET 到来，或多个显式重试并发 | 自动路径不重新开预算；同一轮显式重试合并，不重置正在执行的尝试 |
| C215 | exhausted 的旧责任后又有新变化，旧 publish 晚到 | 新责任不丢，成功仅确认捕获序号，不被旧失败耗尽新预算 |

使用 Deferred/可控发布边界确定请求和通知的顺序；后台定时重试使用有界等待。避免所有断言都依赖固定 sleep，也不无限等待“迟早会成功”。

### C2.5 耗尽状态、显式恢复和页面出口

| 状态 | 自动行为 | 显式操作 |
| --- | --- | --- |
| idle | 没有发布端未确认责任，自动路径不发布 | RV-06 扩展：显式 retryNotice=true 可开启一轮恢复通知，唤醒曾失败消费者；普通同步无变化仍不通知 |
| pending | 按本轮有限预算尝试，失败保留责任 | 已在尝试时加入/观察现有一轮，不重置次数 |
| exhausted | 保留待投递最高序号和最后失败诊断，停止该轮自动尝试 | 用户 sync(retryNotice=true) 重新打开同一责任的一轮预算 |

1. 状态记录至少区分 lastPublished、pending、inFlight、attemptSequence、attempts 和 exhausted。内部命名可依实现调整，不能用 pending=0 同时表示“已成功”和“失败放弃”。
2. 发布端 exhausted 的显式恢复仍复用当前责任、重置该轮 attempts，不改 auth/catalog 文件，也不重放供应商保存。RV-06 另补 idle 时的显式恢复轮次：允许登记一次恢复通知，同一进行中的显式恢复合并；普通读取、自动同步和插件自身同步不登记。此处按新方法 S7 修订，不能用发布端 idle 证明所有消费者成功。
3. 已有 pending/inFlight 时的并发 Retry 不能不断重置预算。使用同一许可/轮次合并；调用者得到当前状态即可，不要求每次点击都触发新发布。
4. 自动 syncVendors、事件消费者回调、普通 GET 和后台定时器都不能将 exhausted 重新设为 pending；避免刷新/事件循环自发制造无限重试。
5. 新的真实数据变化可产生更高通知序号并开启该新责任的预算；旧 inFlight 完成时仅处理其捕获的序号/轮次，不能清理或耗尽新责任。
6. publish 成功后只确认捕获序号；若有更高 pending，继续保留并处理。没有更高责任才进入 idle。失败诊断不包含 key、keyRef 或配置原文。
7. sync 返回 notice.status=exhausted 时，两套页面展示当前目录已读到但状态投递未完成的提示和 Retry refresh；该按钮只调用同步接口 true，不再发认证写入。
8. notice 的成功仅表示 EventV2.publish 成功，不表示每个页面或插件已应用完结果。D2 仍须验证真实消费者；消费者自身失败应由其读取/错误恢复路径处理，不能伪装成发布从未成功。
9. 进程退出后该内存通知责任不承诺恢复。新服务从磁盘初始化与页面同步获得当前数据；持久化事件 outbox 不包含在本轮范围，也不能将通知记录与 B1 的持久化创建 receipt 混为一谈。
