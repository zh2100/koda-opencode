## 4. R1：ATT-002-R2 文本展开与解析耗时

主要文件：`packages/core/src/util/office-text.ts`、`packages/opencode/src/util/office-text.ts` 及各自 `test/util/office-text.test.ts`。

### 4.1 目标设计

对实际解析后的文本统一执行 UTF-8 预算；覆盖 ODS、ODT、ODP 的重复空格、行、列、标题及分隔符。明确区分最终输出预算与中间展开上限，避免同一文本重复扣费，也避免最终被 trim 掉的巨量空白先耗尽内存。

保留默认 16MiB 输出限制和既有归档限制。测试可使用更小预算，但生产入口不能通过非有限数、负数或超大覆盖值取消上限。先梳理覆盖参数的调用者，再验证并约束参数；普通两参数调用保持兼容。

### 4.2 具体步骤

1. 加入小型 OpenDocument 夹具，使用 `A<text:s text:c="..."/>B`，保证空格位于内部且不会被 trim 消除。先用小预算复现超限未被拒绝。
2. 在处理 `text:c` 前验证计数：缺省语义按格式处理，非法值及非安全整数明确失败；不能让无效数字变成不可控的 repeat 参数。
3. 在调用 `repeat`、创建重复数组或进行重复循环之前，安全计算最大展开成本，与剩余预算／中间上限比较。乘法、加法都需验证安全整数。
4. 给 xmlText 的调用方明确传递受限解析上下文；ODS 单元格临时解析与最终行输出分别核算，防止将一份预算重复消费。
5. 将长空白串上的回溯式清理改为线性扫描或经验证的线性等价实现，保留现有换行前空格、制表符及 trim 语义。
6. ODT/ODP 输出合并也通过统一预算入口；检查复用 xmlText 的其他格式是否存在相同展开路径，纳入同一限制而不扩展无关格式功能。
7. 失败继续走调用方已识别的不可读取／超限路径，不返回截断后伪装为完整的内容。确认附件 UI 不把解析失败默认为空正文成功。
8. 同步两份实现，分别执行真实入口测试；不以源文件相同代替运行验证。

### 4.3 回归与验收

| 用例 | 通过标准 |
| --- | --- |
| 小预算下普通文字、中文、表情、内部空格 | UTF-8 字节正确；恰好预算成功，超过 1 字节失败 |
| ODT/ODP 的巨大 text:c | 在展开前拒绝，不分配声明规模的空白字符串 |
| ODS 空格加重复列／行 | 所有倍增成本累计，保留正确列位置 |
| 尾部空白、换行前空白、多个 text:s | 输出语义保持；中间展开同样受限 |
| 3 行正文预算 302/301；A、B 表头预算 7/6 | 前者成功、后者失败，继续覆盖换行计费 |
| 长空格后没有换行 | 不再出现明显的超线性增长；在独立子进程中执行资源保护测试 |
| CP936、现有 DOCX/EPUB 等小样本 | 不破坏既有读取行为 |

性能记录用于比较同一机器上的增长趋势，不引入机器相关的绝对耗时 CI 门槛。大计数拒绝必须由功能断言证明；超时保护触发意味着失败，不能当作“已拒绝”。测试只终止自己创建的子进程。

完成门槛：预算检查早于展开，受影响格式均有边界证据；旧的 ODS 坐标及换行修复继续通过。

## 5. R2：SET-006 跨进程配置与凭据一致性

主要文件：`packages/core/src/relay-auth.ts`、`relay-secret-store.ts`、`util/effect-flock.ts`、相关 Core/Server 测试。

### 5.1 推荐方案与限制

优先复用仓库已有 `EffectFlock`，保留当前文件格式和认证提交顺序，避免仅为此问题引入整套数据库迁移。它使用锁目录、心跳和陈旧锁回收，**不是仅加一次 withLock 就能宣称安全**；锁回收及失去所有权后的写入行为必须通过下述验证。

锁按规范化后的数据目录定位，显式放在共享数据目录的锁子目录中。不能只依赖默认 `Global.state`：两个进程可能共享 data，却使用不同的 state。路径别名、Windows 大小写及可解析的链接应得到一致身份。

### 5.2 具体步骤

1. 盘点所有写入者：认证更新、迁移、回滚、初始化清理、operationId 重试、备用凭据 put/remove；形成统一锁调用链。
2. 在真实两个子进程间设置 IPC 屏障，令二者使用同一初始 revision 修改不同字段，建立丢更新失败回归。备用凭据不同引用的并发增删单独复现。
3. 认证操作锁定整个“读取最新配置 → revision 校验 → 写新凭据引用 → 提交配置 → 登记／执行旧引用清理”边界，不能只锁最后的文件替换。
4. 备用凭据自己的读改写使用共享文件锁，并采用临时文件原子替换；认证锁不能替代对该服务独立调用的保护。
5. 规定锁顺序为认证锁 → 凭据锁。凭据服务不得反向获取认证锁；避免同一非重入锁被嵌套获取。读取认证状态与解析凭据的组合路径也要检查一致性窗口。
6. 取得锁后重新读取 revision。竞争失败者返回明确冲突；调用方刷新状态后重试，不自动拿旧配置覆盖新配置。
7. 保留“新引用写入 → 配置提交 → 退休引用清理”。每次密钥轮换创建独立不可复用引用；冲突回滚只移除本操作拥有且未被引用的凭据。
8. 清理引用前在认证锁内重新检查当前配置；仍被引用的不删除。pendingCleanup 和配置提交一致持久化，只记录引用，不记录密钥正文。
9. 锁超时／失去所有权映射为现有可重试错误或新增明确错误，不继续提交。验证活进程暂停、心跳延迟和陈旧锁回收，防止旧持有者恢复后覆盖新写入。
10. 若现有锁不能证明旧持有者失效后停止提交，先修复锁所有权／活进程回收协议；无法保证时改用数据库原子条件提交与事务性清理记录。此门槛未过时，不关闭跨进程问题。
11. 定义异常退出恢复：临时文件清理、未提交新引用的回收、已提交清理记录的续跑。恢复逻辑不能删除其他活进程正在准备的引用。
12. 保持旧文件可读取；不自动改写真实用户数据。明确不加锁的旧版本与新版本混用无法获得并发保证；不得把这一组合纳入已支持范围。

### 5.3 必需的真实多进程测试

- 同 revision 同时写：仅一个提交，另一个冲突；读取最新 revision 后重试能保留双方修改。
- 共享 data、不同 state，及同一路径别名：仍争用同一把锁。
- 不同备用凭据引用并发 put/remove：互不丢失，文件始终可解码。
- 系统凭据成功、系统凭据不可用而回退文件、双后端删除分别验证。
- 写新引用后退出、配置提交后退出、清理时退出：配置和密钥仍可解析，恢复幂等。
- 同 operationId 重试只补清理；NotFound 与 Bun false 保持幂等成功。
- 活进程暂停超过陈旧窗口后恢复：不能出现两个持有者都成功提交；不得仅测试正常退出。

完成门槛：配置、备用凭据和清理链路全部覆盖；两个 Promise 或两份 Layer 的进程内测试不能代替两个操作系统进程。

## 6. R3：SYNC-005-R2 文件树 reset 失效

主要文件：`packages/app/src/context/file/tree-store.ts`、`context/file.tsx`、对应 store/Provider 测试。

1. 固化 A 请求挂起 → 切 B/reset → 切 A/reset → 放行旧 A → 展开目录的失败回归，断言必须再次读取并显示 new.ts。
2. 为 tree store 增加单调递增的生命周期代次。每次 reset 都递增；请求同时捕获生命周期和目录请求代次。
3. 成功、失败、finally 三个分支都核对生命周期。旧请求不得写节点、loaded/error 状态、弹错误提示或删除新请求的 inflight 记录。
4. reset 清理队列和在途登记；不能只把目录代次 map 清零，否则可能与新请求发生编号碰撞。若有全局生命周期保护，可在保护下安全回收旧 map。
5. 保留 force 刷新、显式删除、父目录发现删除的目录级代次逻辑；生命周期与目录级失效分别负责不同范围。
6. 检查 FileProvider 的 scope 身份与挂载方式。目录字符串不能在服务器切换时混用；需要时将服务器身份纳入 scope，并检查文件正文请求的同类 reset 入口。
7. 增加真实 Provider 场景，确认项目切换确实触发失效，而非只单测手动调用 reset。

测试矩阵：A → B、A → B → A、同 scope reset、旧成功/旧失败、旧 finally 晚于新请求、同名目录删除重建、相似前缀、双服务器同路径。所有时序用受控 Promise。

完成门槛：重置前的任何回调都不能改变重置后的状态；新请求完成前不会被误标 loaded。

## 7. R4：TASK-004 状态收尾与 TASK-001 并发专项

主要文件：`packages/core/src/scheduled-task.ts`、`scheduled-task/sql.ts`、`test/scheduled-task.test.ts`；必要时涉及 Schema/Protocol/Server 的错误映射。

### 7.1 执行语义

采用明确规则：**停用的任务不能新建手动执行，调用方应先启用。** 自动调度已接纳的一次性任务仍可执行，不能因为 advance 将其停用而被误取消。停用与已经开始 running 的执行分开，不能把“暂停后续调度”暗中变成“中断当前会话”。

| 情况 | 目标行为 |
| --- | --- |
| 手动 runNow 时任务已停用 | 在 claim 前明确拒绝，不创建 pending |
| 每日任务已 pending，等待项目锁期间被停用 | 进入 interrupted 等现有适当终态，记录 endedAt 和原因并发布事件 |
| 一次性任务自动 claim 后由 advance 停用 | 已接纳执行继续完成 |
| pending 对应真实活跃的排队执行 | 重复调用返回同一 run，不启动第二次 |
| 遗留 pending，没有可证明的活跃执行者 | 按恢复策略结束旧记录；不得永久返回它，也不得自动重放模型执行 |
| 任务或 run 已删除 | 不重建被删除对象，不遗留新会话 |

### 7.2 具体步骤

1. 将本次隔离数据库复现写成测试：停用每日任务 runNow → 启用 → 再次 runNow，断言不会永久返回同一无执行者 pending。
2. 区分调度触发和手动触发，在取得必要互斥后重新读任务状态，再决定是否 claim；不要只使用锁外读到的 task。
3. 将 stillDue 的布尔早退改为可判断原因的执行前检查。任务不存在、run 不再 pending、任务被停用分别处理。
4. 对仍存在且被取消的 pending 记录写终态、endedAt 和合适原因；发布状态事件。不要把跳过写成 completed。
5. 明确登记本进程已经接纳的排队 run，区分“真的在等待项目锁”和“已经没有执行者”。新逻辑不能把真实排队误判为孤儿。
6. 修复历史 pending 的恢复入口。运行中的其他调度进程不能被误判为退出；先明确同一调度数据库的执行所有者，必要时使用独占调度所有权。没有可靠所有权证据时不要批量重写 pending/running。
7. 重启恢复只收尾和解除阻塞，不自动重放已有会话或模型调用；遵守 SessionExecution 的进程内执行边界。
8. 检查同秒手动重试与 `(task_id, scheduled_at)` 唯一约束：旧记录终态后再次点击不能误报任务不存在；给出一致的幂等／冲突行为并测试。
9. 最终通过正常会话入口执行；不得为修复任务状态另建一套内存模型循环。

### 7.3 TASK-001 受控执行测试

1. 同项目任务 A 在 resume 内等待 Deferred，启动 B，断言 B 尚未 create/prompt/resume；释放 A 后 B 执行。
2. 不同项目 A、B 都能到达受控执行边界，证明跨项目并行，而非只测最终两者完成。
3. A 的 create、prompt、resume 分别失败，确认终态和锁释放；B 能继续。
4. A 被取消、中断或权限拒绝后，验证任务状态收尾与项目锁释放。
5. 手动与自动调度交错、一次性 advance 后执行、排队时停用／删除，均不会留下无执行者 pending 或重复会话。

完成门槛：手动重试不会卡死，真实排队不被误取消，同项目串行与跨项目并行有执行边界证据。此后才可关闭 TASK-001 的专项缺口。

## 9. R6：TASK-002 ask / auto / plan 工具授权

### 9.1 策略约定

以下是本方案的执行约定，实施时应与项目已有产品文案核对；若文案存在冲突先明确行为，不静默改变含义。

| 模式 | 普通允许的只读工具 | 原本需要审批的工具 | 显式 deny / 独立强制审批 | 写入行为 |
| --- | --- | --- | --- | --- |
| ask | 保留既有允许规则 | 等待批准后执行 | deny 继续禁止；独立审批继续执行 | 不得在批准前产生受保护副作用 |
| auto | 按允许策略执行 | 仅将模式可覆盖的普通 ask 转为自动允许 | 不覆盖显式 deny、沙箱限制或独立强制审批 | 仍受工具和资源规则约束 |
| plan | 在 plan 能力范围内执行 | 不能通过审批绕过 plan 禁止的能力 | 保留所有强制限制 | 禁止受限制的写入／执行副作用 |

### 9.2 具体步骤

1. 沿 scheduled task → session create/prompt → runner → ToolRegistry → PermissionV2 跟踪三模式，先建立能够区分 ask 与 auto 的真实工具失败回归。
2. 为任务创建的会话提供会话级执行策略，不能修改全局 Agent 或整个项目权限。策略需要在该会话后续 resume 时仍可取得，不能只放在临时闭包。
3. 明确持久化和旧记录默认值：旧会话维持原行为；未知模式明确失败，不能默认升级为 auto。任务重试的模式取自已接纳执行对应的策略快照。
4. 在权限评估的统一入口组合配置规则、显式 deny、保存的授权和任务策略。明确优先级，避免简单追加 allow-all 覆盖 deny。
5. 工具可见性过滤与执行时权限断言使用一致策略；不能仅从模型工具列表隐藏能力而允许直接执行绕过。
6. plan 不仅选择同名 Agent，还需保证该执行模式的限制不被自定义同名 Agent 或后续切换解除。对实际副作用作断言。
7. 保留完整 Prompt、附件、Agent 引用和 effort；不破坏 durable prompt admission、队列语义和每轮显式 llm.stream 调用。
8. 若持久化或公开接口变化，按依赖方向调整 Schema/Protocol/Server，再生成客户端；运行各受影响包完整类型检查。
9. 将权限拒绝、取消及模型／工具失败接到 R4 的终态与互斥释放；不能挂住整个项目任务队列。

### 9.3 实际工具验收
