# 回滚消息与旧任务列表修复方案

日期：2026-11-24

状态：已授权实施，P0 后端安全边界、持久待执行读取和执行屏障基础已部分实现；原子替换、前端接入和任务清单生命周期尚未完成，不可按完整修复验收。

## 实施进度（2026-11-24）

已落地的基础能力：

- 普通 prompt 接纳在事务内检查 staged revert；没有显式替换凭据的发送返回冲突，不再继续追加隐藏消息。已有输入的精确重试仍返回原记录，异参重用 ID 冲突；只有新接纳且 `resume !== false` 时 wake，精确重试不重启 provider。
- 回滚提交保留 `session_input` 幂等账本，通过 nullable `invalidated_seq` 失效旧分支资格。包括接纳早于保留边界、但仍未提升的 queue；保留首次失效序号，拒绝迟到提升，事务失败不残留事件或投影。迁移保留原 ID、prompt、序号和时间；临时新库重放回归覆盖账本及资格。
- `GET /api/session/:sessionID/input` 提供按接纳序号排序的有效待执行输入与同事务 durable 水位，空事件流水位为 `-1`。读取不提升、不 wake；覆盖认证、缺失 Session、Session 隔离及刷新重读。Schema、协议与 Promise / Effect 客户端已同步生成。此接口尚未接入 App 展示。
- `SessionRunCoordinator.withBarrier` 与进程全局 `SessionExecution.withBarrier` 提供同 Session 短期变更互斥，阻止新 drain、合并屏障期间 wake、保留显式 resume，并允许旧执行退出清理。释放前预留待执行入口，避免唤醒同步等待者时重复启动；不同 Session 独立，失败 / defect / 中断均释放。屏障不自动 interrupt，也不支持同键重入；必须由命令在屏障内重检后显式停止旧执行。当前尚未将旧 revert 入口包装成新的完整安全命令。

仍须实施的交付主路径：显式替换目标及分支版本、单个原子替换事件、准备记录与逐路径文件 CAS / 补偿、App 持久待执行合并及三个回滚入口、任务清单版本 / 继承 / 生命周期及 V1 旧写隔离。不得因上述基础能力已通过测试而启用完整原子替换或受管清单模式。

## 1. 目标与范围

解决两个独立但会相互影响的问题：

1. 选定历史消息重新执行后，回滚状态未结束，新消息及回复继续进入“已回滚消息”列表。
2. 会话已经改做另一项任务，但旧任务清单仍显示为“进行中 / 待处理”，新任务没有清单时尤其明显。

目标行为：

- 用户选择“回滚并重新执行”，一次操作完成定位、回滚、提交原消息和安排执行。新输入持久接纳后立即退出回滚状态，不等待模型成功。
- 编辑后发送也必须结束回滚；不能要求用户逐条恢复历史才能继续对话。
- 已被明确替代的旧任务，其未完成项自动取消、面板收起；已完成项及历史保留。
- 继续原任务、临时插问、无法判断是否换任务时，不误取消原任务。
- 当前已经卡住的会话提供无损恢复入口，不通过后台批量改库解决。

范围：Web 与桌面端共用的会话交互、V2 Session 的接纳 / 投影 / 执行入口、任务列表持久化与同步。V1 独立评估和适配，不能用布局开关代替协议能力判断。TUI 作为共享服务调用方进行兼容回归，不要求本轮新增同款交互。不涉及计划任务、子代理调度或已删除的 task-orchestrator。

本方案与 `specs/session-task-status-repair-plan.md` 并列：该文件解决时间线上的运行 / 完成状态，本方案解决聊天回滚和 `todowrite` 清单生命周期。业务任务 ID 不等于回复轮次、尝试 ID、drain ID 或执行所有权。

## 2. 已核实的实现与限制

### 2.1 回滚

- `packages/app/src/pages/session.tsx`：回滚操作调用 `revert.stage`，将选中消息放回输入框；恢复列表中的一条消息会移动回滚边界，恢复最后一条才调用 `revert.clear`。
- `packages/app/src/pages/session/timeline/model.ts`：可见用户消息截到 `revert.messageID` 之前。边界不清除，新追加的消息仍会落在隐藏区域。
- `packages/app/src/components/prompt-input/submit.ts`：普通 V2 发送经过 `sendFollowupDraft`，先切 agent / model，再调用 `sessions.prompt`，没有提交回滚。
- `packages/core/src/session.ts`：`SessionV2.prompt` 持久接纳输入，再按 `resume` 安排 `execution.wake`，没有处理暂存回滚。
- `packages/core/src/session/projector.ts`：现有 `RevertEvent.Committed` 只删除边界之后的消息，保留边界本身；会删除部分 `session_input`，并清空回滚状态。这与“删除旧的选中消息，再以新 ID 重发”的含边界语义不同，不能直接套用。
- `packages/core/src/session/revert.ts`：`stage` 涉及文件快照恢复；`clear` 恢复回滚前文件快照。仅清除 UI 标记不等于正确处理文件状态。
- `packages/opencode/src/session/revert.ts` / `prompt.ts`：V1 有独立的 cleanup 路径，不能把 V2 的缺口直接认定为 V1 的同一个缺陷。

现有事件机制对单个持久事件及其投影使用事务，提交后再广播。但单独连续发布“提交回滚”“接纳输入”不是同一个事务。禁止用客户端先 commit 再 prompt 的两次请求冒充原子修复。

### 2.2 旧任务清单

- `packages/core/src/session/sql.ts`：`TodoTable` 按 `session_id + position` 保存当前清单，没有任务归属、版本或历史清单标识。
- `packages/core/src/session/todo.ts`：更新会先删除旧行、再插入新行；`todo.updated` 在数据库更新之后发布，当前定义不是可重放的任务历史来源。
- `packages/core/src/tool/todowrite.ts`：只提交 `sessionID + todos`，没有足够信息判断它更新的是哪个任务，也不能拒绝旧任务迟到的更新。
- `packages/app/src/pages/session/composer/session-composer-state.ts`：只要存在未完成项就显示面板；空闲和时间流逝不构成过期条件。

因此，仅给前端加一个“发消息就隐藏面板”的条件无法修复持久状态，也会在刷新后重新出现。

### 2.3 故障证据边界

已观察到同一会话在回滚标记未清除时收到正常的新回复，说明“无法继续”的一部分是隐藏问题，不是所有请求都执行失败。另有真实的 `Provider request failed`，现有记录不足以确定上游原因。本方案保证错误可见、回滚已结束，不宣称顺带修复所有提供方错误。

## 3. 交互规则

### 3.1 明确区分三个操作

| 操作 | 行为 | 是否调用模型 |
| --- | --- | --- |
| 回滚并重新执行 | 回到选中用户消息之前，用该消息内容生成新输入，旧分支退出当前历史，新输入接纳后退出回滚 | 是，安排一次执行 |
| 回滚并编辑 | 回滚到选中消息前，将原文及附件装入草稿，等待编辑；发送后按相同接纳流程退出回滚 | 选择时不调用，发送时调用 |
| 取消回滚，恢复原对话 | 恢复原分支与对应文件状态，清除回滚；不重放旧请求 | 否 |

默认的直接重执行入口明确标为“回滚并重新执行”，不再把“恢复消息”当作重执行入口。保留编辑入口，避免用户只想修改文本却意外调用模型和工具。操作可能撤销文件修改时展示已有文件影响信息；不绕过权限确认。

示例：原历史为 `A → 回复 A → B → 回复 B → C → 回复 C`。对 B 重新执行后，当前历史为 `A → 回复 A → 新 B → 新回复 B`。旧 B、旧回复 B 及后续 C 不再参与模型上下文，但不销毁用于审计 / 恢复的持久事件。

### 3.2 回滚何时结束

- 请求校验或提交失败：不裁剪历史，不清除可恢复的回滚状态，保留草稿并显示失败。
- 新输入持久接纳成功：立即关闭回滚栏。接纳只表示服务端已保存输入，尚未提升时显示“已接收／待执行”，不是正式聊天消息。runner 提升该输入后，才用同一 message ID 将待执行项替换为正式消息；无需等待首个模型事件。
- 接纳后模型失败：正常显示用户消息及错误，不重新进入回滚、不自动恢复旧分支、不自动重复调用提供方。
- 响应丢失但接纳已成功：按同一个 message ID 重试并核实结果，不能生成第二条输入。
- “立即执行”指立即安排正常串行执行，仍遵守权限、排队和工具确认，不保证零等待。

### 3.3 旧清单规则

| 新消息的意图 | 原清单处理 |
| --- | --- |
| 继续原任务、补充约束、回答澄清 | 保留同一任务归属，允许更新 |
| 明确放弃 / 替换旧任务，改做另一件事 | 未完成项转为 `cancelled`，已完成 / 已取消项不变，旧面板退出当前展示 |
| 明确暂时插问，之后继续原任务 | 原任务保留为暂停 / 非当前任务，面板暂不冒充新任务清单 |
| 无法确认关系 | 不取消；可显示“先前任务”标识和手动结束入口，不强行判成当前新任务 |
| 新任务首次写入清单 | 显示新任务清单；不能把旧条目拼接到新清单 |
| 新任务不写清单 | 不显示旧任务作为当前清单；不要求模型先调用 `todowrite` 才清理旧面板 |

禁止仅以“没有调用 `todowrite`”、消息数量、时间间隔、会话空闲、某一步 `stop` 或模型失败作为取消依据。

## 4. 回滚修复设计

### 4.1 服务端统一完成，不依赖客户端补 commit

建议扩展 V2 prompt 接纳契约，区分普通追加与显式分支替换。替换命令必须带客户端实际展示并选定的目标用户消息 ID、预期分支版本（含暂存回滚点的变更）和操作类型，且语义固定为含选中消息的替换。版本由服务端提供；即使先取消回滚再暂存到同一条消息，旧版本也不可复用。

- 直接重执行和编辑后发送共用同一服务方法。
- “回滚并编辑”将目标与版本绑定到当前草稿；按钮和快捷键发送（包括粘贴后发送）均携带该凭据。仅在界面明确提示“从此处重新执行”时才提交替换意图。其他窗口或先前排队的草稿不得从最新 `session.revert` 自动继承该意图。
- 暂存回滚时收到不带替换意图的普通发送，或替换目标 / 版本已过期：服务端返回可恢复的冲突，保留草稿及现有分支，提示刷新并重新选择；不自动改用最新边界重发。无暂存回滚的普通追加沿用原契约。
- 请求使用新的稳定 message ID；不能复用旧 B 的 ID，把“重新执行”误当成精确重试。
- 选中消息必须属于当前 Session，且为允许重执行的用户消息。助手消息 / 工具部件的回滚不在本轮新增语义中。
- 校验附件、agent、model、delivery、回滚点与分支版本后，才进入破坏当前投影的步骤。
- agent / model 需要在同一个命令中确定有效值或在最终接纳时重新确认。不能让提前写入、随后又被裁剪的切换消息决定本次执行参数。

### 4.2 一个可重放的接纳提交

优先使用包含分支替换描述的新版持久接纳事件，由其投影在同一个数据库事务内完成：

1. 再次检查 message ID 幂等性、Session / 分支版本和预期边界。
2. 将旧 B 及后续消息从当前聊天投影移除，保留底层历史事件；范围按服务端 seq 确定，不按客户端时间戳或字符串 ID 排序。
3. 将旧分支下尚未消费的 inbox 输入标为失效，禁止后续醒来再执行；已经提升的旧输入同样退出当前分支。
4. 失效 / 重建依赖被裁剪消息的压缩基线、Context Epoch 和相关历史选择缓存，确保旧分支内容不会从摘要重新进入上下文。
5. 按第 5 节恢复边界对应的任务归属 / 清单，失效旧分支工具写入资格。
6. 记录一条新的 durable `session_input`；清除回滚标记；写入可用于精确重试的分支替换结果。
7. 提交后广播；`resume !== false` 才安排 `SessionExecution.wake(sessionID)`。

不得在事务 / 投影中执行模型、文件恢复或再次嵌套发布事件。必须先用真实库验证“持久事件 + 投影”事务边界，不能在普通事务里调用会提前广播的多个 `events.publish`。

现有 `RevertEvent.Committed` 的保留边界语义保留给旧调用方；新路径采用明确的替换契约，共用内部裁剪逻辑但不静默改变旧事件的回放含义。

### 4.3 幂等与历史输入

当前删除 `session_input` 的方式可能使精确重试失去去重依据。新设计保留 admission 身份，并增加当前分支资格 / superseded 标记；历史输入不能再作为待提升行。

- 先按稳定 message ID 核对已接纳结果和进行中的命令，再检查客户端预期版本。比较不可变请求参数（Session、prompt、delivery、替换目标和版本、任务意图及命令中指定的 agent / model），不以变化后的会话默认值重算请求身份。同一替换请求若已接纳，只返回原结果，不因回滚标记已清除而报冲突；不得再次中断、写文件或唤醒执行。进行中的同一请求加入原操作或返回可查询的处理中状态；同 ID 异参直接冲突。
- 相同 ID 但不同正文、附件、任务转换或回滚目标，返回冲突，不改变历史。
- 已被后续回滚替代的旧 admission 仍可被查到，但精确重试不能重新激活旧分支或启动旧执行。
- 升级前已投影、缺少 inbox 记录的用户消息，继续遵守惰性补齐和冲突检查约束；不能把所有旧消息当成新请求。
- 删除 Session 时可级联清理其数据；普通回滚不能破坏去重账本。

新增字段、Admitted 返回状态及旧输入补齐方式必须在 Schema / Core / Protocol 契约中共同定义，不能只在某个客户端 Map 中去重。

### 4.4 执行互斥与文件状态

回滚属于历史 / 文件变更，需要与同 Session 的执行和其他回滚命令互斥。

1. 先执行 §4.3 的无副作用查询。首次有效命令取得同 Session 的短期变更屏障后，**再次**核对去重结果、分支版本和目标，登记本次操作。只有登记成功的执行者才能中断 runner 或修改文件。最终接纳事务仍执行 §4.2 的条件检查。
2. 屏障阻止新 drain 启动，不阻塞旧 runner 的退出清理；服务端中断旧执行并等待工具清理完毕，停止失败则不裁剪。其他同 Session 的变更按预期版本排队或冲突，不移用到新分支。屏障释放后恢复正常 steer / queue 行为，不对整轮执行加锁。
3. 对涉及的路径保存操作前状态、预期当前状态和计划写入状态（含内容标识、路径不存在等情况）及可恢复的准备记录。文件恢复在数据库事务外进行；逐路径写前核对预期状态。已有外部编辑或无法安全判定时停止并报告文件冲突，不用快照强制覆盖；同一工作树内的其他 Session 也按外部写入处理。
4. 文件恢复或接纳失败时，只补偿已由本操作修改、且当前仍匹配本次写入结果的路径。部分恢复、校验不符或补偿失败进入可诊断的恢复状态，保留准备记录与影响预览。不能把整棵工作树重置为旧快照。
5. 重启时先按命令身份核实是否已接纳；未接纳的部分操作按同一逐路径规则核对，无法确认归属的修改交给用户处理。不得因准备记录存在而重跑提供方。`clear`、取消回滚和移动回滚点同样适用文件冲突保护。

保持 `SessionExecution` 进程全局、Session-ID 驱动；runner、工具、权限和文件系统仍归属 Location。不要引入集群租约，不把 EventV2 replay owner 当执行所有权。

### 4.5 前端同步

- `session.tsx`、`use-session-commands.tsx` 和 `submit.ts` 共用明确的命令能力，防双击、防重复 Enter，保留提交目标的 server scope / Session / prompt ownership。
- 接纳成功后用权威分支结果关闭回滚栏、移除旧分支投影。提供按 Session 和当前分支读取“已接纳、未提升且未失效”输入的服务端视图，刷新 / 重连用它恢复待执行项，包括 `queue` 和 `resume: false`。待执行项不写入 `session_message`，不进入模型上下文，也不因读取而唤醒 runner。收到 `Prompted` 后按同一 ID 合并；历史、待执行列表和实时事件以版本 / 水位归并，晚到的待执行响应不能把正式消息降回待执行。
- `server-session.ts`、`server-sync.tsx`、V2 reducer 和 timeline 对新事件统一处理；旧 history / hydrate 请求晚到不能重新插入已裁剪消息。
- 回滚后的消息、错误、附件和工具展示，实时 / 刷新 / 重连必须一致。缺失消息可补读，但已失效消息的 404 不触发无限重试。
- 不把“HTTP 接纳成功”显示成模型执行成功；停止按钮及错误展示继续使用各自正确生命周期。

## 5. 旧任务清单修复设计

### 5.1 谁确认“已换任务”

不在前端用关键词正则直接取消，也不额外发一次分类模型请求。

采用两级信号：

1. **显式信号**：用户可选择“改做新任务并结束旧任务”或“临时插问”；信号随输入一起持久接纳。空闲时立即改做新任务，或明确停止旧执行并切换的命令，在完成必要的停止协调后，将任务转换与输入接纳原子提交，即使后续模型失败也有效。普通 queue 仅持久记录切换意图，到其真正提升为当前工作时再原子应用任务转换，不能在排队阶段提前取消仍在运行的任务。
2. **自然语言判断**：在已有正常模型 / 工具流程中增加受约束的任务归属决策，结果为继续、替换、临时切换或不确定。决策必须带输入 ID、当前任务 ID 和预期版本，由服务端验证再写入。普通 prose、`todowrite` 缺席、工具列表差异都不是权威决策。

“去处理另一件无关的事”默认建议替换；“先问一下，等会继续”建议临时切换。自动决策不确定时保留旧记录并标为先前任务，提供用户纠正 / 恢复入口。任务转换是产品维护元数据，不赋予模型额外执行权限；具体实现可用窄工具接入，不污染用户正文。

同一输入的决策优先级固定为：**用户显式选择 > 通过服务端校验的结构化判断 > 未判定**。模型不能覆盖显式选择。模型正常回复但未给出归属决策（包括未调用任何工具），与首次判断前请求失败一样，均走“未判定”：不写取消或暂停记录，保留旧任务，以“先前任务（归属未确认）”区分展示，提供“继续此任务 / 结束此任务”入口。不把没有新清单解释为替换，也不追加一次分类请求。

### 5.2 最小持久归属与历史

建议新增独立任务状态及清单版本存储，`TodoTable` 保留为兼容当前清单的投影，不再作为唯一事实来源：

- `session_task_state`：每 Session 的当前业务任务 ID、单调版本、最近归属决策输入 / 来源、当前清单版本等。
- `session_todo_revision`：追加式快照，保存任务 ID、所属分支、父清单版本、Session 内版本、来源输入 / 助手消息 / tool call、来源 seq、转换原因、任务状态和完整条目。结束旧任务也产生版本。为每条输入保存其任务语义开始生效前的继承引用，包括始终没有更新清单的输入。随接纳切换任务的，在接纳事务内取转换前版本；推迟到提升时才生效的，在提升事务内取转换前版本。无清单与历史归属未知使用不同值，不能用当前清单补历史空缺。

任务状态可表达当前、暂停、取消 / 被替代、已完成。条目仍使用现有 `pending | in_progress | completed | cancelled`，不把“暂停”伪装为完成。历史可恢复，普通新清单更新不能把旧清单直接销毁。

通过持久 Session 事件投影更新状态、版本历史和兼容清单；提交后派发兼容 `todo.updated`。持久事件是可重放来源，兼容通知只是同步提示。不得依赖非持久的 `todo.updated` 来重建历史。

按 Session 明确写入所有者。旧模式下保持原读写；启用版本化模式时，在同一提交中登记所有者并建立基线。`packages/opencode/src/session/todo.ts` 的 V1 路径会直接删写同一个 `TodoTable`，须在写入事务内核对所有者：有可信分支 / 任务 / 预期版本的调用转给权威写入服务，否则在删行前返回冲突，不能双写。无法约束共享数据库的旧服务进程时，不启用新版模式或要求先升级写入方。旧客户端仍可读兼容数组。

新版 App 对受管会话只采纳带权威版本的快照或事件；无版本 `todo.updated` 仅触发重新读取，不直接覆盖缓存。GET 和实时更新都要同时校验服务器作用域、Session、分支和版本，丢弃旧响应；未迁移会话维持旧同步行为。不能用前端收到通知的次数代替服务端版本。

具体表结构在实施前核对迁移与事件序列约束；字段用 snake_case，生成 schema / migration 清单走现有脚本，不手工改生成产物。任务 ID 可跨多条回复，不复用计划任务或编排器 ID。

### 5.3 替换、暂停与恢复

- 替换：对旧任务的 `pending / in_progress` 条目写 `cancelled`，原因记为被新任务替代；已完成 / 已取消项原样保留。旧任务快照进入历史，新任务成为当前任务，初始无清单。
- 暂时切换：保留旧任务条目状态与历史版本，当前面板不显示它为新任务清单；可显式返回原任务。不添加一条虚假的“任务完成”记录。
- 新清单：为当前任务写一个新版本，整体替换该任务的清单。若模型未写入，面板保持无当前清单。
- 用户纠正误判：显式恢复目标任务，产生新版本；不删除过去的取消 / 暂停记录，也不自动启动任何模型或工具。
- 手动“结束旧任务”：仅取消未完成项，幂等且按预期版本校验；会话正在执行时需要在安全边界协调，不暗中重置执行状态。

### 5.4 防止旧执行把清单写回来

`todowrite` 运行上下文需绑定业务任务 ID、对应输入 / 助手消息和分支资格。服务端获取权威归属，不信任模型自由指定任意 Session / 任务。

- 同一任务正常顺序更新可以递增版本；不同任务或已失效分支的迟到调用不能覆盖当前清单。
- 旧任务运行期间收到 queue：在 queue 真正成为当前工作前，不提前切走当前任务清单。
- 显式“立即停止旧任务并改做新任务”不是普通 queue：等待旧执行停止后执行任务转换。
- steer 的任务决策在安全 provider-turn 边界生效；不能让正在执行的旧工具继承新任务身份。
- 多个 steer 批次必须明确定义归属；相互矛盾的转换返回冲突 / 待用户选择，不以最后到达的任意 UI 帧为准。
- 工具权限拒绝、提供方重试、停止 / 重连不应单独触发清单取消。

### 5.5 与回滚联动

- 对 B 重执行时读取 **B 所继承的清单版本**，校验其属于当前分支的祖先链，并随分支替换事件持久记录新分支、父分支、分叉目标和继承版本。之后的清单版本从该引用继续；连续回滚和事件重放沿相同引用解析，不能取全 Session 中 `seq < B.seq` 的最大值。明确无清单则继承空状态；旧消息无历史证据则返回“归属未知”，保留原记录供手动认领，不声称还原了当时的任务列表。
- 取消回滚恢复原对话时，恢复原分支对应任务快照，而非从当前可见条目的状态猜测。
- 任一分支的迟到工具更新必须被分支资格检查拦截。
- 回滚涉及的任务恢复与新输入接纳在同一个持久提交中完成，避免显示新历史配旧清单。

## 6. 已有数据与卡住会话的恢复

### 6.1 已卡住的回滚

不能升级时发现 `session.revert` 就自动 commit。现有隐藏区可能包含用户后来发送的新消息和正常回复，直接裁剪会造成用户可见的数据损失。

提供专门的“退出回滚，保留已有消息”修复入口：

1. 只读统计回滚点之后的消息、回复、待接纳输入和文件影响，展示影响预览。
2. 默认不自动执行任何模型请求，不把隐藏区消息全部重发。
3. 用户可选恢复完整原对话与对应文件快照，或确认从指定位置重新执行。先确认数据和文件影响，再调用对应服务命令。
4. 检查隐藏区是否产生过工具 / 文件修改；有冲突时要求选择或人工处理，不笼统声称 `clear` 对所有混合状态都无损。
5. 任何恢复均保留历史事件、同 ID 重试依据和操作结果。

### 6.2 已有旧清单

- 旧库没有任务归属，迁移时作为一份 `legacy / ownership unknown` 清单保留，不按时间或对话条数自动取消。
- 打开会话可展示“先前任务”并提供“继续此任务 / 结束此任务”。明确改做新任务后才按新规则取消未完成项。
- 新客户端连接旧服务器：缺少能力时不暴露不能保证语义的一键重执行，提示升级或使用旧编辑流程；不能降级成先删后发。
- 旧客户端连接新服务器：无暂存回滚时仍可普通追加；暂存时没有显式替换凭据的请求按 §4.1 返回冲突，不裁剪、不重发。任务列表按 §5.2 分离兼容读取与写入资格。多客户端并用须验证，不能假设未知事件一定会被忽略。
- 不修改本机用户会话作为测试夹具，不跑全库批量清理脚本。

## 8. 验收矩阵

### 8.1 回滚与提交

| 场景 | 必须断言 |
| --- | --- |
| `A / B / C` 对 B 一键重执行 | 当前历史只保留 A 及新 B；旧 B 不重复；回滚栏消失 |
| 对 B 编辑后发送、复制新文本发送、附件发送 | 全部经过相同原子路径，正文 / 附件不丢失 |
| 同按钮双击、Enter 重复、HTTP 超时后同 ID 重试 | 一条 admission、一次有效新输入；无重复提供方工作 |
| 同 ID 改正文 / 改目标 / 改任务转换 | 冲突且不裁剪历史 |
| 文件恢复失败、数据库提交失败、补偿失败 | 各自可恢复、错误明确；不谎报成功 |
| 接纳前失败 / 接纳后 provider 失败 | 前者保留原状态，后者回滚已结束且错误可见 |
| 工具运行中回滚，并发另一个客户端提交 | 服务端等待停止或明确冲突；旧结果不能复活 |
| 存在 queue / steer、历史 prompt 惰性补齐 | 被替代输入不执行；原精确重试仍可核对 |
| 回滚目标在压缩基线之前 | 模型请求不含被丢弃分支的摘要 / 历史 |
| 切 agent / model 后回滚重发 | 本次实际使用选择的配置，刷新后不漂移 |
| 提交前后崩溃、广播丢失、乱序 hydrate | 文件 / 数据可核对，历史一致；不自动重跑提供方 |
| `resume: false` | 只接纳并结束回滚，不调用模型 |
| 已卡住会话退出回滚 | 新发送消息不被自动删除或重发，文件冲突有预览 |
| 窗口 A 暂存 B，窗口 C 从旧草稿普通发送；或 A 持有已过期的边界版本 | C 和过期命令均返回可恢复冲突，草稿和旧分支不变；只有携带有效目标和版本的发送能替换 |
| 首次重发已接纳且正在生成，HTTP 响应丢失后同 ID 重试 | 返回原结果；在途回复未中断，文件写入数、唤醒数均不增加 |
| 文件在准备后被编辑，或部分恢复后在补偿前被另一 Session 编辑 | 报告具体路径冲突，不覆盖外部编辑，只补偿仍匹配的本次写入 |
| 接纳成功、提升前刷新；随后提升，旧待执行 GET 晚到 | 回滚栏已关闭，刷新可见一条待执行项；提升前无正式消息，提升后只留一条正式消息；读取不唤醒模型 |

“只执行一次”限于正常接纳去重 / 调度语义。进程在外部调用后崩溃，无法承诺提供方端 exactly-once；不得因此加入自动恢复提供方执行。

### 8.2 清单

| 场景 | 必须断言 |
| --- | --- |
| 原任务继续 / 回答澄清 | 清单及归属保留 |
| 明确替换，无新清单 | 旧未完成项取消，当前面板为空，历史可查 |
| 明确替换，有新清单 | 当前只显示新清单，旧已完成项不变 |
| 临时插问再恢复原任务 | 旧任务暂停而非取消，可显式恢复 |
| 意图不确定 / provider 首响应前失败 | 不误取消；有先前任务及手动处理入口 |
| 显式替换后 provider 失败 | 旧任务仍已取消，不因失败回活 |
| 旧工具迟到、重复事件、旧 GET 晚到 | 不覆盖新任务或较新版本 |
| queue / steer / 多输入批次 | 按实际执行边界切换，不提前取消仍在运行的任务 |
| 回滚到清单更新前 / 取消回滚 | 展示对应分支快照，不混用未来清单 |
| 历史旧库、空清单、全完成 / 全取消 | 不批量猜测取消，不出现刷新后旧面板复活 |
| 多 Session、多 server scope | 任意任务转换不影响其他会话 / 服务器 |
| 正常模型回复，既无结构化归属决定也无新清单；另测决定与显式选择冲突 | 前者不取消并提供手动处理入口；后者以用户选择为准 |
| 同一会话两次回滚，中间替换任务并生成新清单；从持久事件重放 | 每次继承目标输入对应的祖先版本，不选择被丢弃分支的清单；旧库缺少版本时显示未知 |
| 受管会话遭遇 V1 直接写入、无版本通知及迟到的旧 GET | 未授权写入在删除前被拒绝；通知只触发核实，旧响应不覆盖新状态；未迁移会话仍可正常读写 |

### 8.3 分层测试与交付检查

- Core：使用真实临时数据库、快照仓库、受控提供方和现有 Effect 测试设施，扩展 `session-projector.test.ts`、`session-create.test.ts`、`session-runner.test.ts`、`session-run-coordinator.test.ts`、`session-todo.test.ts`、`tool-todowrite.test.ts`，补专用回滚与迁移测试。
- Protocol / Server：验证事务失败映射、能力协商、旧调用方、冲突和同 ID 重试。兼容 SDK 和事件重放必须实际跑通。
- App：扩展 `submit.test.ts`、`server-session.test.ts`、composer state 与 timeline 测试；浏览器贯通真实本地服务器验证新旧布局、重连、刷新、切会话、按钮及键盘，不用纯消息夹具代替端到端测试。
- 桌面端：实机复测卡住场景、快照 / 文件影响、错误与恢复提示。
- 可用性：简繁中文 / 英语，浅深色，英语强制 RTL、真实 RTL 和混合路径文本；逻辑方向样式、焦点顺序、滚动定位、读屏提示正确，不为镜像倒排 DOM。

## 9. 完成标准

必须同时满足以下条件，才可宣布两项修复完成：

1. 重执行或编辑发送成功接纳后，新消息 / 回复 / 错误不再进入回滚列表。
2. 接纳与分支替换原子一致，重试不重复执行，文件失败和进程中断有明确恢复路径。
3. 明确换任务后，即使没有新的 `todowrite`，旧未完成项也能按归属取消并退出当前面板。
4. 继续原任务、临时插问和意图不明不被误取消，旧任务记录可查 / 可纠正。
5. 刷新、重连、历史重放、回滚和迟到工具不会把旧消息或旧清单重新带回当前分支。
6. 已卡住的历史会话可由用户显式恢复，不依赖删除会话、清库或人工改数据库。

不接受的“修复”：仅隐藏面板、发送前客户端先 commit、所有新消息无条件取消旧任务、将取消记成完成、全库自动清理、模型失败后恢复旧回滚、修改真实用户数据来制造验收结果。
