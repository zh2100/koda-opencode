# ACC 后续缺陷详细修复实施方案

日期：2026-11-14；复核补齐：2026-11-15。状态：**设计待实施；本文件不表示修复或验收完成。**

依据：[后续验收记录](./acc-followup-acceptance-results-2026-11-14.md)。本方案只处理 OBS-01 和 ACC-F02，以及使两项修复可验证的必要依赖，不接管全部历史未关闭项。

## 1. 目标、证据和禁止替代的修复

| 编号 | 已确认根因 | 必须达到的结果 |
| --- | --- | --- |
| OBS-01 / P1 | 自动刷新使用旧供应商版本；后续名称保存提高版本，却没有承接未完成的刷新责任 | 两次保存均完成后，最新有效实体有对应的新目录；失效请求不能覆盖结果，也不能吞掉刷新需求 |
| ACC-F02 / P1 | 项目 PATCH 写 config.json，项目加载发现 opencode.json/jsonc | 保存真正参与该项目加载的本地文件，正常连接、取消、清理重建后的 GET 都符合来源合并规则 |

已保存的反例：

- 页面交错专项：2 pass、2 fail，经典和现代布局均在“自动刷新挂起→再次保存名称”失败。
- TCP 来源对照：1 pass、3 fail；正常连接和两种成功提交后的断连均在回读处失败，投递后拒绝的原字节保护通过。
- 首批既有页面冷态读取另有 21.8 秒观察项，热态复验通过。该项不是上述两个根因的证明，不靠增加超时宣称已修复。

以下做法不能作为完成条件：移除版本/实体校验；把每次 Save 都改成全局刷新；吞掉所有 409；禁止用户在任何刷新期间编辑来掩盖责任丢失；只更新内存缓存；让加载器自动读取任意 config.json；自动把合并后的运行时配置全文写回磁盘；把提交后的通知失败报成“保存未提交”。

### 3.1 阶段候选与进入下一阶段的门禁

| 阶段 | 实施范围 | 本阶段退出条件 |
| --- | --- | --- |
| A：认证契约 | 固定原始 R/V 的后端步进前提、普通 mutation 精确重放、创建既有持久化回执兼容；不改项目配置写入 | Core 的 relay-auth/relay-create 及正式 Relay HTTP 契约通过；O24～O29 的后端子样本逐项留证，覆盖失败/未知/重启/淘汰；相关包类型检查通过；未改 App 的既有保护回归保持 |
| B：OBS-01 | 在 A 上实现不可变命令基线、刷新需求协调、旧 ACK/清钥/删除/换服隔离及能力兼容 | O01～O29 的本阶段全部子样本、实际 hook 回归、登记的经典/现代页面通过；Core/App/Server 及受影响公开契约检查通过；已启用能力的真实前后端验证证据齐备；最终交付仍经 S7/S8/S9 |
| C：ACC-F02 | 共享来源/原文与引用预检、目标选择/多锁、两阶段任务、错误与 SDK、必要共享 handoff 修正 | F01～F36 按协议/平台/调用方逐项完成本机范围验证；真实 TCP、磁盘/有效配置/重建闭环、no-op 与提交区分通过；生成与类型检查通过；受影响的阶段 A/B 回归重跑 |

1. 每阶段开始前固定输入候选：HEAD、继承的未提交改动摘要、拟改文件 SHA256、阶段 ID 和证据根；结束时记录输出候选、实际文件差异、命令与退出码。文件摘要是取证，不创建源码备份，也不要求 commit/stash。进入下一阶段前重新核对；发现未解释漂移则先重读差异并补受影响检查，不能继承旧 pass。
2. 能力按“后端契约验证→隔离候选启用→真实前后端验收→交付判定”推进。A 只完成后端契约及 O24～O29 后端子样本验证，暂不在产品能力列表中声明，不代表前端/页面部分已完成，也不关闭 OBS-01。A 的门禁通过后，B 在隔离候选的实际 toState 能力列表中启用 vendor-commit-baseline-v1，接入实际前端，随后验证正式 HTTP 透传、精确版本分支、旧服务器兼容及登记页面；这些依赖能力启用的证据不是候选启用的前置条件。B 的必需样本通过才能进入 C；C 后同一最终候选通过 S7/S8/S9 才可判定该能力可交付。候选启用不操作当前应用、生产配置或发布流程，不增加临时测试专用能力开关，不给全部夹具补 capability 冒充真实启用。
3. 未完成的本阶段必需子样本、失败、无法解释的类型错误，均阻止进入依赖它的下一阶段；修正后仅重跑受影响检查并保留首次失败。平台确实不适用的框架 skip 与缺少环境的未执行分开登记；Linux/macOS/native 等未执行不能变成通过，也不能借此关闭历史跨平台问题。本批本机门禁与未覆盖平台边界在 S0 固定。
4. B 的页面结果只属于 B 输出候选。C 完成后仍须按 S7/S8 在同一最终候选联合验证并重跑登记页面；C 修改共享依赖后不能直接沿用 B 的旧页面 pass。阶段检查通过只是进入下一步的条件，两项缺陷最终关闭仍按 S9，各自的剩余限制按第 14.1 节报告。

#### 3.2.2 每份 manifest 必须登记的字段

1. 身份与上下文：runId、stage、input/output、candidateId、parentBaselineId、UTC 时间、HEAD、工作目录、方案文件摘要、OS/架构、Bun/Node 版本；平台身份仅记录权限测试必要的安全信息。方案版本变更也要记录影响，不静默沿用旧验收范围。
2. 源码范围：完整工作区的路径级状态（含未跟踪文件）、暂存/未暂存标记与 index 摘要；本阶段拟改文件及相关源码、测试、构建/类型检查配置、依赖清单/实际锁文件、生成产物的 SHA256。新增文件登记原先不存在，删除文件保留缺失标记；不能仅凭 HEAD 标识大量未提交改动下的候选。原生隔离产物如参与测试只记来源/摘要，不重建或启用生产后端。
3. 候选标识：由已登记范围内按仓库相对路径排序的“路径、存在状态、内容摘要”清单确定，记录计算规则；隔离日志、假数据和证据输出不计入产品源码候选。下一阶段 input 引用上一 output，并逐项确认共同文件摘要一致；新增依赖先补录其输入状态，范围扩大导致 candidateId 改变必须说明，不能要求不同清单的标识天然相等。
4. 检查清单：关联 O/F 编号和子样本、所需平台/协议、命令、包工作目录、实际退出码、pass/fail/框架 skip/未执行、日志位置及被测 candidateId。命令成功但没有执行目标用例不算通过；页面另记布局、服务 readiness、能力状态及 trace，不记录测试密钥、配置原文、引用展开值或敏感 payload。
5. 能力与环境：阶段 A 记录新能力未声明，B/C/final 记录真实候选的声明及实际 HTTP 证据，旧服务器兼容另记夹具身份。隔离进程记录创建时间、命令行的安全部分、端口与数据根归属；服务必须对应当前候选，源码改完但仍连旧服务不能计入结果。仅哈希源码/构建产物，不把密钥或凭据引用内容的摘要记入基线。

#### 3.2.3 阶段执行与验收步骤

1. 进入阶段：只读采集 input，核对父基线与暂存状态，固定本阶段必需检查、平台边界、具体测试文件和证据路径。已有未提交改动原样保留；同一文件中混有用户改动时先读差异确认归属，不做 reset/stash/整文件覆盖来整理基线。
2. 留下反例：先运行本阶段的实际路径红测试，保存原始命令、候选、退出码与失败阶段。若反例未复现，先核实源码漂移/夹具/归属，不能直接把预设失败改成“已修复”；新增保护性用例不强求旧实现全部失败，但须说明其作用。
3. 实施与检查：按本阶段范围修改，完成要求的生成后再冻结 output；执行定向回归、类型检查、正式 HTTP 或页面门禁。生成命令的实际差异属于源码候选，不能在冻结后悄悄更新 generated。必要新依赖超出已登记范围时先更新工作单及影响说明，沿用现有授权边界，不顺便引入历史未关闭模块。
4. 失败处理：本阶段失败即保留 failed 状态与首次证据，继续在本阶段定位修正，不进入依赖它的下一阶段。修正后建立新的 output 候选，重跑受影响检查；环境缺失记未执行，若是本阶段必需条件则保持待验收，不用跳过、重试次数或更长超时抹平。不得为恢复基线删除或回滚用户修改。
5. 交接：handoff.json 记录 input/output、实际变更文件与原因、通过及未完成子样本、兼容限制、下一阶段允许接触的范围和门禁结论。只有对应必需检查通过且无未解释漂移，才记“阶段通过”；A 通过只说明后端前提，B 通过仍不是最终交付，C 通过仍需 BL-FINAL。
6. 最终固定：S7/S8 使用同一 BL-FINAL；测试前后核对源清单、生成产物和服务归属。若需修改产品/测试实现或影响结果的依赖，建立新候选、重建自己的隔离服务并复跑受影响检查及规定的最终联合验收，不能沿用旧候选的完整结论；只追加证据文件不自动使产品源码候选失效。
7. 关闭登记：BL-CLOSE 保留最终候选与清理结果，比较 index/暂存状态并说明预期变化，不改变用户暂存。交付报告分别列“设计完成、阶段通过、自动验证通过、页面通过、未执行、未关闭”；这些状态按对象填写，不能把一个阶段的通过提升为全部 bug 已修复。

## 4. OBS-01：先定义刷新责任（S1）

### 4.1 把三个不同概念分开

1. **保存命令**：本节专指 RelayAuth 供应商写命令；按原 operationId 执行，精确匹配的成功 ACK 确认该命令的提交事实，不代表上游刷新完成。它不同于项目 PATCH /config 的成功处理语义，后者还允许无写入 no-op，见 S4.5。
2. **后端目录同步待办**：现有 pendingCatalog/catalogSync，表示认证提交后的目录同步/通知责任。沿用其含义。
3. **上游模型刷新需求**：本次需要新增或明确归属的责任，直到最新有效身份的 refresh 与目录读取都成功才满足。

不能仅因 sync 返回新 auth.revision、候选为空、名称保存成功或某个 Promise finally 执行，就认定第 3 项已经完成。成功的上游空列表可以满足需求；“没有成功刷新过的空缓存”不能。

### 4.2 最小状态与归属

每个当前供应商维护一个小记录，字段名称实施时可调整，语义必须固定：

- owner：设置页 scope、生命周期 generation、vendorId、entityId。
- demand：单调的刷新需求序号，以及已满足序号。不是另一个 auth revision。
- target：当前已接纳的供应商 revision，以及地址/凭据变更的本地代次。绝不保存密钥内容或可逆密钥摘要。
- 连接提交水位：按同一 entityId 记录已确认的连接变更/清钥及其原始提交版本，同时保留已成功刷新覆盖的连接水位。原始提交版本只按第 4.6 节取得；不等于响应快照中的 vendor revision。复用 target/完成记录表达，不能用 ACK 到达顺序、全局 auth revision 或用户尚未提交的编辑序号替代。清钥后的屏障不能随 pending demand 清空而删除。
- active：正在执行的请求身份与 completion；排队项只保留最新目标和需求。
- failure：当前目标最后一次可见失败及其错误票据；不能让旧请求清理掉新错误。

优先复用当前 vendorEntities、vendorCatalog、vendorTicket、acceptedCatalog 和 busy 的责任，避免多个互相独立的“最新版本”变量。若新增字段不能说明它与这些已有水位的区别，应删除该字段而不是再增加比较条件。

### 4.3 五条不变量

1. 新需求只来自已确认的配置提交、显式获取模型，或已接纳的外部身份/连接变化；输入框编辑不触发写入或远程刷新。
2. 名称保存/空补丁没有新增连接需求，但不能清除原有未满足需求。
3. 只有正确 owner、正确实体、正确依赖代次的 refresh 成功，再经现有目录合并入口接纳，才更新 satisfied。旧版本、旧实体或旧 scope 成功均无此权限。
4. 请求结束不等于需求满足。失败保留需求和可见重试入口；删除/清钥/销毁可使需求终止，但须有对应成功事件或生命周期依据。
5. 自动补刷不重放 Save、清钥或删除命令，不循环修改 revision 来追赶刷新。

### 4.4 动作转换表

| 动作/结果 | 刷新需求 | 调度规则 |
| --- | --- | --- |
| 保存地址/新密钥成功 | 产生连接新代需求；合并当前最新目标 | 可启动自动刷新；若后端 catalogSync pending，先由其同步责任接续，不能丢需求 |
| 名称保存/空补丁成功 | 保留原需求，目标 revision 前移 | 旧运行若尚未完成，允许新目标接续；无旧需求则不凭空抓模型 |
| 手动 Get models | 产生显式需求；persistDraft 后绑定成功保存的身份 | 调度最新目标，不等待已知过时的挂起请求才开始 |
| Probe | 不凭连接测试结果满足模型需求 | persistDraft 若留下刷新需求，外层动作退出时交回协调入口；probe 自身不是目录刷新 |
| auth/catalog 同步响应 | 只合并当前身份的数据 | 未证明本次上游刷新完成时，不提升 satisfied |
| Save 失败且确定未提交 | 不接纳这次连接变化 | 保留此前已存在需求；不能回滚较新的成功提交 |
| Save 响应丢失/结果未知 | 按第 4.7/4.8 节保留原命令并保守对账 | 不创建新 operationId 自动重放，不根据草稿猜测已提交；无精确证据不确认成功 |
| 清钥成功 | 按提交版本撤销被其覆盖的需求，并保留清钥屏障 | 旧保存 ACK/刷新均不能复活需求或模型；晚到的旧清钥 ACK 也不能撤销后来新密钥的需求 |
| 删除成功/同名重建 | 撤销旧 entityId 的需求 | 重建实体从新 owner 开始，不能继承旧完成/失败 |
| 换服、局部 owner 销毁 | 终止本 owner 的调度与回写权限 | 不关闭共享 SDK/SSE/query，不把旧需求迁到另一服务器 |

补充：旧地址保存 ACK 晚于新名称 ACK 时，只有通过下面的提交水位判定，才登记未满足需求并接续到当前版本；同 entityId 只是必要条件。不能因 applyAuth 拒收旧全量快照就漏记仍有效的提交责任，也不能借补登记倒写旧名称/草稿。

### 4.5 迟到提交与撤销的顺序规则

1. 提交事实按第 4.6 节冻结的 operationId、命令种类、entityId 和可证明的原始提交版本识别、去重；响应快照只通过现有入口合并当前状态，不能给旧命令重新标版本。先判断当前 scope/生命周期/实体，再判断连接提交水位。相同 operationId 的清理重试或重复 ACK 不再次增加需求。不保存原密钥、keyRef 或密钥摘要来比较连接。
2. 清钥命令成功且原始基线可证明时，按第 4.6 节记录该实体的精确清钥提交版本 C，撤销不晚于 C 的连接需求。权威同步明确 hasKey=false 时，可另记该实体当前观测版本 K 的“无钥观测屏障”，终止不晚于 K 且需要密钥的旧需求；K 不冒充清钥命令的确切版本，也不据此把某个 operationId 标成已确认。两类屏障都不能仅因按钮已点击、请求失败或未知结果而建立。
3. 旧保存提交版本 S 不晚于清钥屏障 C 时，只记录旧命令已提交的事实，不登记/调度需求、不恢复 hasKey/模型、不改当前错误或忙碌。清钥保留 entityId，因此不能用 entityId 相同来绕过此条件。
4. 已接纳的更晚连接变更 N 替代旧连接提交 S 时，责任归属于 N。若 N 的刷新仍未完成，仅保留 N 的需求；若 N 已成功刷新并被目录接纳，不因迟到 S 再创建一轮需求。仅更晚的名称/空补丁不构成连接替代屏障，仍保留 O15 的接续行为。
5. 新密钥/新地址在 C 之后明确提交时，按其新 vendor revision 产生新需求；保留历史 C 作比较，不能沿用旧请求句柄。迟到的旧清钥 ACK 不撤销版本更晚的新连接需求，不把当前 hasKey 改回 false。大小比较必须在同一实体内进行，删除/重建后的版本不能跨实体排序。
6. 外部快照无法证明某版本只改了名称还是改了凭据时，不凭“URL/hasKey 看起来一样”假定旧连接仍有效；先走现有只读对账，保留不确定的当前需求，不自动重放写命令。当前权威状态明确无密钥时，不启动需要密钥的自动刷新；明确的后续新连接提交才可重新启用。对账受 S2.3a 的次数和截止时间限制。

### 4.6 原始提交版本来源：固定命令基线（S1.6，本批选定路径）

现有 API 的成功正文包含 AuthState；它是状态快照，不是每个命令不可变的提交回执。RelayAuth.replay 在存在待清理记录时调用 settleCleanup，后者重读最新数据；因此同一清钥 operationId 的首次响应可为 vendor revision 2，清理重试响应可已是 revision 3。现有 OperationReceipt 只服务 vendor-create，committedRevision 是全局 auth revision，不能直接当供应商提交版本。

本批选择**冻结原始命令基线，并以显式后端版本契约推导提交版本**。不新增持久化 mutation 回执表，不改凭据日志布局，不用最新快照补造回执；实现和测试必须满足以下全部前提。

1. 新增开放字符串能力 `vendor-commit-baseline-v1`。它只承诺：对已存在且匹配 expectedEntityId 的供应商，setVendor/clearVendorKey 的首次成功执行在同一认证写锁内先验证全局 expected revision R，再将该供应商原版本 V 恰好加一并提交；只有确定未提交的失败才要求版本不变。已提交后的收尾失败或响应丢失允许磁盘已经加一，按第 4.7 节保留已提交/未知责任；同 operationId 可识别的已提交重试只回放/清理，不再次修改配置版本。快照可以更新，原命令的提交版本仍是 V+1。创建/删除不套用此通用加一公式。
2. 前端在首次真正投递命令前，从同一份已接纳 AuthState 同步捕获 R、该实体的 V、entityId、vendorId、命令种类、operationId、scope/generation 和能力版本；payload.revision 必须等于这份快照的 R，expectedEntityId 来自这份快照。不能拿旧 vendor 参数的 V 配上较新 store.auth.revision，也不能先冻结 V、经过 await 后再读 R。原请求进入既有命令记录后，这组元数据不可变。
3. 把实际提交 DTO 与元数据作为同一命令的两个视图管理：重试仍用原 operationId、原 payload 和原 R/V，不能从最新草稿重建请求；草稿有新编辑时是另一个明确命令，不沿用未知结果命令的 id。复用现有提交记录对敏感 payload 的生命周期，不为版本比较新增密钥副本/摘要；元数据、日志及结果报告不带密钥内容。
4. 只有该精确命令收到确定成功，并且有完整原基线、同一服务器归属及首次基线/响应中可信的能力承诺时，才能把原始提交版本定为 V+1；这是对后端条件写入语义的推导，不是从响应数据猜测。单独收到冲突、确定未提交失败、超时、取消或响应丢失，都不能据此新增“已提交”事实；但它们也不能抹掉此前已取得的提交证据。首次结果未知后重试再返回冲突，不代表首次未提交。后续只读 GET 新状态不能单独证明某个未知结果命令已提交；按第 4.7/4.8 节做精确命令对账或保守保留未知，不自动重放新命令。
5. 推导依据：全局 R 检查在认证写锁内成立，说明首次执行前没有另一笔已提交认证写入越过这份基线；同实体原版本就是 V。本次唯一配置更新使其变成 V+1，即使凭据清理重试后来返回更高快照也不改这个版本。将此推导写进后端契约测试；若任一首次提交分支会不递增、递增多次，或重放成功没有匹配原条件写入的精确命令证据，就不能宣称该能力。相同编号不同命令的兼容收紧、证据丢失及容量规则按第 4.8 节实施，不能只加 capability 后继续返回旧的宽松成功。
6. 示例：clear 的冻结 V=1，原提交 C=2；后来新密钥命令冻结 V=2 并提交 N=3。旧 clear 清理重试即使返回 vendors[].revision=3、hasKey=true，也只提供 C=2 的提交事实。当前快照 3 交给 applyAuth，撤销判断仍用 C=2，不能撤销 N=3 的需求；保存命令的重试同理。
7. 删除以原实体终止规则处理，不从“响应中没有供应商”推导版本。createOnly 继续使用既有创建回执验证 operationId/实体，committedRevision 保持全局单位；不得拿它与 vendor revision 作大小比较。需要创建初始供应商版本时，须由创建契约单独证明，不能借本节的已有实体更新公式补值。
8. 按第 3.1 节先通过后端精确步进/重试契约及阶段 A 门禁，再在阶段 B 的隔离候选 toState 能力列表中启用新能力，之后执行依赖该声明的真实前端/HTTP/兼容验证；最终验收完成才可判定可交付。不要只给测试夹具补一个字符串让前端进入新分支。正式 HTTP handler 保持最新 AuthState 的真实语义并透传开放 capabilities；普通读取不附带伪造命令回执。新老快照经当前 owner 规则合并，不把推导出来的 V+1 写回 auth.vendors[].revision 来制造旧状态。
9. 兼容规则：缺少新能力、原命令基线丢失、实体不匹配或数据来源不可信时，不推导精确 C/S/N，不从最新快照 revision 补值，也不把旧服务器已有的 entity/create-receipt capability 当作这个新契约。仍保留配置已提交结果和现有安全保存路径；刷新用有界只读对账获取当前身份，权威无钥状态可建立第 4.5 节的观测屏障。无法证明的旧提交保持待对账/待刷新，不创建循环或新 operationId 重放。精确版本屏障的关闭证据只覆盖具备新能力的后端；旧后端的保守行为单独验收，不能混称同等保证。
10. 原始基线只在本 owner 的既有命令/未决结果生命周期内保留；重复响应消费至多一次。已销毁 owner 的回包不能迁移给新 owner；重建后没有原始命令记录时只读取当前权威状态，不从本地缓存、最新 revision 或 operationId 字符串重建提交版本。当前请求结果包含的旧/新快照与原命令事实分开清理，不为无限去重新增无界内存表。
11. 外部客户端改动不具备本客户端的冻结命令记录；当前 schema 也没有公开连接变更版本。只能按权威观测及有界对账处理，不能把每个远端 vendor revision 都声称为“连接提交”。若未来需要跨进程/跨客户端精确回执，另行设计不可变、可恢复的提交元数据及容量/兼容规则，本批不假称已具备。
12. Schema/HTTP 的正文形状保持现有 AuthState 和 vendor-create OperationReceipt；本批是增加能力语义及其实现验证。仍按 S6.2 执行公开契约核对和客户端生成，确认开放字符串 capability 的兼容，不能手改 generated 或给旧创建回执加含糊单位的新含义。

### 4.7 失败阶段、提交证据与版本断言

“请求失败”和“配置未提交”必须分开。真实边界以替换配置文件的结果为准：RelayAuth.write 已成功返回、随后 settleCleanup.read 失败时，调用可能报错，但磁盘版本已经递增。不能为兑现“失败不加一”回滚配置、删除当前仍被引用的凭据，或隐藏这次结果未知。

| 阶段/证据 | 版本与磁盘断言 | 客户端/收尾责任 |
| --- | --- | --- |
| 确定在提交前拒绝或失败，且无先前未知尝试 | 原字节不变，vendor/auth revision 不递增 | 记录本次未提交，不新增提交型刷新需求；保留其他已存在责任 |
| 发布已被可靠确认，随后清理、读取、通知或响应失败 | 本命令的配置递增保留；后续其他命令还可能继续推进快照 | 持有确切证据的服务层保留 committed 和待清理责任；客户端只有收到可信成功/既有确认时才认定提交，否则仍按未知对账 |
| 替换结果不明、取消/断连导致确认丢失，或客户端只有通用错误 | 磁盘可能保持旧值，也可能已为 V+1；不能断言一定不变 | 原 operationId、payload、R/V 和未知状态按原生命周期保留；不回滚、不自动产生新写命令 |

1. Core 在实际发布/替换边界保留已有或必要的窄阶段证据，再进入凭据清理；后续 catch/finalizer 不把已确认 committed 降格成确定未提交。仅“调用了 publish/rename”不是提交证据；底层操作尚未结束时也不能先宣布失败未提交。
2. 若提交已确认且保存的安全 AuthState 足以维持现有成功形状，可沿用既有已提交/cleanupPending 收尾语义；若无法可靠构造公开成功结果，仍可走现有错误通道，客户端将其视为未知。内部 committed 标记不能被没有公开证据的前端凭空读取；本批不新增未声明的 committed/error 响应字段，也不把所有 SECRET_STORE_UNAVAILABLE 解释成确定未提交。
3. 原始版本的“恰好 +1”是针对该命令的一次配置提交，不针对每个 HTTP 返回或清理尝试。无其他提交的受控样本中，提交后故障仍保留 V+1；有其他命令交错时，最终快照可以更高，需用命令基线和实际提交屏障分辨，不能要求最终磁盘一直等于 V+1。
4. 首次结果未知后的同 id 检查/显式重试，只有现有命令记录能识别时才确认或补清理；无法识别而返回冲突/错误时，不能把第一次改记为未提交，也不能换新 id 重放。此处不承诺新增跨进程持久化回执或未知恢复能力。
5. 必补反例：在真实 RelayAuth 配置替换成功之后，精确让首次 settleCleanup 读取失败；分别核对 Core 阶段、正式 HTTP 结果、磁盘 vendor/auth revision、后续只读读取以及前端未知状态。另保留清理返回失败、通知失败、响应丢失及取消分支，不能用“提交入口直接拒绝”替代提交后的故障。屏障和故障注入只作用于隔离夹具并记录阶段，不输出配置/凭据原文。
6. O26 和能力验证必须区分上述三类结果：确定未提交失败不递增，已确认提交后收尾失败不二次递增，未知结果不作错误的零递增保证。O26/O28 的后端契约子样本是阶段 A、候选启用之前的门禁；正式 HTTP/前端联合子样本在阶段 B 候选启用之后执行。O28 完整必需子样本未通过，不能判定 vendor-commit-baseline-v1 可交付，也不能声称全链路版本契约验证完成；不把后半段证据倒设为候选启用的前置条件。

### 4.8 精确命令重放与既有客户端兼容

本批选定**收紧服务端重放成功条件**，不新增请求字段，不引入持久化 mutation 回执表。现有 replay(operationId) 仅按编号命中；既有测试把不同密钥、不同 revision 也当作成功重试，这不能支持第 4.6 节的原命令推导，须明确修改实现和相应断言。

1. 已有实体的普通 setVendor/clearVendorKey 的合法精确重试定义为：同 operationId、命令种类、vendorId、expectedEntityId、请求 revision 及实际提交 DTO 完全相同。DTO 按已解码请求的固定字段顺序构造，区分字段缺失与显式值；不从当前草稿重建，不用展示层归一化合并不同请求。创建按本节第 8 条的既有持久化指纹语义验证；删除保留其已确认命令的归属验证。所有种类共用编号归属冲突检查，不能跨 kind/vendor/entity 返回另一命令的成功。
2. 在同一认证写锁内，先分辨命令种类与已有编号归属，再按对应的证据验证器决定重放或首次条件写入。已有实体 mutation 用服务内精确证据；创建优先验证其持久化 creationReceipt/fingerprint，不先被内存记录缺失或当前实体不存在拦截。只有对应验证通过才可调用该编号的 settleCleanup 并返回重放成功；同编号证据不匹配返回既有 REQUEST_CONFLICT，不写配置、不改凭据，也不清理另一命令。没有任何既有提交证据才进入首次 requireRevision/requireEntity；不能先把新请求登记成已提交再绕过这两个检查。
3. 已有实体 mutation 的服务内证据复用并改造现有 cached 记录，不另建无界 Map：保存安全归属、请求 R、阶段与结果，敏感 DTO 的匹配使用每个服务生命周期内随机密钥的 HMAC。固定编码只在计算时使用请求对象，不额外保留密钥明文副本；HMAC 仅用于精确命令匹配，不用于版本排序，不落盘、不进入 AuthState、日志、ref 或测试附件；退出时释放记录和随机密钥。跨种类的创建/删除既有回执仍沿用其原用途，并在进入任何宽松重放路径前做编号归属检查。
4. 默认最多保留 1024 条本批服务内精确重放记录，实施时用可注入的小容量验证，生产默认值单独断言。淘汰必须同时撤销该条的内存可重放结果与匹配证据，不得留下 cached 成功而丢掉身份。已有实体 mutation 仅剩 pendingCleanup 编号或不完整删除记录、没有足够命令证据时，拒绝确认为精确 mutation 成功；清理由已有初始化/维护路径按引用安全规则完成。创建回执不属于这个内存淘汰集合，其持久化指纹仍可独立验证，不能因内存淘汰/重启删除回执、重建签名密钥或拒绝合法创建重试；创建容量继续服从其既有 receiptLimit。
5. 已有实体 mutation 发布成功后、清理/响应可能失败之前，在不可中断的短边界把本服务的已提交证据登记完成；未提交失败与未知按第 4.7 节分类。已有实体 mutation 跨重启仅剩 pendingCleanup 编号，或其内存记录被淘汰时，不根据编号/当前快照重造证据；已存在有效创建回执的创建请求仍走第 8 条。若没有可识别记录，原冻结 R 已被提交推进则按原条件写入返回冲突；R 仍匹配且没有已有编号证据时才可能作为首次条件写入执行。这里不承诺服务生命周期之外的全局编号唯一性，也不允许前端用新 R 改写一个未决命令。
6. 兼容变化明确登记：旧客户端使用相同 DTO 的正常精确重试继续成功；同编号换 key、revision、供应商或命令种类，以前可能成功，现在明确冲突。既有“忽略 sk-two/sk-ignored”用例不能直接删除或算作过时无关断言，应改为冲突且磁盘/密钥不变，并另保留真正相同 DTO 的成功重试。服务重建后无法确认的已有实体 mutation 清理重试改为保守冲突，不再承诺其可用于原命令版本推导；创建的持久化精确重试和独立初始化清理回归仍需通过。
7. O29 必须在 Core、正式 HTTP、实际前端联合验证：已有实体精确重试、同编号跨 kind/vendor/entity/载荷/R、提交后读失败、重启与容量淘汰，以及创建回执在重建/内存淘汰/实体已删除后的独立验证。前端只有精确命令的确定成功才推导 V+1；冲突保留先前未知/已确认事实，不把清钥或保存伪装成成功。O26/O28/O29 的后端子样本及阶段 A 门禁通过后，允许在阶段 B 隔离候选中启用能力以验证实际前端/HTTP；完整必需样本和正常旧客户端路径未通过，不通过阶段 B 门禁、不判定能力可交付。公开响应形状不变，但服务语义变化与 SDK/调用方精确重试兼容结果必须登记。
8. 创建继续使用现有持久化 receiptKey 与 creationReceipt.fingerprint：按既有固定字段、name.trim/baseURL 去尾斜杠等签名规则重算并验证，不能套用本节普通 mutation 的临时 HMAC 或额外要求原始字节相等。签名匹配后仍返回原 OperationReceipt 与真实最新 AuthState，committedRevision 保持全局单位；即使供应商已删除也只确认原创建，不能重建该实体。持久化密钥缺失/损坏仍按原错误阻止初始化或验证，绝不自动生成新密钥覆盖旧证据；跨种类复用该编号及签名不匹配仍拒绝。保留 relay-create.test.ts 的 B108/B111 跨服务重建、B112 指纹冲突、B115/B116 删除后回执及 B114 密钥缺失回归，并纳入联合命令；这些用例不能改为期望冲突来迁就新缓存规则。

## 5. OBS-01：具体改造步骤（S2）

### S2.1 先补实际 hook 红测试

用 Deferred/可控 Promise 建立以下顺序：地址提交成功 → 旧 refresh 挂起 → 名称提交成功 → 放行旧请求为 REQUEST_CONFLICT。断言旧实现没有为最新版本补刷，最终候选为空。保存原始失败日志。

同时保留手动 Get models 能在旧请求仍挂起时完成的现有通过场景，防止“改成单个 Promise 队列”造成退化。

### S2.2 接入提交事件

1. 在首次投递前按 S1.6 冻结原始命令基线，saveVendor/clearVendorKey 同一命令重试复用它；成功路径登记有证据的责任，不只在 `applied && changed` 的 loadCatalog 分支中登记。
2. 区分“接纳 auth 数据”与“知道某次提交已经发生”。按第 4.5 节先做提交去重、撤销/替代及已覆盖水位判断，再补登记仍有效的责任；不能把“同实体旧提交”无条件变成新需求。
3. 名称/空补丁成功只推进目标版本，不能清理未满足需求。
4. `refresh=false` 保留“由外层动作决定何时抓取”的含义；记录责任但不在 persistDraft 中立即启动与自身竞争的自动刷新。
5. addVendor、clearVendorKey、deleteVendor、reload/reset/dispose 复用同一事件入口，不能各自散落修改 Map。

### S2.3 统一刷新协调入口

1. Save 的自动刷新、fetchModels 的显式刷新和重试按钮都调用同一个协调入口；API 请求及现有目录合并仍由 loadCatalog/syncCatalog 执行。
2. 对相同 owner/entity/目标/需求合并请求。只有一个旧请求占槽时，新手动请求可用另一槽开始，不串行等旧请求；两槽均占用时按下一条及 S2.3a 有界排队/失败，不承诺绕过实际投递上限。
3. 每个 owner 最多保留两个尚未结束的模型刷新 HTTP 请求和一个最新排队目标；多次保存合并排队目标。refresh、后续目录读取和冲突对账的实际 HTTP 都经过同一投递约束，不能绕过限额。已超时但 transport 尚未结束的请求仍占用实际投递槽，见 S2.3a。
4. 两个实际槽都占用时，最新动作进入有截止时间、可取消的排队等待。槽结束后重新检查最新目标再投递；到期仍无槽则结束该动作的 busy，显示可重试失败并保留需求，不能无限等待，也不能假装完成。
5. 新目标可以替代旧运行的回写权限。旧 Promise 继续由自己的 finalizer 观察，不能因“过时”丢掉异常或提早宣称网络执行结束。
6. 每次真正发出请求前重新捕获 entityId、供应商 revision、需求序号和目录依赖代次。排队项不能沿用首轮快照。
7. 每个稳定目标最多执行一次请求，加至多一次完成冲突对账后的补发；同目标的终端失败不自动旋转重试。明确接纳的新提交产生新目标，使用新目标的预算，不能因前两个已过时目标耗完额度而拒绝有限保存序列的最终刷新。没有新提交或显式重试时，不能后台另开批次重置预算；真正耗尽的当前失败保留待刷新状态。
8. 每轮完成后的同一个检查/收尾段重新比较需求与最新目标；不留下“检查完没有后继→新需求到来→finally 清 active”丢唤醒窗口。
9. 只在 active 仍属于本运行时清理 active/busy。较早请求结束不能清除较新请求状态。

客户端观察结束、底层 transport 结束与后端业务结束是三个时点；任何一个都不能冒充另一个。SDK 当前只透传调用方 signal，没有可依赖的统一 deadline，必须由本次协调入口补齐下面的规则。

### S2.3a 有限等待、请求超时与晚到收尾

1. 先固定预算：排队等待上限 30,000ms；每次实际 HTTP 从投递到正文读取结束上限 30,000ms；一次稳定目标的动作总预算 90,000ms，包含排队、刷新、目录读取及至多一次冲突对账/补发。预算用单调时钟计算绝对截止时间，剩余时间取各预算最小值；补发或 finally 不重新开始同一动作的总预算。数值为本批默认值，实施若需调整，必须记录原因并同步测试，不靠扩大值消除死锁。
2. 每次请求持有自己的 AbortController，并组合请求 deadline、显式动作取消及 owner 生命周期取消。signal 通过 SDK 的 RequestOptions 传到 fetch；deadline 覆盖 response body 读取，不在收到 headers 时提前清掉 timer。只在模型刷新链路使用，不给 Save/清钥/删除的已接纳发布套相同取消规则，不修改 generated 客户端。
3. 超时/取消首先撤销本次请求的结果接纳资格，并结束对应动作的本地观察；所有 resolve/reject 分支仍由该请求的 completion observer 消费。当前目标超时可见、需求保留；旧目标超时不改新错误。timer、signal listener、busy 和排队唤醒各自仅由所属运行清理一次。
4. 标准 transport 响应 AbortSignal 后，只有其 Promise 实际结束才释放投递槽；释放后检查最新排队目标。如果注入/异常 transport 忽略 abort、Promise 永不结束，不能用 Promise.race 的观察超时伪造槽已释放：保留这两个实际槽，不继续无限投递。最新动作在自己的排队/总截止时间内明确失败，保留重试入口和需求。无法同时保证“不合作 transport 永不结束”“实际未结束请求不超过两个”和“第三次一定成功”，本方案选择有界失败，不声称第三次必定成功。
5. owner 销毁立即取消本 owner 的排队和结果写入权限，不等待不合作 transport 才销毁页面；未结束请求只保留消费晚到结果/异常所需的最小记录，不能保留可回写 store 的闭包或通过定时轮询反复抓取。底层结束时执行一次租约式槽清理；不终止共享 SDK/SSE。跨 owner 的后端终止仍不是本批保证。
6. 预算通过窄的时钟/定时器依赖进行受控测试；使用实际协调入口和 SDK signal 传递路径。测试可在独立作用域注入短预算，另断言生产默认值，不改共享全局时钟或生产超时。另用隔离 TCP 屏障验证标准 fetch 的取消与正文读取超时。不能只验证 Promise.race 返回，或靠固定 sleep 等足 30 秒。

### S2.4 正确处理冲突与错误

- 已知旧 owner/旧实体/被新目标替代的 REQUEST_CONFLICT：作为过时尝试处理，保留尚未满足需求并检查接续；不向当前动作投递旧错误。
- 当前目标返回冲突且本地没有可证明的新版本：只做一次只读 auth/catalog 对账；仍无法确定则结束自动尝试，显示重试/冲突，不重复提交配置。
- 当前上游失败、凭据失败或真正的最新冲突：按当前错误票据显示，保留待刷新责任；不能 catch 后标成功。
- 旧请求失败不得清新错误、覆盖新 notice 或触发旧 action 的 toast。只在协调入口消费明确过时的刷新错误，不改通用 fail 为吞错函数。
- 两种 catalog capability 路径都经同一责任规则；不能仅修 catalog-sync-v1 而破坏旧 candidates/managed 合并路径，也不能放宽现有编辑能力门禁。

### S2.5 完成判定

refresh 成功与目录合并都完成后，核对发出时身份、需求和当前代次。满足则提交本次完成水位；已有更新需求时只确认已完成部分，继续保留最新需求。合法空上游结果按成功处理，不能因模型数量为 0 无限抓取。

## 7. ACC-F02：确定项目写入语义（S3）

### 7.1 固定 API 语义

`PATCH /config` 仍为**当前实例目录的项目设置写入**，不是修改任意获胜来源的通用编辑器；全局设置继续走现有 global API，MCP 定向来源编辑继续走 MCP API。

保留 URL、payload 和成功正文 ConfigV1.Info。成功正文仍是 ACK，不把它冒充已经重新 GET 的合并快照。为错误增加稳定 typed contract，见第 10 节。

### 7.2 本地目标选择规则

从主加载器实际参与合并的有序来源描述中选择，不能再写一份手工优先级清单：

| 当前目录状态 | 写入目标/行为 |
| --- | --- |
| 当前目录只有 opencode.json | 修改该文件 |
| 当前目录只有 opencode.jsonc | 修改该文件并保留注释 |
| 当前目录两个文件共存 | 修改实际来源顺序中后参与的那个，不删除另一份 |
| 当前目录 .opencode 中有实际参与加载的 opencode.json/jsonc | 在当前目录拥有的候选中选择最后参与的文件；以加载器实序为准 |
| 只有父目录/全局配置 | 不写父目录或全局；新建当前目录 opencode.jsonc 作为本地覆盖 |
| 没有当前目录的有效配置文件 | 新建当前目录 opencode.jsonc；仍先做高优先级覆盖预检 |
| OPENCODE_CONFIG 指向外部文件 | 普通项目 PATCH 不修改外部文件；项目本地目标仍按上述规则选择 |
| OPENCODE_CONFIG 指向同一个本地候选且重复加载 | 使用实际最后参与位置，复用规范化文件身份，不重复创建目标 |
| OPENCODE_CONFIG_DIR/home .opencode/组织/环境/托管覆盖请求字段 | 不写这些非当前项目来源；按 7.3 预检决定拒绝或合法 no-op |
| OPENCODE_DISABLE_PROJECT_CONFIG 生效 | 拒绝项目写入，不能写一个加载器明确忽略的文件 |
| 候选损坏、拒绝读取、只读或实际指向项目域外 | 明确失败，不当作缺失，不改写另一份低优先级文件逃避失败 |
| 最终目标是运行时有效、raw 不能直接解析的变量模板 | 继续允许读取；L 上合法无写入 no-op 可成功，否则按 S4.2a 第 8 条返回 409 CONFIG_TEMPLATE_EDIT_UNSUPPORTED，不误报损坏或改写低优先级来源 |

“当前目录拥有”按当前 canonical 实例目录下的这四个逻辑候选限定：根 opencode.json/jsonc、其 .opencode/opencode.json/jsonc。文件或目录别名应解析并检查实际资源域；指向域外的文件符号链接不因逻辑路径在域内就获得写权限。目录大小写/junction 别名不能选择出两份不同目标。未迁移 legacy 协议按 S4.3a 拒绝不兼容的写入别名；规范化协议才承诺在支持的同域别名上成功互斥，不能把两者混成一个“别名通过”结果。

不改变父子项目、home .opencode、OPENCODE_CONFIG_DIR 的加载顺序；尤其不能假设 `.opencode` 在所有环境里都最后合并。配置 disabled 条件和路径判断直接复用主加载规则。

### 7.3 被更高来源覆盖时的行为

1. 在写入前，按目标文件原文补丁计算候选来源，再经与主加载器相同的合并/规范化规则预检。
2. 普通深度合并按请求实际修改的叶字段判断，不能因另一个来源只有 sibling 字段就拒绝整个对象。数组及 image_generation 等特定字段沿用已有领域语义，不能统一当作对象逐叶拆分。
3. 若请求要求改变的值被后续来源确定覆盖，返回 409 CONFIG_SOURCE_OVERRIDDEN，目标和其他文件均不写。
4. 如果请求值已在当前有效快照中满足、且不需要改变本地源，允许明确的无写入 no-op ACK；不提升文件版本、不触发一次虚假提交。
5. 不能证明来源有效性、缺少必要快照或解码失败时明确失败，不能猜测已生效。来源诊断只列字段路径、来源类别和 ref，不泄露配置原文/引用展开值。
6. 验收时以相同来源快照的领域语义为准：例如 instructions 的继承拼接不能误报成“PATCH [] 应清掉所有父配置”。不支持的跨来源删除必须在提交前拒绝或明确保持既有 API 语义，不能静默成功。

这项预检保障已观察来源快照下的写入含义；外部不合作进程或远程组织配置在提交后再变化，仍可能改变有效值。本批不宣称通过普通本地锁解决任意外部来源的原子快照问题。

## 8. ACC-F02：共享来源与原文写入（S4）

### S4.1 先建规则测试

新增 `test/config/project-write-target.test.ts`（名称可在实施时固定），按第 7 节逐格断言固定文件名及修改范围。预期来自方案规则，不调用生产 target selector 计算 expected。

补上项目 PATCH→GET、清理重建→GET 的红测试，并记录失败。不能只换 config.json 这个字符串便跳过来源矩阵。

### S4.2 让加载器提供足够的描述

1. 来源枚举、读取和覆盖顺序共用实现。正常加载与只读预检使用同一顺序，不再扩大同步 discover 的独立规则。
2. 内部来源快照至少包含：逻辑来源、实际文件身份、合并位置、未展开原文/摘要、存在性、归属、读写限制、捕获时的上下文/环境代次。
3. 现有 sources 的 contributed 主要记录 MCP 名称，且全局来源有聚合步骤；**不能直接把它当成所有配置字段的完整 provenance**。补齐所需描述，或提取窄的共享来源快照步骤。
4. 重复文件按实际参与位置处理；不要用 Set 提前去重后改变合并含义。
5. 只读预检不运行插件、不安装依赖、不注解 schema、不初始化缺省文件、不做 TOML 写迁移、不 dispose 实例。
6. 持久化文档和来源记录始终保留 `{env:...}`、`{file:...}` 原文；语义校验使用 S4.2a 的临时展开投影。展开值不能流入待写文档、摘要日志、来源接口或公开错误。不能把“只读”解释成跳过运行时变量展开。
7. 远程来源预取和必要解码在持有本地写锁前完成；锁内只验证快照仍属于当前已观察代次，不在文件锁里等待外部 HTTP。
8. 将快照用途命名区分：P 是锁前只读预检，D 是取得选择锁后对候选集合/身份的决策观察，L 是全部必要租约取得后构造的最终写入基线。P 不提前冻结本地 before/text；进入 L 前不生成待发布补丁。后续比较不得把 P 的“缺失”当作并行首次保存的永久前置条件，详见 S4.3c。

### S4.2a 原文、临时展开投影与引用依赖

当前 loadConfig(readOnly=true) 直接解码原文，跳过 ConfigVariable.substitute；它可用于部分原文读取，不能直接当作本方案与运行时等价的有效性预检。本批提取共享的无写入解析/展开/解码步骤供加载器和预检使用，不改变现有替换、相对路径及缺失值语义，也不借预检运行插件或安装依赖。

1. 为每个来源分开管理 raw 与 effective：raw 是原 JSONC 文本与待写补丁的唯一基础；effective 是局部作用域内经现有变量替换、兼容转换和 Schema 解码后的临时值，只用于共享来源合并、覆盖判断及 no-op。二者不能互相覆盖，不能把 effective 送回 patchJsonc/publish 或来源接口；作用域结束不在缓存或失败记录中保留展开明文。
2. 展开上下文逐来源固定：本地引用相对该来源文件所在目录，虚拟/远程来源使用主加载器原有 dir/env；沿用现有 env 缺失、file 缺失、注释和转义行为，不另实现一套替换算法。引用错误按安全类别映射 CONFIG_DOCUMENT_INVALID 或明确的 CONFIG_SOURCE_READ_FAILED，生成 ref；响应/日志不带替换后文本、引用内容、原始 cause 或完整路径。配置自身语法损坏与依赖拒读分别取证。
3. P 中读取既有来源的引用，并记录必要的本地引用文件身份/存在性、私有版本指纹和实际使用的环境依赖；指纹不得出作用域或进入日志，避免用可猜测凭据摘要作诊断。环境不能只比较 OPENCODE_CONFIG_CONTENT/CONFIG 路由值，应覆盖本次实际使用的 env 输入。远程获取及用于远程认证的必要展开在本地锁前完成；锁内不发外部 HTTP。
4. 在 L 上首次生成补丁后，对候选 raw 再做完整展开与解码，必须包含本次新增加/改变的 file/env 引用，不能只验证旧来源。本地文件读取允许在文档租约内按现有本地读取路径完成，不为引用文件追加任意反向锁；引用若对应受本锁组保护的文档，读取适用于发布后候选状态的原文：未改文档使用 L，目标文档使用候选 raw。通过共享替换步骤的窄只读输入适配实现，不增加递归展开语义；无法可靠模拟的自引用/循环或候选依赖须在提交前明确 CONFIG_PATCH_INVALID，不能用磁盘旧文模拟发布后读取。若本次补丁使远程来源发现或认证依赖必须重新发 HTTP，提交前明确 CONFIG_SOURCE_CHANGED，释放租约且不自动重放；重新发起的明确动作重新预取。
5. P 捕获的外部引用依赖与环境，及 L 新捕获的候选依赖，在发布准入前按各自基线复检。确定变化返回 CONFIG_SOURCE_CHANGED，明确损坏/缺失/拒读按类别失败；不以重新展开并静默吸收依赖变化来“修复”已冻结的补丁。P 到 L 的合法本地文档更新仍遵守 S4.3c，不能被依赖规则一概拒绝。未经共同锁保护的文件、进程环境和远程来源仍有最后检查后的变化窗口，本批只保证已观察快照，不能声称普通锁消除全部外部竞态。
6. 运行时有效性严格沿用“共享变量替换→JSONC 解析→兼容转换/Schema 解码”，不能先要求 raw 是合法 JSONC。例如 raw 为 `{"autoupdate": {env:AUTO_UPDATE}}`、变量为 `true` 时属于可读取的有效模板，不得报 CONFIG_DOCUMENT_INVALID。raw 的语法检查仅用于判断现有无损补丁器能否编辑；覆盖/no-op 比较 effective 的共享领域语义，不直接比较 token 字符串。库错误只提取安全类别，不输出可能带输入片段的整个错误。
7. F35 覆盖旧来源和补丁新引用：成功引用原样落盘；缺失/拒读/展开后无效在提交前拒绝；高优先级引用与请求值相等/不等；同 token 不同来源目录；引用目标文档的发布后候选与无法模拟的自引用拒绝；P/L 后引用或 env 变化；远程重新取数需求；另以未加引号的布尔值/对象模板覆盖有效读取、非目标继承、明确的无写入 no-op、目标编辑 409 和真正无效模板 400；每支核对磁盘、重建 GET、无明文泄露。原 F11 只证明“不复制明文”，不能替代这些有效性测试。
8. 本批选定的模板编辑边界：不新增 token 感知的无损模板编辑器。最终 L 上目标 raw 可由现有 JSONC 补丁器解析时，按原文补丁、再展开验证；若 raw 不能直接解析但 effective 有效（如未加引号的 env 布尔值/对象片段），该文件继续可读，也可以作为非目标继承来源。若请求已按领域语义完全满足且不需改本地源，可在 L 确认后返回无写入 no-op；否则目标需要编辑时返回 409 CONFIG_TEMPLATE_EDIT_UNSUPPORTED，不写磁盘、不转写其他候选，不把展开值格式化回原文，也不自动给变量加引号。effective 本身无效才按既有损坏/依赖错误分类。P 的语义预检不能因这种有效模板先失败；编辑能力只在 L 最终目标冻结后决定。新增目标和可直接解析的 raw 不受该限制；公开提示只说明需先将目标整理为可无损编辑的形式，不输出模板正文或变量值。

### S4.3 目标选择与文档锁的顺序

1. 先按当前实例目录取得稳定的项目目标选择锁，使同时首次保存不能各选不同目标。锁前 P 仅作预检；取得选择锁后才捕获 D，不沿用其他请求提交前的候选集合。
2. 选择锁只用于目标决策和发布协调。实现复用现有 Flock/ConfigDocument 资源根与协议，内部锁键不得与任何实际目标文档键相同，避免再次取到自己持有的锁。
3. 根据 D 中当前目录四个候选（含尚不存在的默认目标）解析协议及最终协调身份，按 S4.3a 去重后稳定排序获取必要租约。再核对 D 的候选存在性/物理身份/参与结构，读取最新原文构造 L，在 L 上冻结目标并首次生成补丁。与 MCP/其他已接入写入者继续共用 ConfigDocument 的真实文档键；来源参与记录不随租约去重而删除。
4. 锁序固定为“项目选择锁→排序后的文档锁”。加载器可选注解仍 tryWithLock，不在锁内调用会重新获取同文档锁的完整初始化。
5. D 到锁集取得期间的候选增加/删除、物理身份或参与结构变化，及 L 冻结后的原文/来源/目录/环境变化，在发布前返回冲突；释放整组，不自动选另一文件。P 到 D/L 之前合作写入者已完成的本地原文变化按 S4.3c 进入初始基线，不一概判为冲突；非本地快照变化仍遵循已声明复检边界。
6. 其他必要高优先级来源以捕获的摘要/身份和当前已观察环境代次复检。未遵守相同锁的外部写入仍是检测边界，不承诺完全消除 pathname race。
7. 锁等待和准备阶段响应取消，发布准入后由 InstanceWork 保留责任直到真实结束。必须落实 S4.3b 的阶段信号与原子准入，不能仅在旧 mutate(body) 外取消 HTTP 等待者。
8. 取得发布结果后按作用域释放选择/文档锁；完整 handoff 与实例 dispose 在服务层异步接续。不能持锁等待会反过来排空当前 mutation 的实例关闭，也不能在当前有限任务内等待自己的 drain。

选择锁的最终键与多锁 API 实施前必须画出与 MCP、schema 注解、全局保存的获取图。若形成反向锁序，先改为准备/验证分段，不能靠更长 timeout 通过测试。本步骤不启用 path-identity 标记或迁移 apply，也不声称关闭 R3-03B。

### S4.3a 最终锁身份去重与 legacy 兼容门禁

1. 严格区分两个集合：来源序列按主加载器的实际参与位置保留重复记录；租约集合按当前协议解析后的协调身份去重。协调身份至少包含 backend、锁所在 coordination directory/资源根、协议 epoch（如有）及最终 key，不能仅按 basename、logical path 或最终 key 字符串跨资源根合并。候选到租约的映射仍保留，方便逐候选复检。
2. 规范化协议下，两候选解析到同一协调身份时只 acquire 一次、release 一次；项目选择锁是独立 namespace，不得与任一文档租约相同。排序以最终协调身份确定，不以未规范化路径排序。取得后复检协议/根/epoch 与物理文件身份，发现变化则释放整组并返回冲突，不带着旧租约换目标或换协议。
3. legacy 无标记根保持原始 ConfigDocument 键和旧目录锁，不能只把本 writer 改为 realpath 哈希。采用明确的兼容限制：所有本版本 ConfigDocument 必写入口，在创建业务锁前比较原键与规范文件键；已有文件用最终路径，未存在文件用最近已有祖先最终路径接上剩余部分，路径文本统一使用同一 ConfigDocument.key 格式。原键与规范键不一致（包括大小写、junction、目录/文件符号链接别名）时拒绝该写入，提示从规范项目路径重开，不偷偷换键或另写文件。保留路由/调用方原始路径至门禁比较，不能先替换成 canonical 再把本来不兼容的旧路径误判为安全。正常规范路径仍使用原来的键，测试须证明历史哈希不变。
4. 上条门禁必须在共享 ConfigDocument 入口同时覆盖 project PATCH、MCP 定向编辑、global 写入、ImageGenerationSettings.update 及 schema 可选注解。必写调用方将窄的别名拒绝映射为可诊断 typed 错误；可选 schema 注解跳过该可选写入，不使正常读取失败。任何必写调用方不得 catch 后当作保存成功、直接写文件或退回另一把锁。项目 API 新增 409 CONFIG_PATH_ALIAS_UNSUPPORTED；MCP 必写路径新增 409 MCP_SOURCE_ALIAS_UNSUPPORTED，纳入公开声明/生成。其他调用方按其现有领域错误通道传播，不增加任意 cause 文本。
5. 实施前盘点所有 ConfigDocument 调用方和绕过它的同文档写入者，逐项标记已保护/只读/不合作。若存在同版本仍允许别名写入的必写入口，不得关闭 F29；不能只在 PATCH selector 拒绝别名然后宣称与 MCP 互斥。旧版本和外部直接写入者不受新门禁约束，仍是 R3-03B/外部写入边界，本批不承诺约束它们。
6. 域外链接先按 CONFIG_TARGET_OUTSIDE_PROJECT 拒绝；同域但 legacy 别名再按上述限制拒绝。规范化协议允许的同域别名需分别测试候选合并顺序与物理租约去重。硬链接继续服从 AtomicDocument 的现有限制，不列为应成功样本。
7. 多锁获取采用单一作用域：第 N 把获取失败/取消时逆序释放前 N-1 把；租约所有权移交按 S4.3b 执行。最终身份计算不暴露底层 token，不加载未选中的 native 后端，不写协议标记；如现有公开接口只返回 key，增加窄的只读协调描述，不能假定 key 已唯一代表资源根。

### S4.3b 任务登记、准备取消与发布准入

现状约束：Config.mutate 将整个 body 交给 InstanceWork.run，后者登记后用独立 runPromiseExit 执行；HTTP 等待者取消不会取消该 body。因此只对旧调用加 timeout/取消等待不能实现本方案。

1. 为项目写入新增窄的两阶段任务入口，沿用 InstanceWork 的 owner/WorkPermit、任务登记及 drain；普通 run() 和其他 mutation 的既有语义不全局改变。请求在投递准备任务前登记 completion，使服务关闭能观察仍在等锁或清理的任务，不能将“准入前完全不登记”作为取消修复。
2. 请求入口捕获真实断连/取消信号并传给准备阶段的专用控制器；实例退出可停止尚未准入的准备工作。准备包含快照校验、选择/文档锁等待、锁内重读和补丁预检。取消要真正通知这段任务，不能只让 HTTP waiter 返回。已经开始的底层不可取消操作必须结束并收尾后才完成任务记录。
3. 全部租约取得、最后只读复检通过后，在同一个不可中断的短临界区检查取消状态和 owner 是否仍允许准入，再将 phase 从 preparing 原子转为 admitted，并移交租约清理责任给已登记任务。此处为本批“已接纳发布”边界；尚未调用 publish 也可能属于已接纳工作。取消先赢则不调用 publish，释放所有已到租约；准入先赢则任务负责继续发布或明确拒绝。
4. acquire 完成与取消同时发生时，晚到租约必须被准备任务/finalizer 接住；不能先结束 scope 再把无人负责的租约交给已退出调用者。任务登记、租约移交和 cleanup owner 各至多一次；不在两个作用域同时注册同一 release。
5. admitted 后撤销请求取消对发布阶段的传播；发布本身的真实失败仍按 AtomicDocument 分类。请求断连只结束 HTTP 观察，不中断实际发布、onCommitted、服务层 ensuring 或 handoff。mutation 的 committed 标记在真正 onCommitted 时设置，不在准入时设置。
6. preparing 取消：无 publish、无 onCommitted、无提交通知；清理完成后从 tasks 移除。admitted 后取消：有且仅有一次实际执行尝试，按真实提交结果通知，不重放；drain 等其真实任务与租约清理结束。handoff 不在当前任务内等待自身 drain，释放租约后单独登记并接续。
7. 用阶段 Deferred 精确控制：等待选择锁、等待第 N 把锁、最后校验、准入临界区、publish 进入、onCommitted、释放完成、handoff。测试同时覆盖取消先赢、准入先赢、晚到 acquire 和服务关闭，不以“客户端 socket 已关”冒充任务已取消或已收尾。

### S4.3c 锁内基线与并行首次保存

1. 锁前 P 只用于无副作用拒绝、准备远程原文和环境描述，不是客户端提交的 expectedVersion。取得项目选择锁后捕获 D；若前一保存已完成，新创建的本地候选自然进入本次 D，不能因它在 P 中缺失就拒绝。此时尚未冻结目标，也没有重放一次已尝试的发布。
2. 按 D 解析/去重/排序取得全部文档租约后，比较存在性、物理身份和合并参与结构是否仍匹配 D。匹配后用锁内最新原文构造 L，并以共享来源顺序首次确定最终目标、生成补丁和做覆盖预检。D 到 L 期间合作写入者只改变同一文件内容时，在生成补丁前读取该内容进入 L；不带着 D/P 的旧 text 覆盖它。若身份/候选结构已变化，返回 CONFIG_SOURCE_CHANGED，不在本轮重选或循环获取另一组锁。
3. L 中受锁保护的同一物理本地文件，必须替换来源链中它的所有实际参与位置，包括 OPENCODE_CONFIG 重复加载，保留各位置和覆盖顺序。不存在的默认目标，其假想加入位置也用共享加载规则推导。不得把最新目标原文与其他位置缓存的同文件旧原文混合后误判有效值。
4. P 捕获而未被本地锁覆盖的父/全局/组织/环境来源仍须按现有摘要/身份/代次复检；不能借“重建本地基线”静默接受它们已变化，也不能在持锁期间重新等待远程 HTTP。外部不合作写入检测边界不扩大。
5. L 冻结以后不再吸收新写入、自动重选或重放补丁；AtomicDocument.before 与 L 的原文一致，后续变化按 typed 冲突/真实发布阶段处理。空补丁/no-op 也在 L 计算，不能只看 P 的有效值提前 ACK。
6. 并发验收分两条：owner 仍允许准入且没有 D/L 冻结后结构变化时，先后取得锁的非冲突补丁基于各自 L 合并，两个已接纳提交都保留；若后请求尚未 admitted 就遇到实例换代/关闭，或 D/L 后来源冲突，则明确拒绝，不以成功 ACK 吞掉补丁。请求仍连接时，已知上下文前置条件变化映射 409 CONFIG_SOURCE_CHANGED；请求已断连则保持取消。两种拒绝均无发布/通知，不自动重试 PATCH。
7. F04 不再要求所有重叠请求无条件 200。分别用 handoff 阶段屏障验证“可接纳的两个提交均保留”，再用真实实例关闭/换代验证“未准入者明确拒绝”。记录实际 ACK、准入次数、磁盘、通知和重建 GET；不能只留一种通过路径。此调整不放宽任何已返回成功后的 GET/磁盘一致性断言。

### S4.4 只写目标原文加本次补丁

1. 锁内读取目标未展开原文，完整有效性按 S4.2a 的“替换→解析→解码”验证；另判断 raw 是否可被无损补丁器编辑。有效模板但 raw 不可直接解析时，按 S4.2a 第 8 条区分合法 no-op 与 typed 409 编辑限制，不误报损坏；真正坏文件保留原字节，不能直接对引用 token 作运行时枚举/有效值判断。
2. 复用 writable 对补丁去除运行时 origin 等不可写字段，不把 config.get() 合并结果作为原文基础。
3. JSONC 用已有 patchJsonc/edit 机制保留注释与未编辑节点；JSON 可以按现有规则格式化，但不能附带继承字段或凭据明文。
4. 新建目标只包含必要 schema 和本次补丁，不复制整个父目录、全局或组织配置。
5. 对候选 raw 按 S4.2a 展开/解码并执行来源覆盖预检与依赖复检，包含补丁新引用；确定无写入 no-op 时不调用 publish。展开结果不得进入发布文本。
6. 调用现有 AtomicDocument.publish，传入实际 before/text/onCommitted；保留临时写入、fsync、读回、身份/版本复检、首次 no-replace 及 Windows ACL 等保护。
7. 发布成功以 onCommitted 标记的真实时点为准。准备/发布未知错误沿用其未提交/未知分类，不降级为直接 writeFile 或 unlink 后重建。

### S4.5 提交、刷新与取消

1. 按 S4.3b 调整项目写入的 mutate/InstanceWork 接入，保留服务层 committed ensuring 和 handoff；不能原样包住整个 body 后声称准备可取消，也不能把刷新责任搬回 HTTP pre-response 或 handler 的正常 return 路径。
2. 项目 PATCH 的 200 表示请求成功处理，分为实际写入与合法 no-op。实际写入必须有 AtomicDocument/onCommitted 的提交证据，再核对 ACK、磁盘、完整 handoff 和重建 GET；合法 no-op 在 L 上确认请求已满足且不需改变本地源，不调用 publish/onCommitted，不递增文件/配置版本，不新增提交通知或 handoff，并释放本次预留。no-op 不清除其他提交已有的未恢复收尾责任。响应正文保持现有 ConfigV1.Info，不新增 committed/noOp 字段，也不靠猜测正文区分提交。
3. 发布前确定失败：无 onCommitted、原字节不变、无提交型通知，原实例仍可读。
4. 准备任务已投递但尚未 admitted 时断连：取消准备并清理，不发布。已经 admitted 后断连：真实任务继续完成或拒绝；至多一次发布尝试，不能为补偿回包再执行一次。两条路径分别留证。
5. 已提交后断连/编码失败：仍履行 handoff，清理结束后下一次 GET 读取新目标。
6. 已提交但 handoff 失败：按 S4.5a 登记可观察的收尾责任、有限安全重试和终态 ref；不回滚磁盘、不把 Save 当未提交重放。HTTP 语义沿用真实已提交结果，不能临时加一个与成功形状不兼容的响应。
7. 提交结果未知：保留当前隔离/阻止重放机制；测试不能通过自动第二次 PATCH 来消除未知。跨进程持久化恢复不是本批已实现能力。
8. 可见性契约不扩大：200 ACK 本身只证明成功处理，不能单独证明发生了发布；实际写入分支以真实提交证据确认发布，no-op 分支必须证明零发布。实际写入的 ACK 不保证异步 handoff 已全部结束，立即 GET 在 handoff 未结束时可能仍读缓存，不能拿该读取关闭验收。测试须暂停真实写入的 handoff 并记录窗口，确认 handoff 完成后下一次 GET 和重建 GET 都是新值；no-op 则核对原字节/身份、零新增提交及锁内已满足的领域语义。实际调用方接续现有配置失效/读取流程，不仅凭 200 计一次新提交，不自动重放 PATCH；不新增未定义的“刷新已完成”成功字段。若产品要求 ACK 即具备读后写一致性，另行调整不自等待的失效顺序和契约后才能宣称保证。

### S4.5a handoff 失败登记、有限恢复与关闭

现有 InstanceWork.handoff 仅在成功时从 handoffs 删除 Promise；失败 Promise 留在集合，drainAll 的 Promise.all 会再次拒绝。这是活动任务与失败责任混在一起，不以 catch(() => undefined) 掩盖，也不能仅删除失败 Promise 而丢掉配置收尾。

1. 活动集合只记录真正尚未结束的执行，两种结果都在唯一 settle 入口移除；任何 handoff 失败都必须先同步登记到共享安全失败汇总，再移除活动项和向调用方交付拒绝，不能依赖调用方 catch 负责登记。本批项目配置独立的收尾记录保存安全 owner/目录域内部身份、提交水位、步骤、尝试次数、状态和 ref，不保存配置原文或凭据。mutation 的 ensuring 在退出任务登记前同步登记该收尾责任，再异步调度，关闭不能落在“mutation 已移除而 handoff 未登记”的空窗。共享 handoff 的 Promise 仍把真实失败交给原调用方，活动集合移除不等于失败已恢复。全局/MCP/其他调用方同样进入共享失败汇总，即使现有调用处 catch(() => undefined)，失败仍可在诊断/关闭时观察；它们不自动纳入项目 PATCH 的重试或准入容量策略，不重写其公开响应。
2. 配置收尾按步骤管理：全局/当前实例缓存失效、实例重建协调、逐个已登记 reload hook。本批先盘点各步骤是否幂等；仅已证明幂等的失效/协调步骤允许自动重试。无幂等证明的任意 hook 失败记为 terminal-failed，不自动重放整个 hooks 列表；成功 hook 不因另一 hook 失败再执行。不能把插件副作用、PATCH、凭据写入或 publish 纳入收尾重试。
3. 每个可重试步骤默认最多两次实际执行（首次加一次自动重试），自动重试退避 250ms；窄的时钟/调度依赖可在测试中注入，生产值单独断言。重试前核对 owner 生命周期、资源域及目标水位；不能复用已经关闭的 ctx/WorkPermit。若较新已确认失效已完整覆盖旧水位，可合并为 covered，须有同域/同作用的证据；不能仅凭“有更新版本”抹掉未完成 hook。
4. service accepting 时按以上预算接续；关闭开始后不新增独立重试批次，取消尚未投递的退避并记为未恢复，允许已投递的安全收尾真实结束。不得为了补 hook 启动新业务实例、绕过 closing 门禁，或在当前 mutation/handoff 内等待它自己的 drain。退出完成只说明实际工作已排空；terminal-failed/未恢复记录仍以安全汇总和 ref 报告，不能写成配置已全部刷新。
5. drainAll 等待实际活动使用 allSettled/等价逐项收集，先排空其他 owner 和已登记实际收尾，再联合全部 handoff 调用方的未恢复失败汇总报告聚合失败；关闭前已结束并从活动集合移除的失败也必须包含，不能仅统计本轮 allSettled 的拒绝。失败 Promise 不得残留活动集合造成每轮再次等待或循环；重复关闭可报告仍未恢复的失败，但不得再次执行 handoff。保留现有 10 秒外层关闭观察预算，不扩大预算、不用超时假称底层已停止。若真实任务尚未结束则保留其观察与责任并报告未排空；退避/失败记录本身不是永不结束的活动任务。
6. 收尾记录按实例/配置域及步骤合并，仅保留各域未恢复责任和最后必要诊断；S0 固定容量（默认 1024 个域/步骤记录）并验证满载策略。不能淘汰仍未恢复记录后报告健康：容量不足时在本批项目 PATCH 的新 mutation admitted 前返回 503 CONFIG_REFRESH_CAPACITY_EXHAUSTED，已有 admitted 提交预留记录名额，其 ensuring 登记不能失败；全局/MCP 等其他 mutation 不顺带改变其公开语义。冻结本次 hooks 清单与准入容量，no-op/确定未提交时释放预留，已提交收尾不能再因容量而丢失。成功/covered 后释放名额；报告只含计数、阶段和 ref。服务内存记录不承诺跨进程持久化，重启通过正常冷加载重建有效配置，历史收尾证据留在隔离验收日志。
7. F36 分别验证：失效首次失败后安全恢复；非幂等 hook 失败不重放；一个 hook 成功而另一个失败；全部失败/预算耗尽；新旧水位覆盖；关闭发生在登记、退避、实际执行期间；另一个 owner 仍能排空；容量预留与拒绝；全局/MCP/一般 handoff 失败发生在 drainAll 之前且被调用方 catch、失败与关闭同轮发生、共享诊断溢出后仍报告失败。每支确认 publish/配置 revision 不再次增加、ACK 语义不回退、真实活动集合最终清空或准确报告仍运行、未恢复 ref 保留；故障解除并完成有效失效后 GET/重建 GET 一致。不能用“已删除失败 Promise”代替恢复证明。
8. 共享失败汇总与项目可恢复记录分开：前者覆盖所有 handoff，默认仅保留最近 1024 个安全诊断条目（类别、来源枚举、阶段、ref），不保留原 Error/Cause、任务闭包、ctx 或配置内容；另有未恢复失败计数及溢出标志，计数饱和也保持失败状态。诊断条目淘汰不得清零失败状态，不能因为集合为空或后续无关成功就报告健康；一般调用方的失败只做记录与报告，不自动重试，不因诊断容量拒绝全局/MCP 写入。项目收尾只有同一责任的成功/covered 证据才可标记其失败已恢复，历史失败计数与当前未恢复状态分开；无法逐条确认的溢出失败维持未恢复，不能猜测恢复。重启后内存汇总重新开始不等于历史失败已恢复，证据报告仍保留。新 Promise 继续只代表真实任务，汇总记录不得伪装为活动任务阻止排空。

## 9. 旧 config.json 保存内容的处理（S5）

修复新写入目标，不等于此前误写的数据已恢复。两者分别记状态。

本批默认规则：

1. 普通 GET/PATCH 不自动加载、导入、重命名或删除项目 config.json；它可能属于其他程序，不能凭文件名或一个 schema 字段认定所有权。
2. 新正确保存不修改旧 config.json，也不复制其内容到备份。它保持原位是保留既有文件，不是新增备份。
3. 增加/记录一个明确的人工恢复流程：用户选定源、目标及字段；只读解析原文，显示安全字段列表与两边版本；不展开引用，不显示凭据内容。
4. 实际导入必须由单独明确动作触发，并携带源摘要和目标版本；重复执行同一计划无二次副作用，版本变更则重新规划。没有来源确认不得自动合并。
5. 导入走同一目标解析、Schema 校验、ConfigDocument 锁、AtomicDocument 提交与刷新；保留合法目标既有字段，只应用明确选择的补丁。原源文件不自动删除。
6. 如本批不实现该显式导入入口，结果必须写“新保存闭环修复，历史误写内容待人工恢复”，不能写“历史数据已全部恢复”。不要在文档中给出尚未实现的 CLI 命令让用户执行。

这项历史恢复不是将 F02 主修复推迟的理由，但必须作为独立交付/未完成项跟踪。

## 10. 错误协议与生成客户端（S6）

当前 PATCH /config 只声明 BadRequest，不能为了处理新边界统一 Effect.die 或复用 MCP 专用 code。

新增窄的 ConfigWriteError 领域错误，在 PATCH 专用入口与稳定 HttpApi handler 装配中分阶段映射；领域服务不得依赖 HttpApi 类。handler 只能看到进入它之后的错误，首次引导错误必须按 S6.1 在 middleware 边界处理。固定以下 code/ref 协议：

| HTTP | code | 文件结果 |
| --- | --- | --- |
| 400 | CONFIG_DOCUMENT_INVALID / CONFIG_PATCH_INVALID | 未提交；坏原文与请求不落盘 |
| 403 | CONFIG_PROJECT_DISABLED / CONFIG_SOURCE_READ_ONLY / CONFIG_TARGET_OUTSIDE_PROJECT | 未提交；不改用别处写入 |
| 409 | CONFIG_SOURCE_CHANGED / CONFIG_SOURCE_OVERRIDDEN / CONFIG_PATH_ALIAS_UNSUPPORTED / CONFIG_TEMPLATE_EDIT_UNSUPPORTED | 未提交；不自动重放补丁；分别说明来源、别名或模板编辑限制，不输出原文 |
| 503 | CONFIG_SOURCE_READ_FAILED / CONFIG_LOCK_TIMEOUT / CONFIG_WRITE_FAILED / CONFIG_REFRESH_CAPACITY_EXHAUSTED | 确定未提交；容量拒绝发生在项目写入准入前，按真实阶段映射 |
| 503 | CONFIG_COMMIT_UNKNOWN | 结果未知；禁止自动重试 PATCH，保留现有对账责任 |

HTTP 类可按状态共用 code union，但 code 不得含任意 cause 文本。ref 为诊断编号，响应不包含配置原文、密钥、完整源路径或替换脚本。不要把已提交后的刷新失败映射为表中的未提交错误。

实施步骤：

1. 给 Config.update 的公开服务错误类型增加上述领域错误，不扩大成 unknown，也不扩大会话错误联合。
2. groups/config.ts 声明各错误；保留现有请求解码 BadRequest 行为。
3. 按 S6.1 接入 PATCH 专用预检/实例上下文层，分别映射 handler 前后错误；稳定服务仍在 builder 中构建。认证、代理、workspace/directory 路由归属保持；共享 MCP/GET middleware 的既有错误协议不被整体改写。
4. 增加真实 HTTP 状态、code/ref、不泄密与无写入测试，分别覆盖冷实例的 handler 前失败、已有实例的 handler 内失败及运行中目标变化；记录预检、store.load 和 handler 是否进入。
5. 在 packages/client 执行 `bun run generate`；再从仓库根执行 `bun ./packages/sdk/js/script/build.ts` 生成旧 SDK。即使某一客户端不包含该路由也记录生成结果，不手改生成文件。
6. 检查 ConfigUpdate 及新增 MCP 别名错误的生成映射、所有调用方是否有自动重试。对 unknown/冲突不自动重放 PATCH；只读 GET 对账可以重试。任何新增 global 必写错误如进入公开契约也必须声明和生成，不把 shared ConfigDocument 的 typed 失败变成未声明空 500。

### S6.1 PATCH 专用预检与首次引导责任

1. 当前 PATCH 使用 InstanceContextMiddleware，它先 store.load 再进入 handler；损坏/拒读会直接响应 MCP_*。本批给项目 PATCH 接入专用的上下文准备层（可扩展现有 ConfigWriteContextMiddleware，但不得影响现有 MCP 使用者），复用认证和 WorkspaceRouteContext，不能只改 handlers/config.ts 的 mapError。
2. 在完整 store.load/插件/依赖引导之前，先按共享来源步骤运行无写入预检：解码路由目录、项目 disabled、资源域/legacy 别名限制、发现/读取/校验来源及目标和明显的权限限制。此 middleware 不自行读取/消耗请求 body；payload 保留 HttpApi 原有单次解码和 BadRequest 行为，依赖补丁内容的检查在 handler 取得已解码值后、准入前执行。预检只构建来源快照，不安装依赖、运行插件、初始化文件、schema 注解、TOML 写迁移或 dispose。预检失败不进入 store.load/handler，不留业务临时文件或提交通知；环境/远程解码也走同样安全错误分类。
3. 预检成功后才进入实际服务上下文准备，沿用稳定 builder 服务。由本 PATCH 启动的引导必须设置 ConfigLoaderWrites=false，抑制已受该开关保护的 schema 注解/缺省文件/TOML 写迁移；普通 GET 等其他入口的默认行为不全局改变。禁止把此开关当作整个引导无副作用的证明：插件、安装等不自动受它约束，P 本身必须复用真正只读步骤。
4. 对预检以后、handler 之前发生的 store.load typed 失败或包裹在 Cause 中的已知配置错误，在 PATCH 专用边界映射 CONFIG_DOCUMENT_INVALID/CONFIG_SOURCE_READ_FAILED 等已声明类型，并生成新的 ref。只匹配明确错误类别；未知 defect 不猜测成“未提交写失败”，也不序列化任意 cause。中断保持中断，不映射为损坏文档。
5. 进入 handler 后的 ConfigWriteError 使用同一领域到 HTTP 映射，避免两张状态表漂移；此映射不接受整份配置作为响应上下文。共享 GET/MCP 仍保留其既有声明；不得把 respondInstanceLoad 的 MCP code 无条件全局替换成 CONFIG code。
6. 冷态测试用全新目录/实例 owner，分别验证坏 JSONC、明确 EACCES/EPERM、项目 disabled、域外及 legacy 别名拒绝，不能用热缓存代替。额外在成功预检后制造读取失败/源变化，证明引导边界和锁内复检均能拒绝。调用 observer 只记录阶段和 ref，不输出配置原文；权限夹具继续遵守原有恢复责任，未实测平台登记 skip/未执行。
7. 引导完成不沿用 P 作为写入 before。按 S4.3c 重新进入 D/L；若已有其他入口启动了共享引导，它造成的、在 D/L 前已完成的合法本地 schema 注解属于最新初始原文，不误报本请求自冲突。D/L 后变化仍拒绝；损坏、域外、权限错误和非本地来源变化不能用重建基线掩盖。服务上下文与快照所属 owner/环境必须匹配，不能用新 owner 执行旧草稿任务。
8. 增加无 $schema 的有效 JSON/JSONC、缺失默认目标和既有共享引导三类冷态样本。在 owner 可准入、非本地来源未变且 D/L 后无身份冲突的样本中，正式 TCP 第一次 PATCH 就成功并读回，不靠第二次 PATCH；共享引导样本限定为 D 前完成的合法本地可选注解，不把真实非本地来源变化混进应成功样本。证明本 PATCH 的 bootstrap 未先发布 schema/缺省文件，真正提交次数和通知符合请求。最终补丁是否包含新文件必需 schema 按 S4.4 区分，不把真实发布时包含 schema 当成引导写入。

### S6.2 Relay 提交版本语义与生成检查

1. 本节与 PATCH /config 的 CONFIG_* 错误协议分开。新增 vendor-commit-baseline-v1 的承诺按 S1.6 和第 4.8 节固定，仅在后端各成功/失败/精确清理回放分支的契约证明后声明；不得给已有 vendor-entity-v1 或 vendor-create-receipt-v1 偷换含义。同编号不同命令的 REQUEST_CONFLICT 属于有意收紧的服务语义，须覆盖既有 SDK/客户端，不新增请求字段或虚构回执。
2. 检查 schema/src/relay.ts 的 AuthState.capabilities 是开放字符串数组、OperationReceipt.kind 仍为 vendor-create，committedRevision 仍为全局版本；不新增 mutationReceipt，也不把 Vendor.revision 改名为提交回执。若实际设计不得不改公开字段，先单独修订本节及兼容测试再实现，不能顺手扩成未知结构。
3. 正式 server/src/handlers/relay.ts 的结果仍可以是清理时的最新状态；只验证 capability 正确透传和身份/快照合并，不要求服务把已更新配置回退到旧命令时点。原始命令版本由持有完整基线的新前端按契约取得，旧前端继续忽略未知 capability。
4. 在 packages/client 执行 bun run generate，再从根执行 bun ./packages/sdk/js/script/build.ts，记录生成退出码与实际差异；即使开放 capability 不产生 Schema 文本变更，也保留生成记录。Core、App、Server 及生成客户端类型检查纳入联合验证；如实际改动 Schema/Protocol 再增加对应包检查，不手改生成文件。
5. 真实 HTTP 样本区分首次成功、清理重试成功、确定未提交失败、提交后收尾故障/未知和普通只读快照；错误状态本身不是零提交证明。同 operationId 可识别重试不二次配置提交，最新快照允许高于原命令版本。公开响应和诊断不新增密钥、keyRef、密钥摘要或整份提交 payload。

| F30 | 服务关闭分别发生在 preparing/admitted/handoff 阶段；ACK 后暂停 handoff | 准备取消并清理、已准入任务排空；不自等待；记录 ACK→GET 窗口，handoff 后及重建读取均新值 |
| F31 | 无 $schema 的 JSON/JSONC、无本地文件、共享 bootstrap 的冷态首次 PATCH | 本 PATCH 禁用 loader 可选写入；D/L 重建合法基线；第一次请求完成闭环，不依赖第二次保存或误报自冲突 |
| F32 | P 为缺失→前请求首次创建→后请求取得选择锁；D/L 后再注入变化 | 前者作为最新初始基线，后者明确冲突；同文件重复来源全部使用 L 原文；不以循环重选/自动重放通过 |
| F33 | ImageGenerationSettings.update 规范路径/缺失文件/legacy 别名及同文档竞争 | 正常保存回读；别名拒绝在临时写入前发生，原字节不变；同一文档与 Config/MCP/全局共用租约，不泄密 |
| F34 | 正式图片设置 HTTP 入口成功、别名拒绝、后续 GET | 保持现有领域 Error→InvalidRequestError 失败契约，不返回假成功或未声明错误；原磁盘/内存不被失败请求改变；恢复规范路径后可保存 |
| F35 | 既有及补丁新 file/env 引用、有效值覆盖、依赖变化、raw 非 JSONC 的有效模板 | 替换后解析/解码；原文可编辑才打补丁，有效但不可编辑的目标区分 no-op 与 typed 409，非目标继承和读取保持；真正无效为 400；引用/依赖复检、重建与无明文泄露均验证 |
| F36 | 全部 handoff 的失败汇总、项目有限恢复、关闭/容量/其他 owner | 全局/MCP/一般失败即使被 catch、早于关闭或诊断溢出仍可报告；仅项目幂等收尾有限重试；排空不丢失败、不重放成功 hook/PATCH/publish；准入预留与安全 ref 保持 |

### 11.1 图片设置共享门禁的实施与回归

1. 将 ImageGenerationSettings.update 明确登记为必写调用方；它当前在 Core 直接选择全局配置文件并调用 ConfigDocument.withLock，不能只审阅 OpenCode Config.update/updateGlobal/updateMcp。门禁必须先于 temporary 写入/rename，失败后不选另一配置文件绕过拒绝。
2. 保持 ImageGenerationSettings.Error 的现有领域通道；alias 拒绝映射为安全且可操作的错误说明，例如要求使用规范配置目录，不在 message 中附 key、原始 cause、配置全文或完整路径。HTTP 仍由正式 handler 映射现有 InvalidRequestError；不把项目 API 的 CONFIG_* 或 MCP_* 错误直接透传到这条 API。若实施确需改变公开错误形状，先更新声明/生成和 F34，不能让运行时返回未声明结构。
3. 服务级样本覆盖默认目录、自定义 OPENCODE_CONFIG_DIR、尚无配置文件、已有 JSON/JSONC、同域大小写/junction/符号链接（按平台能力）和共享物理文件竞争。legacy 不兼容别名明确失败、规范路径成功；规范化协议的合法别名使用同一最终租约。读取允许与写入拒绝分别验证，不把别名只读成功当作写入成功。
4. 并发使用真实 ConfigDocument 租约屏障：图片设置先等待另一写入者，在放行前不能创建 tmp/rename 或改字节；反向持锁也验证。该模块现有临时文件/rename 的其他原子性限制不在本批顺便重写；本测试仅证明新门禁、互斥及既有更新行为没有被共享改动破坏。
5. 正式 HTTP 覆盖服务端实际选择的数据根和文件，拒绝时同时断言状态、公开错误类型、目标原字节、无敏感内容，以及后续 GET/恢复规范路径保存。配置/图片协议相关既有回归一并保留，不用可选 schema 的“跳过写入”规则处理这个必写入口。

## 12. 现有反例测试如何迁移，避免误判修复

当前 TCP 反例为了证明缺陷，明确断言旧 config.json 有新值、opencode.json 保持旧字节。修复后正确目标应当变化，因此以下夹具断言必须随契约调整：

1. 只有 opencode.json 的案例，预期发布目标固定为该文件；spy/barrier 也拦截该目标。不能仍等待 config.json 导致测试超时。
2. “旧 config.json 不变”成为负向断言；原 opencode.json 应含补丁且保留未编辑字段。
3. **PATCH 成功后 GET 新值、投递次数、通知次数、拒绝原字节、重建后读取等行为断言不可删除或放宽。**
4. 测试期望从已确定的来源案例推导，不能直接拿 selector 的返回值作为唯一 expected，避免实现和测试同时选错仍转绿。
5. 首次确认夹具路径后才投递请求；before 文档、请求 readiness、准备开始、admitted、断连、真实发布完成、handoff 完成分别有信号。成功断连样本必须等 admitted 再断连，准备取消样本必须证明仍在 preparing，不能混用“已投递”。完整 handoff 应观察生产入口返回的实际完成 Promise（必要时用作用域内的透传 observer）或等价的完整收尾，不用一个自定义 reload hook 被调用就代替其他 hook 也完成。全流程有界，finalizer 释放屏障并等待自己投递的任务。
6. 准备失败时测试必须在准备阶段失败，不能挂到 120 秒后被误记为产品取消问题。

页面 finally 仍先完成路由处理、记录状态再销毁 owner，最后读取最新 revision/entityId 删除夹具；即便测试失败也保留动作附件。截图如需要，在关闭页面前显式保存。

## 14. 发布与历史问题的边界

- 本方案没有授权重启当前应用、提交、推送或修改版本；实施与验收可在隔离环境完成。
- F02 新保存闭环与历史误写 config.json 的人工恢复分别报告，不合并为一个“全部数据已修复”。
- 不自动关闭：I30～I39 尚未覆盖的共享请求取消/编码分支，OBS-02 精确 EPERM 归因，全部 fs/producer/TOML 剩余矩阵，R3-03B、RF-07 跨平台、macOS、安装 Electron 与 Bun 单文件。
- 本批修复目标是已确认两处根因的完整闭环，不承诺排除所有尚未执行路径上的缺陷。发现范围外确定缺陷时另编号记录，先完成本批可验证工作，不把所有模块再次混成一批。

### 14.1 必须随结果交付的兼容限制

下列行为是本方案选定的边界，不是尚未执行用例的通过结果；最终报告逐项给出已验证/失败/未执行及证据，不能省略限制后宣称“所有重试均可恢复、所有配置均可保存”。

| 边界 | 必须向使用者说明的行为 | 验收对应 |
| --- | --- | --- |
| 普通供应商 mutation 的重试 | 同编号不同命令明确冲突；精确证据在重启/淘汰后缺失时可能无法确认原提交，前端保留未知并只读对账，不换新编号自动重放 | O26～O29；不得混同确定未提交或精确成功 |
| 创建的持久化回执 | 继续按既有持久化指纹独立确认，不能套用普通 mutation 的内存失效限制；密钥缺失/损坏仍阻止验证，不再生成来覆盖 | O29 与 relay-create 的既有指定回归 |
| 有效变量模板的编辑 | 运行时合法但 raw 无法无损编辑的最终目标仍可读、可继承；需要改变目标时返回 CONFIG_TEMPLATE_EDIT_UNSUPPORTED；符合条件的无写入 no-op 可成功，不展开后写回 | F12/F35；读取能力与写入能力分别报告 |
| 配置保存的成功 | 项目 PATCH 的 200 包括实际提交与合法 no-op；实际提交的 handoff 可尚未完成，不提供新增的立即读后写一致性承诺 | F12/F15/F30/F35/F36；不可只用 200 或一次 GET 关闭 |
| 平台、别名与历史内容 | legacy 不兼容别名仍拒绝；未执行平台、历史误写 config.json 人工恢复和第 14 节历史未关闭项继续单列 | F10/F20/F28/F29 及 S9 报告，不跨范围关闭 |

如果产品要求超出这些边界（例如重启后所有 mutation 均可确认、任意有效模板均可编辑、ACK 后立即一致），必须先单独修订协议/实现范围和验收规则；不能在本批实现中临时承诺，也不能把现有边界写成未知的“后续优化”。

## 15. 方案实施前自检结论

已在设计层检查以下易遗漏点：手动获取不与单个旧挂起请求串行，两槽占满时有界排队/失败；旧 ACK 也可能带来未完成连接责任；backend pending 与上游需求不可混用；finally 不得丢唤醒；清钥/删除/重建/换服各有终止规则；数组/拼接字段和后置来源覆盖不是普通 JSON 深合并；原来源记录不等于全字段 provenance；目标选择锁不能与文档锁自等待；原 TCP 测试的 config.json 夹具须随新契约调整；历史错误文件不自动导入；typed 错误必须生成客户端；实际提交后的取消与响应编码仍有独立收尾。
