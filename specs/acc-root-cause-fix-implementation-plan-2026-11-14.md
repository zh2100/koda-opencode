### 3.2 统一选择规则（P2）

- 经典布局读取 useServer().current。
- 现代布局保留 global.settings.server.selected()，不把设置 picker 反向写成全局 active。
- 在稳定的设置 owner 下读取选择 accessor；选中连接不存在时显示既有不可操作/加载状态，不用旧连接兜底。
- 两种布局都经过 SettingsServerDataProviders。以目标连接身份和局部生命周期建立 keyed 子树；显示名称不是身份。
- A → B → A 必须产生新的设置局部代次，即使第二个 A 复用了 Global 的同一个 SDK。
- 同 key 移除重加、连接实例/参数变化也要重新核对归属；如果真实共享资源没有随连接变化更新，单独登记 Global 的最小必要修复和影响测试。

先尝试在现有 SettingsServerScope 中完成以上规则。若原 owner 销毁导致选择 accessor 停止更新，才把设置专属挂载提升到稳定 owner；不得在未验证前扩大通用 Dialog 改动。

### 3.3 按目标重新绑定资源（P3）

1. 从 global.ensureServerCtx(connection) 获取目标已有共享资源。
2. QueryClientProvider、ServerSDKProvider、ServerSyncProvider 指向同一服务器；Models 的局部视图在该边界下创建。
3. 切换先使旧设置局部票据失效，再解绑本页订阅与独占请求。禁止 queryClient.clear、全局 cancelQueries 或关闭共享 SSE。
4. 只持有共享 query Promise 的页面没有底层取消权；关闭时停止接纳即可。AbortSignal 只用于本页独占请求。
5. 草稿、error、busy、待补读及弹窗身份归属到局部代次，不跨服搬运。保留已有不同供应商并发、分片接纳与错误票据语义。

### 3.4 审计五种动作的目标捕获（P4）

| 动作 | 发出前固定 | 切服后的处理 |
| --- | --- | --- |
| 保存 | 原 SDK、server scope、局部代次、entityId、草稿版本、既有 operationId | 服务端可以在原服提交；不能清新页面草稿或关闭后来弹窗；提交后失败只补确认/刷新 |
| 清密钥 | 原实体与凭据/配置版本、独立命令身份 | 未提交保留旧钥；已提交清理由原服务负责，不由 B 页面代偿 |
| 删除 | 原 entityId、版本、原命令身份 | 精确重试沿用既有 receipt；不能删除同 ID 后继 |
| 连接测试/获取模型 | 地址与认证版本、SDK、请求序号 | 换地址/清 key/删除后拒绝旧成功；只释放本次 token |
| 读取/刷新 | 原 scope、局部代次、分片水位 | A 结果不能写 B；回到新 A 也不接纳旧 A 票据 |

不为了本批增加另一套幂等协议，不重新引入已移除的统一密钥/智联密钥功能；清密钥只覆盖现存供应商凭据功能。

## 4. ACC-02：失败引导与缓存生命周期修复

### 4.1 明确实际资源与绕过入口（P6）

先列出下列生产调用图，再修改缓存：

- InstanceStore：load、completeLoad、reload、dispose、disposeDirectory、disposeAll、onConfigReload 和服务 finalizer。
- InstanceState：make/get、invalidate/invalidateAll，所有直接绕过 InstanceStore 的调用者。
- registry：InstanceState disposer、两处 PTY/Location disposer、其他注册者及 CLI/实例销毁入口。
- Config：get 环境变更、invalidate、mcpSource changed、update/updateGlobal/updateMcp、loadConfig 的 schema 补写，以及 loadGlobal 的默认初始化、旧 TOML 配置迁移和更新后通知；逐入口记录已持锁/非阻塞尝试与提交模式。
- Config 初始化途中已取得的资源、依赖安装 fiber/底层 Promise、插件初始化与各自最终所有者；列明退出时哪些任务还能派生文件写入、其准入许可和锁/文件句柄归属。
- 请求前置 InstanceContextMiddleware、Config 路由装配与 handler，以及 lifecycle.ts 中 markInstanceForDisposal/Reload、响应前回调和 disposeMiddleware。
- AppRuntime/CLI 独立运行时桥接、EffectBridge.bind/make、run-service.attachWith 与原始 ManagedRuntime.dispose 的拥有者；不能只盘点完整 Context 捕获而漏掉白名单引用桥接。

对每类资源写明：实际创建点、缓存键、目录/location/workspace、是否借用、owner token、释放句柄、是否幂等、是否可重试、是否仍有后台任务。

内部引导 owner 不改公开 HTTP/SDK 数据结构。优先由 InstanceStore 在 canonical InstanceContext 创建时建立内部 ctx → owner 映射，后续 load 返回同一个 ctx；请求与桥接保留该引用。若采用独立 Effect owner 服务，必须同时接通 middleware、run-service.attachWith、EffectBridge.bind 及 CLI 桥接，不得假设新服务会自动穿过所有运行时。禁止把旧 ctx 映射到后继 owner；克隆 ctx 必须有明确映射规则。轻量来源上下文不冒充可访问 InstanceState 的 ready 实例。非 InstanceStore 创建的现有资源明确标成独立所有者，不能将“未知”归到当前代。

### 4.3 先拆来源读取与完整销毁（P8）

当前 mcpSource changed 同时执行 invalidate、invalidateAll、reload hooks、registry.disposeInstance，再在同一请求读取状态；路由在 handler 前还会由 InstanceContextMiddleware 执行 store.load。若只改 mcpSource，无法实现纯来源读取；若直接增加目录锁，又容易形成等待自己或误清 PTY。P8 必须先完成第 4.7 节的声明式路由与上下文拆分。

具体顺序：

1. 从实际加载流程提取可复用的来源发现/原文合并阶段，保留 ConfigPaths.discover、实际来源顺序、远程/环境/托管/.opencode/重复文件位置与未展开引用。
2. 来源快照仅做必要读取、解析和版本计算；不调用含 ensureGitignore、依赖安装、插件准备的完整 loadInstanceState 冒充纯读。
3. mcpSource 改用来源快照；获胜文件已删除仍返回空，不能缓存补回；读拒绝/损坏保留既有错误。
4. 来源变化需要运行时生效时，向 Config 的配置版本刷新或 InstanceStore 显式交接提交明确原因；不在读取 handler 内执行全目录销毁或重放整个 handler。
5. Config.get 的环境变化和显式 invalidate 采用相同协调规则。真正全局更新可以按受影响目录刷新，但每个目录独立交接，不让来源 GET 无条件 invalidateAll。
6. 旧请求持有只读快照可完成本次读取；需要可变资源时校验 owner，不能通过旧请求的 InstanceState.get 隐式创建后继代资源。写操作仍在提交处检查最新实体/配置版本。
7. 保留显式完整 reload/dispose 的既有终端关闭语义，不能把所有销毁都改成“只换 Config”而泄漏应释放资源。

出口：I13、I14、I23、I24 受控交错通过，来源读取无安装/插件副作用，无自等待，无跨目录误清。

### 4.4 建立目录代次与有限状态交接（P9）

Entry 除当前 deferred 外，内部记录唯一 owner、阶段、原 boot Exit、实际资源记录、共享清理任务与诊断关联。数据结构名称可适配项目风格，但以下转换必须保留：

| 当前阶段 | 触发 | 必须执行 | 后续 load |
| --- | --- | --- | --- |
| 不存在 | load | 短临界段登记 Entry，安排服务 scope 的 boot | 加入同一 boot |
| loading | boot 成功 | 按 Entry 身份发布 ready | 返回同一上下文 |
| loading | boot 失败 | 先固定原 Exit 和本代责任，再转 cleaning；不先删 Entry | 等待交接或接收有界错误 |
| cleaning | 所有实际责任完成 | 条件移除该 Entry，保留脱敏失败记录 | 后续独立请求可建新代 |
| cleaning | 超时/失败 | 保留任务与剩余责任，进入明确隔离状态 | 不得创建竞争新代 |
| failed-cleanup | 允许补清理 | 对剩余可重试责任开启一个共享有界周期 | 同周期只等待，不各自重投 |
| ready | 显式 reload/dispose | 进入既有完整销毁交接，按实际资源范围处理 | 服从交接结果，不绕过 |

实施要求：

1. 同目录共享“创建/标记/条件发布”的短交接；不用一把锁包住整个 boot、HTTP handler、网络或 WebSocket。
2. 用户取消仅中断自己的等待。引导属于服务 scope；清理有服务拥有的账本和第 4.9 节规定的退出观察责任，不因一个客户端取消丢失其他等待者和资源。不能把可能永久挂起的底层释放直接作为无界 join 的 scope finalizer，再声称外层 timeout 能约束它。
3. boot 失败的所有 Deferred 都有完成路径；清理还没结束时不让原请求永久悬挂。
4. 清理器使用获取时捕获的资源，不再 load/reload 同目录取自己的清理目标。
5. reload、onConfigReload、disposeAll、退出都经过相同交接，删除当前 onConfigReload 中“先删 map，再等待并 ignore”的责任漏洞。
6. 不同目录继续并行。按 Entry 身份有条件删除；旧完成回调不能删新 Entry。
7. 显式 reload 失败时保持已完成提交事实，不重放保存、prompt 或其他外部副作用。插件有部分副作用时先定义其幂等/不可重试边界，不能承诺通用自动重放。

### 4.5 实际清理账本与 registry 结果（P10）

1. 账本在资源实际创建时登记，不按服务注册时间推断本代所有权。字段包含 resourceId、实际键、owner、状态、捕获的释放任务/句柄、尝试次数、结果和时间预算。
2. ScopedCache 仍可按目录组织，但必须有能校验本次实际缓存单元的 owner 记录和捕获释放责任；不能只靠再次按目录 invalidate 返回成功证明释放。
3. 库 invalidate 先删除再 close，Scope.close 也不保证重跑失败 finalizer。因此不修改依赖源码，也不把第二次空 invalidate 记成成功；在应用层保留实际 close 的任务和剩余可重试底层释放。
4. 同步 throw 和 Promise reject 分别在每个 disposer 的独立投递边界捕获，全部目标都要尝试并观察。返回内部清理结果，不抛裸 AggregateError 给 HTTP。
5. 成功资源不重复释放。尚在执行的任务不能再次投递。仅对能证明幂等且持有真实句柄的剩余释放重试。
6. 失败代仅清本代资源；借用的既有 PTY/Location/共享资源保持原 owner。完整销毁使用独立 reason 和目标集合，不遗漏原有 PTY 释放。
7. 10 秒单周期总预算、最多 2 次可重试尝试、后续共享恢复周期和退出观察沿用原报告 5.5；不用每次尝试重新计算 10 秒。
8. 等待预算到期不等于底层停止。运行期间晚到任务由服务账本观察，退出期间由第 4.9 节的独立观察记录继续持有实际任务；成功只更新原 owner 的账本，失败保留原因。永久挂起时保持隔离和有限错误返回，不谎报 Scope 已关闭。
9. 已结束失败可以由后续独立恢复周期补剩余责任；反复请求不得无限并行重投。最终释放成功也不抹去第一次失败记录。
10. 在服务退出边界输出脱敏的未完成责任及失败摘要。底层不可终止时如实报告，不把超时包装成干净释放。

### 4.6 真实读取和错误映射（P11）

- access(R_OK) 只能作提示，不能作为可读证明；不以换一种 access 检查代替生命周期修复。
- 优先复用实际配置读取与统一来源发现规则，避免多一套预读优先级；任何预检之后发生的真实读取失败仍进入 P9/P10。
- 原配置读拒绝保留 MCP_SOURCE_READ_FAILED / 503 和原 ref；原损坏保留 MCP_DOCUMENT_INVALID / 400 和原 ref。清理失败不覆盖原 typed 错误。
- 后续请求被未完成清理阻止时使用既有 503/ref，内部关联旧责任。真正未知缺陷保留项目未知错误路径，不伪装为权限问题。
- 中断保留中断，其他共享等待者仍接收原错误；不以 Effect.ignore 吞掉退出/清理错误。
- 原 Cause 与清理 Cause 在内部保留，公开 JSON 只给协议允许字段；日志仅记录白名单和脱敏关联，不直接 stringify 配置、凭据或可能含正文的 Cause。
- 检查 InstanceContextMiddleware 前置失败及 handler 内失败两条路径：状态、code/ref、Content-Type、JSON 非空与脱敏都需断言。
- 默认不变更公开协议/SDK。若最终差异确实改变公开契约，按仓库要求重新生成客户端，禁止手改生成文件或扩大错误类型掩盖实现问题。

P11 出口：完整引导的原冷启动反例恢复为 200；I01～I25 适用项及 I26～I67、实例原有测试和错误映射通过。来源读取、提交收尾、运行时退出各自有证据。实际无法释放的资源必须明确拒绝后继且保留责任，不伪造恢复或干净退出。

### 4.7 来源接口的前置上下文与服务拆分（P8-A）

本节是 P8 的前置实现，不是 handler 层的可选优化。当前 ConfigApi 整组挂 InstanceContextMiddleware；后者在 handler 前执行完整 store.load。目标是保留 API 路径、config.mcpSource 标识、响应和客户端调用形态，拆掉来源 GET 对完整实例引导的依赖。

采用以下分工：

| 路径 | 上下文与执行策略 | 必须保持 |
| --- | --- | --- |
| GET /config/mcp/:name | Config 组的轻量请求上下文 → 稳定来源快照服务；不调用 store.load 或运行时 Config.get | 认证、workspace 解析/转发、目录/工作树来源边界、原文及错误契约 |
| GET /config、providers 等运行时读 | 同一轻量上下文 → 共享的完整引导包装 → 原 handler | 真实 store.load、canonical ctx/owner、原数据和 typed 错误 |
| PATCH /config、PATCH /config/mcp/:name | 明确保留完整引导及提交时版本校验，接第 4.8 节收尾责任 | 锁、原来源及版本检查、提交结果、原错误映射；不因 GET 拆分改写写入语义 |
| 其他实例路由 | 继续原完整实例中间件 | 既有访问及生命周期语义 |

实施步骤：

1. 在 ConfigApi 的声明式 group 上接入专用轻量上下文 middleware，保留 Authorization、WorkspaceRouting 及代理的既有有效顺序。Config 组不再先无条件完整引导；其他组不改变。
2. 轻量上下文仅包含已校验的 directory、workspace 和来源发现必需的 worktree 信息。目录/工作树解析不得通过 Config.get、Plugin.init 或 store.load 间接回到完整引导；审计其自身 I/O，不能把“无安装/插件副作用”夸成进程完全不写任何数据库。
3. 完整引导包装在运行时读写 handler 前统一调用 store.load，并提供 canonical InstanceRef、WorkspaceRef 和 owner。复用原 instance-context 的错误转换；不复制一套会漂移的 status/ref 规则。以声明式服务/函数复用，不在 handler 临时构建 Layer。
4. 提取稳定的来源快照服务，与运行时配置加载复用来源发现/合并逻辑。其依赖图不得包含需要完整初始化才能读取来源的环；远程来源允许必要的认证读取与网络请求，但不展开用户 {file:}/{env:} 引用给界面，也不安装包或初始化插件。
5. configHandlers 的来源 handler 直接使用该服务；运行时读写 handler 使用完整引导包装。按现有项目规范在组及 server.ts 装配边界提供稳定服务，不用 raw router/字符串 URL 判断规避 typed middleware。
6. 核对 InstanceHttpApi 和独立 ConfigApi 等实际导出的装配路径，确保没有一条监听入口继续套旧的无条件完整引导。不能全组取消 InstanceContext 后漏给运行时 handler 补回引导。
7. 对比 OpenAPI、operationId、错误联合和生成客户端。默认保持公开契约；若装配变化影响生成结果，按仓库命令生成并审阅，不手改生成文件，不静默改变 config.mcpSource 的客户端归属。
8. 真实 TCP 测来源 GET 的成功、损坏、拒绝及取消，同时观察没有 boot/依赖安装/插件初始化，且前后无配置文件写入。再用未认证请求和 workspace/代理场景确认没有放开访问。

### 4.8 提交完成到响应之间的收尾责任（P9-A）

必须修改或复用 lifecycle.ts 的 markInstanceForDisposal/Reload、disposeMiddleware 和 Config 写 handler 的接入。现有 pre-response 回调/WeakMap 可以保留为传输通知，但不能继续是责任的唯一登记处。

责任分成两个时点：磁盘提交成立时必须已经有服务拥有的收尾票据；真正释放按原 owner 的资源使用边界和 coordinator 执行，不要求等到浏览器收到 ACK。

1. 提交前，在服务拥有的账本建立票据，固定 mutation 标识、原 ctx/Entry/owner、预期版本、清理原因和状态 prepared；只登记，不预先销毁。
2. 未投递写入前取消且确认未提交，关闭 prepared 票据即可。一旦底层写入已投递，票据及该写入的真实完成观察由服务接管，客户端取消只停止等待，不能释放仍在写入所需的锁。
3. 按第 4.12 节以目标文件的原子发布成功（已有文件替换或合法首次创建）为提交点，临时文件写完不算 committed。由服务任务观察发布的真实完成，再在短的不可中断状态交接中标记 committed 并使精确收尾责任生效；不能在原子发布成功与票据登记之间留下可取消空隙。不要把整个文件 Promise 或网络操作包进无界屏蔽区来代替所有权交接。
4. 失败按第 4.12/4.12.1 节区分发布前失败、发布结果未知、发布成功后收尾失败。普通 fs.writeFile 拒绝不能证明原文件未变化；只有已证明本次未提交且目标保持适用的旧状态，或竞争创建的他人文件未被本次修改时，才能结束未提交票据。结果未知或部分损坏保留隔离及核对责任，不盲目重放、不用旧全文覆盖可能存在的新版本。提交成功后的刷新/收尾失败保留已提交事实与待办。
5. coordinator 在原写入临界阶段结束、相关资源可安全交接后执行收尾；不等客户端 ACK，也不为等待响应而占住目录锁。需要资源使用票据的调用者要明确何时退出可变资源访问；不能未经保护就释放还被旧 handler 使用的对象，也不能等待所有 WebSocket 断开。
6. pre-response、正常响应、响应编码失败、断连和请求 finalizer 只通知/加入同一票据，不能重复创建、重复释放或取消已提交责任。旧响应只能指向捕获的 owner，不能按“当前目录最新实例”补做销毁。
7. 通过 canonical ctx 映射接通普通 Effect、Promise/ALS 与 CLI 桥接；如果采用独立 owner 服务，补齐 run-service/bridge 的引用传播测试。EffectBridge.make 捕获完整 context 不代表其他白名单桥接也自动正确。
8. 票据处于 prepared/写入中时不启动冲突新代；committed 后按配置版本执行既有刷新/销毁语义，不重放插件、会话、prompt 或写 handler。成功返回 true 等现有公开形态保持不变；网络中断仍按既有重读/幂等规则确认。
9. 本批承诺同进程存活期间的投递与取消安全，不声称内存票据可跨进程崩溃恢复。磁盘已提交而进程退出时，新进程按真实配置启动，不为恢复页面自动重放上次命令。

### 4.9 运行时退出、等待预算与实际完成（P10-A）

必须区分三个事实：调用者等待已结束、清理底层任务已完成、ManagedRuntime 的 Scope 已实际关闭。10 秒是前者的观察预算；没有证据时不能用于承诺后两者或操作系统进程退出。

已知机制证据：此前独立内存探针在 finalizer 底层 Promise 挂起时观察到 runtime.dispose 仍 pending，释放底层 Promise 后才完成。这不是产品修复通过结果，说明只在内层加 timeout 不足以证明退出有界。

采用明确的应用级退出观察边界：

1. AppRuntime 进入 closing 时按第 4.11/4.11.1 节原子地停止新的业务准入，先 quiescing 停止生产者的新投递，再 draining；固定已接纳有限任务树，已有任务只允许在原许可内完成必要后续。先排空真实写入及其租约，不因要关闭服务而先中断它们，也不能边关闭边删目录。
2. 仅在第 4.11 节的排空条件满足后，才启动一次原始 ManagedRuntime.dispose，并保存真实 Promise/Exit、任务清单和 owner。排空尚未完成时 rawDisposeStarted=false，不能先启动再靠观察 Promise 补救。观察记录由应用模块持有，不只依赖正在关闭的 scope 中的 child fiber。
3. 停止生产者、排空和原始 dispose 共用同一绝对截止时间：使用既有清理周期剩余预算，无周期时最多单独 10 秒，不能每阶段重新计时。耗尽时返回退出未完成失败，记录处于 quiescing、draining 还是 disposing；未启动的原始 dispose 不得提前启动，已启动的继续观察。各阶段均不能标 closed、清空责任或 resolve 成功。
4. 该观察层不能只调用一个可能因 uninterruptible finalizer 而无法返回的 Effect.timeout。需要直接保存原始 Promise 的成功/失败处理，再由独立的可取消观察者等待截止时间；不向原始任务传播调用者取消，也不留下未观察的 Promise 拒绝。
5. 超时之后，原始任务与错误记录仍由应用级观察记录持有；晚到完成只更新 actualClosed/剩余责任，不把已返回的超时失败追改为成功。不重新投递正在执行的释放，也不先关闭其仍需借用的依赖。
6. 若原始 dispose 自身拒绝，保留它与各资源的 Cause；观察调用返回失败，不吞成清理成功。重复退出请求加入同一退出周期和原始任务；测试应能区分对外失败结果与后来的实际完成。
7. 对仍直接注册在 Scope 上的库 finalizer，审计实际等待边界；无法做到可观察/有界交接时如实保持 closing 和故障诊断，不声称 Scope 已完成。此方案不强制终止用户应用，也不保证底层永久挂起时 OS 进程会自动退出；若产品另有强制退出时限，须独立设计，不用本方案的 10 秒观察预算冒充实现。
8. preload 必须检查实际 runtime 关闭与本轮写入任务都已完成后才开始递归删除。dispose 失败/超时且实际资源未收尾时，保留隔离目录并使测试非零退出；不能为了“总要 cleanup”与存活写入竞争。可安全独立恢复的权限夹具仍执行其自身收尾。
9. 用真实 ManagedRuntime/Scope 及实际 AppRuntime 退出包装验证：挂起 finalizer 时观察按预算失败，actualClosed 仍 false、无目录删除、无新业务准入；释放底层屏障后只完成原始一次关闭，记录 actualClosed。再覆盖底层拒绝与重复退出。
10. 永久挂起测试放在专用子进程，父进程只管理本轮子进程并保存超时及残留诊断。父进程在核验子进程退出后处理其隔离目录；不能靠测试框架超时直接算通过，也不能将子进程被终止记为资源正常释放。

### 4.10 防假通过与新增正式验收义务（P7-A / P11-A）

以下 I26～I39 与原 I01～I25 同时生效，都是待实施验证义务，不是新增通过数量。

| 编号 | 路径/交错 | 必须观察的结果 |
| --- | --- | --- |

| I27 | 来源 GET 轻量读取的冷/热、成功/损坏/拒绝 | 不调用完整 boot，不安装/初始化插件，不写配置；结果及未展开引用符合原契约 |

| I32 | 写入已投递未完成时取消，随后成功/拒绝 | 真实 Promise 被观察，锁/票据不提前释放；成功接 committed，失败保原错，不盲目重放 |

| I35 | 实际运行时 finalizer 挂起超出观察预算 | 对外明确失败，actualClosed=false，原始 dispose 仍被观察，没有新业务、没有目录删除或第二次 dispose |
| I36 | I35 后原任务晚到成功/失败 | 原任务只执行一次；真实状态更新但原超时结果保留；所有拒绝被观察 |
| I37 | 退出期间重复 dispose、一个等待者取消 | 共用原始关闭任务/周期，取消不丢责任；不重建 runtime，原有已投递写入仍受观察 |
| I38 | preload 遇 runtime 退出失败/后台写入未结束 | 整批非零退出、诊断保留；不与存活资源竞争删除；父进程确认退出后才独立收尾 |
| I39 | 客户端取消完整引导，另一请求仍等待 | 取消客户端不强求收到 503；共享失败与清理由服务记录，存活客户端得到正确 typed 错误；恢复后完整路径可成功 |

I26 通过真实入口的 loader/资源计数或正式测试层观察验证，不新增产品诊断接口。boot/失败缓存的结构性断言使用实际实现，不能在测试中复制缓存状态机。I35～I38 必须跑真实退出边界，纯内存机制探针和只断言外层计时都不能替代。

### 4.11 原始 dispose 前的写入排空（P10-B）

排空是 P10-A 的硬性前置步骤。保存 Promise 引用只能证明有人观察结果，不能阻止 Scope.close 中断 fiber 并提前执行锁或句柄 finalizer。

退出阶段固定为：accepting → closing/quiescing（停止生产者的新投递）→ closing/draining（完成已投递任务）→ closing/disposing → 实际 closed。关闭准入与启动 quiescing 在同一协调边界生效；各阶段共用原关闭周期与绝对截止时间，超时/失败保留具体阶段与责任，不能直接跳到 closed。

1. 在投递写入或可能派生写入的任务之前取得内部准入许可，并登记 owner、实际任务、将使用的文件/锁及完成条件；许可与登记发生在同一个短交接内，不能先投递后补计数。
2. closing 与新许可授予共用准入闸门。从进入 quiescing 起拒绝新的外部业务；此前已接纳的任务树仍持有原许可，可完成提交、状态交接和必要收尾，不把这些后续误当新业务拒绝而丢失提交结果。
3. 父任务派生必要子任务时先在原许可下登记，再投递；父任务在仍能派生必要子任务时不释放其生产者责任。长期定时器/订阅与有限任务树分开登记，不能把未来 tick 一并算入原任务树许可。排空条件不仅是当前 pending 数为零，还必须已确认长期生产者不再投递，且没有仍开放的有限任务生产者。检查和转入 disposing 在同一协调边界完成，避免零计数后又出现写入。
4. 盘点范围包含直接配置写入、同目标 schema 注解、依赖安装及其他在本轮 runtime 中可能继续写隔离根的后台任务。借助独立 runtime/Promise/回调进入的写入也必须登记；不能只统计 InstanceStore 的 fiber。确有另一所有者时，记录其关闭/等待约定，不冒认它已随 AppRuntime 关闭。
5. 写入许可由实际任务持有，不由 HTTP 请求作用域持有。调用者取消/断连不能触发仍在写入所需租约的释放；相关文件句柄和租约的 finalizer 必须绑定任务真实完成。不能仅在请求 finalizer 中 await 一个已经被取消的 Effect fiber。
6. 确认所有已投递目标写入/替换已结束、结果已登记、必要句柄已关闭、相关租约已按获取时身份安全释放，以及没有待派生写入后，才允许 rawDisposeStarted 从 false 原子变为 true。其他仍待执行的无写入资源清理由后续原始 dispose 承担。
7. 排空超时期间不能调用原始 dispose 来“加速”释放：保持 draining、保留任务/依赖/租约及应用级观察，向调用者返回明确失败，不重建 runtime、不接纳新业务、不删除目录。不得通过放开锁让另一写入者与残留任务竞争。
8. 晚到任务结束后，服务继续按原票据登记提交/失败并完成租约释放。排空条件真正成立时，观察记录可推进唯一一次原始 dispose；不新增等待预算，不把早先超时返回追改为成功。若排空仍失败，继续保留诊断，不用重复退出请求重置截止时间。
9. 对 drain 内失败但真实已停止的任务，记录其错误并根据实际剩余资源决定能否进入 disposing；错误存在不必永远阻止安全释放，但不能以错误已记录代替资源已停止。最终关闭报告保留此前失败。
10. 正式回归必须在写入真实挂起时调用实际退出入口，观察 rawDisposeStarted=false，并用独立竞争者确认原锁仍被持有；放开写入后确认提交/失败、锁释放、raw dispose 的实际先后顺序。仅比较日志或计数不足以代替租约竞争验证。

本节只修生命周期顺序，不切换锁后端或改锁协议。永久挂起时的处理仍遵守第 4.9 节：保持明确失败及责任，不承诺操作系统进程会自动结束。

#### 4.11.1 长期生产者先停投递，已投递执行再排空（P10-B 补充）

现有 snapshot/index.ts 的 cleanup 通过 Effect.repeat + Effect.forkScoped 周期执行，并会运行 git gc。若长期循环只在原始 Scope.close 时停止，而排空又要求循环先结束，会形成方案层面的循环等待；当前尚未实施新协调器，不能把此风险写成已复现的产品死锁。

1. P6 盘点每个 timer、订阅、watcher、事件回调及其 owner，区分“可以继续产生任务的控制句柄”和“已经投递的一次执行”。对无写入能力的生产者记录依据；对可能派生写入的生产者明确 stop/ack、任务登记与释放入口，不能只列循环 fiber 数量。
2. closing 先关闭外部准入，同时使生产者的新投递许可失效；执行取消后续定时、解绑订阅或关闭回调入口等停止动作。stop 必须在 raw dispose 之前可调用，不能只挂在 Scope finalizer；finalizer 仅可复用同一幂等停止入口。不得通过中断整个循环 fiber 来提前释放正在执行任务的锁或句柄。
3. 定时器唤醒、回调已排队与 stop 竞争时，在实际投递任务前通过同一准入闸门复检。已在 closing 前完成准入的那次执行继续持有有限任务许可；尚未准入的 tick/回调不得再开始业务。订阅解绑不代表队列为空，晚到回调仍须受失效代次/闸门约束。
4. 已准入执行可派生完成本次动作所必需的有限子任务，按第 4.11 节先登记后投递；不得把周期循环、自动续订或未来 tick 作为“必要子任务”无限延长原许可。停止后续调度不撤销已投递底层 Promise 的所有权。
5. stop/ack 只证明未来不会再投递；实际写入、子任务、句柄和租约继续由 drain 等待。只有所有相关生产者已确认停止投递、有限任务树排空，才进入唯一原始 dispose；清理控制句柄也不得提前释放执行中租约。没有任务的空闲周期服务不必等下一次 tick 或等待 raw Scope.close 才能达到排空条件。
6. stop 失败或实际完成未知时保留 quiescing、具体生产者身份及资源责任；已确认停止但任务未结束时保留 draining。两者均不得标 closed、删除目录或强行 raw dispose。晚到停止确认后沿同一关闭周期继续，不能重置预算或把先前超时追改为成功。
7. P10-B 的实施出口须包括真实 Snapshot 周期服务和盘点中具有不同停止机制的生产者；用真实注册/停止入口与受控执行屏障验证，不以 sleep 一个周期或复制调度器状态机替代。无需为本方案引入通用后台任务框架。

### 4.12 配置文档原子提交与失败后磁盘确认（P9-B）

当前 Config.updateMcp 使用 fs.writeFileString，ConfigDocument.withLock 只负责互斥，不提供原子文件替换。普通写入可能先截断目标再报错，不能把 Promise 拒绝统一归成“未提交且旧文件不变”。

本批将配置文档提交原语纳入 core/config/document.ts 或紧邻的专用模块；不全局替换 FSUtil.writeFileString。实现前按第 4.12.2 节盘点 Config.update、updateGlobal、updateMcp、schema 注解、默认初始化与旧 TOML 配置迁移，统一接入或给出不绕过原子提交的明确证明；按第 4.12.3 节固定锁归属，不能机械地在每层重新加锁。凭据、锁协议迁移及其他存储仍按原协议处理。

提交状态与处理规则：

| 阶段/结果 | 目标文件事实 | 票据与公开行为 |
| --- | --- | --- |
| 尚未替换，临时文件写入/校验失败 | 旧目标字节、链接和元数据应保持 | 确认未提交，保留原错误，清理本次临时文件；不销毁后继 |
| 替换投递中，真实结果未返回 | 不能据等待取消断言旧/新 | 继续持有许可、任务和锁，观察实际结果，不重放保存 |
| 原子替换成功 | 新文档已对该文件路径可见 | 在短交接内记 committed；后续校验/刷新/清理失败不倒退为未提交 |
| 替换明确失败且验证旧目标完整 | 旧文档仍在 | 按既有错误契约失败，保留旧版本；不得先删除目标再重试 |
| 不能证明目标仍旧或完整 | 结果未知/内容异常 | 保留票据、诊断和该目标的安全阻止状态，重新读取核对；不自动覆盖、回滚或重放 |

实施步骤：

1. 保持现有逻辑来源标识、版本算法和 LockProtocol 选择规则。目标物理路径与锁键是不同概念，不能为原子替换擅自把未迁移根的锁键改为新 canonical 哈希，也不宣称解决历史跨协议/别名互斥问题。
2. 在现有配置锁保护下解析源路径、链接及最终目标，先按第 4.12.1 节选择替换或合法创建分支。已有目标读取旧文档和必要的身份/元数据；目标缺失仅在调用者明确允许时进入创建分支。执行各自适用的原有 source/version/可写性检查。逻辑 source 仍用于 HTTP 契约；对符号链接应更新其实际目标而保留链接本身，junction/大小写别名不能创建另一份配置。
3. 在最终目标所在目录以独占创建方式生成本次操作唯一的临时文件，初始权限不宽于已有目标或首次创建策略的要求，登记临时文件身份及清理责任。它只保存待提交新内容，不建立旧源码或旧配置备份，不把内容输出到日志。
4. 完整写入临时文件，核对字节与配置语法/Schema，并按平台提交原语要求完成 flush/close。临时写入结束不等于目标提交。取消由第 4.8 节的服务任务处理，不在底层仍写临时文件时先删除它。
5. 保留目标所需 mode/ACL 等安全元数据；禁止简单套用临时文件默认继承权限。Windows 须验证现有可用替换 API 的覆盖行为、共享句柄拒绝和 ACL 保持；POSIX 须验证同文件系统替换及 mode。若平台 API 不能提供所需保证，先实现并验证对应适配，不能退回原地截断或“删目标再 rename”。
6. 对符号链接、只读目标、硬链接及不支持所需语义的文件系统制定明确策略。无法安全保持链接/元数据语义时，在目标修改前按既有错误边界明确失败；不得静默改变链接关系或放宽权限。Windows 无符号链接测试权限时不能标该场景通过。
7. 发布前重新确认父目录/目标身份、链接指向、来源归属和预期版本仍匹配；首次创建须以不覆盖已有目标的原子发布防止检查后出现竞争文件。发现变化按既有边界退出，不自动转为另一种提交模式。使用已经验证过的同目录原子发布原语，禁止复制覆盖、先 unlink 目标或失败后降级到 writeFileString。
8. 原子发布成功（替换或首次创建）就是本次单文件提交点，立即登记 committed，再执行缓存失效、通知及临时清理。为兼容现有成功布尔响应，纯提交后清理失败记录内部待办，不再冒充 MCP_WRITE_FAILED/未提交；当前页面仍按既有待刷新/重新读取路径确认结果，不增加未经定义的公开字段。
9. 替换前失败时，在仍有安全互斥及任务结果的前提下核对原目标字节/身份，验证可证的未提交事实。若发现此前原地写入、外部变化或不完整内容，转结果未知/异常，不拿旧全文自动覆盖；不能靠覆盖回去让测试变绿。
10. 临时清理只针对本次捕获的文件身份；失败保留引用和重试责任，不按共享目录或文件名前缀清理其他任务。提交后的清理失败不回滚新目标。进程意外退出后的残留若要自动清理，必须另有安全所有权规则；本批不凭年龄删除或自动重放待提交内容。
11. 显式记录原子可见性与断电持久性的区别。本批提交点沿用成功替换后的单文件可见语义，不把它写成多文件事务或跨进程崩溃恢复承诺；若要求断电后可持久，需按目标平台补文件/父目录同步及实测，不能靠 rename 名称推断。
12. 新原语保持既有公开错误 code/ref 和 JSONC 最小补丁语义；不把继承字段、展开凭据写回项目文件。不得扩大公开错误类型来掩盖结果未知；内部诊断与对外已提交/失败结果分开。

#### 4.12.1 合法首次创建与已有目标替换分流（P9-B 补充）

Config.update 与 updateGlobal 当前允许缺失文件按空配置合并后保存；updateMcp 的来源文件缺失则有既有 404 语义。原子提交不得把前两条合法首次保存变为“旧文件不存在”失败，也不得借创建分支重建已删除的 MCP 来源。

1. 调用者显式声明提交模式及缺失语义：Config.update/updateGlobal 允许首次创建，updateMcp 仍要求获胜来源存在；同目标 schema 注解只处理其已读取且版本匹配的文档，不凭旧缓存创建已删除文件。默认初始化与旧 TOML 配置迁移是独立入口，按第 4.12.2 节显式允许其既有创建行为，不能和既有文件注解混为一谈。不要在 helper 内对任意 ENOENT 自动创建。
2. 锁内将目标状态分成“已有且可读取”“确认不存在”“读取/解析/权限异常”。只有确认不存在且允许创建，才以既有空配置规则生成新文档；EACCES/EPERM、损坏文档、目标是目录或链接目标不可安全确定时按既有错误边界退出，不伪装成空文件。
3. 对创建路径解析最近已有祖先、父目录身份及剩余路径，防止大小写/junction 别名创建另一份配置；保持原有锁键和协议。允许创建哪些父目录必须逐调用者记录既有行为或已有初始化前提，本批不新增任意目录自动创建。若原路径允许建父目录，保留其权限与链接检查规则；若父目录无效或发布前身份变化，在目标修改前退出。
4. 新文件没有旧 ACL/mode 可复制，应沿用调用者既有安全权限策略，并实测 Windows 预期继承/限制与 POSIX mode/umask；临时内容在发布前也不得更宽。已有目标仍执行第 4.12 节的元数据保持，不把创建策略用于放宽已有文件。
5. 首次创建同样先独占创建同目录临时文件、完整写入/校验并关闭必要句柄，再用已验证的“不覆盖已有目标”原子原语发布。仅检查目标不存在后普通覆盖式 rename 不满足要求；不得直接对最终路径 writeFileString、先建空目标再填充，或创建失败后自动切换成替换模式。平台不支持所需保证时，发布前明确失败，不能降级。
6. 发布时若另一写入者已创建目标，本次不得覆盖该文件；按调用者现有错误边界返回竞争失败，清理自己的临时文件。需要重试时重新读取、重新校验并形成新的受控操作，不在原提交票据中无条件重放或覆盖。通过真实竞争者验证目标字节不变，不把本进程内锁测试当全部竞争证据。
7. 首次发布成功才登记 committed；无外部竞争创建时，发布前可证失败应保持目标不存在；若竞争者已创建，证明本次未覆盖其文件，不把他人文件误判成本次 committed。结果未知时保留核对责任。提交后清理/刷新失败、取消与租约释放规则与替换分支一致；此分支的“旧状态”是不含目标文件，不虚构旧版本或旧文件元数据。失败留下的本次空父目录只按已证明所有权处理，不递归删除共享父目录。
8. 现有第 4.12 节的状态表与 I44～I51 描述已有目标替换；首次创建按本节及 I52～I55 解释，并适用相同服务票据/原子可见性/取消责任。不能把“读取旧目标失败”直接当成创建失败结果确认。

#### 4.12.2 写入入口覆盖、默认初始化与旧 TOML 配置迁移（P9-B 补充）

以下入口清单是最低覆盖范围。P6 仍须检查本轮源码是否新增同目标写入者；找到新增入口先登记再实施，不以此表代替实际调用图。配置 TOML 迁移与 R3-03B 锁协议迁移不同，本节不启用后者。

| 真实入口 | 目标与发布模式 | 锁与行为必须保持 |
| --- | --- | --- |
| Config.update | 项目 config.json，已有文件替换或允许首次创建 | 保留现有 withLock；锁内读取、合并并提交 |
| Config.updateGlobal | globalConfigFile() 选定的文件，已有文件替换或允许首次创建 | 保留现有 withLock、候选优先级与 JSON/JSONC 语义，不因改提交 helper 另选文件 |
| Config.updateMcp | 捕获的获胜来源，仅已有文件替换 | 保留来源/版本检查和缺失 404，不重建删除项/来源 |
| loadConfig 的 schema 注解 | 已读取的原文件，仅版本匹配时替换 | 保留 tryWithLock；拿不到锁跳过可选注解，不升级为阻塞锁 |
| loadGlobal 的默认 schema 初始化 | 原 globalConfigFile() 目标，确认不存在时首次创建 | 保留 tryWithLock 和原环境门禁，竞争创建不得覆盖 |
| loadGlobal 的旧 TOML 配置迁移 | 全局 config.json，已有文件合并替换或首次创建；提交后处理 legacy config | 保留 tryWithLock；已有 JSON 值优先，目标发布成功后才能处理旧源删除 |

1. 默认初始化仅在 OPENCODE_CONFIG、OPENCODE_CONFIG_DIR 和 OPENCODE_CONFIG_CONTENT 均未指定的原有条件下执行。保留原全局文件选择和建父目录行为；锁内重新确认目标不存在，再走原子不覆盖创建。竞争者抢先创建时不覆盖它，继续沿既有加载流程读取真实文件，不把可选初始化竞争升级成无条件引导失败。
2. 默认初始化仍属于完整加载器的既有副作用。第 4.7 节的轻量来源服务不得为了复用它而调用 loadGlobal 或引入默认文件创建。显式环境路径/内容的隔离样本使用不含 legacy config 的默认根，证明未因默认初始化写入该目录；存在 legacy 的迁移样本另列，不能把初始化门禁误解为禁止全部既有全局迁移。
3. TOML 迁移在现有目标锁内捕获旧源身份和原文版本，读取目标的最新内容；转换 provider/model 等原有字段时只保留原文引用。按现有 defaults → current 合并，已提交 JSON 值优先，不用旧 TOML 覆盖它。目标缺失走创建分支，目标存在走替换分支；不能绕开同目标普通保存的锁和版本检查。
4. 先原子发布目标并登记内部 committed 事实，再处理与既有合并顺序一致的内存结果及旧源删除。发布前失败或结果未知均保留旧源；未知结果先核对，不自动重新投递迁移写入。旧源删除前复检捕获身份/版本，已改变则保留，不按路径盲删替换后的文件。
5. 目标已提交但旧源删除失败时，保留新目标与旧源，记录脱敏清理责任；不能倒退成未提交、回滚目标或丢失第一次清理错误。后续加载必须仍以当前 JSON 为优先，不把遗留 TOML 当作可无条件覆盖的新命令；清理重试只针对可证明归属的旧源。该路径不承诺跨文件事务或进程崩溃后的自动重放。
6. 可选注解、初始化和既有迁移保持原加载器的错误/中断边界；不得靠外围 catch 吞掉内部未完成写入、未知提交或清理责任。没有 HTTP 请求时由服务登记内部任务及提交状态，不虚构页面票据；取消、退出排空和租约释放仍按第 4.8/4.11 节执行。

#### 4.12.3 提交原语与锁拥有者的明确契约（P9-B 补充）

ConfigDocument.withLock 会等待获取锁；tryWithLock 用于加载器的可选写入，拿不到便跳过。Config.update 已在锁内调用 loadFile，loadFile 又可能触发 schema 注解。原子提交接入必须保留这条非阻塞关系，不能制造嵌套自等待。

1. 内部“已持锁提交”只做锁内目标校验、临时文件、原子发布和结果登记，不再调用 withLock/tryWithLock，也不自行释放调用者的租约。只能从受控的持锁回调或目标绑定的内部许可调用；不能用可随意传入的 locked: true 布尔值绕过互斥。
2. “获取锁后提交”的包装只为尚未持锁的入口提供。每次操作的锁只能由一层获取，持有范围覆盖首次读、合并/版本检查、发布与必要的结果交接；不能读完后才加锁。包装取得许可后调用同一个已持锁实现，不复制两套提交逻辑。
3. update/updateGlobal/updateMcp 的现有 withLock 回调调用锁内实现。加载器 schema 注解、默认初始化和 TOML 迁移保留现有 tryWithLock 回调，在成功取得租约后调用同一锁内实现；tryAcquire 失败时不调用提交，不排队等待同一写入者，也不启动临时文件写入。
4. Config.update 持锁加载无 schema 配置时，注解尝试仍可跳过，正常配置保存继续完成。不得把 loadFile 的可选补写改为调用阻塞包装；也不得为消除嵌套而把目标读取/版本检查移到锁外。
5. 显式写入等待锁时保留既有可取消等待；底层写入投递后由实际任务持有许可，锁内实现真实结束后才由唯一获取者释放。锁内实现不能调用需要再次取得同一锁的 loader/刷新/通知路径；需要重新读取或做 schema 校验时使用不附带写入副作用的读取/解析步骤。
6. I65～I67 必须通过真实配置入口和实际锁实现验证有界完成、非阻塞跳过及互斥；仅检查 helper 调用次数或把锁改成可重入的 mock 不足以证明无自等待。不得为这次提交重构更改锁协议、键或全局可重入语义。

平台原语、完整写入入口、合法首次创建、锁归属与非阻塞语义、ACL/链接保证共同构成 P9-B 的实施出口。不能只补一个 rename helper 或只在内存模拟文件系统上通过就标完成。

## 5. OBS-02：测试收尾 EPERM 定位和修复

### 5.1 已知事实与诊断顺序（P12）

当前 test/preload.ts 的重试只识别 EBUSY；EPERM 直接抛错，Windows EBUSY 耗尽还会直接 return。后者也是清理可见性缺口，需一起审计；本轮实测的是 EPERM，不能把未实证的占用原因写成定论。

在新的隔离证据根执行最小正式联合，不改 ACL 掩盖失败：

1. 在删除抛错当场记录 code、syscall、相对隔离根的 path/dest、PID、时间、实际失败文件类型；检查是否在隔离根内以及是否涉及重解析点。
2. 保留 AppRuntime.dispose 开始/完成、目录实例/共享服务退出、依赖任务投递/底层结束/锁释放的关联时间。只给本轮任务打内部关联，不记录 npm 私有凭据。
3. 进程仍存活时检查精确失败路径的权限/属性和句柄。句柄诊断工具存在则查询，否则记录工具缺失，不能用目录清单替代占用证据。
4. 判断是本进程句柄、外部临时占用、恢复后的 ACL/只读属性，还是删除自身竞争。原权限安全描述符与恢复后状态比较，不执行放宽 ACL 的诊断“修复”。
5. 若未复现，保留原失败并用受控资源建立删除竞争；受控样本只能验证机制，不能据此认定历史那一次原因。

### 5.2 按证据选择改法（P13）

| 诊断结论 | 应改位置与办法 | 禁止替代办法 |
| --- | --- | --- |
| 本进程已知连接/文件句柄未释放 | 给实际 owner 补作用域收尾，等待真实释放后再删除 | 只加 GC 或延长 sleep |
| 后台安装/文件 Promise 脱离生命周期 | Config 创建任务时登记责任，退出时等待底层真实完成；必要时修改 Npm 调用边界并补专项 | 仅将 forkDetach 换成 forkScoped 后就认为不可取消 Promise 已结束 |
| 权限恢复不完整 | 在唯一权限夹具入口修正并验证恢复，不额外创建另一恢复路径 | preload 放宽整个根 ACL |
| 已证明外部短暂占用，稍后自行恢复 | 根内目标可有界重试 EPERM/EBUSY，并实际验证删除；记录重试结果 | 永久吞异常或无限重试 |
| 原因未证实 | 保留失败与证据，继续缩小最小复现 | 把 afterAll 移到进程退出后或修改测试期望为成功 |

Npm 线索：config.ts 存在 forkDetach；core/npm.ts 使用 Arborist 的实际 Promise。取消 Effect fiber 不等于 reify 停止。若该线索成立，需持有并观察底层 Promise 到真正完成，锁也只能在真实写入结束后释放；同时测正常完成、拒绝、取消与运行时退出。不盲目屏蔽整个安装的取消，也不无限延长退出等待。

### 5.3 收尾改造和回归（P14）

1. 按第 4.9 节区分退出观察结果和实际关闭。只有原始 AppRuntime 关闭及本轮后台写入均完成，才递归删除；超时/失败且资源仍活跃时保留目录、记录原因并非零退出，不能边写边删。
2. 删除重试使用一个明确总预算和有限次数。默认以现有名义 3 秒等待量作为设计起点，实施时记录实际值；若实测需要调整，解释原因，不把参数当根因修复。
3. 不论 EPERM/EBUSY，预算耗尽都抛出带脱敏诊断的失败；删除结束后确认目标不存在。移除 Windows 耗尽直接 return 的假成功路径。
4. 拒绝越界目标和目录重解析点的危险递归清理；Windows 原生 PowerShell/文件 API 全程完成操作，不跨 shell 拼接路径。
5. 用独立测试进程验证真实 preload 的退出码：正常删除、受控暂时占用后释放、永久拒绝、后台写入尚未结束、释放失败。永久错误必须非零退出且保留诊断。
6. 控制测试不得改生产目录，错误路径不得泄露文件内容。测试后恢复权限并清理自己资源，失败收尾同样列入结果。

OBS-02 只有在“底层责任修复有证据 + 正式联合整批退出 0 + 实际无残留”都满足时关闭。只补 EPERM 重试属于清理健壮性改善，不能宣称已找到历史占用根因。

## 6. OBS-01 和导航不稳定的专项定性（P15）

本节不预先改产品，以免把测试观察问题误当实现缺陷。

1. 为保存命令、保存触发的自动刷新、按钮触发的手动刷新分别建测试请求关联，不能只按 URL 接收“第一个 refresh”。
2. 用上游/提交/刷新屏障安排“保存已提交但自动刷新未结束”再点击 Get models；断言该按钮在既有产品语义下应禁用、排队或显式冲突的哪一种行为。
