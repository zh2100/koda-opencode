## 5. D01、D02：取消开始门闩，统一操作所有权

### 5.1 收紧平台适配器契约

1. 将 apply 从 `apply(file, started)` 改为只接收 file 的操作。started 回调不再控制生命周期。
2. 删除 openedGate、openGate、opened 及以 ctx.started 决定是否清理的分支。
3. Windows、POSIX 和受控测试适配器同步迁移，不保留一套自动补 started 的兼容接口。
4. 测试如需控制“进入操作”“真正修改”的时点，在适配器内部使用自己的 Deferred/Promise，仅用作外部观察，不能回流为收尾资格。
5. apply 的返回/拒绝代表该次底层操作真正结束。Windows 子进程必须等待实际结束；POSIX 必须等待 chmod Promise。禁止 detached 子进程或未等待的权限写入。

### 5.2 投递前建立责任

1. 原权限和恢复上下文仍由无权限修改的 acquire 阶段准备。
2. 开始修改前进入窄小不可中断区域。
3. 在调用适配器之前登记“已投递、可能修改，需要收尾”，即使随后同步抛错也不能跳过恢复。
4. 在同一保护区域创建唯一 mutation Promise 并立即附上 resolve/reject 处理，保存统一的完成结果。
5. 同步抛错、返回 status 非零、返回 error、Promise 拒绝均转为明确失败，保留原原因；不等待额外开始事件。
6. mutation 被投递后，必须等其真正结束才允许恢复。操作可能已经部分生效时，采用保守恢复。
7. 唯一允许零次恢复的分支：尚未投递任何权限修改，例如捕获快照失败或在进入修改前即取消。

### 5.3 取消语义

1. 投递前取消：不调用 apply，不恢复权限，保留中断。
2. 投递后取消：记录/保留取消，等待该次操作结束，再统一恢复，整体最终仍为中断。
3. 适配器内部暂停但尚未真正写权限，仍属于已投递。不能因实际写入尚未发生而提前放弃所有权。
4. 恢复必须晚于 apply 完成。整个生命周期结束后，不得仍存在能够修改该文件的后台 Promise 或子进程。
5. apply 完成并完成必要状态记录后，探测和 HTTP 请求恢复正常可中断。不能把整个 HTTP 请求放入不可中断区域。
6. 若取消与 apply 失败同时出现，原操作失败也要保留为可追溯信息，不能因中断竞争而静默丢失。

### 5.4 结果处理必须完整

| apply 结果 | 请求是否执行 | 收尾责任 |
| --- | --- | --- |
| 返回成功并完成真实拒绝探测 | 可以执行 | 正文结束或取消后统一收尾 |
| 返回 error/status 非零 | 不执行 | 等操作结束后恢复，报告原错误 |
| 同步抛错 | 不执行 | 保守恢复，报告原异常 |
| Promise 拒绝 | 不执行 | 保守恢复，报告原拒绝 |
| 操作仍挂起时取消 | 不执行或中断当前阶段 | 等操作完成再恢复，保留中断 |

不得通过 Promise.race 只取开始通知、忽略最终结果，也不得吞掉未处理的 Promise rejection。

## 6. D03：唯一释放路径保留错误

### 6.1 使用有错误通道的统一资源边界

推荐将 withConfigReadDenied 组织为一次 Effect.acquireUseRelease：

- acquire：写入测试文档、捕获原权限和构造上下文，不修改权限。
- use：已登记责任的 apply、拒绝探测、HTTP/受控请求回调。
- release：唯一 finish，等待已投递操作、恢复并验证原权限、汇总错误。

当前 Effect 版本的 acquireUseRelease 支持 release 错误。实现前核对版本签名，用实际回归证明失败与中断的组合结果。

权限修改不能移入 acquire 的未完成部分，因为 acquire 失败时不保证进入 release。

### 6.2 移除双出口

1. 删除只在正常路径里手动 finish、在 finalizer 里 finish(...).pipe(Effect.ignore) 的结构。
2. release 返回的失败必须到达最终 Exit/Cause，不使用 ignore、catch(() => void) 或只打印日志来消除它。
3. 不为防止错误重复而全局忽略 release。应由 finish 的完成结果和幂等状态避免重复 OS 操作。
4. 幂等验证仍可保留在夹具内部测试观察边界，但真实调用者不能自行再触发释放。
5. withConfigReadDenied 返回成功必须在资源释放完成之后；调用者此时才能读取并断言文件状态。

### 6.3 finish 与错误记录

1. 根据“已投递”判断是否需要等待和恢复；不能依赖适配器开始通知。
2. 等待 mutation 结束，统一处理其完成状态。正文已经传播的同一错误不重复包装多份，取消时未传播的操作失败仍保留。
3. 保持最多两次恢复的同一预算。恢复命令、读取、mode/ACL 验证中的异常或失败都计入这套预算，不能绕过后续尝试。
4. 恢复成功后保存最终已恢复状态；失败历史只追加，不清空。
5. 普通正文失败、缺陷、中断与清理失败都应出现在最终 Cause 的对应部分。不以一个只含字符串的新 Error 抹去全部错误身份。
6. 环境变量、实例和数据库的清理仍保持独立，权限收尾失败不能阻止它们释放。

| 正文结果 | 清理结果 | 必须观察到的整体结果 |
| --- | --- | --- |
| 成功 | 首次恢复成功 | Success |
| 成功 | 首次恢复失败、第二次成功 | Failure；资源已恢复，首次错误保留 |
| 失败 | 恢复成功 | 原正文失败 |
| 失败 | 恢复失败 | 原正文与恢复错误都可见 |
| 中断 | 恢复成功 | Cause 含中断 |
| 中断 | 一次失败后恢复成功 | Cause 含中断和首次恢复错误；资源已恢复 |
| 中断 | 两次恢复失败 | Cause 含中断及两次恢复错误；资源未恢复 |

### 8.1 取消控制方式

1. 等待适配器内部发布“已进入但尚未写权限”的信号。
2. 对整个 withConfigReadDenied fiber 请求中断，不在控制器此处等待中断完成。
3. 由独立控制器释放真实修改操作，然后等待目标 fiber 及其 release 结束。
4. 检查操作轨迹、实际资源状态和完整 Cause；不能只检查内部 stage。
5. 将所有受控异步操作 join 完成，再做最终状态断言，避免断言后仍有晚到动作。

如需证明取消不会过早完成，使用明确的控制信号或有界完成观察；超时仅判定死锁，不作为顺序正确的证据。禁止用 sleep 猜测调度已发生。

### 8.2 断言质量要求

- 不允许成功或失败二者任一即可的恒真断言。
- 不允许用例体直接 return 充当平台 skip。
- 恢复次数断言必须同时配合错误、最终权限及执行顺序断言。
- 不能为让回归通过而让适配器必然先通知 started，或在断言前额外手工恢复一次。
- 使用同一真实夹具，失败注入限制在适配器边界，不全局替换 fs、进程或 Effect。

## 9. 实施顺序与每步产物

1. 固化 B01–B03，保存失败基线。补齐 B04–B10 的受控边界。
