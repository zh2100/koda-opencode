## 3. 统一动作契约：先写规则，再写代码

### 3.1 身份与阶段

前端动作至少区分：

1. serverScope：使用项目已有的稳定服务器身份，不能仅靠供应商 ID、显示名称或组件是否存在。
2. scopeGeneration：本次设置局部上下文的生命周期代次；A → B → A 的后一个 A 是新局部生命周期，共享服务器 SDK 可以保持原实例。
3. entityId：实体真实身份；同名、同业务 ID 重建不等于原实体。
4. operationId：命令身份；原命令精确重试复用，新编辑、新命令必须新建。
5. requestSequence 与字段/供应商水位：解决同一生命周期内乱序、分片合并与用户编辑保护。

这些身份沿用现有类型和编号，不在多层各自生成一套。不为没有相应语义的只读刷新新增服务端写入协议。错误和忙状态分别持有归属，不能只用全局“最后一次请求”。

统一阶段为：创建意图 → 校验身份/版本 → 发出请求 → 服务端提交（写动作）→ 接纳 ACK → 刷新投影 → 清理。HTTP 返回与页面刷新不是同一个提交时点。

### 3.2 五类动作的责任

| 动作 | 身份及提交时点 | 回包接纳 | 取消及清理 |
| --- | --- | --- | --- |
| 保存供应商/密钥 | 服务器、entityId、operationId、预期版本；以服务端事务提交为准 | ACK 确认原草稿；请求后编辑保留；切服后不写新页面 | 提交前可取消等待；提交后不假装回滚；凭据清理/通知由原服务作用域负责 |
| 清除密钥 | 原实体及命令身份；以配置提交为准 | 清原草稿须确认编辑水位，不能清新输入；hasKey 来自接纳的新状态 | 未提交失败保留原密钥；已提交清理待办不能因关窗遗失 |
| 删除供应商 | 原 entityId 及命令身份；以删除提交为准 | 精确重试沿用既有 receipt 语义；旧 ACK 不删除同 ID 后继 | 仅清本次所有的凭据/缓存；取消不代表服务端未删除 |
| 连接测试/获取模型 | 捕获服务器、实体、地址/认证版本及请求序号；纯探测无配置提交，若有目录提交按既有事务执行 | 期间清密钥、换地址、删除或重建后拒绝过时成功 | 释放本次 token/许可；不清后继 token；网络取消不漏清理 |
| 刷新设置/目录 | 捕获服务器、生命周期和各分片基线；刷新本身不增加认证配置版本 | 合并未变化分片，空快照有明确删除语义；旧失败不覆盖新错误 | 停止旧订阅/等待，旧结果不得写 B；失败保留可重试责任 |

补充规则：

- 同供应商同动作继续遵守既有“最新请求拥有忙状态”；不同供应商互不覆盖，不改成所有请求完成才统一解除。
- A 上已发出的写命令可以在 A 提交；切到 B 后只允许更新仍有效的 A 缓存，不能写 B、清 B 草稿或关闭 B 新弹窗。若 A 作用域已销毁，由重读恢复状态，不复活它。
- 已提交但刷新失败，要展示已提交/待刷新，只重试刷新；不得再次保存或删除来补页面。
- 服务端确认失败不得显示成功；网络断开且提交未知时不得断言回滚，应按既有幂等查询/重试规则确认。
- 所有清理都绑定获取时的资源、实体及代次；不能重新读取“当前服务器”来释放旧资源。
- 生命周期销毁先使旧回包失去写入资格，再停止订阅和等待；最终清理有独立归属。

## 4. ACC-01 根因与实施设计

### 4.1 根因链

SettingsServerScope 只在现代布局创建 SettingsServerDataProviders；经典布局直接返回原 children。全局切服会销毁原服务器作用域，但 Dialog 的独立 root 可以继续存活。经典弹窗保留旧 owner 提供的 SDK，所以界面指示器已为 B，请求仍发往 A。

这是请求目标错误，不能只在 hook 内增加回包序号。

### 4.2 改动步骤

1. 列出经典设置、现代设置、供应商页、Models 页及嵌套编辑弹窗的实际挂载路径，标记 Global、QueryClient、ServerSDK、ServerSync、Models 的提供者与所有者。
2. 在设置根边界明确选择服务器：经典取当前全局服务器；现代取既有设置 picker 的选择。复用现有 accessor，实施时从真实类型确认，不新增平行状态。
3. 两种布局都进入同一 SettingsServerDataProviders 边界，按稳定服务器身份及设置局部生命周期重建绑定与页面状态，复用 Global 拥有的共享资源。服务器暂不可用时显示已有加载/无服务器状态，不能 fallback 到旧可编辑页面。
4. 该边界必须由能跨路由服务器销毁存活的稳定 owner 驱动；仅把 Show 改为无条件渲染不保证修复。若当前 Dialog owner 仍使选择 accessor 停止更新，应将设置专属挂载提升到稳定 owner，保持通用 Dialog 语义。
5. QueryClient、SDK、同步数据的 provider 引用同步切换到目标服务器既有资源；只重建设置页自己的 Models provider、查询观察者和局部状态，不销毁 Global 的 QueryClient/SDK/ServerSync。审计 props.children 是否提前求值并捕获旧上下文，必要时改为在新 provider 下创建。
6. 切服使设置页旧局部代次失效，只取消设置页独占读取、解绑局部订阅，不取消其他消费者共用的 query 或服务事件流。草稿、错误与忙状态不得跨服复用；回到 A 读取真实状态，不继承旧生命周期。
7. 保存/删除/清 key 在点击时捕获命令归属，后续回调不临时读取 B 的 SDK。旧操作完成不得关闭后来打开的弹窗。
8. 验证 Models 页及聊天侧现有模型缓存收到正确服务器数据；本批不修改 Session/Timeline。若必须扩大，先按 app/AGENTS.md 采集生产性能基线并另列影响面。
9. 保留现代 picker 既有语义与 FUP-02 并发状态规则。除非证明局部边界无法修复，不修改通用 Dialog root 生命周期。

退出条件：旧两条页面失败转绿，跨服真实写操作、Models 和第 4.3 节 U13～U18 通过；关闭重开不再是切服生效的必要步骤，共享消费者保持正常。


### 4.3 设置局部状态与共享资源的所有权

现有 Global.ensureServerCtx() 按服务器 key 缓存 QueryClient、SDK、ServerSync，其 root 属于 Global。设置页不是这些资源的唯一消费者。“重建设置上下文”只表示重新建立局部 provider 绑定，不表示重建或 dispose 共享资源。

| 资源 | 所有者 | 切服/关闭设置时允许操作 | 禁止操作 |
| --- | --- | --- | --- |
| QueryClient、SDK、ServerSync 的共享实例与事件流 | Global 对应服务器上下文 | 切换引用，解绑本页观察者 | queryClient.clear()、共享实例 dispose、取消全部查询或关闭共享事件流 |
| 设置页草稿、错误、busy、操作票据 | 本次设置页局部生命周期 | 提升局部代次并销毁 | 用共享 SDK.scope 代替局部生命周期代次 |
| 设置页独占请求、订阅、模型视图 | 创建它们的局部 owner | 取消独占读取、取消本页订阅、销毁本页 provider | 释放共享底层连接或其他页订阅 |
| 已提交 A 命令的后续投影/清理 | 原服务 scope；缓存操作带 A 身份 | 原服务完成；仍有效的 A 缓存按版本接纳 | 由 B 弹窗代偿、清 B 草稿、为晚到回包复活旧页面 |

服务器选择具体映射：经典布局使用 useServer().current（全局 active 对应连接）；现代布局使用 useGlobal().settings.server.selected()。两个 accessor 不互相赋值，不以现代 settings 选择冒充经典 active。无可用服务器时禁止 SDK fallback 到其他旧连接。

挂载规则：

1. 在稳定 owner 下读取服务器 accessor，keyed 边界只管理设置局部生命周期；A → B → A 的第二个 A 复用同一个有效共享 SDK 也必须产生新局部代次。
2. 同 key 连接若被移除后重加、认证连接参数或共享上下文实例改变，重新核对归属；不能仅以显示名称或 origin 判同一次生命周期。
3. 只有 Global 原有服务器移除/退出逻辑可以关闭共享资源；本批不新增设置页反向清理 Global 的通道。
4. 设置请求如果借用共享 query 的 Promise，销毁时只停止局部接纳；没有独占取消权就不调用共享 cancelQueries。局部 HTTP AbortSignal 只能交给自己创建的请求。
5. 检查 provider 引用、SDK 目标和 QueryClient 目标三者一致；供应商与 Models 的界面派生状态使用同一局部归属规则。

## 5. ACC-02 根因与实施设计

### 5.1 根因链和不能遗漏的边界

Windows 实测 access(R_OK) 成功而 readFile 抛 EPERM。预检未阻止 Config 首次失败进入 InstanceState 的 ScopedCache。completeLoad 仅移除外层 Entry，目录服务失败缓存未失效；disposeAll 又失去该目录的清理入口。

另有必须处理的实现边界：instance-registry.disposeInstance 当前使用 Promise.allSettled，却不报告 rejected 结果。直接调用它不能证明清理成功。本批须验证并收口清理结果的观察机制，不能在报告里默认所有 disposer 成功。

### 5.2 采用的生命周期方案

以 InstanceStore 为同目录加载、替换和清理的协调入口，保留目录级缓存机制，不在所有服务上盲目关闭失败缓存。协调只跨越有限的加载/交接步骤，不持有一把锁包住完整 HTTP handler；请求内 MCP 来源刷新按第 5.4 节执行，失败清理按第 5.5～5.6 节限定到本代资源。目录记录有唯一 Entry/代次和阶段：loading、ready、cleaning、failed-cleanup（内部状态，名称可依项目风格调整）。

同目录任何创建新代、reload、配置重载回调、disposeDirectory、disposeAll 都参与该协调；不同目录继续并行。不能只保护 completeLoad 而让 reload/onConfigReload 绕过。

| 阶段 | 对后续请求的规则 | 所有权 |
| --- | --- | --- |
| loading | 共享当前加载结果，可取消自己的等待 | 引导任务属于服务 scope，不因一个客户端断开杀死所有共享等待者 |
| ready | 返回有效上下文 | 当前 Entry 拥有已注册的目录状态 |
| cleaning | 不启动后继引导；等待交接可取消 | 失败/销毁代持有目录清理责任 |
| failed-cleanup | 明确失败；仅对持有实际句柄且可重试的剩余清理执行有界重试 | 保留任务结果与资源责任；不能以再次 invalidate 返回成功解除阻止 |
| 已完成清理 | 条件移除旧 Entry，允许新代创建 | 旧代不得再按目录清理新代 |

失败请求保留原始错误，后续独立请求在清理完成、权限恢复后启动新代；不无限自动重放引导。短状态交接可以不可中断，等锁、读文件、等网络与全程清理不能无界屏蔽取消。

### 5.3 具体修改顺序

1. 审计 InstanceState 与 registry 的全部注册者/调用者，列出谁能绕过 InstanceStore 发起同目录初始化。若有绕过入口，接入同一协调或带代次隔离，不能宣称只加外层锁即可完整保护。
2. 先建受控生命周期测试：Config 首次失败、清理被屏障挂起、并发 load/reload、旧清理晚到。记录真实 init/finalizer 次数，禁止复制缓存逻辑做假实现。
3. 将失败 Entry 保留到清理完成；先登记本代实际资源的清理记录，再转 cleaning，等待有限收尾，最后按 Entry 身份发布结果和条件移除。不得“先删 Entry，再无条件 runDisposers(directory)”，不得把全目录 registry 清理当成失败代清理。
4. registry 对选定资源集合继续尝试全部 disposer，独立承接同步抛错和 Promise 拒绝，输出可观察的内部结果。失败引导调用本代清理，显式整实例销毁才走全量集合；禁止统一改为抛 AggregateError 后由调用者失控传播。原错误与清理错误按第 5.7 节分别保存、映射。
5. 若清理失败或尚未完成，保留实际任务/资源句柄、代次和原失败；区分可重试失败与仍在执行，不重复投递同一释放。按第 5.5 节的次数与截止时间完成交接；超时不代表清理完成，后续请求不得使用残留缓存或创建竞争新代。
6. load、reload、dispose、disposeDirectory、disposeAll、onConfigReload 与 Config.get/invalidate/mcpSource 的直接失效入口均纳入调用清单。按第 5.4 节拆分来源读取、配置快照刷新与完整销毁；不在清理器内递归等待本目录 load，也不等待发起重载的 HTTP 请求自己结束。所有请求等待及 Deferred 均有明确完成路径。
7. 校正 bootstrap 读取边界：复用 ConfigPaths.discover 与主加载器的真实来源顺序，不以 access 成功证明可读；优先由实际 Config 读取返回 typed 错误，必要预读使用同一读取规则。预读成功后文件仍可能变化，实际读取失败仍须走完整清理。
8. 保持来源缺失、首次损坏、权限拒绝、远程/环境/托管来源的既有区别；保持 400、503、ref 与脱敏规则，不吞读错或返回空配置。
9. 先确认配置成功，再执行插件等后续初始化；失败后的重试不重放已发生的业务副作用。为插件初始化计数设受控断言，避免为“恢复”再次创建会话、执行 prompt 或外部任务。
10. 不直接修改权限夹具的既有所有权规则。withConfigReadDenied 仍是唯一入口；等待取消不等于底层权限修改完成，恢复必须等修改落定。
11. 正式化 C:/fup-next-20261113 中的真实 TCP 回归：迁入项目测试目录，使用正式 Server.listen、scoped 临时目录和既有测试层。测试包装器只观察 TCP 取消与夹具收尾，禁止为产品添加测试接口。

退出条件：Windows 两条冷启动失败均直接恢复；无手动 dispose、预热、重启或换目录；第 5.4～5.7 节及 I13～I25 均满足，失败代不误清后继、PTY、活跃请求或丢失错误。


### 5.4 请求内重载与协调入口：避免绕过和自等待

当前 Config.mcpSource() 在 changed 分支依次执行 invalidate、InstanceState.invalidateAll、reloadHooks、registry.disposeInstance，再在同一请求中读取 InstanceState。这个具体入口必须修改，不能留到“后续审计”。Config.get() 因环境变化直接失效的分支也必须纳入。

采用以下分工，不新增“完整请求期间持锁”的机制：

| 路径 | 允许范围 | 协调方式 |
| --- | --- | --- |
| mcpSource 读取原文与来源链 | 发现来源、解析、按现有优先级合并、检查获胜来源与版本 | 生成本次读取快照，不发全目录 disposed，不初始化插件/PTY |
| Config 快照更新 | 更新该目录的配置快照及其版本/缓存 | 通过 Config 自己的有限刷新任务；不借读取接口销毁整实例 |
| 冷启动失败收尾 | 仅关闭失败代实际创建的资源 | InstanceStore 的 Entry/代次交接及本代清理账本 |
| 显式 reload / dispose / 服务退出 | 按原产品语义替换或关闭完整实例 | InstanceStore 协调，明确关闭原因，不与来源读取混用 |

实施顺序：

1. 把来源发现、未展开原文读取、来源优先级合并和 source/version 计算从运行时初始化中分离，复用同一实现。不得直接把可能带依赖安装、插件准备等副作用的 loadInstanceState 当成纯读取函数。
2. mcpSource 删除其“失效所有目录 + reload hooks + 全目录 registry 清理”的组合调用，改走有限的来源快照刷新。保持远程 well-known、环境内容、托管偏好、显式文件、.opencode、继承引用及获胜文件缺失的既有语义。
3. 如本次读取还需使运行时配置生效，将原因与目录配置版本交给 Config/InstanceStore 对应协调任务，复用已有通知，不在来源查询中再次发起完整初始化。不重放原保存命令或 HTTP handler。
4. 目录协调只保护“读取当前 Entry → 标记阶段/责任 → 安排任务 → 条件发布”的短交接；等待任务时释放互斥，取消只影响等待者。底层仍在运行的任务继续由服务 scope 观察，不能丢失。
5. 同目录嵌套请求带原 Entry 身份识别归属。清理器禁止调用本目录 load/reload 来取得自己将释放的状态，必须使用已捕获句柄。不得因增加重入锁而让清理等待自身 Deferred。
6. 已经进入 handler 的旧请求不会因为新请求调用 load 而自动失效。可继续使用的不可变快照在当前请求内保持一致；若操作需要最新可变状态，提交前重新检查配置/实体版本。不得让旧请求通过 InstanceState.use 悄悄创建新代资源。
7. 不给完整 HTTP handler 或 WebSocket 的整个存活期持有目录互斥，也不要求来源读取等所有活跃连接退出才返回。完整销毁按既有终端关闭语义收尾，恢复性读取不触发这条路径。
8. 若发现现有调用者无法区分来源读取与运行时重载，先补调用图并完成职责拆分再写缓存补丁；这属于 S1/S4 的阻断项，不能留给验收时临时修复。

专门验证：两个来源读取同时发现 changed；来源读取与显式 reload 交错；同目录已有进行中的请求；全局配置变化涉及多个目录。断言没有自等待、没有重复初始化、没有跨目录 invalidateAll、没有旧代重新创建可变资源。

### 5.5 清理账本、失败重试和截止时间

已核对本机安装的 Effect 实现：ScopedCache.invalidate 先从 map 删除条目，再 Scope.close；第二次失效因条目不存在可以直接成功。Scope finalizer 也不能假定会因再次 close 自动重跑。因此“再次 invalidate 成功”不是已释放证据。

清理账本必须在首次释放前登记，记录内部资源 ID、目录、owner Entry/代次、释放函数或可观察任务、状态、原失败、各次清理结果、尝试次数和截止时间。不保存配置原文或凭据。服务注册 disposer 的时间不能替代缓存条目实际创建的时间。

按资源区分处理：

- 对作用域正常关闭：保留实际 close 任务及其结果。任务尚未完成只能等待/观察，不重复关闭；完成后记录释放验证结果。
- 对可重试的底层释放：在资源取得时登记捕获本资源句柄的幂等释放函数，成功时清除责任；失败时记录仍未释放部分。重试该函数，不重跑整段已执行的 finalizer 或已成功的其他释放。
- 对无法证明可重试的 finalizer：保留阻止状态和可定位诊断，不把第二次无资源可失效视为成功。实施前必须把影响本批恢复路径的释放变为可观察、幂等操作；无法做到则该失败路径不算完成。
- 对所有操作：旧 owner 的完成通知只能更新旧账本；不能使用目录名称定位并释放后继资源。

本批设计默认采用以下预算，属于待实现参数，不是实测结论；如项目已有更严格的预算可沿用并在结果中记录实际值：

| 对象 | 默认规则 | 到期行为 |
| --- | --- | --- |
| 单次失败代清理交接 | 最多 2 次可重试释放尝试，共用自第一次投递起 10 秒总截止时间 | 保留 pending/failed-cleanup，完成调用者错误结果，不释放新代引导资格 |
| 同一清理任务的客户端等待 | 可取消，且不超过上述剩余预算 | 中断自身等待；任务及所有权仍由服务 scope 持有 |
| 后续请求补清理 | 未完成任务只加入等待；已结束失败且允许重试的剩余责任开启一次有界恢复周期 | 同周期共享任务，禁止每请求并行投递或自动无限循环 |
| 服务退出观察 | 最多使用剩余预算；无活动周期时单独 10 秒收尾预算 | 报告未释放资源，不谎报干净退出；不启动新业务工作 |

超过截止时间不等于底层 Promise 或不可中断 Scope.close 已结束。必须从可取消的等待端返回错误，保留实际任务的晚到观察；不能只加 timeout 后清空责任。晚到成功经 owner 校验可解除隔离，晚到失败继续保留原因。若底层永久挂起，该目录继续拒绝新代引导，并给出脱敏 ref；不能为“自动恢复”并发再执行同一释放。

原失败与全部清理失败历史一直保留；第一次恢复失败、第二次成功时可标最终资源已恢复，但不能把该次调用整体改成无错误成功。完成次数按具体资源断言，不要求不同恢复周期永远只执行一次。

### 5.6 失败代清理与完整实例销毁分离

registry 是跨服务注册集合，包含 InstanceState 与 PTY 使用的 LocationServiceMap 失效回调。冷启动失败不得直接运行全部目录 disposer，否则可能关闭在失败代引导之前就存在的终端、连接或其他成功资源。

最低实现契约：

1. 服务级注册记录稳定 resourceId 与种类；每次缓存/资源实际创建时记录 owner token。token 至少包含目录和 Entry 代次；已有资源只被借用时不转移所有权。
2. 失败代账本记录“本代实际新建/接管且需释放”的资源，清理使用捕获句柄及 expected owner 条件。注册者是单例并不表示本次引导创建了它的所有缓存。
3. 既有 PTY/Location 或成功实例资源没有本代 owner 时，失败清理一律不选中；新代不得覆盖旧资源所有权后再清它。确需接管的资源必须先完成有证据的交接。
4. 保留显式完整实例销毁入口及其既有 PTY 关闭行为，与失败代清理使用不同原因/目标集合。不能通过把所有资源都排除，破坏真正 dispose/reload/退出的收尾。
5. registry 对选定集合收集所有结果：每个 disposer 先独立捕获同步抛错，再观察返回 Promise；一个失败不阻止其余执行。同步抛错不得发生在 allSettled 参数构造期间而中止后续投递。
6. LocationServiceMap 的内部资源保持原有 location/workspace 身份边界；不得为本批清理统一按裸目录清掉其他 workspace。本批先做实际键与调用者核对，确需改 Core 时登记扩围并补 Core 类型与回归。
7. 清理统计记录 resourceId、owner、调用次数和结果，不输出终端内容或配置。新代资源必须有独立 token，旧清理无法释放它。

必须各有正常对照：失败代引导时已有 PTY/连接仍可使用；显式销毁时原本应关闭的资源实际关闭。仅断言 disposer 调用次数不足以证明资源安全，至少用一个真实隔离终端/连接或对应正式 Location 层断言存活与释放。

### 5.7 内部完整 Cause 与公开 HTTP 错误分开

内部保存原始 boot Exit/Cause、原 McpEditError 与 ref、各资源清理 Cause、是否仍有后台任务以及 owner。registry 返回内部结果，不把 AggregateError 或含底层正文的异常直接扔到 HTTP。

现有 InstanceContextMiddleware 根据 typed McpEditError 返回协议错误，其他未知 Cause 可以进入 die/空白 500；因此必须在入 middleware 前选择公开错误，不能依赖聚合 Cause 中“第一个碰巧找到的错误”。

| 情况 | 对调用者的结果 | 内部保存 |
| --- | --- | --- |
| 原配置读拒绝，清理成功或失败 | 保留 MCP_SOURCE_READ_FAILED 的 503 和原 ref | 原读错、所有清理错误及是否完成 |
| 原配置损坏，清理又失败 | 本次保留 MCP_DOCUMENT_INVALID 的 400 和原 ref | 原解析错与清理错，不由清理错覆盖 |
| 后续请求因残留清理不能安全读取配置 | 既有 MCP_SOURCE_READ_FAILED / 503，生成关联到残留责任的新 ref | 旧责任 ref、新请求 ref、未完成资源 |
| 其他既有 typed 403/404/409 | 保持原 code/status/ref，不能因收尾变成成功或无正文 500 | 原失败与收尾结果 |
| 真正未知缺陷且无既有公开配置错误 | 保持项目未知错误处理，不伪装成权限拒绝 | 完整内部诊断；本批不能因此宣称 typed 路径通过 |
| 客户端/任务被中断 | 保留中断 Exit，不制造成功，也不为已断连客户端强行发送响应 | 中断与同期清理错误，不使用 Effect.ignore 吞掉 |
| 写配置已提交，随后刷新/清理失败 | 保持既有已提交/待刷新确认，不把收尾异常改成未提交 | 已提交事实、待办和失败原因 |

实现时在 InstanceStore 失败发布及 Config handler 对应边界保留原 typed 错误，额外 Cause 写内部结构化诊断；必要时调整 middleware 对内部结果的读取，不能序列化整个内部结构。已取消等待不改变共享任务其他等待者收到的原错误。

HTTP 回归必须实际检查响应状态、code/ref、Content-Type、非空 JSON，以及不包含原文、密钥、文件内容、内部堆栈。还要验证内部记录同时包含两个错误，并非仅把公开输出“修成 503”却丢掉清理失败。本批不新增公开 error code 或扩大 SDK 错误联合来绕过边界。

- 两种布局：经典跟随全局服务器，现代跟随设置 picker；至少在真实页面各走一条完整链。

- 所有写动作核对请求体中测试实体与请求 origin，并对照 A/B 隔离配置和凭据引用。日志不输出真实或假密钥正文。

连接测试若与“获取模型”共享入口但提交行为不同，拆成两个子用例；不能用纯探测通过代替目录提交路径。未实现或无法观测的格标“待验收”，不得写“不适用”规避。
