# 输入框提交到错误工作目录：修复方案与验收标准

日期：2026-11-23。基线：`HEAD ac5272bc2a` 加当时的未提交改动，Windows，Bun `1.4.3`。状态：**代码修复及定向单元验证完成，桌面复验待执行**。本文记录已复现的前端投递问题，不代表真实 Shell 已在错误目录执行；自动化通过不等于整体验收完成。

## 问题与复现

从 `packages/app` 执行：

```sh
bun test src/components/prompt-input/submit.test.ts -t "reads the latest worktree accessor value per submit"
```

同一个提交控制器先在 `/repo/worktree-a` 提交 Shell 请求，再将 `selected` 改为 `/repo/worktree-b` 并再次提交。第一次投递目录为 A；第二次期望 B，实际记录为 `/repo/main`。该差异在组合运行和单独复测中均出现。断言检查的是测试客户端记录的投递目录，不是命令输出。

现有用例同时假设第二次提交要创建新会话，却没有模拟切换到新草稿。不能据此断定正确目标必然是 B，也不能将预期直接改成主目录：同一草稿的续发属于 A，明确新建的草稿才应采用新选的 B。

## 原因与修复位置

`packages/app/src/components/prompt-input/submit.ts` 的 `createPromptSubmit` 在创建会话后保存 `promotedSession`，供路由尚未就绪时续发使用。`handleSubmit` 每次先从当前项目 SDK 初始化目录和客户端。再次提交时，`promotedSession` 使 `isNewSession` 为假，跳过新会话的工作树分支；而切换到已恢复会话目录的分支要求存在 `routedSession`。因此，复用刚创建的会话时，可能出现**会话属于 A，客户端和投递目录仍属于主项目**的组合。仅调整 `newSessionWorktree()` 的读取时机无法解决这个问题。

## 会话判定与异步边界（复核补充）

- 有 `params.id` 时以本次提交捕获的服务器和路由 ID 为准。`input.info()` 只有在属于当前目标时才可复用；不能因缓存中存在另一会话就跳过恢复，也不能仅因没有路由 ID 就认定一定要创建。当前 `isNewSession` 的判断与后续 `submissionInfo ?? promotedSession` 不是同一条件，实施时应统一。
- 无路由 ID 时，已提升的会话仅对其来源草稿有效。`packages/app/src/context/prompt.tsx` 有 `draftId` 时使用 `{ draftID }`，否则使用 `{ dir, id }`。后者在同一目录连续新建时不能单独区分两个无 ID 草稿；应核实控制器重建，或使用明确的新建动作标识草稿生命周期。工作树选择和 `New session` 等显示标题都不是身份。自动命名不在此修复范围内。
- 异步请求归属与界面归属分开处理：请求应继续发给原目标，完成回调不能把后来打开的草稿提升为该会话。当前 `submit.ts` 在创建返回后才读 `search.draftId`；实施时应在等待前捕获来源身份，并在提升草稿、导航或重定向输入前核对归属。此处是代码审查发现的风险，尚无桌面复现。

## 实施步骤

1. **先区分续发与新建。** 检查 `prompt-input.tsx`、`prompt-input-v2.tsx` 在打开新草稿、切换标签及路由交接时是否重建控制器。保留同一草稿在路由交接期间复用 `promotedSession` 的能力；若控制器跨草稿复用，则用实际草稿和服务器身份限定其有效范围。不要用工作树选择变化推断草稿变化，也不要在每次发送后无条件清空它。
2. **统一提交目标。** 在 `handleSubmit` 中先确定目标会话。已有或刚创建的会话以其 `session.directory` 为准；只有确需创建会话时才用 `newSessionWorktree()` 解析 `main`、指定工作树或 `create`。从本次提交捕获的服务器取得对应目录的 SDK 和同步上下文；Shell、普通提示、斜杠命令、排队草稿及乐观更新应使用同一目标。不要在异步恢复或创建返回后重新读取当前标签的服务器。已指定的路由会话恢复失败时保留输入并停止，不回退到主目录发送。
3. **拆分回归用例。** 在 `packages/app/src/components/prompt-input/submit.test.ts` 中分别模拟下表前两个场景，以真实的草稿切换或控制器生命周期区分它们。若界面会复用控制器，不要只靠测试中手动创建第二个控制器来证明修复有效。保留既有的冷路由恢复、切换服务器和目录归属用例。

本次不修改协作下线接口、数据库迁移或生成的 SDK。

## 验收矩阵

| 场景 | 通过标准 |
| --- | --- |
| 同一草稿在 A 首次发送，路由尚未更新就续发 | 仅创建一个会话；两次请求使用同一会话 ID、同一服务器和 A 的目录客户端；主目录没有收到请求。 |
| 从 A 明确打开新草稿，选择 B 再提交 | 新建不同 ID 的会话，创建参数 `location.directory` 和实际投递目录均为 B；不使用 A 的会话。 |
| 同目录显式新建另一草稿，仍选择 A | 即使目录和显示标题相同，也创建不同 ID 的会话；旧会话不接收新草稿的消息。 |
| 提交后、异步创建或恢复返回前切换标签或服务器 | 原请求仍绑定提交时的服务器和目标目录；返回时不提升新草稿、不抢回焦点，不改写新草稿的输入。 |
| 已有路由会话未加载 | 恢复成功后向该会话提交；恢复失败则不投递、不创建替代会话，输入仍可重试。 |
| 普通提示、Shell、斜杠命令 | 分别断言会话 ID、实际客户端目录和投递次数；不能只检查创建参数。 |

## 实施记录（2026-11-23）

- 修改 `submit.ts`：将已提升会话与服务器 scope、草稿 ID 和捕获的输入对象绑定；无路由 ID 时不再复用任意 `input.info()`。已有路由的会话仍按 ID 匹配或恢复。先统一会话选择，再判断是否创建，并将续发的目录 SDK、同步上下文和草稿目录绑定到 `session.directory`。
